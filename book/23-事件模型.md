# 第 23 章 事件模型：日志是字符串，事件是协议

状态能可靠落盘了，接下来要回答：这一轮到底发生了什么？日志不够，我们需要事件。

## 23.1 四个 printf 的故事

在 `observ` 包出现之前，L0、L1、L2、L3 各有一套事件类型，也各有一份 `fmt.Printf` 打印逻辑。

它们"看起来"一样：都有一个 `Kind`、一个 `Phase`、一句话。但没有任何东西真的把它们接住：

- 加一种新事件，要记得改四个地方的 switch；
- 忘了改，就静默不打；
- 想做"按工具统计失败率"，没有统一的字段；
- 想比较两次运行的过程，只能 diff 文本。

`observ` 包把它们统一成一种 `Event`。这是迁移，不是并存。

为什么要强调"不是并存"？因为两套事件形状并存，迟早会出现"一套有、一套没有"的字段，然后统计口径开始分叉。

## 23.2 强类型与自由字符串的分界

`Layer` 和 `Kind` 是强类型（`type X string` + 常量），`Phase` 是自由字符串。

判据是：拼错的后果有多重。

- `Layer` / `Kind` 会被用作聚合维度、map key、事件校验；拼错会静默分裂出一列新的统计。
- `Phase` 是"哪一个节点/角色"，由装配决定；每加一个节点都改枚举是错的。

> 强类型的必要性 = 拼错的后果有多重。
> 被用作键/聚合维度 → 必须强类型；只用来显示 → 可以是数据。

而 `Phase` 的数据来自节点名，节点名又是 `Kind` 的持有者——它不需要再枚举一次。

## 23.3 kindSpec：事件类型的契约

每种 `Kind` 在 `kindSpecs` 里有一条规格（`event.go:178`）：

```go
var kindSpecs = map[Kind]kindSpec{
    KindStart:     {NeedsPhase: true, Desc: "开始跑一跳"},
    KindLLMCall:   {NeedsPhase: true, NeedsUsage: true, Desc: "一次模型调用"},
    KindToolCall:  {NeedsPhase: true, NeedsTool: true, Desc: "要调用一个工具"},
    KindReconcile: {NeedsPhase: true, NeedsReconcile: true, Desc: "对账不符"},
    KindDone:      {Desc: "这一轮完成"},
    ...
}
```

它约束的是"缺了它这一类事件就没有意义"的字段：

- `KindLLMCall` 缺用量 → 作为成本原料完全失效 → 必须约束；
- 缺模型名 → 还能用（只是按模型切片少一维）→ 不约束。

不这么划线，每加一个字段就加一条要求，最后没人能发出一个事件。

`Validate` 校验这些约束；错误信息会列出合法取值（从同一张表派生）。

## 23.4 Event 的字段：哪些该存，哪些是派生值

`Event`（`event.go:296`）有几个关键字段：

- `RunID` / `Span` / `Layer` / `Phase` / `Kind`：身份与分类；
- `Err`：为什么失败；
- `Detail`：发生了什么（一句话）；
- `ToolName` / `ToolArgs`：工具名（元信息）与参数（正文）；
- `SystemPrompt` / `UserPrompt` / `Response`：正文；
- `Model` / token 数 / `Duration`：环境与成本；
- `Reconcile`：对账。

两个"没有"很重要：

### 没有 `Seq`

"谁先谁后"是录播的属性，不是事件的属性：

- `Recorder` 的顺序 = 切片下标；
- `JSONLTracer` 的顺序 = 行号。

存一个序号就要维护它；维护就会漏；漏了就有一个会说谎的字段。

### 没有"总数"

一轮的总 token 是"把 `KindLLMCall` 加起来"（`Recorder.Usage`），不是另一个字段。

理由不是省字段，而是 L2-3 的教训：一个由多处维护的数字，一定会不一致。

> **只能有一份明细**，统计都从它派生。

### Detail 的边界

`Detail` 是自由文本，很容易变成"什么都能装"。所以源码里写了一句话：

> **能被算出来的，不许写进 `Detail`。**

"第几步"等于数 `KindStart` 的条数——不要写。它曾经是 `graph.Event.Step`，后来被删了，因为它是一个派生值。

## 23.5 Reconcile：捕捉"成功但不对"

`Reconcile`（`event.go:243`）记录：

```go
type Reconcile struct {
    What     string // "页数"
    Declared int    // 声明 3
    Actual   int    // 实际 2
}
```

它捕捉的是静默的错：流程走完了、没有报错，但内容不对。

比如：

- 声明 3 页，实际渲染 2 页；
- 声明 3 条要点，实际 2 条；
- 声明 4 张图，实际 5 张。

一个 `mismatch: true` 不够——它只告诉你"不对"，不告诉你差在哪。所以 `Declared` 和 `Actual` 两个数都要在。

`Diff()` 会输出"少 2"、"多 1"这种带方向和幅度的说明。

## 23.6 Behavior：行为指纹的射程

`Behavior()`（`event.go:497`）返回：

```text
Layer|Kind|Phase|Err|Detail
```

它用来比较两次运行的过程是否相同。

一个事件里装着两类东西：

- 行为：发生了什么 → Layer / Kind / Phase / Err / Detail；
- 环境：在什么条件下 → RunID / Duration / token 数。

"确定性"只覆盖行为，不覆盖环境。

把环境算进行为 → 两次运行永远不同 → 判据永远红 → 被关掉；
把行为漏掉 → 真的不同被判相同 → 假绿。

> 假绿比假红糟得多：假红会被修，假绿会被信任。

`TestBehaviorProjectsOutTheEnvironment` 两个方向都测：环境量变，指纹不变；行为量变，指纹必须变。

## 23.7 Tracer：出口是端口

`Tracer` 只有一个方法：

```go
type Tracer interface {
    Trace(Event)
}
```

它不返回 error。观测失败不该让业务失败——观测可重建，业务不可重建。

实现：

- `Recorder`：内存收集，开发/测试/评测用，顺手校验；
- `JSONLTracer`：一行一个事件，追加写，崩溃时已写的都在；
- `Fanout`：发给多个出口，按参数顺序；
- `NopTracer`：什么都不做（"没有出口"是一个合法状态，不是 nil）；
- `WithRedact` / `LocalAndRemote`：本地完整、远端脱敏（第 24 章）。

`Fanout` 的顺序有意义：把不可重建的放前面。本地录播丢了就没了，上游可以重试。

`JSONLTracer` 无缓冲：每个事件一次 write。慢一点，但崩溃时最后一条也在。

它写失败时：

- 记下第一个错误；
- 只向 stderr 打一次警告；
- 不刷屏（一个坏磁盘会产生几十万条错误）；
- `Err()` 随时可查。

> 观测自己的失败，只能走观测之外的路。

## 23.8 对照 OpenTelemetry / 框架

OpenTelemetry 的 span/event 也是强类型、可聚合的。区别在于：

- 本仓库没有引入 OTel，事件模型是自建的；
- 它把"行为"和"环境"分得很清（`Behavior`）；
- 它把"对账"做成一等事件（`Reconcile`）。

框架能给你 span、attribute、exporter；但**哪些字段属于行为、哪些属于环境、哪些错误必须被对账**，仍然是你的业务判断。

## 23.10 拓展：只加常量，不加契约

给 `observ` 加一个 `KindCacheHit`，只加常量，不改 `kindSpecs`。跑一下 `AllKinds` 和 `Validate`，看哪里开始不一致。

这个实验会告诉你：为什么“加一种事件”不是只加一个常量。校验、清单、错误提示必须从同一张表派生，否则迟早有一处漏掉。
