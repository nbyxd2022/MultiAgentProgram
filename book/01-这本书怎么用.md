# 第 1 章 这本书怎么用：为什么读代码学不会 Agent

这本书不按源码目录讲，而是按“一个 Agent 需要解决哪些问题”讲。第 1 章先把学习方式定下来：你会怎么读、怎么练、怎么判断自己真的会了。

## 1.1 一个熟悉的场景

你打开 `internal/graph/runner.go`，找到 `drive()`。两百多行，每隔三行一段注释。每个字都认识：checkpoint、pending、decision、budget、persist。你花了一个晚上读完，合上文件，感觉自己理解了。

第二天有人问你：

> 如果把 checkpoint 里的 `Pending` 去掉，只保留产物，会发生什么？

你答不上来。你记得 `Pending` 很重要，但说不清它挡住了哪一个具体的故障。

这不是你不够聪明。这是"读代码"这种学习方式的固有缺陷。

## 1.2 三种错觉

读一个写得很好的仓库，会产生三种错觉。它们都很舒服，也都很有害。

### 错觉一：流畅错觉

一段代码配上一段解释，读起来很顺。顺，会让你把"我能跟上这段话"误当成"我能做出这个决定"。

这两件事差得很远。看懂"`StaleReasons` 会沿 `BasedOn` 向上传播"，和面对一个具体场景时判断"这里到底该重算，还是该标脏"，是两种能力。前者是阅读，后者是设计。

### 错觉二：后见之明

看到 `CanSkip` 里同时检查"产物存在、没有 `Shortfall`、没有 `StaleReasons`"，你会觉得"当然应该这样"。

但你没经历过那个选择：如果只检查"产物存在"，会发生什么？如果一个产物只有一半（`Shortfall`），继续用它会怎样？如果上游变了、下游没变，怎么知道它是旧的？

答案看起来总是显然的，问题从来不是。 学习的价值在问题那一侧，不在答案那一侧。

### 错觉三：词汇错觉

读完这个仓库，你会学会很多词：ReAct、黑板、HITL、checkpoint、fail-closed、失效传播。

会用这些词，不等于有判断。面试官只要追问一句"你这个 `MaxSteps` 为什么是 8，不是 3，也不是 100"，词汇就会露馅。

## 1.3 学习的最小单位：一个会失败的版本

这本书的每一章，都从一个能跑但有缺陷的版本开始。我叫它"坏版本"。

比如讲 ReAct 循环，我不会先给你看仓库里完整的 `RunWithMessages`。我会先给你一个"只调用一次模型"的版本：

```go
resp := callModel(messages)
if len(resp.ToolCalls) > 0 {
    result := executeTool(resp.ToolCalls[0])
    // 注意：这里故意不把 result 放回 messages
}
return resp.Content
```

你把它跑起来，会看到一个具体的现象：模型一直在请求同一个工具，或者干脆返回空内容。你被卡住了。

然后我们才引入"把工具结果作为一条 `tool` 消息追加回上下文"，再引入"循环直到模型不再请求工具"，最后才引入"最大步数"。

先有故障，再有机制。 这样你记住的不是一个名词，而是一个因果链：因为没有 X，所以发生了 Y；加了 X 之后，Y 消失了；X 的代价是 Z。

仓库自己的演进也是这个形状：L0 先跑通，L1 暴露丢字段，L2 暴露编排失控，L3 暴露恢复问题，L4 暴露不可评测。每一层都是被上一层的故障逼出来的。 这本书只是把这条线按依赖顺序重新走一遍。

## 1.4 三遍法

整本书分三遍。

### 第一遍：心智模型（第 1 到 3 章）

目标只有一个：知道 Agent 运行时到底在做什么。

你会看到模型 API 的原始请求和响应，会写一个 150 行的最小 Agent，会理解"模型只负责决定下一步，运行时负责真的去做"。

这一遍不追求完整，也不追求优雅。能跑、能解释，就够了。

### 第二遍：逐层重建（第 4 到 27 章）

从 L0 到 L4，每一层自己写一遍。顺序是依赖顺序，不是仓库的历史顺序：

1. 单 Agent 与 ReAct（L0）
2. 评审闭环与结构化产物（L1）
3. Supervisor、黑板、失效传播（L2）
4. 图编排、HITL、断点恢复（L3）
5. 事件、预算、评测（L4）

每一层结束时，你都能回答："如果没有这一层，上一层的哪个故障会回来？"

### 第三遍：对照与收口（第 28 到 30 章）

这时你已经有自己的版本了。我们才回到仓库，逐模块 diff：

- 哪些地方仓库做得更好，为什么？
- 哪些地方你的版本更简单，为什么？
- 哪些注释是错的，怎么验证？
- 如果重新设计，你会保留什么、删掉什么？

先有自己的答案，再看参考答案。 顺序反了，参考答案就变成了背诵材料。

## 1.5 每一章怎么用

每一章固定八段。你不需要一次记住全部，按顺序走：

1. 一个具体故障：先读场景，别急着看代码。
2. 坏版本：自己敲一遍。不要复制粘贴。
3. 让它失败：跑起来，观察现象。失败的信息比你想象的多。
4. 机制：先自己想"怎么修"，再看我给的方案。
5. 对照仓库：打开 `file:line`，看参考实现和你的差异。
6. 练习：至少做第一个和"删掉它会怎样"那个。
7. 过关标准：过不了就不要进下一章。后面的内容会依赖它。
8. 延伸：有余力再看，第一遍可以跳过。

一个很具体的建议：**每章准备一张纸，左边写"我以为"，右边写"实际是"。** 一章结束，如果两边一样，说明这一章对你太简单；如果右边一片空白，说明你只是读过去了。

## 1.6 你需要准备什么

- Go 1.21 或更高版本。能看懂 struct、interface、goroutine 的基本用法。
- 一个 OpenAI 兼容服务的 API Key。前两章不需要，第 3 章开始用它做验收。
- 每天 1 到 2 小时。少于 30 分钟，建议改成两天一章，不要碎片化。
- 一个记录卡点的文件。不要写"今天学了 ReAct"，要写"我以为循环是框架做的，实际是我自己写的"。
- 愿意动手。这本书不提供"读完就会"的捷径，因为那种东西不存在。

## 1.7 我们之间的约定

1. 我不会一次把整章代码全给你。 核心部分要你自己敲。你敲错了、跑不通，才是学习发生的地方。
2. **卡住超过 30 分钟，先写下完整的报错和你的猜测，再来问。** 不要直接要答案；直接要答案会让这一章失效。
3. **每章的"为什么"问题，先自己回答，再看参考答案。** 答错没关系，答错的地方就是你的地图。
4. 你觉得某一章太慢，可以直接说。 但不要跳过第 2 到 7 章。它们是后面所有内容的地基。

## 1.8 第一个练习（不写代码）

在开始第 2 章之前，先做一件事：

```powershell
go run ./cmd/l0
```

这是一个不需要 API Key 的离线 Demo。观察它的输出，然后回答三个问题：

1. 这一轮里，模型被调用了几次？你是怎么从输出里数出来的？
2. 它先调用了哪个工具，后调用了哪个？中间隔了什么？
3. 最后的总结是谁写的：模型，还是程序？

把你答不上来的问题写下来。不要现在去找答案。 第 3 到 7 章会逐个回答它们。提前看答案，你会失去"原来如此"的那个瞬间。

## 1.9 小结与自检
合上书，用自己的话回答：

- 三种错觉分别是什么？各举一个你身上的例子。
- 为什么这本书要求先写"坏版本"？
- 为什么不能从 L4 的可观测和预算开始学？

如果答不出来，回到 1.2 和 1.3 重读。这一章没有代码，但它是整本书最重要的一章：**学习方式错了，后面的努力都会变成"看起来会了"。**

## 1.9.1 拓展：找一件“框架替你做的事”

拿一个你用过的框架（Eino 也可以），列出它替你做的三件事。然后挑其中一件，问自己：如果去掉它，最先坏掉的具体现象是什么？

比如“框架帮你保存对话历史”——去掉之后，模型会忘记上一轮说过什么。这个答案越具体，你越知道自己接下来该学什么。
