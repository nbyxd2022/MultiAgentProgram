# 第 19 章 图执行：`Outcome`、`Next`、自环与上限

坏图挡在门外了。图能跑之后，接下来是执行中的边界：节点能返回什么、失败算什么、重试怎么停。

## 19.1 一个循环，两条路径

`internal/graph/runner.go` 的核心只有一个 `drive`。

- `Run`：读 checkpoint，有就接着跑，没有就新建；
- `Resume`：先把人的回答落盘，再调用同一个 `drive`。

没有单独的 "resume 循环"。

为什么能这样？因为位置由产物推导（第 17 章）：没有游标，就不需要"从游标往后跑"；只需要问 `CanSkip`，已经做完的节点自然被跳过。

`drive` 开头还有一件事：

```go
if st.Pending != nil && st.Pending.Decision == nil {
    return Result{Status: StatusInterrupted, Interrupted: st.Pending}, nil
}
```

有一个没被回答的中断时，什么都不做，就地停下。

为什么必须显式挡住？因为中断的那一跳已经把产物写进黑板了。如果不挡，`CanSkip` 会把它当成"已完成"，直接跳过——问题被静默忽略，用户以为系统在等他，系统却已经跑完了。

## 19.2 Outcome 的三种组合

节点返回 `*Outcome`，其中两个字段可以独立组合（`graph.go:204`）：

| Product | Interrupt | 含义 | 例子 |
|---|---|---|---|
| 有 | 无 | 正常产出，继续 | 大多数节点 |
| 有 | 有 | 做完了，停下来等人确认 | `confirm_artifact` |
| 无 | 有 | 需要人给信息才能做 | `ask_user` |
| 无 | 无 | 不产出，按默认调度继续 | 纯检查节点 |

第三种是"先问、再产出"。仓库的协议支持它，但没有节点使用（`SubAgentNode` 只实现 `confirm_artifact`）。这是一个刻意的限制：为用不到的场景预留开关，会提前制造两套并存的语义。

`Next` 是另一个维度：

- 空：按图的默认调度；
- 自己：这一跳重做；
- 其他节点：必须有一条边支撑（`CheckOutcome` 会检查）。

## 19.3 step：装配、执行、校验、入库

`Runner.step`（`runner.go:618`）做四件事：

1. 还原黑板：节点只能读（`NodeInput.board` 未导出）；
2. 取上游：按 `Needs` 取最新版，生成 `{ref, summary}`；
3. 执行节点：带上 `Topic`、`Hint`、`Inputs`、`RunID`、`Attempt`、`Answer`；
4. 校验并入库：`CheckOutcome` 校验 `Next`；`putProduct` 写黑板并填 `BasedOn`。

注意第 2 步不需要"缺前置"的分支：`Graph.Next` 按拓扑序选择，被选中的节点其依赖一定已就绪。走到这里还缺东西，就是图或 Runner 的 bug。

第 3 步的 `Answer` 只送给中断发生的那个节点（`pendingAnswer.forNode`）。它不是"只送一次"：同一个节点在一次运行里可能重试多次，而人的答案本来就是它的输入，重试时当然还应该看得见。

## 19.4 自环：有界重试

`Outcome.Next == 自己` 表示"这一跳没做好，再来一次"。

它是节点表达"素材不够再搜一轮"的唯一方式。判断逻辑写在节点自己里（它最懂自己做得够不够），而不是散在图定义里。

但有界性必须由 Runner 保证：

```go
const maxRunsPerNodeDefault = 4

runs[name]++
if runs[name] > r.maxRunsPerNode {
    return ..., fmt.Errorf("节点 %s 在一次运行里被执行了 %d 次（上限 %d）—— "+
        "它在反复要求重做自己，请检查它的重做判据是否**无界**", ...)
}
```

三个细节：

1. 上限是 4，不是节点数；因为重试会让步数大于节点数；
2. 计数不跨进程：一次 `Run` 的边界是"进程活着的一段时间"，中断会结束它；跨越恢复还在重试，意味着人在反复同意重试，那不是死循环；
3. 错误信息指向"判据无界"，而不是"步数不够"。

> 一个只写"要不要重试"、不写"最多几次"的判据，是无界的。最坏结果不是多花 token，而是这一轮永远跑不完。

## 19.5 预算与持久化

循环里的顺序（`runner.go:439-565`）：

```text
检查 ctx
  → 选 next（Graph.Next）
  → runs++ / 上限检查
  → guard.Allow(Steps:1)   // 事前问
  → step()                 // 执行节点
  → guard.ReportUse(...)   // 事后记（成功失败都记）
  → 有 Interrupt → 存 Pending + persist + 返回 Interrupted
  → 有 Next → 设为下一跳
  → persist                // 每跑完一个节点就落盘
```

几个关键点：

### 预算触顶不是 error

`guard.Allow` 不通过时，Runner 不返回 error，而是 `StatusBudgetStopped`，并 persist 当前状态。

为什么？因为"预算用完"是我们自己设的上限被触发，不是异常。返回 error 会让调用方把已经做好的产物一起丢掉。

这与 L2-9 的"触顶但已提交要保留成果"是同一条。

### 每跑完一个节点就落盘

这是"进程被杀也不丢"的全部内容。

如果只在最后落盘，中断/崩溃会丢掉整轮。

### 记账在失败时也做

`ReportUse` 在 `if err != nil` 之前。失败的模型调用也可能已经花了钱（L2-9 实测：连续失败 10 次烧掉 55321 tokens）。

## 19.6 失败的五种形态

| 形态 | Runner 的处置 | 能否恢复 |
|---|---|---|
| 节点返回 error | `StatusAborted` + error，已完成产物保留 | 可以再 `Run` |
| 节点 panic | `callNode` 转成 error（带 stack），不重试 | 可以再 `Run` |
| ctx 取消 | `StatusAborted` + 明确说"产物都在磁盘上" | 可以再 `Run` |
| 预算触顶 | `StatusBudgetStopped`，不返回 error | 可以调大预算再 `Run` |
| 达到节点上限 | `StatusAborted` + "判据无界" | 先修节点判据 |

`callNode`（`runner.go:606`）用 `defer recover()` 把 panic 翻译成 error：

```go
err = fmt.Errorf("节点 %s 发生 panic（这是一个 bug，不是外部故障；"+
    "产物与状态未受影响，可以直接重跑）: %v\n%s", n.Name(), p, debug.Stack())
```

为什么节点边界是 recover 的正确位置？

- 工具、模型、schema 断言全在节点里面；
- 包住这一处，就包住了它们全部；
- panic 发生在节点内，而状态写入全部由 Runner 控制，所以 checkpoint 仍然自洽。

它不重试、不掩盖：panic 是代码 bug，不是外部故障。

## 19.7 节点失败 ≠ 图失败

节点失败时：

- Runner 返回 error；
- 但**已经完成的产物仍在黑板/checkpoint 里**；
- 调用方可以修好节点后再次 `Run`，`CanSkip` 会跳过已完成的部分。

这是"失败也要保留成果"的另一个应用。

但要注意：Runner 不会自动重试失败的节点。重试策略应该由节点自己（自环）或调用方决定。Runner 只负责"跑一步、记账、落盘"。

## 19.8 Runner 不做什么

- 不并行（`Layers()` 只是候选）；
- 不自动重试失败节点；
- 不做补偿事务；
- 不在同一个进程内"从错误处继续"（调用方再 `Run` 一次即可）。

这些边界要写清楚，否则下一个人会以为 Runner 是一个"全能调度器"。

## 19.9 练习

先自己做，再看 `answers/19-参考答案.md`。

### 练习 1：让节点永远重做自己

写一个节点，永远返回 `Next = 自己`。

观察：

- 第几次执行时被上限拦住？
- 错误信息有没有指出"判据可能无界"？
- 已经产出的版本还在黑板上吗？

### 练习 2：Product + Interrupt

写一个节点，返回一个产物 + 一个 `confirm_artifact` 中断。

观察：

- Runner 返回什么状态？
- checkpoint 里的 `Pending` 是什么？
- 如果人在下一次 `Run` 里 confirm，`CanSkip` 会跳过这个节点吗？

### 练习 3：只有 Interrupt

写一个节点，只返回中断（没有 Product），类型 `ask_user`，Prompt 是"请给一个主题"。

观察：

- `Decision.Validate` 要求 `Note` 非空吗？
- 如果 confirm 时 Note 为空，会报什么？
- 如果通过，节点下一次能拿到 `Answer` 吗？

### 练习 4：节点 panic

在节点里 `panic("boom")`。

观察：

- Runner 返回的是 error 还是崩溃？
- 错误里有没有 stack？
- checkpoint 还能读吗？再 `Run` 会怎样？

### 练习 5：节点返回 error

让节点返回 `fmt.Errorf("模拟失败")`。

观察：

- 状态是什么？
- 之前的产物还在吗？
- 再 `Run` 一次，会从哪开始？

## 19.10 拓展：三种返回值

让一个节点依次返回三种 `Outcome`：

1. `Product: nil, Next: ""`；
2. `Product: 有, Next: ""`；
3. `Product: nil, Next: 自己`。

观察 Runner 分别怎么调度、怎么记账。这个实验能让你分清“没有意见”“产出后继续”“要求重做”三种语义，而不是把它们都当成“跑完了”。
