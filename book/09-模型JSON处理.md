# 第 9 章 让模型稳定输出 JSON：提取、修复、校验

提交结论变成了契约，可模型不一定按契约写。它会加一句话、用 Markdown 包起来、把末尾逗号写错。

## 9.1 一个每天都会遇到的失败

你让模型提交一份评审结论，Prompt 里写得很清楚：

```text
只返回 JSON，不要加任何解释。
```

它返回：

```text
好的，这是评审结果：
```json
{
  "issues": [
    {"level": "major", "field": "bullets[1]", "message": "第二条太空", "fix": "补一个数据"}
  ]
}
```
```

于是 `json.Unmarshal` 失败。你改 Prompt，加"不要用 Markdown"，它下一次又换了个花样：末尾多了个逗号，或者把对象包在引号里。

这不是模型"故意作对"。这是概率模型在格式上的固有方差。工程上的正确做法不是继续加感叹号，而是承认它会发生，并在代码里留一层。

这一层就是 `internal/llmjson`。

## 9.2 两个动作，职责不同

`llmjson` 只做两件事，而且顺序不能反：

### 动作一：Extract

从一段混着自然语言的文本里，抠出第一个完整的 JSON 值。

```go
ExtractObject("好的，结果：{\"a\":1} 希望有帮助") // {"a":1}
ExtractArray("结果如下：[1,2,3]")               // [1,2,3]
```

它的实现是一个小型状态机（`llmjson.go:61`），不是正则。原因很直接：JSON 有嵌套和转义，正则处理不了。

几个细节：

- 它尊重字符串里的括号：`{"a":"}"}` 里的 `}` 不算结构；
- 它只找第一个完整值，不合并多个；
- 如果括号不配平（比如输出被截断），它返回空串，而不是"从起点到结尾"。

最后一条很重要：截断的 JSON 不能假装完整。 交给 `Repair` 去救，救不了就让下游报错。

### 动作二：Repair

修几种高频的、不会改变语义的畸变：

| 畸变 | 例子 | 修法 |
|---|---|---|
| 整体被引号包住 | `"{\"a\":1}"` | 剥掉最外层引号 |
| 单引号当定界符 | `{'a':1}` | 全部换成双引号 |
| 尾逗号 | `{"a":1,}` | 去掉逗号 |

它不修：

- 缺逗号；
- 缺引号；
- 截断；
- 注释；
- `NaN`；
- 十六进制。

修不了就返回原文（`llmjson.go:152`）。这不是偷懒，而是一个安全选择：下游的报错里会带上模型真正给的内容，而不是一个空串或 `{}`。原文是排查的线索，空值会把线索擦掉。

> 仓库里有一个反例：`cmd/l4` 的 `mustJSON` 在序列化失败时返回 `"{}"`。那会掩盖真实输入。它只用于自测脚本，但这个小差异值得你记住。

### 顺序为什么不能反

如果先 `Repair` 再 `Extract`：

```text
"好的，这是结果：{...}"
```

`Repair` 会把它当成一个畸形的字符串去修，可能修出一些谁也看不懂的东西；再 `Extract` 就找不到正确的结构了。

正确顺序是：

```text
原始文本 → Extract（找结构）→ Repair（修小毛病）→ json.Unmarshal（判语法）→ Validate（判语义）
```

`llmjson.Clean` 就是前三步：

```go
func Clean(s string, wantArray bool) string
```

它不保证结果是合法 JSON。它只保证"尽力了，而且没丢掉原文"。`json.Unmarshal` 这一步永远不能省。

## 9.3 三个层次，别混在一起

模型输出出错，至少有四类原因。每一类应该由不同的层处理：

| 层次 | 问题 | 谁处理 | 处理不了时 |
|---|---|---|---|
| 语法 | 多一句话、Markdown 包裹、尾逗号 | `llmjson` | 返回原文，让 `Unmarshal` 报错 |
| 结构 | 缺必填字段、类型不对 | `json.Unmarshal` + 手写校验 | 回灌给模型 |
| 语义 | `level="严重"`、`field` 为空、页数不对 | 业务 `Validate` | 回灌给模型 |
| 截断 | `finish_reason=length` | Agent 层（第 3 章） | 重试/加长输出，不要"修" |

一个常见的错误是：把语义问题当成语法问题去修。

例如模型返回：

```json
{"issues": []}
```

语法完全正确。但它可能是"检查过了，没有问题"，也可能是"我根本没检查"。`llmjson` 帮不了你；只有 `submitted` 标志（第 8 章）能区分。

再例如：

```json
{"pages": [{"title": "趋势"}]}
```

语法正确，但缺了 `bullets`。`Repair` 不会替你补；补了就是替模型编数据。正确做法是让 `Validate` 报错，把错误回灌。

## 9.4 仓库在哪里用它

L1 的 Critic 在解析 `submit_review` 参数时用了它（`internal/agents/critic.go:301`）：

```go
if err := json.Unmarshal([]byte(llmjson.Clean(args, false)), &in); err != nil {
    return "", fmt.Errorf("参数不是合法 JSON: %w", err)
}
```

L2 的四个角色（research / outline / designer / renderer）的解码函数也都用了它。

它只在工具参数 / 模型提交内容这一层使用，不用于解析内部协议（黑板的 JSON 是我们自己序列化的，不需要修）。这个边界很重要：

> **修复只该用在"不可信的模型输出"上，不该用在"我们自己写的数据"上。**

如果连内部数据都要修，说明序列化层已经坏了，修只会掩盖问题。

## 9.5 为什么不引入完整的 JSON 修复库

参考实现用了一个第三方库做完整修复。这个项目坚持标准库，所以只做了三种高频畸变。

这不是"手写更牛"，而是一个取舍：

- 完整修复库能救更多情况，但它的行为你未必能完全解释；
- 只修三种覆盖不了所有情况，但每一种都是确定的、可测试的、不会改变语义的。

更重要的是，作者把边界写在了注释里（`llmjson.go:136-151`）：

> 一个"看起来能修一切"的函数，比一个"写清了只修三种"的函数**危险得多**。

因为前者会让人放弃去看原文。

## 9.6 一个完整的例子

模型返回：

```text
好的，结果如下：{"issues":[{"level":"major","message":"第二条太空","fix":"补数据"},]}
```

逐层处理：

1. Extract：找到 `{...}`，括号配平，抠出对象；
2. Repair：去掉 `,]` 里的尾逗号；
3. Unmarshal：成功，得到 `issues[0]`，但 `field` 为空；
4. Validate：`field` 必填（第 8 章练习 2 的补丁），报错；
5. 回灌：模型看到 `field 不能为空`，补上 `bullets[1]`；
6. 再次提交：通过。

注意第 3 步和第 4 步的分工：

- `Unmarshal` 只保证"这符合 JSON 语法和 Go 类型"；
- `Validate` 才保证"这符合业务契约"。

语法成功不等于业务正确。 这是整章最该带走的一句话。

## 9.7 和 JSON mode / structured outputs 的关系

如果服务商支持 JSON mode 或 structured outputs，应该优先用：

- 它们能在解码阶段约束格式，显著降低语法错误；
- 但它们不保证语义正确：字段可以为空、枚举值可以拼错、内容可以是编的；
- 它们也不保证"模型真的检查了"，`submitted` 仍然必要。

所以层次是：

```text
structured outputs / JSON mode  →  减少语法错误
llmjson                         →  兜底语法错误
Validate                        →  保证业务契约
submitted / completion check    →  保证"真的做了"
```

四层各司其职，不能互相替代。

## 9.8 练习

先自己做，再看 `answers/09-参考答案.md`。

### 练习 1：给 Extract 补测试

写四个用例：

1. `{"a":"}"}`：字符串里的 `}` 不能当结构；
2. `{"a":{"b":1}}`：嵌套对象要配平；
3. `{"a":1`：截断，应返回空串；
4. `你好 {"a":1} 再见 {"b":2}`：只返回第一个。

这个练习会让你真正理解"为什么不能用正则"。

### 练习 2：写一个 `ParseAndValidate`

把四层串起来：

```go
func ParseAndValidate(raw string, out any, validate func() error) error
```

要求：

- 先 `llmjson.Clean`；
- 再 `json.Unmarshal`；
- 再 `validate`；
- 错误信息里带上是哪一层失败（"语法" / "语义"），不要把三者混成一句"参数错误"。

### 练习 3：追踪一条坏输入

构造一条同时包含三种问题的输入：

- Markdown 包裹；
- 尾逗号；
- 缺一个必填字段。

然后逐层判断：哪一层能修、哪一层能报、哪一层必须回灌。写一张表。

### 练习 4：该修还是该重试？

给下面四种情况选择处理方式，并说明理由：

1. 输出被 `finish_reason=length` 截断；
2. `field` 为空；
3. JSON 外面多了一句"好的"；
4. `level="严重"`。

提示：1 和 3 是不同层的问题；2 和 4 是语义问题；"修"只适用于 3 这一类。

## 9.9 拓展：截断和畸形不是一回事

给 `Clean` 喂一段被截断的 JSON（比如去掉最后两个字符），观察它返回什么；再交给 `json.Unmarshal`，看错误落在哪一层。

然后换一段只是多了尾逗号的 JSON，重复一次。两次的结果应该不同：前者只能重试，后者可以修复。分清这一点，你排查时就不会把“输出被截断”误判成“模型不会写 JSON”。
