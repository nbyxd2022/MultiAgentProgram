# 第 16 章 部分成功：Shortfall 与"完成"的判定

过期讲清楚了，还有一种状态没处理：产物存在、也新鲜，就是只完成了一半。

## 16.1 三页里失败了一页

`renderer` 要渲染 3 页：

- 第 1 页成功；
- 第 2 页成功；
- 第 3 页写盘失败。

如果把它当成整体失败：

- 返回 error；
- 已经成功的 2 页被丢掉；
- 用户什么也拿不到。

如果把它当成成功：

- 返回 2 个文件；
- 但下游/用户以为 3 页齐全；
- 第 3 页的缺失被静默吞掉。

两种都不对。正确的做法是第三种状态：

> **产物存在，但不完整；交付已完成的部分，并明确说明缺口。**

`internal/agents/renderer.go:220` 就是这么做的：

```go
if len(result.Files) == 0 {
    return nil, fmt.Errorf("renderer: %d 页全部渲染失败", len(outcomes))
}
return result, nil
```

只有全部失败才是 error；部分成功返回一个合法的 `RenderResult`，里面同时带 `Files` 和 `Failed`。

## 16.2 Shortfall 是怎么进入信封的

`RenderResult` 实现了可选接口 `schema.Partial`（`artifact.go:119`）：

```go
type Partial interface {
    Shortfall() []string
}
```

`RenderResult.Shortfall`（`artifact.go:450`）把 `Failed` 翻成人话：

```text
第 3 页：写盘失败
```

`NewArtifact` 在产物刚被造出来、信息最全的那一刻，问它一次（`artifact.go:197`）：

```go
if p, ok := any(payload).(Partial); ok {
    if gaps := p.Shortfall(); len(gaps) > 0 {
        a.Shortfall = gaps
    }
}
```

然后把答案固化到信封上。

为什么不放在 payload 里，让编排者去解码？

- 编排者一旦开始解码 payload，就会开始读业务字段；
- 读字段之后，它就会想"顺便重排一下"；
- 那就是企业仓库 A2/A3 的坑。

信封上的 `Shortfall` 只是几句人话，编排者读它，和读 `Summary` 没有区别。

## 16.3 三种"没有完成"，三种修法

| 状态 | 含义 | 反馈 | 修法 |
|---|---|---|---|
| Missing | 完全没产出 | "还没有产出 X" | 去跑那个角色 |
| Incomplete | 产出了，但有缺口 | "X 已经做过，但第 3 页失败" | 补缺口，不要整个重做 |
| Stale | 产出了，也完整，但依据过期 | "X 依据的上游变了" | 先重做上游，再回来 |

Supervisor 把这三件事分开算（`supervisor.go:256`）：

```go
missing, incomplete, stale := s.gaps()
if len(missing) == 0 && len(incomplete) == 0 && len(stale) == 0 {
    // 完成
}
```

`Result.Complete()`（`supervisor.go:176`）要求三者都为空。

为什么要分开？因为反馈必须准确：

- 说"render 还没产出" → 模型会把整件事重做一遍；
- 说"render 已经做过，但第 3 页没出来" → 模型只会去补那一页；
- 说"render 的依据过期了" → 模型会按顺序重做上游。

一句不准确的反馈，换来一整轮浪费。

## 16.4 完成判定是代码的事

从 L1 到 L4，同一个模式反复出现：

| 层 | 判据 | 代码 |
|---|---|---|
| L1 | `Deliverable()`：没有硬问题 **且** 评审完整 | `issues.go:235` |
| L2 | `Complete()`：Missing / Incomplete / Stale 都为空 | `supervisor.go:176` |
| L3 | `CanSkip()`：存在 ∧ 完整 ∧ 新鲜 | `state.go:410` |
| L4 | 评测硬判据：产物种类、页数、必备文本 | `eval` |

它们都在回答同一个问题：

> **模型说"完成了"，系统凭什么相信？**

答案是：不靠相信，靠检查。

- L1 检查"评审有没有跑完"；
- L2 检查"该有的有没有、全不全、对不对"；
- L3 检查"能不能跳过"；
- L4 检查"结果是否符合期望"。

这就是从"单 Agent"到"可交付系统"的分界线：完成是一个系统状态，不是模型的一句话。

## 16.5 一个真实 bug：Shortfall 没人读

`artifact.go:443` 的注释记录了 L2-2：

> 在此之前，`Failed` 只在 `renderer.go` 里被构造、在 `cmd/l2` 里被打印——**全仓没有任何一处"判断逻辑"读它**。

于是"2 成功 1 失败"在编排者眼里和"3 页齐全"长得一模一样。

修法不是"让模型注意一下"，而是：

1. `RenderResult` 实现 `Partial`；
2. `NewArtifact` 把 `Shortfall` 放进信封；
3. `Supervisor.incompleteRequired` 读信封；
4. `Result.Complete` 把 `Incomplete` 纳入判据；
5. `CanSkip` 也检查 `Shortfall`。

五处缺一不可。只加字段、不接判断，等于没加。

## 16.6 Shortfall 不该用来表达什么

`Shortfall` 的语义很窄：尝试了，但有一部分没完成。

不要用它表达：

### 1. "完全没有"

research 一条发现都没有，不是 `Shortfall`，是"空结果"。它可能是一个合法结果（确实没搜到），也可能是失败；要由角色自己决定返回空产物还是 error。

### 2. "数量不对"

outline 只有 2 页，但期望 3 页。这是契约不满足，应该由 `Validate` 报错，而不是 `Shortfall`。

因为 `Shortfall` 的意思是"我知道缺了什么，先交付其余部分"；"页数不对"往往意味着上游/模型根本没理解任务，应该重做，而不是降级交付。

### 3. "我没做"

没做就是 Missing，不是 Incomplete。把两者混为一谈，反馈会误导。

一个判断口诀：

> **Shortfall 是"我做了，但没做全"；不是"我没做"，也不是"我做错了"。**

## 16.7 可选接口的取舍

`Partial` 是可选能力，不是 `Payload` 的必选方法。

为什么？

- 大多数产物不会残缺：`Research` 要么有发现、要么没有；`Outline` 要么是完整的几页、要么交不上来；
- 强迫每个产物实现一个恒返回 nil 的方法，只会让真正的契约（`Kind` / `Summarize`）被噪音淹没。

这和 `StatsReporter`、`TimeoutReporter` 是同一个取舍：接口要小，能力要可探测。

代价是：消费方要用类型断言，且必须记得检查。但这是可控的，因为 `NewArtifact` 是唯一入口。

## 16.8 顺序问题：先报不完整，还是先报过期？

`CanSkip` 的顺序是：

1. 存在？
2. `Shortfall` 非空？→ 报不完整；
3. `StaleReasons` 非空？→ 报过期。

也就是说，一个产物既不完整又过期时，先报"不完整"。

在拓扑调度下，这通常是安全的：上游过期会先被调度重跑，等下游真正执行时，上游已经新鲜。但如果调度器不保证"上游优先"，就可能出现"重跑了下游，却仍然基于过期上游"的情况。

这是一个值得在 L3 设计里检查的点：**报错顺序不只是文案问题，它会影响调用方的修复顺序。**

## 16.9 对照 Eino / LangGraph

很多框架把节点错误当成"这一跳失败"，然后：

- 重试整个节点；
- 或者中止整张图。

但"部分成功"需要显式建模：

- 节点返回一个带缺口的结果，而不是 error；
- 图的完成判定要能读到这个缺口；
- 下游要知道"哪些部分可用、哪些不可用"。

这需要框架支持"非二值的节点结果"，或者你自己在 State 里加一个 `Shortfall` 字段。仓库选择了后者：把缺口放进产物信封，让所有层都能读。

## 16.11 拓展：把 Shortfall 换成 error

把 `Shortfall` 换成直接返回 `error`，再跑一次“三页失败一页”的场景。观察系统会丢掉什么。

如果整个任务因此失败，你已经完成的两页就白做了；如果当成成功，缺的那页又没人知道。这个对比能让你判断：什么时候该降级交付，什么时候该整体失败。
