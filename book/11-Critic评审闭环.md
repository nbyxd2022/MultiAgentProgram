# 第 11 章 Critic：可执行的评审意见与三种失败模式

产物和版本管住了，可“存在”不代表“可以交付”。这一章加一个评审者，重点不是再问模型一遍，而是让返工能收敛。

## 11.1 一个永远停不下来的评审

你写了一个 Critic，Prompt 是：

```text
请评审这份幻灯片，指出所有可以改进的地方。
```

第一轮，它说"第二条有点空，建议补数据"。第二轮，它说"第三条可以更凝练"。第三轮，它说"第二条和第三条有点重复"。第四轮，它又说"第二条有点空"。

每一轮都有问题，每一轮都在改，但总分没有下降。评审变成了一个永不满足的甲方。

这不是 Critic "太严格"，而是系统缺了三样东西：

1. 一张分级的判据表（什么问题必须改、什么问题可以不改）；
2. 一个停止条件（什么时候算够好）；
3. 一个 best-so-far（最后一版不一定是最好的）。

L1 的整个设计，就是围绕这三件事展开的。

## 11.2 硬判据与软判据

L1 把检查分成两类：

| 类型 | 谁做 | 例子 | 特点 |
|---|---|---|---|
| 硬判据 | 代码（`tools.Check`） | 标题为空、要点超长、条数不对、HTML 标签 | 零 token、确定性、可复现 |
| 软判据 | LLM（Critic） | 空洞、不可验证、换句话重复、跑题 | 有 token 成本、概率性、可能有误报 |

顺序是：先硬后软。

`Critic.Review`（`internal/agents/critic.go:88`）第一步就是跑 `tools.Check`，然后把硬判据的结论注入 Critic 的 Prompt，并明确告诉它"这些已经查过了，不要重复报告"。

为什么？

- 让 LLM 去数"要点是不是 3 条"，又慢又贵还可能数错；
- 代码一次就能算对，而且不花钱。

> **硬判据交给代码，软判据才交给 LLM。** 这不是为了省钱，而是为了让"确定的"和"概率的"各归其位。

## 11.3 一条问题必须长什么样

`schema.Issue`（`internal/schema/issues.go:107`）有五个字段：

```go
type Issue struct {
    Level   Level   // blocker / major / suggestion
    Field   string  // bullets[1] / title
    Message string  // 错在哪
    Fix     string  // 怎么改
    Source  Source  // rule / critic
}
```

四个字段缺一不可，少一个都会退化成"没用的抱怨"：

- 没有 `Level`：代码不知道要不要为它返工；
- 没有 `Field`：生成器不知道改哪里；
- 没有 `Message`：不知道错在哪；
- 没有 `Fix`：模型只能猜怎么改。

严重度有权重：blocker=3、major=2、suggestion=1（`issues.go:52`）。这样一份报告可以折算成一个可比较的分数。

但要注意：分数是给人看的，问题清单是给模型用的。 停止条件看分数，返工 Prompt 看清单。

## 11.4 三种失败模式

Critic 不是"越严格越好"。它有三种典型的失败。

### 失败一：讨好

模型倾向于说"整体不错"，或者只给一些无关痛痒的建议。更隐蔽的是：它可能根本没检查，却返回一个空的 `issues`。

仓库的防线有三层：

1. **`submit_review` 的 `submitted` 标志**（第 8 章）：不调用工具 = 评审未完成，而不是"没问题"；
2. 硬判据兜底：机械问题不依赖 Critic；
3. 严重度纪律：`submit_review` 拒绝 `blocker`，致命问题只能由代码判。

### 失败二：震荡 / 过度挑刺

Critic 每轮都能挑出新问题，生成器改 A，下一轮又改回 B。系统永远不收敛，token 一直烧。

仓库的防线：

- **`Deliverable()`**：没有 blocker/major 且评审完整，就可以停；
- **`BetterThan`**：加权总分更低者更优；分数相同看硬问题数；再相同看评审完整性；
- **`Best[T]`**：只保留历史最好的一版，不被最后一版覆盖；
- **`staleLimit=2`**：连续两轮没有刷新最好成绩，判定停滞；
- **`maxRounds=4`**：硬兜底，必须停。

这五个机制里，`Best` 最容易被忽略，但最重要：**返工是震荡的，最后一版经常不是最好的那一版。**

### 失败三：评审错位 / 不完整

Critic 评的是第 2 轮的产物，但生成器已经改到第 3 轮；或者它说"第二条"，但生成器重新生成后"第二条"变成了另一条。

仓库的防线：

- `Report.Round` / `Report.Subject`：记录评审的是哪一轮、哪一版；
- `Field`：把"第二条"变成 `bullets[1]`；
- `Incomplete`：评审没跑完时，报告显式标记，`Deliverable()` 返回 false；
- 受限局部修复：`MergeLocal` 由代码强制只改指定字段，模型越界会被回退；
- best-so-far 重新渲染：交付时重渲染最好的一版，保证磁盘上的文件与评审的版本一致。

> 最后一条是 L1 的一个技术债补丁：文件名由标题派生，后续轮次会同名覆盖。真正的解法是版本化文件名，L3 会处理。

## 11.5 Prompt 是建议，代码是保证

L1 的返工分两种：

- 整体重写：存在无法精确定位的问题；
- 受限局部修复：只有可定位的问题，只允许改指定字段。

Prompt 里会写"不要改其他字段"，但那只是建议。真正保证"只改该改的"的是 `schema.MergeLocal`：

```go
merged, violations := schema.MergeLocal(prev, slide, scope)
```

越界的改动会被回退，并打印 violations。

这和全书反复出现的一条原则一致：

> **不要在 Prompt 里承诺一个代码不保证的东西。**

Prompt 可以减少浪费，但不能替代校验。

## 11.6 完整流程

`cmd/l1` 的一轮：

```text
生成（generator）
  → 取产物（由工具交出，不让模型转述）
  → 局部修复合并（如果本轮是局部修复）
  → QuickFix（零 token 的确定性修复）
  → 评审（硬判据 + 软判据）
  → best-so-far（只在更好时更新）
  → 停止条件（Deliverable / 停滞 / 轮数上限）
  → 下一轮或交付
```

三个细节：

1. 产物由工具交出（`renderer.LastSlide()`），不是从模型回复里解析；
2. QuickFix 先吃掉便宜的问题（`tools.QuickFix`），LLM 只处理需要判断的；
3. **交付 best-so-far，不交付最后一版**；如果 best 不能算"已验证合格"，就降级交付并说明原因。

## 11.7 对照 Eino / LangGraph

在 Eino 或 LangGraph 里，Critic 只是一个节点。你可以画一个"生成 → 评审 → 条件边"的图，看起来和 L1 一样。

但框架不会替你决定：

- 什么问题必须改（分级）；
- 什么时候停（停止条件）；
- 保留哪一版（best-so-far）；
- 评审没跑完怎么办（Incomplete）。

**这些是"评审系统"的设计，不是"图"的设计。** 图只是把它们串起来。

## 11.8 练习

先自己做，再看 `answers/11-参考答案.md`。

### 练习 1：让 Critic 只返回自然语言

把 `submit_review` 去掉，让 Critic 在最终回复里写"第二条有点空，建议补数据"。

然后回答：

- 生成器怎么知道改哪一条？
- 怎么判断它"检查过了"还是"没检查"？
- 怎么统计严重度？

这个练习的目的是让你体会：没有结构化提交，评审无法驱动返工。

### 练习 2：模拟一个讨好型 Critic

写一个 Mock，永远返回：

```json
{"issues": []}
```

但不调用 `submit_review`（只在文本里说"没问题"）。

观察：

- `Review` 会返回什么？
- `Deliverable()` 会返回什么？
- 如果调用方忽略了 error，会发生什么？

然后再让它调用 `submit_review` 并提交空数组。两次的结果有什么本质区别？

### 练习 3：模拟震荡

写一个 Critic Mock，交替返回：

- 第 1 轮：`bullets[1]` 太空；
- 第 2 轮：`bullets[1]` 太满；
- 第 3 轮：`bullets[1]` 太空。

观察 `Best` 和 `staleLimit` 的行为：

- 第几轮停止？
- 交付的是哪一版？
- 如果没有 `Best`，会交付哪一版？

### 练习 4：评审错位

构造一个场景：Critic 评的是第 1 轮的产物，但生成器已经产出了第 2 轮。

回答：

- 需要哪些字段才能发现"评的不是当前版本"？
- `Field` 为什么不够？
- 你会把版本号放在 `Report` 里，还是放在 `Issue` 里？

### 练习 5：新增一个严重度？

有人提议加一个 `info` 级别，权重 0。

回答：

- 它和 `suggestion` 的区别是什么？
- 权重 0 会不会让某些问题被"静默洗掉"？
- 如果加，`Level.Valid`、`Weight`、`submit_review` 的校验、停止条件分别要改哪里？

## 11.9 拓展：让 Critic 交白卷

写一个 Mock：只在文本里说“整体不错”，永远不调用 `submit_review`。跑一轮，看 `Incomplete` 和 `Deliverable()` 怎么处理它。

然后再让它调用 `submit_review` 并提交空数组。两次都“没有发现问题”，但系统给出的结论应该完全不同。这个对比就是“没检查”和“没问题”的分界线。
