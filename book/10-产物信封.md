# 第 10 章 产物信封：版本、引用与血缘

模型输出清理干净了，产物本身还没地方放。只塞进一个 map，旧版会被覆盖，下游也说不清自己用的是哪一版。

## 10.1 一个不会报错的错误

假设你用 `map[string]string` 存产物：

```go
board["outline"] = "第一页：趋势；第二页：成本；第三页：基础设施"
board["design"] = "第一页：左文右图；第二页：三栏；第三页：时间线"
```

第一轮跑完，渲染出 3 页。然后用户改了主题，`outline` 重跑，覆盖成新内容：

```go
board["outline"] = "第一页：政策；第二页：竞争；第三页：出海"
```

`design` 没有重跑，还是旧的。

渲染器读到新的 `outline` 和旧的 `design`，检查"页数都是 3"，通过。于是：

> **新内容配上了旧版式。**

页数对、字段全、类型没错、没有任何一层报错。这就是最危险的一类故障：系统成功地做错了。

要发现它，必须回答两个问题：

1. 这份 `design` 是基于哪一版 `outline` 做的？
2. 那个版本还是最新的吗？

`map[string]string` 回答不了。这就是信封和版本存在的原因。

## 10.2 为什么不用 State 传产物

State（Eino 的 State、LangGraph 的 State）解决的是"一次运行里的共享数据"。它适合放：

- 当前主题；
- 已完成的节点；
- 运行期的配置。

但它不适合直接放产物，因为产物需要：

| 需求 | State 通常不提供 |
|---|---|
| 版本 | 同一个 key 覆盖后，旧版没了 |
| 引用 | 下游拿到的是值，不是"第几版" |
| 血缘 | 这份产物基于哪一版上游 |
| 新鲜度 | 上游更新后，下游是否过期 |
| 审计 | 谁在什么时候产出了什么 |

黑板（`internal/state/blackboard.go`）补的正是这五件事。它不是"另一个 map"，而是追加式产物存储。

## 10.3 信封的八个字段

`internal/schema/artifact.go:165`：

```go
type Artifact struct {
    Key        string
    Kind       Kind
    Version    int
    ProducedBy string
    Summary    string
    Shortfall  []string
    BasedOn    []Basis
    Payload    json.RawMessage
}
```

逐个说：

### Key：身份，不是文件名

`Key` 是黑板上的逻辑标识，例如 `research`、`outline`、`design`、`render`。

同一个 Key 可以有多个版本。Key 不包含版本，版本是独立字段。

### Kind：类型，必须双重校验

`Kind` 是 `research` / `outline` / ... 之一。`Decode`（`artifact.go:253`）会做双向校验：

- 信封说它是 `outline`；
- payload 解出来的 `Kind()` 也必须是 `outline`。

只信信封，就可能拿到"装错了"的产物：类型没报错、字段都在，但语义全错。

### Version：由黑板分配

`Version` 从 1 开始，由 `Blackboard.Put` 分配（`blackboard.go:83`）。`Put` 拒绝调用方自己指定版本（`:75`）：

```go
if a.Version != 0 {
    return ..., fmt.Errorf("Put 不接受外部指定的版本号...")
}
```

为什么？因为"谁拥有它，谁维护它"。如果每个调用方都自己拍版本号，必然撞车或跳号。

而且校验失败必须在写入之前，保证零副作用（`:84`）。否则一次非法提交会白白推进版本号，让后续引用全部错位。

### ProducedBy：谁产出的

角色名，或者 `"code"`。

`Topic` 的 `ProducedBy` 是 `"code"`（`artifact.go:326`），因为主题是代码写进黑板的，不是模型产出的。这样排查时一眼能看出"这一版有没有模型参与"。

### Summary：形状投影，不是全文

`Summary` 由代码从 payload 派生，不是模型自述。

看 `Research.Summarize`（`artifact.go:361`）：

```go
return fmt.Sprintf("research「%s」：%d 条查询 / %d 条发现", ...)
```

它只投影形状，不含正文。判据是：

> 摘要必须能让下一跳判断"要不要去黑板取全文"，并且能让人读懂这条链。

`RenderResult.Summarize` 还会在失败时补一句"X 页未产出"（`artifact.go:461`）。为什么要强调？因为如果摘要只说"3 个文件"，下一跳会以为全都成功了。

### Shortfall：存在不等于完整

`Shortfall` 是可选能力（`Partial` 接口，`artifact.go:119`）。产物自己报告缺口：

```go
func (r RenderResult) Shortfall() []string {
    // "第 3 页：写盘失败"
}
```

为什么不做成必选？因为大多数产物不会残缺，强迫它们实现一个恒返回 nil 的方法，只会淹没有用的契约。

这个字段修复的是一个真实 bug（L2-2）：渲染 3 页、失败 1 页，编排者只看"黑板上有 render"，就宣布"产物齐全"。"存在"不等于"完整"。

### BasedOn：血缘，给代码比较

```go
type Basis struct {
    Key     string
    Version int
}
```

为什么不是 `"outline@1"` 这样的字符串？

因为要给代码比较。字符串必须先解析再比较，而"格式"与"解析"一旦分处两地就会漂移。给模型看的是 `Ref()` 字符串，给代码比的是 `Basis` 结构（`artifact.go:131-143`）。

### Payload：不透明字节

`json.RawMessage`。编排者不解码它，只读信封上的元信息。

这条边界很关键：一旦编排者能解码 payload，它就会开始读业务字段，最后变成"每个节点都知道其他节点的数据结构"——那正是多 Agent 系统腐化的开始。

## 10.4 引用：`key@version`

`RefOf` 返回 `outline@2`（`artifact.go:284`）。

为什么要带版本？因为这样引用就是不可变的：

- 黑板追加 `outline@3` 时，`outline@2` 依然指向它当时的那一版；
- 返工/重试时，旧引用不会"指向漂移"；
- 日志和回放能精确重放当时看到的那一版。

`ParseRef`（`blackboard.go:160`）支持两种写法：

| 写法 | 含义 | 谁用 |
|---|---|---|
| `outline` | 最新版 | 人看看板、临时查询 |
| `outline@2` | 指定版本 | 写进流程的引用、日志、回放 |

版本号必须是正整数。`outline@0`、`outline@x`、`@1` 都会被拒绝。

## 10.5 黑板的四条不变量

`Blackboard` 很小，但有四条不能破的规矩：

### 规矩一：追加，绝不覆盖

同一个 key 每 `Put` 一次就多一版。这是 `key@version` 能成立的前提。

### 规矩二：进出都是深拷贝

`Payload` 是 `[]byte`，引用类型。不拷贝的话，一个 Agent 取到产物、顺手改了 `Payload[0]`，黑板里的那份就跟着变，其他 Agent 完全不知道自己拿到了脏数据。

`Put`、`Get`、`Snapshot` 都做了深拷贝（`blackboard.go:90`、`:127`、`:203`）。

### 规矩三：校验是零副作用的

非法提交不能推进版本号。否则一次失败会让后续所有引用错位。

### 规矩四：快照必须校验版本序列

`LoadSnapshot`（`blackboard.go:231`）检查：

- map 的 key 与信封的 key 一致；
- 版本从 1 开始、逐 1 递增、与下标一致；
- 每份产物都过 `Validate`。

为什么要这么严？因为 `Get("outline@2")` 是靠 `versions[version-1]` 取值的。快照里一旦有洞（`[1,3]`）或乱序（`[2,1]`），就会静默取到另一份产物。

> 一份读不出来的产物会让任务失败；一份被错取的产物会让任务**成功地做错**。后者危险得多。

## 10.6 血缘与新鲜度

`BasedOn` 记录"我基于哪一版上游"。`BasesOf` 从一批上游产物生成它（`artifact.go:310`）。

`StaleReasons`（`artifact.go:505`）做传递式检查：

```text
topic@1 → research@1 → outline@1 → design@1 → render@1
```

如果 `outline` 重跑成 `outline@2`：

- `design@1` 依据 `outline@1`，直接过期；
- `render@1` 依据 `outline@1` 和 `design@1`，直接过期（outline 变了），同时通过 `design` 间接过期。

`StaleReasons` 用后序遍历：先走完上游，再报告自己。于是返回的列表天然是可执行的修复顺序——先重跑 `design`，再重跑 `render`。如果先报 `render`，你照着做一遍还是会被同一条规则拦下。

它还用一个 `visited` 集合兜住环：即使 `BasedOn` 出现循环，也不会无限递归。

注意：`StaleReasons` 返回的是原因列表，不是布尔值。有原因 = 过期。这样调用方既能判断，又能把原因原样交给模型当待办。

## 10.7 Handoff：只传引用和摘要

`Handoff`（`artifact.go:274`）只有两个字段：

```go
type Handoff struct {
    Ref     string
    Summary string
}
```

payload 全文不进上下文。要全文的人，拿 `Ref` 去黑板取。

为什么？两个理由：

1. 省 token：一页 HTML、一份完整 JSON，可能在上下文里被重复传很多次；
2. 防漂移：如果每个下游都复述一遍全文，每复述一次都可能改写一点，最后没有人知道哪份是真的。

`HandoffsOf` 和 `BasesOf` 都放在 `schema`，因为已经有两个调用方（L2 的 SubAgent 和 L3 的 Runner）。两份实现就是两种漂移的可能。

## 10.8 信封不解决什么

不要把它当成万能：

- 不校验 payload 的业务语义：它只校验信封字段和 Kind 一致性；`Research` 有没有 findings、`Outline` 页数对不对，要各自的 `Validate` 做；
- 不负责调度：它只记录血缘，不决定"谁该先跑"；那是图编排（第 17 到 22 章）；
- 不负责持久化：黑板在内存里，存盘是 checkpoint（第 22 章）；
- 不解决冲突合并：同一 key 的多个版本是并存的，选哪一版是调用方的事。

## 10.9 练习

### 练习 1：验证追加与深拷贝

用 `state.NewBlackboard()`：

1. `Put` 同一份 key 两次，版本分别是多少？
2. `Get("key@1")` 和 `Get("key@2")` 是否都能取到？
3. 把 `Get` 返回的 `Payload` 改一个字节，再 `Get` 一次，黑板里的内容变了吗？

### 练习 2：构造一条血缘链

写入 `topic@1` → `research@1`（BasedOn topic@1）→ `outline@1`（BasedOn research@1）。

然后重跑 research，写入 `research@2`。

用 `StaleReasons(outline, latest)` 检查 `outline@1`。回答：

- 它返回几条原因？
- 原因里提到的是哪个 key？
- 如果 `outline` 还有下游 `design`，`design` 的检查结果是什么？

### 练习 3：ParseRef 的边界

对下面每个输入，写出 `(key, version, err)`：

```text
outline
outline@2
outline@0
outline@x
@1
""
```

### 练习 4：设计一个 Summary

给一个 `Outline` 产物写 `Summarize()`，要求：

- 不超过 100 字；
- 包含页数和前几页标题；
- 不包含每页的全部要点（那是 payload）。

然后构造一个 `RenderResult`，让它的 `Summary` 在失败时明确写出"X 页未产出"。

### 练习 5：什么时候该有 Shortfall

下面三种情况，哪些应该产生 `Shortfall`？

1. 3 页渲染成功 2 页，第 3 页写盘失败；
2. research 找到 0 条发现；
3. outline 只有 2 页，但期望 3 页。

提示：`Shortfall` 表达的是"产物存在，但不完整"；"完全没有"和"数量不对"要分别用别的判据。

## 10.10 拓展：让模型写摘要，看它会不会说谎

把 `Artifact.Summary` 换成模型自己写的一句话，再故意让上游多出一版。观察下游会不会发现“摘要和 payload 对不上”。

代码派生的摘要不一定更聪明，但它不会编。这个实验想让你记住：摘要的职责是“帮下一跳判断要不要取全文”，不是“替产物下结论”。
