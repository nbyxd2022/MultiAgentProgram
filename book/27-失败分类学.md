# 第 27 章 失败分类学：跑 20 次，给失败起名字

通过率有了，但它只告诉你“有没有问题”，不告诉你“下一个动作”。这一章给失败起名字。

## 27.1 通过率是一个太粗的指标

假设你跑 20 次，通过 16 次，通过率 80%。

这个数字告诉你什么？

- 有 4 次失败；
- 但为什么失败？不知道；
- 该修哪里？不知道；
- 修完之后会不会变成 90%？不知道。

而如果你把 4 次失败分类：

```text
2 次：模型输出被截断（finish_reason=length）
1 次：上游 review 过期，downstream 没重跑
1 次：工具参数错，模型重试 3 次后放弃
```

下一步立刻清楚：

- 截断 → 加 max_tokens 或分段；
- 过期 → 修调度顺序；
- 参数错 → 改工具描述或错误提示。

> **通过率告诉你"有没有问题"；失败分类告诉你"下一个动作是什么"。**

## 27.2 一套可用的分类

按"失败发生在哪一层"和"下一步该看什么"来分，不要按错误文案分。

### A. 未跑完（Run Error）

用例/任务根本没有结束。

典型原因：

- 模型调用失败（网络、超时、限流）；
- 预算触顶；
- 图执行报错（节点 error / panic）；
- context 取消。

下一步：看 `Verdict.Err` / Runner 的 error，不是看产物。

### B. 缺产物（Missing）

跑完了，但某个必需产物根本没有。

典型原因：

- 角色没被调度；
- 角色跑了但没提交；
- 提交了但 Kind 不对。

下一步：看 `Missing` 列表和调度日志。

### C. 不完整（Incomplete）

产物存在，但 `Shortfall` 非空。

典型原因：

- 渲染 3 页，1 页失败；
- 研究只完成了一部分。

下一步：补缺口，不要整个重做。

### D. 过期（Stale）

产物存在、完整，但依据链过期。

典型原因：

- 上游重跑，下游没重跑；
- 依赖声明不准确；
- 人工修改后没有按顺序修复。

下一步：按 `StaleReasons` 的顺序，先上游后下游。

### E. 错位（Mismatch / Decode）

产物存在，但类型/内容对不上。

典型原因：

- 信封 Kind 与 payload Kind 不一致；
- 两个节点抢同一个 key；
- payload JSON 坏了。

下一步：看产物本身，不是看角色。

### F. 评审/提交失败（Submit / Review）

角色跑了，但结论没有合法提交。

典型原因：

- 没调用 `submit_*`；
- 调用了但 JSON 非法；
- 字段缺失/枚举非法；
- 评审没跑完（`Incomplete`）。

下一步：看回灌的错误与提交回执。

### G. 成本/时间异常（Budget / Wall）

跑完了，但成本或时间明显不对。

典型原因：

- 重试风暴；
- 上下文过长；
- 打转（max steps）；
- 工具结果过大。

下一步：看 `Metrics.Steps` / `AgentSteps` / token / wall，找异常点。

### H. 恢复/人工失败（Resume / HITL）

中断或恢复出了问题。

典型原因：

- 中断过期；
- 回答不合法；
- 决策没有落盘；
- attempt/ID 对不上。

下一步：看 `ResumeErrorKind` 与 `Pending`。

## 27.3 分类的三个判据

### 判据一：可行动

一个分类必须能指向"下一步看哪里"。

"模型表现不好"不是分类——它不告诉你去看 Prompt、上下文、工具还是模型。

"输出被 length 截断"是分类——下一步很清楚。

### 判据二：互斥

顶层分类要互斥，否则一次失败会被算两次，统计就失真。

例如：

- "缺产物"和"不完整"是两件事：前者是没做，后者是做了但没做全；
- "未跑完"和"判据没过"是两件事：前者看 error，后者看产物。

### 判据三：能计数

分类要能聚合：

```text
本次 20 次：A 2 / B 1 / C 3 / D 4 / E 0 / F 2 / G 1 / H 7
```

不能计数的分类，只是描述，不是指标。

## 27.4 仓库里的真实失败，各自叫什么

| 事件 | 分类 | 根因 | 修法 |
|---|---|---|---|
| L1-3 评审没跑完，却被当"没问题" | F | `Incomplete` 只进 error，没进数据 | 把状态放进 `Report`，`Deliverable` 检查 |
| L2-1 新内容配旧版式 | D | 只查存在性，没查新鲜度 | `StaleReasons` + 传递检查 |
| L2-2 3 页里失败 1 页，系统说齐全 | C | `Failed` 只打印，没人读 | `Shortfall` 进信封，完成判断读它 |
| L2-9 角色超时，模型换 10 种措辞重试 | G | 没有熔断/连续失败计数 | 熔断 + 把失败次数告诉模型 |
| L3-1 换 Hint 重启，血缘仍说新鲜 | H/输入 | Hint 没进状态 | Hint 存状态 + 比对 |
| L3-2 中断永不过期 | H | `ExpiresAt` 没有生产者 | Runner 统一填 TTL |
| L4 `CostMilli` 永远是 0 | G/空壳 | 没有价格表 | 接真实模型时补 |
| L4 `KindReconcile` 没人发 | E/空壳 | 没有"声明 vs 实际"的对照点 | 出现页数不符时补 |

这张表比"通过率 80%"有用得多。

## 27.5 跑 20 次，具体怎么做

### 第一步：固定变量

- 固定用例集；
- 固定模型与温度；
- 固定预算；
- 记录 commit。

否则你比较的不是"改动前后"，而是"两次不同的实验"。

### 第二步：每次记录一张卡

```text
run id:
case id:
结果: pass / fail / error
分类: A~H
失败判据:
关键指标: steps / agent_steps / tokens / wall
一句话根因:
```

### 第三步：先修最贵的两类

不要按"最容易修"排序，按"影响最大"排序：

- 出现频率；
- 每次的成本；
- 是否阻塞其他修复。

### 第四步：修完再跑同一组

不要换用例，不要换模型。否则数字不可比。

## 27.6 一个反例：用"平均分"指导一切

假设软判据平均分从 7.2 降到 7.0。

这只说明"某几页变差了"，不说明：

- 是内容不完整？
- 是可读性下降？
- 还是模型这次心情不好？

软判据是线索，不是判据（第 26 章）。失败分类才是行动依据。

## 27.7 练习

先自己做，再看 `answers/27-参考答案.md`。

### 练习 1：给四个注入分类

跑：

```powershell
$env:L4_BAD_CASE="1"; go run ./cmd/l4
$env:L4_JUDGE_REFUSES="1"; go run ./cmd/l4
$env:L4_HUGE_TOKENS="outline"; go run ./cmd/l4
$env:L4_LOOP_FOREVER="outline"; go run ./cmd/l4
```

给每次失败分类（A~H），并写出"下一步该看什么"。

### 练习 2：设计一张失败卡

用 27.5 的模板，给你最近一次失败写一张卡。

要求：

- 分类只能选一个；
- 根因必须是一句话；
- 下一步必须是一个动作，不是"再查查"。

### 练习 3：找一次"分类错误"

构造一个场景：你以为是"模型不行"，实际是"产物过期"。

回答：

- 只看最终输出，你能区分吗？
- 需要哪些事件/字段才能区分？
- 你会把哪个字段加进报告？

### 练习 4：给仓库加一个失败分类字段

假设你要在 `Verdict` 里加：

```go
FailureKind string
```

回答：

- 谁来填？
- 填错了会怎样？
- 它能替代 `Failed []string` 吗？

### 练习 5：20 次实验计划

设计一次"改 Prompt 前后"的实验：

- 用多少条用例？
- 每条跑几次？
- 记录哪些指标？
- 怎么判断"变好"不是噪声？

## 27.8 小结与自检
合上书，回答：

- 通过率为什么不够？
- A~H 八类分别是什么？各对应什么下一步？
- 分类的三个判据是什么？
- 为什么"未跑完"和"判据没过"必须分开？
- 为什么修失败要按"影响"而不是"容易"排序？
- 软判据平均分为什么不能指导下一步？
- 一次可比较的实验要固定哪些变量？

能答出五题以上，再进下一章。

## 27.8 拓展：写一张失败卡

给最近一次失败写一张卡：结果、分类、根因、下一步。

写不出来，说明你还没定位；写得出来，下一步就已经有了。这张卡也是你做实验记录的最小单位。
