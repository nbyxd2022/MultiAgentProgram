# 第 5 章 工具协议：从 Go 函数到 JSON Schema

消息的形状定下来了，接下来是工具契约。模型怎么知道该传什么参数、工具又该怎么把错误说清楚，是这一章要回答的问题。

## 5.1 一个失败场景

你有一个生成幻灯片的工具，参数是：

- `title`：字符串
- `bullets`：字符串数组

模型返回了：

```json
{
  "title": "新能源汽车趋势",
  "bullets": "渗透率提升；成本下降；出口增长"
}
```

`bullets` 是一个字符串，不是数组。工具解析失败，返回 `json: cannot unmarshal string into Go struct field ...`。模型看到这段错误，又把同样的参数发了一遍。三轮之后，达到最大步数。

问题不在模型"笨"。问题在三个地方：

1. 工具描述没有给出参数示例；
2. 错误信息是给 Go 程序员看的，不是给模型看的；
3. 工具没有在错误里告诉模型"正确形状长什么样"。

这一章就是把这三个地方拆开。

## 5.2 一个工具的三层

仓库里的工具不是一个函数，而是三层：

| 层 | 代码位置 | 谁在用 | 作用 |
|---|---|---|---|
| 契约 | `internal/tool/tool.go:53` 的 `Definition` | 模型 | 告诉模型"我叫什么、能做什么、参数是什么" |
| 内核 | 例如 `RenderSlideHTML.Render` | 你的代码、测试 | 真正干活，不关心 JSON 协议 |
| 适配器 | `internal/tools/render_slide.go:154` 的 `Execute` | Agent/注册表 | 把模型给的 JSON 字符串解析成内核参数 |

再加一个注册表：

- `internal/tool/registry.go:14`：按名字找到工具；
- `internal/tool/registry.go:40`：按稳定顺序返回全部契约；
- `internal/tool/registry.go:49`：按名字执行，未知工具返回明确错误。

### 为什么内核和适配器要分开？

看 `RenderSlideHTML`：

```go
// 内核：直接渲染一页，不解析 JSON
func (t *RenderSlideHTML) Render(slide schema.Slide) (string, int, error)

// 适配器：解析模型给的 JSON，再调用内核
func (t *RenderSlideHTML) Execute(_ context.Context, args string) (string, error)
```

这个拆分带来三个好处：

1. **单测可以直接调 `Render`**，不用构造 JSON；
2. **编排代码可以直接调 `Render`**，不用先把结构体序列化再解析；
3. 只有模型调用那条路径才走 `Execute`，协议问题不会污染内核。

这和 L0 的"端口-适配器"是同一个思路，只是缩小到了一个工具内部。你用过 Eino，应该熟悉这种"工具实现"和"工具描述"分离的设计；区别在于，手写时你需要自己决定哪一层负责校验、哪一层负责副作用。

### 一个具体的教训：副作用要在成功之后才登记

`RenderSlideHTML.Execute` 在写盘成功之后，才更新"最近一次产物"：

```go
path, size, err := t.Render(in)
if err != nil {
    return "", err
}

// 只有成功写盘，才记录产物
t.mu.Lock()
t.last = ...
t.mu.Unlock()
```

如果提前记录，一次失败的渲染也会被登记，后续就会去评审一个"根本不存在的版本"。**副作用和状态登记的顺序，是工具层最容易犯的错之一。**

## 5.3 工具描述是提示词的一部分

模型看不到你的 Go 代码，它只看得到 `Definition` 里的 `Description` 和参数说明。所以，工具描述不是"注释"，是提示词。

一个可用的描述至少回答四个问题：

1. 它做什么？ 一句话。
2. 什么时候该用？ 给出触发场景。
3. 什么时候不该用？ 防止模型拿它做别的事。
4. 参数有什么约束？ 尤其是容易歧义的地方。

对比一下：

```text
// 差
查询天气。

// 好
查询某个城市当前的实时天气。
何时使用：用户询问今天/此刻的温度、降雨、风力时。
不要用于：历史天气、气候趋势、天气预报。
参数 city 必须是城市名，例如"北京"、"上海"；不要传省份或经纬度。
```

第二版没有更长，但每一句都在减少模型猜的空间。

### 约束只有一个来源

仓库的 `RenderSlideHTML.Definition` 里，数字全部来自 `schema` 常量：

```go
fmt.Sprintf("标题不超过 %d 字；bullets 为 %d-%d 条纯文本要点，每条不超过 %d 字",
    schema.MaxTitleRunes, schema.MinBullets, schema.MaxBullets, schema.MaxBulletRunes)
```

为什么？因为约束写在两处，两处都会失守。之前这里写死过"2-5 条"，而检查器按 `MinBullets=3` 判，模型无论怎么改都过不了。同一个约束，只能有一个来源。

> 但要注意：描述里写了上限，不代表工具真的检查了。`RenderSlideHTML.Render` 目前只检查标题非空、bullets 非空，并没有检查 `MaxTitleRunes`。这是第 5.8 节的一个练习：**描述是承诺，`Execute` 要兑现承诺。**

## 5.4 参数设计：让模型少猜

几条实用规则：

### 规则一：优先用显式字段，不要用自由文本

```text
差：{"instruction": "把标题改短一点，再加三条要点"}
好：{"title": "...", "bullets": ["...", "...", "..."]}
```

自由文本让模型承担"解析意图"的责任，结构化字段让代码承担。能让代码做的，不要交给概率模型。

### 规则二：参数不要太多

一个工具超过 5 到 6 个参数，模型出错的概率会明显上升。可以考虑：

- 拆成多个工具；
- 把一组相关参数收成一个对象（仓库的 `TypeObject` 就是为此补的）；
- 把运行时可推导的参数（用户 ID、会话 ID）从 schema 里去掉，由运行时注入。

### 规则三：数组和对象要描述元素形状

仓库的 `tool.Parameter` 是一棵树：

```go
type Parameter struct {
    Name        string
    Type        ParameterType
    Description string
    Required    bool
    Items       *Parameter  // Type=array：元素长什么样
    Properties  []Parameter // Type=object：有哪些字段
}
```

`render_slide_html` 的 `bullets` 就是 `TypeArray + Items=TypeString`。如果只写 `"type":"array"` 而不写 `items`，模型就不知道元素该是什么。

### 规则四：能枚举就不要用自由字符串

仓库的 `Parameter` 目前没有 `enum` 字段，这是一个真实的能力缺口。如果你要加，最小改动是：

1. `tool.Parameter` 加 `Enum []string`；
2. `internal/llm/openai.go` 的 `paramSchema` 里，如果 `len(p.Enum) > 0`，写入 `"enum": p.Enum`；
3. 给一个测试，确保枚举出现在最终 JSON Schema 里。

这个练习的价值不在代码量，而在让你看到：**协议层的表达力不足时，正确做法是扩展协议，而不是让业务去将就。**（仓库补 `TypeObject` 时也是这个理由，见 `internal/tool/tool.go:22` 的注释。）

## 5.5 错误契约：让模型能自愈

工具返回的 `error` 不会直接给用户，而是被 Agent 转成一条结构化结果：

```json
{
  "ok": false,
  "tool": "render_slide_html",
  "error": "bullets 必须是字符串数组",
  "hint": "请检查参数是否符合工具定义；如无法修复，请改用其他工具或调整方案。"
}
```

代码在 `internal/agent/agent.go:318` 的 `formatToolError`。

这个设计有三个要点：

### 要点一：错误是数据，不是异常

工具返回 `error`，Agent 不 panic、不直接退出，而是把错误包成 JSON 回灌。模型看到 `ok=false`，有机会修正参数。

### 要点二：错误信息要可操作

对比：

```text
差：json: cannot unmarshal string into Go struct field Slide.bullets of type []string
好：bullets 必须是字符串数组，例如 ["要点1","要点2"]；你传的是字符串。
```

第二版告诉模型"错在哪、正确形状是什么"。模型不需要懂 Go 的反射错误。

### 要点三：不是所有错误都该回灌

这条很重要，但仓库目前的 `formatToolError` 没有区分。它把所有工具错误都加上同一句 hint。实际系统里至少要分两类：

| 类型 | 例子 | 该不该回灌 |
|---|---|---|
| 模型可修复 | 参数类型错、缺必填字段、枚举值非法 | 该 |
| 运行时/配置错误 | API Key 错、工具未注册、磁盘满、权限不足 | 不该；应快速失败并让人类处理 |

如果把第二类也回灌，模型会反复重试一个它根本修不了的问题，烧钱且拖延。第 7 章会把这条分类补上。

## 5.6 注册表：顺序也是协议的一部分

`Registry` 很小，但有两个细节值得注意。

### 细节一：`Definitions` 保持注册顺序

```go
func (r *Registry) Definitions() []Definition {
    out := make([]Definition, 0, len(r.order))
    for _, name := range r.order {
        out = append(out, r.tools[name].Definition())
    }
    return out
}
```

为什么不用 map 直接遍历？因为 map 的遍历顺序是随机的。工具清单的顺序会影响提示词的内容，进而影响模型行为；更实际的是，调试时你需要两次运行的提示词完全一样。

### 细节二：同名工具会被覆盖

```go
if _, exists := r.tools[name]; !exists {
    r.order = append(r.order, name)
}
r.tools[name] = t
```

同名注册不会报错，而是覆盖，同时保留原顺序。

这是一个取舍：覆盖让"后注册的实现替换前一个"成为可能（测试里有用），但也可能掩盖一个装配错误（两个模块注册了同名工具，你以为是两个，实际只有一个）。

在更大的系统里，我更倾向于同名注册直接报错，把问题在装配期暴露出来。仓库选择了覆盖，你可以在第 29 章的差异审计里重新评估这个决定。

### 细节三：未知工具的错误要列出可用工具

```go
return "", fmt.Errorf("未知工具: %q（可用工具: %v）", name, r.Names())
```

模型看到"可用工具有哪些"，才有机会改用正确的工具。错误信息不只是给日志看的，也是给模型看的。

## 5.7 对照 Eino：schema 是自动生成还是手写？

你用过 Eino 的工具抽象，可能见过两种做法：

1. **从 Go 结构体/函数签名自动生成 JSON Schema**（省事，但描述往往很弱）；
2. 手写工具描述与参数（啰嗦，但可控）。

仓库选择了第二种：`Definition()` 是手写的，参数树也是手写的。

自动生成的代价是：**描述通常来自字段名或注释，模型得到的上下文很少。** 对简单工具够用；对"什么时候该用/不该用"这种判断，自动生成基本帮不上忙。

你可以把 Eino 的做法当作对照：它替你省掉了 schema 的机械部分，但工具描述的质量仍然是你的责任。框架不会替你写清楚"这个工具不该用来做历史天气查询"。

## 5.8 练习

先自己做，再看 `answers/05-参考答案.md`。

### 练习 1：改一个描述，观察调用率

把 `book/code/ch03/tools.go` 里 `get_weather` 的描述改成：

```text
查询天气。
```

然后接真实模型，问"北京今天热不热？"再问"北京历史上七月平均气温是多少？"

观察：

- 第一个问题它调用工具吗？
- 第二个问题它会不会也调用（不应该）？
- 把描述改回带"何时使用/不要用于"的版本，结果有什么变化？

这个练习没有精确指标，但你会亲眼看到描述是提示词。

### 练习 2：给参数加 enum

给 `book/code/ch03` 增加一个 `set_style` 工具：

- 参数 `style`，只允许 `"简洁"`、`"详细"`、`"学术"` 三个值；
- 先只在描述里写"只能是这三个值"，观察模型是否遵守；
- 再给 `Parameter` 加 `Enum` 字段，并在生成 JSON Schema 时写入 `"enum"`，再观察。

比较两次的遵守率。这个练习会让你理解：**能用 schema 表达的约束，不要只写在描述里。**

### 练习 3：让描述里的约束真正生效

`RenderSlideHTML` 的描述说标题不超过 `schema.MaxTitleRunes`，但 `Render` 只检查了非空。

1. 在 `Render` 里补上长度检查，返回一个可操作的错误；
2. 接真实模型，让它生成一个超长标题；
3. 观察模型看到错误后，会不会自己改短。

这是一个"描述—校验—错误—自愈"的完整闭环。做完你会明白：**只写描述不写校验，等于给模型一个它无法验证的承诺。**

### 练习 4：把错误信息改成人话

找一个工具解析失败的分支，把 Go 的原始错误改成"模型能看懂"的错误。例如：

```go
return "", fmt.Errorf("bullets 必须是字符串数组，例如 [\"要点1\",\"要点2\"]；收到的是 %T", in.Bullets)
```

然后让模型用错误参数调用，观察它第二次是否改对。

## 5.9 拓展：描述也决定“该不该调”

把 `get_weather` 的描述删到只剩“查天气”，再问“北京历史上七月平均气温是多少”。它会不会调用？

这个实验让你看到：描述不只影响参数怎么填，还影响模型判断“什么时候不该用这个工具”。后一种错误更隐蔽，因为工具调用本身“成功”了，只是用错了地方。
