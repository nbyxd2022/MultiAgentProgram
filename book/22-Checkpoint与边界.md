# 第 22 章 Checkpoint、原子写盘与"何时不该用图"

恢复语义讲完了，可它依赖一个前提：磁盘上的状态不能是半截的。这一章看 checkpoint 怎么写盘。

## 22.1 一次写盘被杀会留下什么

`os.WriteFile` 的语义是"先截断，再写"。

如果写到一半进程被杀：

- 文件存在；
- 内容只有一半；
- 它看起来和一个正常文件一模一样。

下次启动，你只会看到 `unexpected end of JSON input`——完全看不出"是上次写崩了"。

L3 的全部承诺（"进程死了能接着跑"）都建立在 checkpoint 上。如果 checkpoint 本身可能是半截，这个承诺就是空的。

## 22.2 原子写的五步

`internal/checkpoint/file.go:79` 的 `Save`：

```text
① 创建同目录临时文件 ckpt-XXXX.tmp
② 写入内容
③ fsync 临时文件
④ rename 临时文件 → 目标 .json
⑤ fsync 目录
```

每一步都有理由：

### ① 临时文件必须在**同目录**

`rename` 只在同一文件系统内原子。放到 `/tmp` 再 rename 到项目目录，可能变成"复制 + 删除"，不再原子。

### ② 写入后 fsync

没有 fsync，rename 之后机器崩掉，可能出现"文件名在、内容还在页缓存里没落盘"——一个 0 字节或半截的文件。

### ③ rename 是原子替换

POSIX 保证 `rename(2)` 原子。任何时刻，目标文件要么是旧的完整版，要么是新的完整版。

### ④ fsync 目录

`rename` 修改的是目录项。只 fsync 文件不够，断电后可能出现"文件内容在、名字不在"。

Windows 不允许 `os.Open` 一个目录，所以 `syncDir` 容忍失败。这是持久化强度的差异，不是正确性差异（不会产生半截文件）。

### ⑤ Windows 的 rename 重试

Windows 的 `MoveFileEx(REPLACE_EXISTING)` 在目标正被另一个写入者占用时会返回 `ERROR_ACCESS_DENIED`。

仓库实测：12 个 goroutine 并发 Save 同一个 run，Windows 上 6 次失败。

所以 `renameWithRetry` 做有界重试（3 次，递增短等待）。

注意：它不区分错误类型。判断一个 rename 失败是不是瞬时的，需要平台相关错误码；写错会变成"Linux 上看着对、Windows 上静默不重试"。有界重试最多多花几毫秒，然后原样返回错误。

> **失败是安全的，只是不理想。** 契约的核心是"永远看不到半截文件"，而不是"Save 永不失败"。

## 22.3 FileStore 的四条规矩

### 规矩一：一个 run 一个文件

`runID.json`。简单、可读、易备份。

### 规矩二：只认 `.json` 后缀

`List` 会忽略 `ckpt-*.tmp`。

为什么？因为"写到一半被杀"会留下临时文件；如果把它也列出来，调用方会去 Load 一个残缺副本——而它看起来和正常 run 一模一样。

这是"存在 ≠ 完整"在存储层的同一个形状：一个能被列举出来的东西，必须真的可用。

### 规矩三：拒绝空内容

`Save` 不接受长度为 0 的内容。

写进去之后，那份空文件就和"曾经正常、后来被截断"的文件无法区分。在源头挡住，错误信息还能带 run id。

### 规矩四：run id 必须能安全拼进路径

`fileName` 只允许 ASCII 字母、数字、`-`、`_`、`.`，最长 128 字节。

为什么不"清洗"（把 `/` 换成 `_`）？

因为清洗会制造碰撞：`a/b` 与 `a_b` 都会变成 `a_b`，两个 run 共用一个文件，后写顶掉先写，且无人知晓。

拒绝则把问题暴露在调用方的错误上，而不是变成数据事故。

## 22.4 一个只装在门上的锁

`cmd/l4` 会做：

```go
dir := filepath.Join(outDir, "ckpt", c.ID)
os.RemoveAll(dir) // ← 这一步不经过 FileStore
```

`c.ID` 来自 JSONL 用例集。如果它是 `../../x`：

- `FileStore` 的校验形同虚设；
- `RemoveAll` 会删掉 `outDir/ckpt` 之外的目录。

**一道只装在门上的锁，挡不住从窗户进来的人。**

修法不是"在 cmd/l4 里再写一遍校验"（两处会漂移），而是把唯一的一份校验导出为 `checkpoint.ValidRunID`，让"碰磁盘之前"的那一步自己验。

现在 `cmd/l4` 已经调用了它（`cmd/l4/main.go:277`）。

这个例子值得记住：

> **校验要放在"拥有危险能力的那一层"之前。** 否则你校验的只是"正常路径"。

## 22.5 State 里到底存了什么

`State`（`graph/state.go:134`）：

```go
type State struct {
    Version   int
    RunID     string
    Board     map[string][]schema.Artifact
    Pending   *Interrupt
    Hints     map[string]string
    CreatedAt time.Time
    UpdatedAt time.Time
}
```

没有 `Node` 游标，没有 `Done` 集合，没有 `Topic` 字段。

- 完成是产物的属性，不是节点的属性；
- 下一步可以从 `CanSkip` 算出来；
- Topic 从黑板上的 `topic@1` 读，不另存一份（否则它会说谎）。

`Validate` 会检查：

- 版本、run id、黑板非空、时间戳；
- `topic` 产物存在且可解析；
- `Pending` 与 State 属于同一轮（防串台）；
- 黑板版本序列连续、信封与位置一致。

`Marshal` 在写盘前自校验：能在源头挡住的问题，不要留给下游的读方。

## 22.6 全量快照的代价

`Board` 是全量快照，不是增量日志。

为什么可以这样？因为黑板是追加、绝不覆盖的，所以"全量快照"与"截取一个时间点"在语义上等价。

但代价是：每跑一个节点，就要把整个黑板写一遍。

如果黑板很大（比如 100 页 HTML 全文都在里面），写盘会成为瓶颈。L3 的取舍是"还没到那一步"；真要优化，再引入增量日志或外置大产物。

这也解释了为什么 `RenderResult` 只存文件路径，不存 HTML 正文：大产物外置，上下文和 checkpoint 都只留指针。

## 22.7 什么时候不该用图

图不是"更高级"，它是一种取舍。以下场景不适合：

### 1. 任务很短、一次就完

一个单 Agent + 一个工具就能完成的任务，引入图只会增加：

- 建图与校验；
- State/checkpoint 的代码；
- 节点适配器；
- 恢复语义的理解成本。

**不要为了"看起来像 Agent 系统"用图。**

### 2. 流程高度开放

如果"下一步做什么"完全取决于模型对当前情况的判断，而且没有稳定的节点集合，图会很难受：

- 你要提前枚举节点；
- 分支要靠 `Outcome.Next` 或条件边；
- 加一种新任务就要改图。

这种场景用 Supervisor 更合适（第 12 章）。

### 3. 不需要恢复和 HITL

图的核心价值是：

- 顺序确定性；
- 断点恢复；
- 人工中断；
- 审计。

如果这些都不需要，固定流水线或单 Agent 更简单。

### 4. 吞吐/延迟敏感

当前 Runner 是串行的；每个节点跑完还要写一次全量 checkpoint。

高吞吐场景下，这两点都会成为瓶颈。

### 5. 节点集合不稳定

如果角色是动态生成的（比如按用户输入临时决定有哪几个步骤），图的"建图期校验"就失去了意义。

## 22.8 一张决策表

| 需求 | 推荐 |
|---|---|
| 单步任务、工具调用 | 单 Agent |
| 固定几步、不需要恢复 | 流水线 |
| 开放任务、模型决定下一步 | Supervisor |
| 需要顺序保证、恢复、HITL、审计 | 图 |
| 外层流程固定、内层探索开放 | 图 + Supervisor 节点 |
| 高吞吐、低延迟 | 不用图（或先做并行/增量 checkpoint） |

**选架构的标准不是"哪个更先进"，而是"哪个的代价你愿意付"。**
