# 第 25 章 预算：五维、fail-closed、失败也花钱

观测出口管住了，可光看见还不够，还得能停下来。一次跑飞的循环，账单可能从几毛变成几十块。

## 25.1 一个没有预算的 Agent

如果没有预算：

- 模型可以一直调用工具；
- 每次调用都花钱；
- 一次跑飞的循环，账单可能从几毛变成几十块。

L0 的 `MaxSteps` 只挡住了"步数"，没有挡住 token、成本、时间。

L4 的 `budget` 包补的是这件事。

## 25.2 五个维度

`Usage` / `Limits`（`budget.go:108`、`:152`）：

| 维度 | 单位 | 谁能报 |
|---|---|---|
| Steps | 次 | Runner（每跑一跳） |
| PromptTokens | token | Agent（每次模型调用） |
| CompletionTokens | token | Agent |
| CostMilli | 厘（1/1000 元） | 目前**没有生产者** |
| Elapsed | time.Duration | Runner（每跳实际执行时间） |

### 零值 = 上限 0

`Limits{}` 的五维都是 0，含义是"什么都不让做"（fail-closed）。

这是刻意的：

> 一个忘记配预算的调用方，应该得到"跑不了"，而不是"无限花钱"。

要"不限"，必须显式用 `NoLimit`（-1）或 `NoWall`：

```go
budget.New(budget.Limits{
    Steps:            10,
    PromptTokens:     budget.NoLimit,
    CompletionTokens: budget.NoLimit,
    CostMilli:        budget.NoLimit,
    Elapsed:          budget.NoWall,
})
```

**"不限"是一个需要被写下来的决定，而不是忘记配置的默认结果。**

### 一个真实的文档漂移

`budget.go` 的开头还写着"四维"，而 `Dims()` 返回五维；`Limits` 的结构体注释也有"四维额度"的字样。

代码是对的，文档是旧的。这类漂移不会让程序出错，但会让读代码的人困惑——第 29 章会把它列进差异审计。

## 25.3 检查与记账分离

`Guard` 只有三个方法：

```go
Allow(need Usage) Decision
ReportUse(used Usage)
Snapshot() Snapshot
```

- `Allow`：检查"再做一步会不会超"，不记账；
- `ReportUse`：记录"这一步实际用了多少"；
- `Snapshot`：看现状。

为什么分开？

- 事前不知道真实用量（token 要跑完才知道）；
- 事后再记，账才是真实的；
- 代价是有个时间窗口：检查和记账之间，其他执行者可能插入。

企业仓库的注释说这个窗口在并发下"可能多放一次"。仓库的 `budget.go:12` 说：我们这里是单进程串行，窗口不存在。

这是一个很好的"抄之前先问为什么"的例子：

> 同一句注释，在它的系统里是事实，在我们的系统里不成立。
> 错的是"照抄"这个动作，不是那句话。

将来图并行执行时，要么接受这个窗口，要么改成"事前预留 + 事后结算"。

## 25.4 时间：守卫只做加法

`Usage.Elapsed` 是实际执行耗掉的时间，不含人等待。

它由执行节点的那一层报进来（`Runner`），不是守卫自己看时钟。

为什么？

因为"时间"有三个不同的东西：

1. 事实：这一轮从哪一刻开始（`State.CreatedAt`）；
2. 用量：这一步实际执行了多久（执行者知道）；
3. 墙钟：现在减起点（含人等待）。

守卫如果自己记开始时刻，就会：

- 发明一个事实（"这一轮从我被创建时开始"）；
- 每次重启归零，崩溃三次拿到三倍预算；
- 把人思考的时间算进"这一轮跑了多久"。

所以：

> **守卫能做对的是加法，不是时间。**
> "这一步执行了多久"是**量**出来的，和 token 是同一类东西——执行者报，守卫累加。

墙钟（含人等待）是另一个判据，由 `context` 的 deadline 表达。

## 25.5 时间维曾经是个"孤儿"

`budget.go` 的记录：`Elapsed` 曾经不在 `Limits` 里，而是藏在 `guarded.maxWall`。

后果：

- `Dims()` 不列它；
- `Bounded()` 不看它；
- `remaining()` 算不出它；
- `DescribeLimits()` 不渲染它。

**一个字段该在哪里，不是排版问题——它决定了哪套规矩会管到它。**

把它收进 `Limits` 之后，五维走同一条判据，所有循环自动生效。

还有一个"想开豁免"的教训：

有人论证"零时间的运行没有意义，所以 `Elapsed` 的零值可以读作不限"。

但这个理由同样适用于 `Steps: 0`——而我们从没给步数开豁免。

> 如果一条豁免的理由同样适用于别的维度，那它就不是这一维的特性，
> 而是"我想给这一维开个后门"。

所以没有豁免：五维一条规矩。

## 25.6 成本维目前没有生产者

`CostMilli` 在 `Usage` / `Limits` 里，但全仓只有 `cmd/l3` 和 `cmd/l4` 把它设为 `NoLimit`——没有任何地方真的报过成本。

这意味着：

- 预算的"成本"维度目前是声明存在、实际未接线；
- 你只能通过 token 间接估算钱；
- 要接上，需要一个价格表 + 每次调用后计算 `CostMilli`。

这是第 29 章差异审计要列的一类：

> **有字段、有类型、有校验，但没有生产者。**

它不是 bug，但它是一个"看起来有、实际没有"的能力——比没有更危险，因为你会以为它在工作。

## 25.7 预算要告诉模型

`Decision.Notice` 是给模型看的一句话：

```text
prompt_tokens 预算不够了（上限 100000，已用 99000，这一步要 5000）——
请基于已有的信息收尾，不要开始新的步骤
```

为什么每次都提醒，而不是只在开始时说一次？

因为 L2-9 的实测：`research` 的 `MaxSteps` 是 6，模型完全不知道，于是一直搜到第 6 步被强制终止，之前搜到的素材全部丢弃。

> **一个不告诉模型的预算，等于没有预算。**

`SubAgent` 还有 `BudgetNotice(steps)`，把剩余步数写进 Prompt。

## 25.8 失败也花钱

`Agent` 只在成功拿到响应时记账：

```go
resp, genErr = a.Client.Generate(...)
if genErr != nil {
    return genErr
}
a.emit(llmCallEvent(...))
a.guard.ReportUse(...)
```

失败的调用没有 `Usage`，因为 `llm.Client` 的契约是"成功返回 Response，失败返回 error"。

而 L2-9 的实测是：

> 同一个角色连续失败 10 次、烧掉 55321 tokens，最后仍然失败——钱一分没少花。

`Runner` 对此的处置是"失败也记步数和执行时间"（`runner.go:518`），但 token 仍然记不到。

这是一个已知缺口：

- 预算账本少记失败尝试的钱；
- `Stats.Steps` 数的是 `KindStart`（循环轮次），不是实际模型调用次数；
- 启用重试后，一轮里可能发生 3 次调用，但 `Steps` 只加 1。

补它需要让 `llm.Client` 在错误里也带用量，或者由适配器估算。触发条件是"出现按失败率对账的真实需求"。

## 25.9 预算在哪里接线

- `Agent`：每次成功调用后 `ReportUse` prompt/completion；
- `Runner`：每跳 `Allow(Steps:1)`，执行后 `ReportUse(Steps:1, Elapsed)`；
- `cmd/l4`：默认 `NewUnlimited()`，`L4_HUGE_TOKENS` 时设 prompt 上限 100k，用来演示触顶；
- `cmd/l3`：步数 + 执行时间。

注意：`cmd/l4` 的默认评测守卫是不限额——所以评测不会因为预算而误判，预算演示是单独的开关。

## 25.11 拓展：跑一次零值

用 `budget.Limits{}` 跑一次，观察 fail-closed；再把五维都设成 `NoLimit`，对比两次的结果。

你会看到，“不限”是一个显式选择，而不是没配置时的默认值。这个区别在真实系统里很要命：一个忘记配预算的服务，应该跑不动，而不是无限花钱。
