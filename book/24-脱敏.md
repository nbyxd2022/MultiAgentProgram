# 第 24 章 脱敏：白名单、反射测试与 `Detail` 的教训

事件变成协议了，可事件里既有元信息也有正文。发给远端之前必须脱敏，这一章看白名单和一条真实的泄露教训。

## 24.1 一个会泄露的工具回执

假设你有一个远程观测出口（前端看板、上游 tracing 服务）。

事件里有一个字段：

```go
Detail string // "这一步发生了什么"
```

它看起来像元信息："已就绪、跳过：research"。于是 `Redact` 把它保留了。

但实际运行里，`Detail` 还会装：

- `KindToolResult` 的工具返回原文（检索片段、文件内容、API 返回）；
- 工具失败的原始错误（可能带路径、域名、用户输入）。

于是"脱敏"后发出去的观测，带着完整的工具回执。

**一个"元信息"的标签，被贴在了一个装着正文的字段上。而那条标签是注释，不是类型——所以没有任何东西会因为它不成立而报错。**

这是 R59 的修复：`Detail` 现在不复制到脱敏副本里。

## 24.2 两个出口，要求相反

企业仓库的 `emitTrace` 做三件事：

1. 本地 tasklog ← 完整（offline replay 的依据）；
2. 上游/前端 ← 脱敏（避免 prompt/response 泄露）；
3. 顺序：先本地、后上游。

关键认知：两个出口的差别不只是"开/关"，还有脱敏。

- 本地要完整，因为排查需要原文；
- 远端要脱敏，因为可能是第三方或前端；
- 顺序先本地，因为本地录播丢了就没了，上游可以重试/补发。

`observ` 用两个组合子表达这件事：

```go
tracer := observ.LocalAndRemote(file, remote)
```

它等价于：

```go
Fanout{file, WithRedact(remote)}
```

`WithRedact` 是一个包装器：它只把 `Redact()` 后的副本转交给 inner。

为什么做成包装，而不是"调用方记得调 Redact"？

因为"每个调用点都要记得做同一件事"就是 R23 那条教训。把它做成类型上的事实，就不可能忘。

## 24.3 白名单，而不是黑名单

`Redact`（`event.go:426`）返回一个新结构，只复制要保留的字段。

这是白名单，不是"清空已知的正文"。

理由是失败的方向：

| 方案 | 漏一个字段的后果 |
|---|---|
| 黑名单 | 正文被发出去 → **泄露**（后果重，且不会报错） |
| 白名单 | 少一个元信息 → 后果轻，**而且容易发现** |

显式列出每个字段还有一个副作用：加新字段的人会被迫决定它属于哪一边，而不是"默认它不敏感"。

## 24.4 当前保留与丢弃的字段

保留（元信息）：

- `RunID` / `Span` / `Layer` / `Phase` / `Kind` / `Err`；
- `ToolName`（可聚合、可切片）；
- `Model`；
- `PromptTokens` / `CompletionTokens` / `Duration`；
- `Reconcile`。

丢弃（正文）：

- `SystemPrompt` / `UserPrompt` / `Response`；
- `ToolArgs`；
- `Detail`（R59 修复）。

为什么 `Detail` 本地要留？

因为"这一步到底发生了什么"有诊断价值，而这个价值只对本地录播成立。

取舍是：

> **本地留全文，外部清空**——而不是"两边都留一句话"。
> 后者会让本地录播在排查时不够用。

## 24.5 反射看门人：一条差点永远为真的测试

`TestRedactPreservesEveryMetaField` 用反射检查每个字段：

- 名字命中正文词表（`Prompt` / `Response` / `Args` / `Payload` / `Body` / `Content` / `Detail`）的字符串字段 → 必须被清空；
- 其余字段 → 必须逐字保留。

这条测试的来历值得单独讲。

### 第一版守错了方向

第一版写的是"正文类字段必须被清空"。

然后作者注入了一个 `ToolArgs` 字段去验证它会拦——它没拦。

因为白名单里根本没有 `ToolArgs`，所以 `rr.ToolArgs` 必然是空串；那个断言永远不成立。

> **它是一条看起来在守、实际恒真的测试。**

这比没有测试更危险：它绿着，你以为有人在看门。

修法是把方向反过来：守元信息那一侧。因为白名单漏掉正文是安全的（正文不可能泄露），漏掉元信息才是会静默丢失的那一侧。

### 命名约定 + 类型约束

正文词表按字段名匹配，但只对字符串字段生效。

为什么加类型约束？

第一版没加，`PromptTokens` 撞上了 `Prompt`，被判成正文——而它是数值，是元信息，必须保留。

纯命名约定会把它误判，而误判的方向是"要求清掉一个该保留的字段"。

### 防空跑

测试最后检查 `checkedMeta > 0`。

为什么？如果字段列表或命名约定变了，一个元信息都没检查到，这条测试只是安静地绿着，什么都没验证。

这是"防空跑"原则的又一次应用。

## 24.6 反射测试的局限

命名约定能强迫你面对"这个字段敏不敏感"，但它不能替你判断。

两个反例：

- `UserID` 不命中正文词表，测试会要求保留它。但 UserID 是 PII，可能不该发给远端。
- `Err` 是元信息，测试要求保留。但错误原文可能包含用户输入、路径、域名。

所以：

> 反射测试守的是"**字段有没有被分类**"，不是"**分类对不对**"。

真正的脱敏策略仍然需要人做判断，必要时加显式的分类字段（如 `Sensitivity`）或单独的 sanitizer。

## 24.7 一个尚未接线的能力

`LocalAndRemote` / `WithRedact` 已经实现，也有测试，但我在当前仓库里没有找到生产调用点。

这意味着：

- 脱敏能力是存在的；
- 但目前所有 Demo 的观测出口都没有真正连到"远端"；
- 所以 `Detail` 泄露是潜在问题，不是当前正在发生的泄露。

这也是一个值得记住的工程事实：

> **一个没有被装配的能力，等于不存在。**
> 但它和"没有实现"不同：实现 + 测试意味着接线时不用重新设计。

## 24.8 脱敏不是安全边界

需要明确它不解决什么：

- 不加密：脱敏后的事件仍是明文落盘/传输；
- 不做访问控制：谁能读本地完整录播，是另一个问题；
- 不防元信息泄露：RunID、ToolName、Err 都可能含敏感信息；
- 不防侧信道：token 数、耗时、事件顺序也可能泄露信息。

脱敏只是"把正文从远端出口拿掉"，不是"这套观测系统是安全的"。

## 24.9 练习

先自己做，再看 `answers/24-参考答案.md`。

### 练习 1：加一个 `UserID` 字段

给 `Event` 加：

```go
UserID string `json:"user_id,omitempty"`
```

- 它命中正文词表吗？
- 反射测试会要求保留还是清空？
- 如果它是 PII，你会怎么改？

### 练习 2：把 `Detail` 加回白名单

在 `Redact` 里加 `Detail: e.Detail`。

跑测试。回答：

- 哪条测试会失败？
- 失败信息有没有指出"Detail 是正文"？
- 为什么这条测试能抓住它，而代码评审不一定能？

### 练习 3：本地完整、远端脱敏

用两个 `Recorder`：

```go
local := observ.NewRecorder()
remote := observ.NewRecorder()
tracer := observ.LocalAndRemote(local, remote)
```

发一条带 `UserPrompt`、`ToolArgs`、`Detail`、`ToolName` 的事件。

回答：

- local 里哪些字段有值？
- remote 里哪些字段为空？
- 顺序上 local 先收到还是 remote 先收到？

### 练习 4：把秘密放进 `Err`

构造一条 `Err` 含用户输入的 event，例如：

```go
Err: `读取文件 C:\users\alice\secret.txt 失败`
```

回答：

- `Redact` 会保留它吗？
- 这算不算泄露？
- 你会怎么处理（改 Err 的生成方式、单独 sanitizer、还是把 Err 也当正文）？

### 练习 5：设计一个敏感性分类

给 `Event` 加一个字段：

```go
Sensitivity Sensitivity // "public" / "internal" / "secret"
```

回答：

- 它和 `Redact` 的白名单是什么关系？
- 谁来设置它？
- 如果设置错了，会有什么后果？

## 24.10 小结与自检
合上书，回答：

- 为什么本地和远端的要求相反？
- 为什么 `Redact` 用白名单？
- `Detail` 为什么被改成正文？
- 反射测试守的是哪一侧？为什么方向要反过来？
- 为什么正文词表只对字符串字段生效？
- `LocalAndRemote` 的顺序为什么本地在前？
- 脱敏不解决哪些问题？

能答出五题以上，再进下一章。

## 24.10 拓展：把 Detail 加回白名单

把 `Detail` 加回 `Redact` 白名单，跑测试。看哪条测试会红，以及失败信息有没有指出“`Detail` 是正文”。

这条测试就是你以后加字段时的看门人。它不替你判断敏感不敏感，但它会逼你面对这个问题。
