# 第 15 章 失效传播：StaleReasons 为什么必须传递

产物进了黑板，但不等于一直有效：上游变了，下游还是旧版。这一章看失效怎么沿依赖链传播。

## 15.1 一个所有检查都通过的错配

```text
topic@1 → research@1 → outline@1 → design@1 → render@1
```

现在用户改了主题，`topic` 变成 `topic@2`。

系统重跑 `research`，得到 `research@2`。然后直接渲染：

- `outline@1` 还在；
- `design@1` 还在；
- 页数一致；
- 类型正确；
- 没有任何一层报错。

但 `outline@1` 是基于 `research@1` 写的，而 `research@1` 是基于旧主题写的。整条链的内容都已经过时了。

**只查"直接依据是不是最新版"，发现不了这个问题：**

- `outline@1` 的依据是 `research@1`，而 `research` 的当前最新版还是 `research@1`（只有重跑 research 才会变成 @2）；
- 所以 `outline` 的直接检查通过；
- 但 `research@1` 的依据 `topic@1` 已经不是最新了。

这就是间接过期。要发现它，必须沿着 `BasedOn` 一路往上走。

## 15.2 一份产物"有效"的三个条件

`internal/graph/state.go:410` 的 `CanSkip`：

```text
可以跳过 ⟺ 存在 ∧ 完整 ∧ 新鲜
```

- 存在：黑板上有这个 key；
- 完整：`Shortfall` 为空；
- 新鲜：`StaleReasons` 为空。

这三条在 L2 是"能不能交付"，在 L3 是"能不能跳过"。同一个判据跨阶段复用，说明它抓到的是本质。

三条各自报各自的错，因为修法完全不同：

| 状态 | 含义 | 该做什么 |
|---|---|---|
| 不存在 | 没做过 | 去跑那个节点 |
| 不完整 | 做了，但有缺口 | 重跑/补齐那个节点 |
| 不新鲜 | 做过了，但依据过期 | **先重做上游**，再回来 |

把"不新鲜"报成"不存在"，模型会把整件事重做一遍；把"不完整"报成"不存在"，也会白烧一轮。

## 15.3 为什么必须传递

`StaleReasons` 的遍历是传递的（`artifact.go:505`）：

```go
for _, b := range cur.BasedOn {
    now, ok := latest(b.Key)
    if !ok {
        continue
    }
    walk(now) // 先深入上游
    if now.Version != b.Version {
        mine = append(mine, ...)
    }
}
out = append(out, mine...)
```

它做两件事：

1. 递归走 upstream：先把上游的过期问题收集起来；
2. 比较直接依据：如果上游当前版本与我记录的版本不同，报告自己过期。

如果只查一层：

- `outline@1` 的依据是 `research@1`，最新还是 `research@1` → 通过；
- `design@1` 的依据是 `outline@1`，最新还是 `outline@1` → 通过；
- `render@1` 也一样 → 通过；
- 但整条链都建立在过期的 `topic` 上。

**传递遍历是唯一能发现"上游的上游变了"的方法。**

## 15.4 后序遍历：返回的是修复顺序

注意代码顺序：先 `walk(now)`，再检查自己。

这产生后序遍历：上游的原因先进入列表，自己的原因后进入。

为什么？因为这份列表是给模型当待办用的：

- 如果先报 `render` 过期，模型去重做 `render`，但它的依据 `design` 还是旧的，做完还是会被拒；
- 先报 `design`，再报 `render`，模型照着从上往下做，一次就能通过。

举例：

```text
render@1 的依据：outline@1、design@1
design@1 的依据：outline@1
outline 已经出了 @2
```

`StaleReasons(render)` 的输出顺序大致是：

```text
1. design：design@1 依据的 outline@1 已经更新到 outline@2
2. render：render@1 依据的 outline@1 已经更新到 outline@2
```

先 `design`，后 `render`。这是一条可执行的修复顺序。

`internal/schema/basis_test.go` 里有一条专门的测试 `TestStaleReasonsOrdersByFixOrder`，守的就是这个顺序。

## 15.5 去重与环

遍历使用一个 `visited map[Basis]bool`：

- 去重：同一个上游被多个下游共享时，只走一次；
- 兜住环：即使 `BasedOn` 出现循环，也不会无限递归。

环在正常数据里不该出现（图构建期会检查），但 `StaleReasons` 是一个纯函数，不能假设调用方一定传了合法的图。一个纯函数不该因为输入坏而栈溢出。

另外，遍历顺序完全由 `BasedOn` 切片决定（DFS），不用 map 遍历。所以同一个输入两次调用，输出顺序完全一致——这是可 diff、可回归的前提。

## 15.6 上游缺失：不在两处报同一个问题

如果 `BasedOn` 指向的 key 在黑板里根本不存在：

```go
now, ok := latest(b.Key)
if !ok {
    continue
}
```

`StaleReasons` 选择跳过，不报告。

为什么？因为"上游不存在"是存在性问题，由 `missingNeeds` 负责报告。同一个问题在两处报，反馈会啰嗦，模型反而更难判断。

这是一个通用原则：一个事实只在一个地方报告。 否则两处的措辞迟早不一致。

## 15.7 "过期"不等于"错误"

`StaleReasons` 返回非空，只说明"这份产物基于旧版上游"，不说明：

- 它的内容是错的；
- 它一定不能交付；
- 它需要被删除。

它只说明：**如果你要继续用它的结论，你需要知道它的依据已经变了。**

系统可以选择：

- 重跑上游，再重跑它；
- 接受它（如果变更不影响它的结论）；
- 让人确认。

`CanSkip` 选择的是最保守的一种：不跳过，重新做。这是安全的默认，但可能带来不必要的重算。

## 15.8 代价：过度依赖会带来重算风暴

如果每个产物都把自己的 `BasedOn` 写成"所有上游"，那么任何一个上游变化，整条链都会过期。

这不一定错，但代价高：

- 重算多；
- token 多；
- 延迟高。

所以 `Needs()` 要尽量精确：只声明真正影响你产出的依赖。

- `design` 依赖 `outline`（页数和标题）；
- `render` 依赖 `outline` 和 `design`；
- `outline` 依赖 `research`。

不要为了"保险"把 `topic` 加到每个产物的 `BasedOn` 里——它已经通过 `research` 传递下来了。血缘链本来就是传递的。

## 15.9 对照增量构建与数据管道

这套机制和增量构建系统（Make、Bazel）、数据管道（DAG 调度）是同一个思想：

- 每个产物记录输入版本；
- 输入变了，产物标脏；
- 按拓扑序重算；
- 只重算受影响的部分。

区别在于：这里的"脏"不是删除缓存，而是保留旧产物 + 报告原因。因为旧产物可能还有审计价值，也可能在人工确认后继续使用。

Eino/LangGraph 的 State 通常不提供这套血缘；你可以自己加，但要在 State 里维护版本与依赖。黑板把这个能力放进了存储层。

## 15.10 练习

先自己做，再看 `answers/15-参考答案.md`。

### 练习 1：间接过期

构造：

```text
topic@1 → research@1 → outline@1
```

然后写入 `topic@2`（不重跑 research）。

对 `outline@1` 调用 `StaleReasons`。回答：

- 它直接依据的 `research@1` 还是最新，为什么 `outline` 仍然被判过期？
- 返回了几条原因？
- 原因里提到的是 `topic` 还是 `research`？

### 练习 2：直接过期

构造：

```text
research@1 → outline@1 → design@1
```

重跑 `outline` 得到 `outline@2`。

对 `design@1` 调用 `StaleReasons`。回答：

- 它返回几条原因？
- 如果 `design` 还有下游 `render`，`render` 的结果会包含哪些原因？
- 修复顺序是什么？

### 练习 3：环

构造两个产物 A、B，让 A 的 `BasedOn` 包含 B，B 的 `BasedOn` 包含 A，版本相同。

调用 `StaleReasons(A, latest)`。回答：

- 它会无限递归吗？
- 返回什么？
- 这个结果说明"环"被发现了吗？

提示：`visited` 只保证终止，不保证报错。环应该在构建期被发现，而不是在这里。

### 练习 4：上游缺失

构造一个产物，`BasedOn` 指向 `ghost@1`（黑板里没有）。

调用 `StaleReasons`。回答：

- 它报错吗？
- 谁应该报告这个"上游不存在"？
- 如果两处都报，会有什么问题？

### 练习 5：过度依赖

把 `topic@1` 加到 `outline`、`design`、`render` 的 `BasedOn` 里。

然后写入 `topic@2`，对 `render` 调用 `StaleReasons`。回答：

- 返回几条原因？
- 有多少是重复的？
- 这样做比"只依赖直接上游"更好还是更差？

## 15.11 拓展：给 BasedOn 加一个不存在的 key

给某个产物的 `BasedOn` 故意加一个黑板里没有的 key，再调用 `StaleReasons`。它不会报错，而是跳过。

想清楚：这个“上游不存在”应该由谁报告？如果 `StaleReasons` 也报，会不会和 `missingNeeds` 报同一件事？这两个问题想明白，你就不容易把“过期”和“缺失”混成一种错误。
