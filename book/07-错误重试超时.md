# 第 7 章 错误回灌、重试、超时与最大步数

循环的边界清楚了，但还有几件脏活：调用失败了怎么办、等太久怎么办、失败了钱算谁的。

## 7.1 一个会让你赔钱的场景

你接上一个限流很严的模型服务。第一次调用返回 `429 Too Many Requests`。你的程序直接失败。

你听说要重试，于是把整个 `Run` 包进了重试：

```go
retry.Do(ctx, policy, func(ctx context.Context) error {
    final, err = a.Run(ctx, input)
    return err
})
```

第二次运行时，第一次已经执行过的 `save_note` 又被执行了一遍；如果它是扣款、发邮件、写数据库，后果就不只是多一个文件。

更糟的是：三次重试都在几毫秒内完成，因为限流根本没恢复；你得到的是三倍的账单和同一个错误。

这个场景里有三个独立的问题：

1. 什么错值得重试（分类）；
2. 重试放在哪一层（位置）；
3. 失败的成本有没有记账（核算）。

这一章逐个拆。

## 7.2 错误分类：只回答"重试有没有用"

打开 `internal/errclass/errclass.go`。这个包只有两个类别：

```go
const (
    Retryable Class = "retryable"
    Permanent Class = "permanent"
)
```

为什么只有两个？因为当前只有一个消费者：重试。类的数量由消费者决定，不由"错误的丰富程度"决定。企业仓库可能有 25 个错误类型，因为它要同时喂给告警、日志、Controller 分流；我们只有一个问题要回答：再来一次会不会好？

### 分类优先级

`errclass.Of` 的顺序不能换：

1. 错误自己声明：实现了 `RetryableError` 接口的，听它的；
2. **`context.Canceled`**：人取消的，不重试——他要的就是停；
3. **`context.DeadlineExceeded`**：整体超时，不重试——只会更慢；
4. **`net.Error` 且 `Timeout()`**：网络抖动，可重试；
5. **兜底 `Permanent`**：不认识的错，不重试。

第 5 条是有方向的选择：不认识的错误重试，可能是在放大一个真问题。"参数非法"重试三次，只是用三倍的钱得到同一个错误。

### 一个真实的缺口：HTTP 429/5xx 没有被分类

看 `internal/llm/openai.go:177`：

```go
if resp.StatusCode != http.StatusOK {
    return nil, fmt.Errorf("模型服务返回 HTTP %d: %s", resp.StatusCode, truncate(...))
}
```

这是一条普通错误。`errclass` 看不到状态码，只能走兜底 `Permanent`。也就是说：

> **仓库有重试机制，但最常见的可重试错误（429 / 500 / 502 / 503）目前不会被重试。**

这不是理论问题，是接真实模型时第一个会遇到的。修法不是改 `errclass` 去解析字符串，而是让错误自己声明：

```go
type HTTPStatusError struct {
    StatusCode int
    Body       string
}

func (e *HTTPStatusError) Error() string { ... }

func (e *HTTPStatusError) Retryable() bool {
    return e.StatusCode == 429 || e.StatusCode >= 500
}
```

然后在 `openai.go` 返回这个类型。`errclass` 一行都不用改——这正是 `RetryableError` 接口存在的理由。

> 这也是第 5 章那条"结构优先于字符串"的延续：**不要用 `strings.Contains(err.Error(), "429")`**，那会把日志里恰好出现的 "429" 也当成限流。

## 7.3 重试机制：机制与策略分开

`internal/retry/retry.go` 把"怎么重试"和"什么错值得重试"分开了：

- `Do` 是机制：循环、等待、返回尝试次数；
- `Policy.CanRetry` 是策略：默认用 `errclass.CanRetry`；
- `Policy.Backoff` 是策略：默认不退避；
- `Policy.Attempts` 是总尝试次数（含第一次）。

几个细节值得记住：

### 细节一：`Attempts <= 0` 归一成 1

"试 0 次"不是一个有意义的配置。参考实现里这个 bug 会让 `fn` 从未被调用，却返回一个"失败"；更糟的是 `Error()` 里对 nil 解引用会 panic。

仓库的修法是显式归一：至少试一次。这是一个很小的决定，但它避免了一整类"配置写错 → 程序崩溃"的问题。

### 细节二：退避必须能被 ctx 打断

```go
select {
case <-ctx.Done():
    return i, ctx.Err()
case <-time.After(d):
}
```

如果用户已经取消，重试循环还在 `time.Sleep`，那就是"抗命"。等待也必须可取消。

### 细节三：不可重试时返回原始错误

```go
if !canRetry(err) {
    return i, err
}
```

不是所有失败都要包成 `*retry.Error`。第一次就知道不该重试的错误，返回原始错误，调用方的 `errors.Is` 少绕一层。

### 细节四：退避不是可选项，是限流场景的必需项

`retry.Fixed` 只是"每次都等同一个时长"，它够用，但不是最好的。指数退避 + 抖动更好；不过在没有并发规模之前，先不要引入自己解释不清的复杂度。

## 7.4 超时：最隐蔽的参数

`internal/llm/openai.go` 里有四个环境变量：

```text
OPENAI_BASE_URL
OPENAI_API_KEY
OPENAI_MODEL
OPENAI_TIMEOUT
```

超时默认 60 秒，非法值回退默认值。它还通过 `TimeoutReporter` 暴露出来，`boot.Describe` 会把它打印在 Demo 表头：

```text
openai:gpt-4o-mini · 单次超时 1m0s
```

为什么要专门打印？因为超时是"看不见却能让每一步都失败"的参数。L2-9 接推理型模型时就撞上过：单次调用超过 60 秒，屏幕上只有 `context deadline exceeded`，人根本不知道等多久算超时、这个值是谁定的、能不能调。

### 两种超时要分开

| 超时类型 | 来源 | 该不该重试 |
|---|---|---|
| 单次 HTTP 请求超时 | `http.Client.Timeout` / `net.Error` | 可以；换个时机可能成功 |
| 整体任务 deadline | `ctx` 的 `DeadlineExceeded` | 不该；重试只会更慢 |

`errclass` 把后者归为 `Permanent`，把前者（`net.Error` 且 `Timeout()`）归为 `Retryable`。这个区分很细，但很实用。

## 7.5 失败也要花钱：账本里的一个洞

`internal/agent/agent.go` 的注释里有一句很重要的实测：

> 同一个角色连续失败 10 次、烧掉 55321 tokens，最后仍然失败——那次的钱一分没少花。

但当前代码只在成功拿到响应之后记账：

```go
resp, genErr = a.Client.Generate(...)
if genErr != nil {
    return genErr
}
a.emit(llmCallEvent(...))
a.guard.ReportUse(...)
```

失败的调用没有 `Usage`，因为 `llm.Client` 的契约是"成功返回 `Response`，失败返回 `error`"，错误里不带 token。于是：

- 预算账本少记了失败尝试的钱；
- `Stats.Steps` 数的是 `KindStart`，也就是"循环进了几轮"，不是"真正发起了几次模型调用"；
- 一旦启用重试，一轮里可能发生 3 次调用，但 `Steps` 只加 1。

这不是让你现在去改 `llm.Client` 的契约。它是一条需要知道的边界：

> **预算守卫能拦住"下一次"，但拦不住"已经花掉但没记上的钱"。**

真要补，需要让 `Client` 在错误里也带用量，或者由适配器在失败时上报一个估算值。那是另一个设计决定，触发条件是"出现按失败率对账的真实需求"。

## 7.6 工具错误：回灌，但不要自动重试

工具执行失败时，Agent 会把错误包成 JSON 回灌（`internal/agent/agent.go:318`）：

```json
{
  "ok": false,
  "tool": "render_slide_html",
  "error": "bullets 必须是字符串数组",
  "hint": "请检查参数是否符合工具定义；如无法修复，请改用其他工具或调整方案。"
}
```

这解决了"模型能不能自愈"的问题，但还有两个没解决：

### 问题一：所有错误都被当成"模型可修复"

`formatToolError` 对任何错误都加同一句 hint。但下面这些错误，模型修不了：

- API Key 错；
- 工具未注册；
- 磁盘满；
- 权限不足。

把它们回灌，模型会反复重试一个它根本修不了的问题。正确做法是给错误加一个类别：

```json
{"ok": false, "error_kind": "runtime", "retryable": false, "error": "..."}
```

模型看到 `runtime`，就知道该停止并报告，而不是继续猜参数。

### 问题二：不要自动重试有副作用的工具

`retry.Do` 只应该包住模型调用，不应该包住工具。工具可能写文件、发请求、扣款；自动重试会重放副作用。

如果某个工具确实值得重试（比如只读的 HTTP GET），重试应该放在工具内部：它最清楚自己是否幂等、该退避多久、哪些状态码可重试。

## 7.7 机制存在，但没有接上

我在当前仓库里没有找到任何 `cmd` 给 `Agent` 配置 `Retry`。`Agent.Options.Retry` 的零值是"试一次"，所以所有 Demo 实际上都没有启用重试。

这是一个典型的工程缺口：

> **一个没有被装配的机制，等于不存在。**

它不是 bug（默认不重试是安全的，因为重试会花钱），但它意味着：你在读 `retry` 包时以为系统会重试，实际不会。第 29 章做差异审计时，这类"有代码、没接线"的项要单独列出来。

## 7.8 练习

先自己做，再看 `answers/07-参考答案.md`。

### 练习 1：让 429 变成可重试

给 `internal/llm/openai.go` 加一个 `HTTPStatusError` 类型：

- 429 和 5xx 实现 `Retryable() bool { return true }`；
- 其他 4xx 返回 false；
- 写一个单测，验证 `errclass.CanRetry` 对 429 返回 true、对 400 返回 false。

这个练习的价值：你会亲手把"错误分类"从字符串判断变成类型契约。

### 练习 2：在第 3 章的 Agent 里接上重试

把 `book/code/ch03/agent.go` 的 `Generate` 包进 `retry.Do`：

```go
_, err := retry.Do(ctx, policy, func(ctx context.Context) error {
    resp, err = a.Client.Generate(ctx, req)
    return err
})
```

写一个"第一次失败、第二次成功"的 Client，观察：

- 模型调用了几次？
- 工具调用了几次？
- 如果失败发生在工具执行之后，工具会重跑吗？

### 练习 3：在退避期间取消

把退避设成 2 秒，启动一次运行，1 秒后取消 `ctx`。观察：

- 重试循环是等满 2 秒，还是立刻返回？
- 返回的错误是上一次的错误，还是 `context.Canceled`？

### 练习 4：数清"步数"和"调用次数"

启用重试后，比较：

- `Stats.Steps`（数 `KindStart`）；
- 实际 `Generate` 被调用的次数（在你的 Client 里加计数器）。

如果一次成功、两次重试，两个数差多少？

然后回答：`Steps` 到底该表示"循环轮次"还是"模型调用次数"？这两种口径分别适合什么场景？

### 练习 5：区分工具错误

把 `formatToolError` 改成带 `error_kind` 的版本：

- 参数解析失败、缺字段、枚举非法 → `"model_fixable"`；
- 未知工具、权限、磁盘 → `"runtime"`。

然后用一个会返回 runtime 错误的假工具，观察模型是否会停止重试。
