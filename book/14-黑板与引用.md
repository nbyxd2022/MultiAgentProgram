# 第 14 章 黑板：为什么传引用，不传全文

适配器只把 `{ref, summary}` 交给子 Agent。为什么不能把全文传下去？这一章看黑板。

## 14.1 一次 45KB 的交接

假设你生成 3 页 PPT，每页 HTML 约 15KB。

如果每一跳都把全文放进上下文：

```text
research 全文 → outline
outline 全文 → designer
designer 全文 → renderer
每页 HTML → Supervisor 汇总
```

粗算一下：

- 3 页 × 15KB ≈ 45KB；
- 经过 4 个角色，每次都要重发历史；
- 45KB 大约几万 token，乘以轮数，成本和延迟都会爆。

更糟的是：每经过一个模型，就多一次被改写的机会。

Supervisor 可能"帮"你总结一下，Designer 可能"顺手"调整一段文案，Renderer 可能重新组织 HTML。最后没有人知道哪份是原始产物。

黑板的做法是：

```text
产物只存一份 → 上下文里只传 {ref, summary} → 要全文的人自己取
```

## 14.2 黑板是什么，不是什么

`internal/state/blackboard.go` 的 `Blackboard` 是一个追加式共享产物存储。

它不是什么：

- 不是消息队列：没有订阅、没有推送；
- 不是缓存：不淘汰、不自动过期；
- 不是 State：State 是"一次运行里的变量"，黑板是"跨角色共享的产物"。

它只做一件事：**按 key 存产物，每次 Put 追加一个版本。**

为什么单独一个包，而不是塞进 `schema`？

- `schema` 是"数据长什么样"（协议）；
- `state` 是"数据存在哪里"（存储）。

协议应该稳定，存储会演进（L3 要加 checkpoint）。分开之后，换存储不必动协议。

## 14.3 五个操作

| 操作 | 语义 |
|---|---|
| `Put` | 追加一版，版本由黑板分配 |
| `Get` | 按 `key` 取最新，或按 `key@version` 取指定版 |
| `Keys` | 列出所有 key（字典序） |
| `Versions` | 某个 key 有几版 |
| `Snapshot` / `LoadSnapshot` | 导出/还原全量快照，带完整性校验 |

一个容易忽略的点：`Get("outline")` 返回最新版，`Get("outline@2")` 返回指定版。

给流程用的引用必须带版本；不带版本的写法只适合人看看板。为什么？第 14.5 节会讲。

## 14.4 为什么只传引用

### 代价一：token 与上下文窗口

上下文里只放 `{ref, summary}`，通常几十个 token；全文可能是几万 token。

多 Agent 系统里，一个产物会被多个下游消费、被多轮重发。把全文放进上下文，成本是乘法，不是加法。

### 代价二：漂移

如果每个下游都复述一遍全文，每复述一次都可能改写一点。最后：

- 日志里是 A；
- Designer 看到的是 B；
- Renderer 拿到的是 C；
- 没有人能解释差异从哪来。

引用是不可变的：`outline@2` 永远指向那一版，不会因为后面出了 `@3` 而变。

### 代价三：污染

共享可变状态最危险的地方是：**一个人改了，所有人都受影响，而且不会报错。**

黑板用"进出深拷贝"隔离这种污染（第 14.6 节）。

### 代价四：选择性访问

大多数角色不需要上游全文：

- `outline` 需要 research 的发现；
- `designer` 需要 outline 的页标题和要点；
- `renderer` 需要 design 和 outline；
- 但没有一个角色需要所有上游的所有字段。

把"取全文"变成显式动作（`SubAgentInput.Fetch()`），才能看出谁真的需要它。

## 14.5 Handoff 只有两个字段

`internal/schema/artifact.go:274`：

```go
type Handoff struct {
    Ref     string
    Summary string
}
```

`Ref` 是 `outline@2`，`Summary` 是代码派生的一句话（"outline：3 页 [趋势 / 成本 / 出海]"）。

没有 `Payload`，没有 `Files`，没有 `Title`。

这不是"为了省字段"，而是**物理上不允许 Supervisor 搬运数据**。第 13 章说过：`subAgentTool` 的参数只有一个 `hint`，连"塞上游数据"的地方都没有。

> **不要用 Prompt 说"不要搬数据"，要让代码里没有地方可搬。**

## 14.6 深拷贝：共享可变状态的隔离

`Artifact.Payload` 是 `json.RawMessage`，本质是 `[]byte`——引用类型。

如果不拷贝：

```go
a, _ := board.Get("outline@1")
a.Payload[0] = 'X' // 黑板里的那份也变了
```

下一个 Agent 取到的是被改过的数据，而且没有任何报错。

所以：

- `Put` 存深拷贝（`blackboard.go:90`）；
- `Get` 返回深拷贝（`blackboard.go:127`）；
- `Snapshot` 导出深拷贝（`blackboard.go:203`）；
- `LoadSnapshot` 还原深拷贝（`blackboard.go:268`）。

这个坑在仓库里已经踩过三次（`Report.Merged`、`render_slide`、`MergeLocal`），而黑板最危险——它是**唯一一处真正的跨 Agent 共享可变状态**。

## 14.7 版本：为什么不能被覆盖

`Put` 拒绝调用方指定版本（`blackboard.go:75`），版本由黑板在锁内分配（`:83`）。

版本序列必须从 1 开始、逐 1 递增。`LoadSnapshot` 会检查这一点（`:256`）：

```text
第 1 个位置的版本号必须是 1
第 2 个位置的版本号必须是 2
...
```

为什么这么严？因为 `Get("outline@2")` 是靠 `versions[version-1]` 取值的。

如果快照里有洞（`[1,3]`）或乱序（`[2,1]`），`Get` 会静默取到另一份产物。

> 读不出来的产物会让任务失败；被错取的产物会让任务**成功地做错**。

版本还有一个作用：引用不可变。

第 1 轮里，`design` 基于 `outline@1` 做出来。第 2 轮 `outline` 重跑成 `@2`。`design` 里的 `BasedOn` 仍然写 `outline@1`——这让我们能发现"它过期了"，而不是"它悄悄用了最新版"。

## 14.8 并发：锁与"零副作用校验"

`Blackboard` 用 `sync.RWMutex`：

- `Put` 在写锁内分配版本、校验、追加；
- `Get` / `Keys` / `Versions` 用读锁；
- 校验失败时不写入，版本号不推进。

最后一条很重要：一次非法提交如果先推进版本号再校验失败，后续所有引用都会错位。校验必须零副作用。

> 诚实说明：仓库的并发安全目前只做了锁和单测，没有跑 `-race`（本机没有 C 编译器）。这是一个已知的验证缺口，第 29 章会再次提到。

## 14.9 引用不解决什么

不要把黑板当成万能：

- 不校验 payload 的业务语义：`Research` 有没有 findings、`Outline` 页数对不对，要各自的 `Validate` 做；
- 不负责调度：它只存，不决定谁先跑；那是 SubAgent/Graph 的事；
- 不负责持久化：`Snapshot` 只是导出内存状态，写盘是 checkpoint（第 22 章）；
- 没有 GC：旧版本会一直累积。长任务、多轮返工下，内存会涨。这是一个真实限制，不是"以后再说"的借口；
- 没有细粒度权限：`schema.Reader` 只能读，但不能限制"只能读某几个 key"。

## 14.10 对照 Eino / LangGraph

Eino 的 State、LangGraph 的 State 都是"把数据放在一个共享结构里往下传"。

它们很方便，但也很容易变成"把全文塞进 State"：

- 上下文变长；
- 每个节点都能改 State；
- 版本与血缘要自己补。

黑板是另一种取舍：

- 数据外置，上下文只放引用；
- 追加而非覆盖；
- 版本与血缘是存储层的一等公民；
- 代价是要自己管理读取、GC、持久化。

没有哪种一定更好。**如果任务是短链路、数据小，State 更简单；如果是长链路、大产物、需要审计，黑板更合适。**

## 14.11 练习

先自己做，再看 `answers/14-参考答案.md`。

### 练习 1：算一笔 token 账

假设：

- 一页 HTML 15KB；
- 3 页；
- 经过 4 个角色，每个角色平均重发 2 次历史。

比较两种方式的上下文体量：

1. 全文交接；
2. `{ref, summary}` 交接（ref 约 20 字节，summary 约 80 字节）。

不要求精确 token 数，用数量级说明差异。

### 练习 2：验证深拷贝

```go
b := state.NewBlackboard()
a, _ := schema.NewArtifact("note", "code", schema.Topic{Text: "hello"})
a, _ = b.Put(a)

got, _ := b.Get("note@1")
got.Payload[0] = 'X'

again, _ := b.Get("note@1")
fmt.Println(string(again.Payload))
```

预期输出是什么？如果把 `Get` 的深拷贝去掉，输出会变成什么？

### 练习 3：版本漂移

1. 写入 `outline@1`，拿到 `ref1 = outline@1`；
2. 再写入 `outline@2`；
3. 用 `ref1` 去 `Get`。

回答：

- 取到的是哪一版？
- 如果用 `Get("outline")`，取到的是哪一版？
- 为什么流程引用必须用带版本的写法？

### 练习 4：设计一个 GC 策略

黑板没有 GC，旧版本一直累积。假设你要加一个：

- 哪些版本可以删？
- 还在被 `BasedOn` 引用的版本能删吗？
- 未完成的中断、日志、回放还持有 ref 的版本能删吗？
- 删了之后，`Get("outline@2")` 应该返回什么？

写出三条规则，并说明为什么"简单按时间删"很危险。

### 练习 5：只读接口够不够

`schema.Reader` 只提供 `Get`，但没有"只能读某几个 key"的能力。

如果有一个不可信的第三方 Agent，你会怎么设计权限？

- 每个 Agent 一个允许的 key 列表？
- 还是给它一个独立的视图？
- 这会给黑板增加什么复杂度？

## 14.12 拓展：把 Summary 也去掉

把 `Handoff` 里的 `Summary` 也去掉，只留 `Ref`。问自己：模型还能判断“要不要取全文”吗？

如果不能，Summary 应该写什么、不该写什么？这个练习会逼你区分“摘要”和“正文”：摘要不是缩小的正文，而是帮助下一跳做决定的元信息。
