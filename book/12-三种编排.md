# 第 12 章 三种编排：流水线、模型路由、图

两个角色的闭环走完了。角色变成四个之后，“下一步派给谁”就成了一个架构问题。

## 12.1 一个四角色的任务

任务：根据主题生成 3 页 PPT。

四个角色：

```text
research  → 查资料
outline   → 写大纲
designer  → 定版式
renderer  → 渲染 HTML
```

依赖关系是明确的：

```text
research
   ↓
outline
   ↓
design
   ↓
render
```

现在问题来了：谁来决定"下一步派给谁"？

有三种答案，对应三种编排方式。

## 12.2 方式一：固定流水线

代码直接按顺序调用：

```go
research.Run(ctx, topic)
outline.Run(ctx)
designer.Run(ctx)
renderer.Run(ctx)
```

优点：

- 确定性最强：每次都是同样的顺序；
- 最容易调试：出错就知道在哪一步；
- 不需要额外的路由 token。

缺点：

- 不灵活：如果某个角色失败，要不要重试？如果 research 发现资料不够，要不要多查一轮？如果 design 想跳过某页？这些分支都得写死在代码里；
- 角色之间强耦合：加一个角色，就要改调用链。

适合：流程稳定、步骤固定的生产任务。比如"每天凌晨把 A 数据转成 B 报表"。

## 12.3 方式二：模型路由（Supervisor）

把每个角色包装成一个工具，交给一个 Supervisor Agent。Supervisor 本身就是一个 ReAct Agent：

```text
Supervisor（模型）
   ├── 工具：research
   ├── 工具：outline
   ├── 工具：design
   └── 工具：render
```

它通过调用工具来"派活"，子 Agent 完成后，工具结果自动回灌给 Supervisor，它再决定下一步。

`internal/agents/supervisor.go` 就是这么做的：

- 每个 `SubAgent` 被 `NewSubAgentTool` 包装成工具（`supervisor.go:189-196`）；
- Supervisor 用 `agent.New` 构造，复用第 3 章的循环（`:200`）；
- 它的 Prompt 明确写："你不创作内容，不搬运数据，只路由"（`:464`）。

### 为什么是"工具"而不是"transfer_to_agent"？

因为工具调用已经提供了现成的机制：

- 派活 = 调用工具；
- 子 Agent 完成 = 工具返回结果；
- 回到 Supervisor = 工具结果自动进入上下文。

不需要再造一套"转交"协议。这也让"路由的合法值集合"就是"工具名集合"，而工具名必须过 `schema.Kind.Valid()`，天然挡住"路由到不存在的角色"。

### Supervisor 不做的事

三条硬规矩（`supervisor.go:24-29`）：

1. 不创作内容；
2. 不搬运数据：上下文里只有 `{ref, summary}`，正文不经过它；
3. Prompt 里不出现业务字段名（title / bullets / pages）。

第三条最容易被违反。一旦 Supervisor 开始读 `title`、`bullets`，它就会开始"逐字段提取重组"——那正是企业仓库 A2/A3 的坑：让概率模型做无损数据搬运，必然丢字段。

### 完成判断必须由代码做

Supervisor 的模型说"我做完了"，不算数。代码会检查三件事（`supervisor.go:256-259`）：

```text
Missing     —— 该有的产物有没有？
Incomplete  —— 有产物，但有没有缺口（Shortfall）？
Stale       —— 有产物，但依据链是不是过期了？
```

三者都为空，`Result.Complete()` 才返回 true（`:176`）。

外层还有 `supervisorRounds=3`（`:71`）和 `MaxSteps=12`（`:108`）两个硬兜底。

### 构造期校验

`NewSupervisor` 在启动时就检查（`:87-105`）：

- 每个角色的 `Kind` 合法；
- 两个角色不能产出同一种 Kind（否则黑板 key 撞车）；
- `Required` 里的每一种产物都必须有角色负责（否则任务永远无法完成）。

配置错了当场就炸，而不是跑到一半才发现某个角色永远调不通。

### 缺点

- 路由是模型决定的，可能选错；
- 多一轮路由就多一次 token；
- 模型的"完成"判断不可靠，必须靠代码兜底；
- 没有持久化：进程挂了，这一轮就没了；
- 没有 HITL：不能在中间停下来问人。

## 12.4 方式三：图编排

图的做法是：每个节点声明自己依赖什么，边由依赖推导出来。

```go
type Node interface {
    Name() string
    Kind() schema.Kind
    Needs() []schema.Kind
    Run(ctx context.Context, in NodeInput) (*Outcome, error)
}
```

- `research.Needs() = []`
- `outline.Needs() = [research]`
- `design.Needs() = [outline]`
- `render.Needs() = [outline, design]`

`BuildGraph` 会：

- 检查依赖是否有生产者；
- 检查 Kind 是否唯一；
- 检查有没有环；
- 推导出边；
- 算出拓扑序。

`Runner` 按拓扑序执行，不需要模型来决定"下一步"。顺序是代码保证的，不是"检查"出来的。

L3 还在此之上加了：

- HITL 中断（产出后停下来问人）；
- checkpoint（进程挂了能恢复）；
- 节点级重试上限；
- panic 转 error。

这些是第 17 到 22 章的内容。

优点：

- 确定性最强；
- 可恢复、可审计；
- 加一个节点只需要声明 `Needs()`，不用改调度器。

缺点：

- 不灵活：分支、循环、动态角色都要显式建模；
- 需要提前想清楚依赖；
- 对"开放式任务"（不知道该做什么）不友好。

## 12.5 三种方式放在一起

| 维度 | 固定流水线 | 模型路由（Supervisor） | 图 |
|---|---|---|---|
| 谁决定下一步 | 代码写死 | 模型 | 代码（依赖推导） |
| 确定性 | 最高 | 低 | 高 |
| 灵活性 | 最低 | 最高 | 中 |
| 路由成本 | 0 | 每轮一次模型调用 | 0 |
| 可恢复 | 自己实现 | 难（状态在模型上下文里） | checkpoint |
| HITL | 自己实现 | 难 | 原生支持 |
| 典型失败 | 分支写死、加角色要改代码 | 选错角色、提前宣布完成 | 依赖建模错、图太复杂 |
| 适合 | 稳定流程 | 开放式任务 | 可审计、长流程 |

注意：这张表不是"图最好"。图在开放式任务上会很难受，因为你需要提前知道有哪些节点；而 Supervisor 在需要恢复和审计时很难受，因为它的决策过程在模型上下文里。

## 12.6 为什么 L2 还不够

L2 已经能跑通四角色，但它的"顺序保证"是软的：

- Supervisor 可能先调 `outline`，但 `SubAgentTool` 会检查依赖，发现 `research` 没做，拒绝；
- 拒绝之后，模型可能再试一次，也可能换一个角色；
- 如果模型一直选错，`MaxSteps` 会兜底，但这一轮就浪费了。

而且 L2 没有：

- 进程级恢复：Supervisor 的对话历史在内存里，挂了就没了；
- 人工确认：不能在"大纲生成后"停下来问人；
- 节点级幂等：同一个角色被重复调用，副作用可能重放。

所以 L3 把"顺序"从模型手里拿走，交给图。这不是"图更高级"，而是当任务需要恢复和审计时，模型路由不再合适。

## 12.7 怎么选

一个简单的决策顺序：

1. 流程固定、步骤少 → 固定流水线。不要为了"看起来像 Agent"引入模型路由。
2. 任务开放、步骤不确定 → Supervisor。让模型决定下一步，但完成判断必须由代码做。
3. 需要恢复、审计、人工确认 → 图。顺序由依赖保证，状态可持久化。
4. 混合 → 图里放一个 Supervisor 节点。外层流程确定，内层探索开放。

一个常见的错误是：用 Supervisor 做固定流程。结果是多花路由 token，还引入了一个"模型可能选错"的失败点。

反过来，用图做开放式任务也很痛苦：你必须提前枚举所有节点，而开放式任务恰恰不知道下一步是什么。

## 12.8 对照 Eino / LangGraph

你用过这两个框架，可以把概念对上：

| 本仓库 | Eino | LangGraph |
|---|---|---|
| Supervisor | ADK Supervisor / 中心化编排 | Supervisor 节点 + 条件边 |
| SubAgent-as-tool | Agent 包装成 Tool | 子图 / 工具节点 |
| Graph + Needs | Graph / Chain | StateGraph + edges |
| Checkpoint | 需要自己接 | Checkpointer |
| HITL | 需要自己接 | interrupt |

框架给你的是"编排原语"；选哪种编排、完成判断怎么做、失败怎么恢复，仍然是你的设计。

## 12.9 练习

先自己做，再看 `answers/12-参考答案.md`。

### 练习 1：画三种编排

用 12.1 的四角色任务，画出：

1. 固定流水线的调用顺序；
2. Supervisor 的工具调用图；
3. 图的节点与边。

然后标注：每种方式下，"如果 research 失败"会发生什么？

### 练习 2：跑一次 L2，观察路由

```powershell
go run ./cmd/l2
```

观察 Supervisor 调用了哪些工具、顺序是什么、每次调用的返回是什么。

然后跑故障注入：

```powershell
$env:L2_SKIP_ORDER="1"; go run ./cmd/l2
```

观察：当模型跳过前置角色时，依赖检查会不会拒绝？拒绝信息长什么样？

### 练习 3：让一个必需产物无人负责

在 `cmd/l2` 里把 `Required` 加一个不存在的 Kind，例如 `schema.Kind("video")`。观察 `NewSupervisor` 是否在启动时报错。

这个练习验证"构造期校验"的价值：错误在装配时暴露，而不是跑到一半。

### 练习 4：模拟 Supervisor 提前停止

写一个 Supervisor Mock：第一轮只调用 `research`，然后返回"完成了"。

观察：

- `Result.Complete()` 返回什么？
- `Missing` 里有哪些 Kind？
- 下一轮的 `reminderPrompt` 会说什么？

### 练习 5：选一种编排

场景：一个客服工单系统，需要：

- 先分类工单；
- 根据分类决定查知识库、查订单、还是转人工；
- 所有操作要能审计；
- 人工可以随时接管。

你会选哪种编排？为什么？需要补哪些能力？

## 12.10 拓展：在每条箭头上标“谁负责重试”

给第 12.1 节的四角色任务画三张图：流水线、Supervisor、图。然后给每条箭头标一句“如果这一步失败，谁负责重试、重试几次”。

画完你会发现，选编排方式其实是在选“失败责任放在哪里”。这比比较“谁更先进”有用。
