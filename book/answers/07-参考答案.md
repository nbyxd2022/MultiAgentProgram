# 第 7 章 参考答案

## 练习 1：让 429 变成可重试

在 `internal/llm` 里加一个错误类型：

```go
type HTTPStatusError struct {
    StatusCode int
    Body       string
}

func (e *HTTPStatusError) Error() string {
    return fmt.Sprintf("模型服务返回 HTTP %d: %s", e.StatusCode, truncate(e.Body, 300))
}

// 429 限流、5xx 下游故障：再试一次可能成功。
// 其余 4xx 是请求本身有问题，重试只会得到同一个错误。
func (e *HTTPStatusError) Retryable() bool {
    return e.StatusCode == http.StatusTooManyRequests || e.StatusCode >= 500
}
```

然后在 `openai.go` 里：

```go
if resp.StatusCode != http.StatusOK {
    return nil, &HTTPStatusError{StatusCode: resp.StatusCode, Body: string(respBody)}
}
```

测试：

```go
func TestHTTPStatusErrorRetryable(t *testing.T) {
    if !errclass.CanRetry(&HTTPStatusError{StatusCode: 429}) {
        t.Fatal("429 应该可重试")
    }
    if !errclass.CanRetry(&HTTPStatusError{StatusCode: 503}) {
        t.Fatal("503 应该可重试")
    }
    if errclass.CanRetry(&HTTPStatusError{StatusCode: 400}) {
        t.Fatal("400 不应该重试")
    }
}
```

注意：`errclass` 一行都不用改。它通过 `RetryableError` 接口识别，而不是靠字符串匹配。

## 练习 2：在第 3 章的 Agent 里接上重试

最小改法（在 `book/code/ch03/agent.go` 里）：

```go
import (
    "context"
    "fmt"
    "strings"
    "time"

    "multiagent/internal/retry"
)

var resp *LLMResponse
_, err := retry.Do(ctx, retry.Policy{
    Attempts: 3,
    Backoff:  retry.Fixed(500 * time.Millisecond),
}, func(ctx context.Context) error {
    var genErr error
    resp, genErr = a.Client.Generate(ctx, LLMRequest{
        Messages: history,
        Tools:    a.Tools.Definitions(),
    })
    return genErr
})
if err != nil {
    return "", err
}
```

写一个测试 Client：

```go
type FailOnceClient struct {
    calls int
    inner Client
}

func (c *FailOnceClient) Generate(ctx context.Context, req LLMRequest) (*LLMResponse, error) {
    c.calls++
    if c.calls == 1 {
        return nil, &HTTPStatusError{StatusCode: 429}
    }
    return c.inner.Generate(ctx, req)
}
```

预期：

- `calls == 2`（第一次失败，第二次成功）；
- 工具执行 1 次（失败发生在模型调用层，没走到工具）；
- 如果失败发生在工具执行之后的那次模型调用，工具也不会重跑，因为工具不在重试范围内。

## 练习 3：在退避期间取消

```go
ctx, cancel := context.WithTimeout(context.Background(), time.Second)
defer cancel()

_, err := retry.Do(ctx, retry.Policy{
    Attempts: 3,
    Backoff:  retry.Fixed(2 * time.Second),
}, func(ctx context.Context) error {
    return &HTTPStatusError{StatusCode: 429}
})
```

预期：

- 第一次失败后进入退避；
- 1 秒后 `ctx.Done()` 触发，`retry.Do` 立刻返回 `context.DeadlineExceeded`；
- 不会等满 2 秒，也不会尝试第二次。

这验证了退避必须可取消。没有这个 `select`，用户取消之后程序还会继续等、继续试。

## 练习 4：数清"步数"和"调用次数"

假设一次循环里发生了 3 次 `Generate`（1 次成功 + 2 次重试）：

- `KindStart` 只在循环开始时发 1 次 → `Stats.Steps = 1`；
- 实际 `Generate` 调用 3 次 → 你的计数器是 3。

差 2 次。

这不是简单的"数字不对"，而是口径问题：

- 如果 `Steps` 表示"循环轮次"，那它适合描述"任务走了几步"；
- 如果 `Steps` 表示"模型调用次数"，那它适合成本核算与重试分析。

仓库的注释说它数的是"真的发起了几次模型调用"，但实现数的是 `KindStart`。在没有启用重试时两者一致；一旦启用重试，就会分叉。

修法二选一：

1. 把每次尝试都发一条 `KindStart`（改事件语义）；
2. 把字段改名为 `Rounds`，并另加一个 `ModelCalls`。

关键是：**先定义口径，再写指标。** 不要让一个字段同时承担两个含义。

## 练习 5：区分工具错误

可以给 `formatToolError` 加一个类别参数：

```go
func formatToolError(name string, err error) string {
    kind := "model_fixable"
    if errors.Is(err, ErrRuntimeTool) {
        kind = "runtime"
    }
    payload := map[string]any{
        "ok":         false,
        "tool":       name,
        "error_kind": kind,
        "retryable":  kind == "model_fixable",
        "error":      err.Error(),
    }
    ...
}
```

哪些算 runtime：

- 未知工具（装配错误，模型无法修复）；
- 权限不足；
- 磁盘满；
- 配置缺失（API Key 等）。

哪些算 model_fixable：

- JSON 解析失败；
- 缺必填字段；
- 类型错；
- 枚举值非法。

观察：模型看到 `retryable:false` 时，更可能停下来报告，而不是继续重复同一个调用。

## checkpoint 的简要答案

- **两个类别**：因为只有一个消费者——重试。类的数量由消费者决定。
- **默认不重试**：不认识的错误重试可能放大真问题，三倍的钱得到同一个错误。
- **不能重跑整个 Run**：工具可能有副作用，重跑会重放写文件/扣款/发请求。
- **两种超时**：单次 HTTP 超时可重试；整体 deadline 超时重试只会更慢。
- **失败的钱**：`Client` 的错误不带 usage，失败尝试无法记账；需要改契约或在适配器估算。
- **工具错误**：参数类错误回灌；配置/权限/未知工具等 runtime 错误应快速失败。
- **没接线等于不存在**：`Retry` 机制存在，但当前 cmd 没有配置，默认只试一次。
