# 第 6 章 参考答案

## 练习 1：给第 3 章的 Agent 加统计

在 `Agent` 上加一个字段：

```go
type Stats struct {
    Steps            int
    ToolCalls        int
    PromptTokens     int
    CompletionTokens int
}
```

在 `Run` 里累加：

```go
var stats Stats

resp, err := a.Client.Generate(...)
if err != nil {
    return "", err
}
stats.Steps++ // 只有真正成功的调用才计数
stats.PromptTokens += resp.PromptTokens
stats.CompletionTokens += resp.CompletionTokens

for _, tc := range resp.ToolCalls {
    stats.ToolCalls++
    ...
}
```

然后打印 `stats`。

和仓库的 `Stats()`（`internal/agent/agent.go:189`）对比：

- 仓库从事件流里数 `KindStart` 和 `KindToolCall`，token 从 `Recorder.Usage()` 取；
- 你的版本另存了一份 `stats`。

两者现在看起来一样，但一旦出现"事件流有、stats 没有"或反过来，就会不一致。仓库的选择是**只保留一份明细（事件流），其他统计都从它派生**。这就是"总量只能有一份明细"。

## 练习 2：制造一次"提前终止"

Mock 可以这样写：

```go
type EarlyStopClient struct {
    turn int
}

func (c *EarlyStopClient) Generate(_ context.Context, _ LLMRequest) (*LLMResponse, error) {
    c.turn++
    if c.turn == 1 {
        return &LLMResponse{
            ToolCalls: []ToolCall{{
                ID:   "call_1",
                Type: "function",
                Function: FunctionCall{Name: "get_weather", Arguments: `{"city":"北京"}`},
            }},
            FinishReason: "tool_calls",
        }, nil
    }
    return &LLMResponse{Content: "完成了。", FinishReason: "stop"}, nil
}
```

注意：第二次调用时，工具结果**还没有**被回灌，但 Mock 已经返回了最终回复。Agent 会认为任务完成，直接返回"完成了。"

预期观察：

- 循环正常结束；
- `out/note-*.md` 不存在；
- 用户看到"完成了"，但实际什么都没做。

这就是"模型说完成"和"任务完成"的差别。

## 练习 3：给循环加一个完成判定

最小版本：

```go
final, err := a.Run(ctx, input)
if err != nil {
    return err
}

if _, statErr := os.Stat("out/note-天气笔记.md"); statErr != nil {
    return fmt.Errorf("任务未完成：笔记文件不存在")
}
return final
```

更通用的版本是让工具返回结构化产物，再由完成判定检查"产物种类是否齐全"。这正是第 10 章（产物信封）和第 19 章（节点产出检查）要做的事。

做完这个练习，你应该能回答：

> 为什么不能让模型自己说"完成了"就结束？

因为模型只对"下一步"负责，不对"系统状态"负责。系统状态必须由代码检查。

## 练习 4：重试位置实验

### 实验 A：只重试 `Generate`

```go
_, err := retry.Do(ctx, policy, func(ctx context.Context) error {
    resp, err = client.Generate(ctx, req)
    return err
})
```

如果 `Generate` 失败一次，然后成功：

- 模型调用 2 次；
- 工具执行 0 次（因为第一次就失败了，还没走到工具）；
- 如果失败发生在工具执行之后（下一次模型调用），工具不会重跑。

### 实验 B：重试整个 `Run`

```go
var final string
err := retry.Do(ctx, policy, func(ctx context.Context) error {
    var err error
    final, err = a.Run(ctx, input)
    return err
})
```

如果第一次 `Run` 已经执行了 `save_note`，然后在后续模型调用失败，重试会：

- 从一条新的 `history` 开始（`Run` 内部重新初始化）；
- 再次执行 `save_note`；
- 如果你用的工具带计数器/写日志，你会看到副作用被执行了两次。

结论：

> **重试的位置，由"哪一层没有副作用"决定。** 模型调用没有副作用，可以重试；工具调用可能有副作用，不能因为一次模型失败就重跑。

## checkpoint 的简要答案

- **为什么一次调用不够**：模型看不到工具执行结果；结果必须在下一轮调用中才可见。
- **显式 ReAct vs 原生工具调用**：前者解析文本协议，后者用结构化 `tool_calls`；仓库用后者。
- **四条不变量**：一轮一次模型调用；所有请求的工具都执行；所有结果都回灌；终止只有自然/硬两种。
- **重试位置**：只包住 `Generate`，避免重放工具副作用。
- **自然终止 vs 最大步数**：前者是模型判断，后者是成本/死循环兜底；都不保证任务完成。
- **显式推理的局限**：文本可能是事后编的，不能当作正确性证据；它适合调试和审计，不适合作为唯一判据。
