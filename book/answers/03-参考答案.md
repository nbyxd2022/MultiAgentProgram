# 第 3 章 参考答案

先做完练习再看。下面的代码是形状，不是唯一写法。

## 练习 1：加第三个工具

`word_count` 的定义可以这样写：

```go
type WordCount struct{}

func (WordCount) Definition() ToolDefinition {
	return ToolDefinition{
		Type: "function",
		Function: FunctionDefinition{
			Name:        "word_count",
			Description: "统计一段文本的字符数与词数。用户要求统计长度时使用。",
			Parameters: map[string]any{
				"type": "object",
				"properties": map[string]any{
					"text": map[string]any{
						"type":        "string",
						"description": "要统计的文本",
					},
				},
				"required": []string{"text"},
			},
		},
	}
}

func (WordCount) Execute(_ context.Context, args string) (string, error) {
	var in struct {
		Text string `json:"text"`
	}
	if err := json.Unmarshal([]byte(args), &in); err != nil {
		return "", fmt.Errorf("参数不是合法 JSON: %w", err)
	}
	chars := len([]rune(in.Text))
	words := len(strings.Fields(in.Text))
	raw, _ := json.Marshal(map[string]any{
		"ok":         true,
		"characters": chars,
		"words":      words,
	})
	return string(raw), nil
}
```

在 `main.go` 里注册：

```go
registry.Register(WordCount{})
```

然后把用户输入改成：

```text
统计"多智能体系统"这几个字的长度，并保存成笔记
```

观察结果：

- 模型可能先调 `word_count`，再调 `save_note`；
- 也可能先保存笔记，再统计；
- 也可能不调用 `word_count`，直接自己数（模型确实会数错，这也是一个观察点）。

顺序不重要。重要的是：**它有没有在需要的时候调用工具，以及工具描述是否足够清楚。**

## 练习 2：把最大步数改成 1

把：

```go
MaxSteps: 6,
```

改成：

```go
MaxSteps: 1,
```

再跑 Mock。预期结果：

1. 第 1 步执行 `get_weather`（北京、上海）；
2. 循环结束，因为 `step` 已经到达 1；
3. 返回错误：`达到最大步数 1，仍未收敛`。

这个练习想让你看到：**工具执行了，不等于任务完成了。** 任务完成的条件是"模型在拿到工具结果后，给出了不再请求工具的最终回复"，而不是"某一次工具调用成功了"。

## 练习 3：让工具报错

把输入改成"查火星的天气"，并接真实模型运行。

可能的结果（因模型而异）：

1. 模型看到 `{"ok":false,"error":"没有 火星 的天气数据"}`，改为查询"北京"或直接说明无法查询；
2. 模型重复用同样的参数调用，直到达到最大步数；
3. 模型编造一个天气结果（这是最坏的情况，说明系统提示词不够强）。

如果出现第 2 种，最大步数会拦住它；如果出现第 3 种，说明仅靠错误回灌不够，还需要在提示词或校验层加约束。

这里先不做修复。第 7 章会把错误分类，并讨论"哪些错误该回灌、哪些该直接失败"。

## 练习 4：打印完整历史

在 `Agent.Run` 的返回之前加一段：

```go
for i, m := range history {
    fmt.Printf("[%02d] role=%-9s content=%.80q tool_call_id=%s\n",
        i, m.Role, m.Content, m.ToolCallID)
}
```

一次 Mock 运行大约会看到：

- 1 条 system；
- 1 条 user；
- 每一步 1 条 assistant（可能带 tool_calls）；
- 每个 tool_call 1 条 tool 消息。

所以历史长度大致是：

```text
2 + 步数 + 工具调用总数
```

如果任务有 10 步、每步 2 个工具调用，历史会到 30 条以上。每条消息都要在下一轮重新发给模型——这就是"上下文会越来越长、token 会越来越贵"的来源。

第 4 章会讨论：哪些消息可以裁剪，哪些绝对不能删。

## 本章 checkpoint 的简要答案

- **为什么放回 assistant 的 tool_calls？** 它是协议的一部分，告诉模型"你刚才请求过哪些调用"，否则 tool 消息没有对应的请求。
- **自然终止 vs 最大步数？** 前者是模型说"我完成了"，后者是运行时说"不许再跑了"。前者管正确性，后者管成本与死循环。
- **工具错误为什么变数据？** 让模型有机会修正参数；但配置错误、未知工具这类错误不该回灌，否则模型会无效重试。
- **`length` 和"不会写 JSON"？** `length` 是输出被截断，JSON 不完整；后者是模型能力或提示词问题。修复方向不同。
- **仓库多了哪四样？** 重试（只重试单次模型调用）、事件、预算上报、从事件派生统计。它们都是工程能力，不是循环本身。
