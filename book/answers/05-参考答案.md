# 第 5 章 参考答案

## 练习 1：改一个描述，观察调用率

差的版本：

```text
查询天气。
```

好的版本：

```text
查询某个城市当前的实时天气。
何时使用：用户询问今天/此刻的温度、降雨、风力时。
不要用于：历史天气、气候趋势、天气预报。
参数 city 必须是城市名，例如"北京"、"上海"；不要传省份或经纬度。
```

可能的观察：

- "北京今天热不热"：好描述更容易触发 `get_weather`；差描述也可能触发，但参数可能变成 `{"query":"北京今天热不热"}` 或 `{"location":"北京"}`。
- "北京历史上七月平均气温"：好描述更可能**不调用**实时天气工具，因为描述里明确说了"不要用于历史天气"；差描述更容易误调用。

结论不是"好描述一定 100% 正确"，而是：**描述缩小了模型的猜测空间，错误率会下降。** 具体下降多少，要用一组固定问题去测（第 26 章）。

## 练习 2：给参数加 enum

仓库的 `tool.Parameter` 目前没有 `Enum`。最小改动：

```go
// internal/tool/tool.go
type Parameter struct {
    Name        string
    Type        ParameterType
    Description string
    Required    bool
    Enum        []string      // 新增：允许的取值
    Items       *Parameter
    Properties  []Parameter
}
```

然后在生成 JSON Schema 时写入：

```go
// internal/llm/openai.go 的 paramSchema
if len(p.Enum) > 0 {
    s["enum"] = p.Enum
}
```

工具的 `Definition`：

```go
{
    Name:        "style",
    Type:        tool.TypeString,
    Description: "页面风格；只能是简洁、详细、学术之一",
    Required:    true,
    Enum:        []string{"简洁", "详细", "学术"},
}
```

观察重点：

- 只在描述里写"三个值"时，模型偶尔会传"简约"、"专业"这类近义词；
- 加了 `enum` 之后，服务端会在生成阶段约束取值，违规率通常明显下降。

结论：**能用 schema 表达的约束，不要只写在描述里。** 描述是提示，schema 是约束。

## 练习 3：让描述里的约束真正生效

在 `RenderSlideHTML.Render` 里补上长度检查：

```go
if n := len([]rune(title)); n > schema.MaxTitleRunes {
    return "", 0, fmt.Errorf(
        "title 超长：最多 %d 字，收到 %d 字。请缩短标题后重试",
        schema.MaxTitleRunes, n)
}
for i, b := range slide.Bullets {
    if n := len([]rune(b)); n > schema.MaxBulletRunes {
        return "", 0, fmt.Errorf(
            "bullets[%d] 超长：最多 %d 字，收到 %d 字。请缩短这一条后重试",
            i, schema.MaxBulletRunes, n)
    }
}
```

注意错误信息的写法：

- 说清**限制是多少**；
- 说清**实际是多少**；
- 说清**该怎么改**。

接真实模型跑一次超长标题，观察它是否会在下一轮改短。如果它反复失败，说明错误信息还不够可操作，或者模型没有把错误当回事——这两种情况要分开排查。

## 练习 4：把错误信息改成人话

改之前：

```text
json: cannot unmarshal string into Go struct field Slide.bullets of type []string
```

改之后：

```text
bullets 必须是字符串数组，例如 ["要点1","要点2"]；收到的是字符串。
```

一个可操作的模板：

```text
<字段> 必须是 <类型/形状>，例如 <示例>；收到的是 <实际类型或值>。请修正后重试。
```

不要把所有错误都改写成"参数错误"——那样模型只知道错了，不知道错在哪。

## checkpoint 的简要答案

- **工具的三层**：契约（Definition，给模型看）、内核（真正干活）、适配器（解析 JSON 并调用内核）。分开是为了让内核可测试、可被代码直接调用，协议问题不污染业务。
- **描述回答四个问题**：做什么、何时用、何时不用、参数约束。
- **约束一个来源**：描述是承诺，`Execute` 是兑现；两处各写一份，迟早不一致。
- **该不该回灌**：模型可修复的参数错误该回灌；配置/权限/磁盘/未知工具这类运行时错误不该回灌，应快速失败。
- **注册表顺序**：保证两次运行的提示词一致，便于调试与复现；同名覆盖会掩盖装配错误。
- **自动生成 schema 的代价**：省机械工作，但描述通常很弱，模型缺少"何时用/不用"的判断依据。
