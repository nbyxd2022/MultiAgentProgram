# 第 2 章 参考答案

先做完练习再看。答案不是标准答案，观察结果可能因模型和服务商不同而略有差异。

## 练习 1：读懂一次响应

需要找到的三个东西：

- `finish_reason`：如果模型决定调用工具，通常是 `tool_calls`。
- `tool_calls[0].id`：一个字符串，例如 `call_abc123`。它是这次调用的配对 ID。
- `tool_calls[0].function.arguments`：**是字符串**，例如 `"{\"city\":\"北京\"}"`，不是 JSON 对象。

如果你用的是不返回工具调用的模型，这三个字段可能不存在，`finish_reason` 会是 `stop`。这本身就是一次有价值的观察：**模型是否支持 function calling，是选型时要确认的事实。**

## 练习 2：描述决定行为

把描述从"查询某个城市当前的天气"改成"获取数据"，常见的结果有三种：

1. 模型不再调用工具，直接回答"我无法获取实时天气"——因为它不知道这个工具能做什么。
2. 模型调用工具，但参数名或参数值变得随意，例如传 `{"query":"天气"}` 而不是 `{"city":"北京"}`。
3. 模型仍然按原来的方式调用——说明这个模型对工具名和参数名更敏感，描述的影响较小。

三种结果都指向同一个结论：**工具描述是模型唯一的接口文档。** 描述含糊，模型就只能猜；猜错不是模型的问题，是契约没写清楚。

一个可操作的写法是：

```text
查询某个城市当前的天气。
何时使用：用户询问实时天气、温度、降雨、风力时。
不要用于：历史天气、气候趋势、天气预报。
参数 city 必须是城市名，例如"北京"、"上海"。
```

## 练习 3：补上第二次请求

关键代码形状如下（省略了错误处理）：

```go
// 第一次响应：resp
// 假设 resp.ToolCalls[0] 是 get_weather

toolResult := `{"temperature":22,"condition":"晴"}`

messages = append(messages,
    message.AssistantToolCall(resp.Content, resp.ToolCalls...),
    message.ToolResult(resp.ToolCalls[0].ID, resp.ToolCalls[0].Name, toolResult),
)

second, err := client.Generate(ctx, llm.Request{
    System:   "你是一个简洁的助手。",
    Messages: messages,
    // 这次可以不给工具，先把"模型如何使用工具结果"看清楚
})
```

预期结果：

- `content` 不再是 `null`，而是一句基于 22 度和晴天的回答；
- `finish_reason` 通常是 `stop`；
- 如果你把 `toolResult` 改成 `{"temperature":-40}`，回答会跟着变——这说明模型确实读到了工具结果，而不是在猜。

一个容易忽略的点：`message.AssistantToolCall(resp.Content, resp.ToolCalls...)` 里的 `resp.Content` 可能是空字符串。这没问题；协议要求保留 `tool_calls`，内容可以为空。

## 练习 4：删掉 `tool_call_id`

如果 `tool` 消息缺少 `tool_call_id`，OpenAI 通常会返回 400，错误信息类似：

```text
Missing required parameter: 'messages[3].tool_call_id'.
```

不同兼容服务的措辞可能不同，但一定是 **4xx**，而不是模型层面的回答。

这个错误的价值：它把"协议配对错误"和"模型不会回答"区分开了。以后看到 400，先检查消息结构；看到 200 但内容不对，再去怀疑提示词或模型。

## 本章最重要的一句话

> 模型从来没有执行过任何工具。它只是返回了一个"我想调用这个工具"的请求；执行、回灌、循环和终止，全都是运行时的工作。
