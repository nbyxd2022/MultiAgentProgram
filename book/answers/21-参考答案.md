# 第 21 章 参考答案

## 练习 1：模拟"已回答未消费"

预期：

- checkpoint 里 `Pending.Decision` 非 nil；
- 下一次 `go run ./cmd/l3` **不会再问一遍**；
- 它会重放 confirm，继续往下走；
- confirm 无副作用，所以重复重放没有影响。

这就是"已回答未消费"状态的价值：崩溃不会让答案凭空消失。

## 练习 2：重复 confirm

第一次 confirm 消费掉决定后，`Pending` 被清掉并落盘。

再执行 `-answer=confirm`：

```text
run l3-demo 没有在等待回答的中断（上一次的回答可能已经被消费掉了）
```

这算不算幂等？

- 从**状态**看，重复 confirm 不会改变结果；
- 从**API**看，第二次调用返回错误。

所以更准确的说法是：**confirm 的语义是幂等的，但 `Resume` 这个接口不是"可重复调用"的。**

## 练习 3：revise 的副作用

如果被 revise 的节点写一个带时间戳的文件，执行到一半被杀，再恢复：

- 节点会被**再执行一遍**；
- 副作用会执行两次；
- 仓库没有通用幂等键。

能否接受，取决于副作用：

- 写同名文件覆盖：近似幂等；
- 发邮件、扣款：不能接受，需要业务侧幂等键（例如订单号、请求 ID）；
- 纯计算：天然幂等。

这就是"at-least-once + 幂等"的现实取舍。

## 练习 4：换主题，不换 run id

```powershell
go run ./cmd/l3 -topic="另一个主题"
```

预期：拒绝。

错误信息会说"同一个 run id 配不同的输入等于两件事共用一个身份（血缘会串）"。

正确做法：

- 在图上新增一版 `topic`（`topic@2`），让 `StaleReasons` 把下游标脏；
- 或者换一个 run id，把新主题当成一次新任务。

直接换调用参数是**最差**的做法：黑板上会混着两次输入产生的产物，而血缘判据认为它们是同一条链。

## 练习 5：v1 快照

预期：

- 不会拒绝；
- 会发一条 `KindNotice`："这份快照是 v1（没有 hints 字段）—— 本次不做输入一致性校验"；
- 不自动补 hints。

为什么？因为 v1 记录里**没有这个信息**。补上本次 hints 会把"我们不知道"变成"我们编了一个值"，而血缘判据会从此认为所有产物都基于这套 hint——一个永久的谎。

**放行 + 保持 v1 + 明确告知**，比"补一个看似合理的值"更诚实。

## checkpoint 的简要答案

- **三个窗口**：回答未落盘 → 再问；已回答未消费 → 重放；执行到一半 → 重放并重跑节点。
- **at-least-once**：节点可能重复执行，副作用可能重复。
- **三种意图**：confirm 无副作用；revise 重跑节点；abort 停止。
- **幂等责任**：Runner 保证已完成节点跳过、决策重放；不保证副作用只执行一次。
- **run id + topic**：同一身份不能配两个输入，否则血缘串。
- **六种恢复错误**：not_found / expired / corrupt / too_old / from_future / bad_decision；处置不同。
- **没有游标**：恢复只是再读状态，`CanSkip` 决定从哪开始。
