# 第 18 章 参考答案

## 练习 1：五种坏图

### 1. 两个节点同名

```text
节点名 "outline" 重复（名字必须是唯一标识）
```

### 2. Kind 不合法

```text
节点 video 的 kind="video" 不合法
```

### 3. 两个节点产出同一个 Kind

```text
节点 A 与 B 都产出 "outline"：它们会抢同一个黑板 key
```

### 4. 依赖没有生产者

```text
节点 designer 依赖 "ghost"，但没有节点产出它、它也不在预置输入里 —— 这条前置永远不会就绪
```

### 5. 环

```text
图里有环：a → b → c → a
```

最能让排查者直接知道怎么修的，是第 4 条：它明确说了"没有节点产出它、也不在预置输入里"，你立刻知道要加节点或加预置。第 5 条也给出了路径，价值同样高。

## 练习 2：重复 Kind 的版本歧义

```text
A: outline@1
B: outline@2
A: outline@3
```

- `Get("outline")` → A 的 @3；
- `Get("outline@2")` → B 的产物；
- 下游 `BasedOn: outline@2` 以为是 A 的，因为 `Basis` 只有 key + version，没有 `produced_by`；
- `Decode` 的双向 Kind 校验**发现不了**：两个都是 `outline`，Kind 一致。

这就是为什么"一个 key 只能有一个产出者"必须在建图期强制。

## 练习 3：环的路径

错误信息会包含完整路径，例如：

```text
图里有环：a → b → c → a
```

没有 `cyclePath` 时，你只知道"有环"，不知道是哪几个节点。排查会从"看路径"变成"逐个删节点试"。

为什么不能靠 `MaxSteps` 兜底：

- `MaxSteps` 是运行期的成本保险，不是环检测；
- 环可能表现为"一直不满足依赖"，而不是"跑很多步"；
- 到那时错误信息是"达到最大步数"，会把你引向"预算不够"而不是"图有环"。

## 练习 4：缺失依赖 vs 运行期卡住

如果绕过 `BuildGraph` 直接跑 Runner：

- `Next` 每次都选中这个节点；
- 它的 `CanSkip` 永远 false（前置不存在）；
- Runner 可能在 `MaxSteps` 后报"达到最大步数"。

这个错误是误导性的：真实原因是"少了一个生产者"，但错误说的是"步数用完了"。

所以必须在建图期拒绝。

## 练习 5：预置输入冲突

把 `topic` 同时放进 `Presets` 和一个节点的 `Kind()`：

```text
预置输入 "topic" 同时被节点 X 产出 —— 它是输入还是产品？两者只能选一个
```

为什么更隐蔽：

- 两个节点抢 key，你至少能看到"两个角色"；
- 输入与产品抢 key，表面上都有"topic"，很容易被认为是同一条链的正常部分；
- 但 `StaleReasons` 假设 `topic@1` 是"用户输入"，一旦节点写出 `topic@2`，"输入变了"和"产品变了"就混在一起，无法区分根因。

## checkpoint 的简要答案

- **五种形态**：名字空/重复、Kind 非法、Kind 重复产出、依赖无生产者、环；外加预置输入冲突。
- **为什么建图期**：错误靠近来源、运行期代价高、确定性纯计算。
- **重复 Kind**：版本号交替、引用来源含糊、Decode 也查不出。
- **环路径**：只说"有环"不够，要知道哪几个节点咬住。
- **确定性**：起点和依赖都排序；边排序；拓扑序稳定。
- **不检查**：payload 语义、节点行为、运行期新鲜度、并行安全、预算。
- **预置当产物**：根节点也有上游，StaleReasons 无特例。
