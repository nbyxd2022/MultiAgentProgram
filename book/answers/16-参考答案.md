# 第 16 章 参考答案

## 练习 1：制造一次部分成功

```powershell
$env:L2_RENDER_FAIL="第三页标题片段"; go run ./cmd/l2
```

预期：

- `RenderResult.Files` 有 2 个路径；
- `RenderResult.Failed` 有 1 条，包含页码与失败原因；
- `Shortfall` 是类似 `["第 3 页：..."]`；
- Supervisor 的 `Incomplete` 是类似 `["render：第 3 页：..."]`；
- `Result.Complete()` 返回 false。

关键：系统仍然交付了 2 页，而不是整体失败；但完成判定不会说"全部完成"。

## 练习 2：只加字段，不接判断

如果没有实现 `Partial`，也没有读 `Shortfall`：

- `Artifact.Shortfall` 为空；
- `Supervisor.incompleteRequired` 什么也看不到；
- `Result.Complete()` 只看 Missing / Incomplete / Stale，于是返回 true；
- 系统认为 render 完成了。

这个 bug 为什么"看起来像成功"？

- 产物存在；
- 类型正确；
- 页数可能也对；
- 只有 `Failed` 字段里藏着缺口，而没有任何判断逻辑读它。

这正是 L2-2 的真实形态。测试应该在 `Result.Complete()` 或 `CanSkip()` 这一层断言，而不是只测 `RenderResult` 的字段。

## 练习 3：Research 的 Shortfall

5 条发现、2 条没有来源，有三种设计：

1. **视为不完整（Shortfall）**：产物可用，但下游要知道有 2 条未证实；
2. **Validate 拒绝**：来源是硬契约，没有来源就不许提交；
3. **允许但标记**：在 `Finding` 上加 `Verified bool`，让下游决定怎么用。

推荐第 3 种或第 1 种，取决于业务：

- 如果下游会把研究结论直接当事实引用，来源缺失是严重问题，应该 Validate 或 Shortfall；
- 如果下游只是用研究做灵感，允许未证实但标记更灵活。

关键：**"没有来源"必须是一个显式状态，不能静默通过。**

## 练习 4：10 页里失败 3 页

可能的摘要：

```text
render：7/10 页成功，3 页未产出（第 2、5、8 页）
```

`Shortfall` 逐页列：

```text
["第 2 页：写盘失败", "第 5 页：模板渲染失败", "第 8 页：标题冲突"]
```

下游的选择：

- 不应该整体重做 10 页；
- 应该只重试失败的 3 页；
- 如果失败原因是同一个（比如磁盘满），先修环境，再重试；
- 交付 7 页 + 明确说明缺口，而不是"全部失败"。

## 练习 5：完成判定的顺序

`CanSkip` 先报"不完整"，再报"过期"。

在**拓扑调度**下是安全的：

- 上游过期会先被调度重跑；
- 等下游真正执行时，上游已经新鲜；
- 此时下游即使先报"不完整"，也不会基于过期上游重跑。

在**非拓扑调度**下可能有问题：

- 调度器先看到下游不完整，直接重跑它；
- 但它依据的上游仍然过期；
- 于是产出一个"仍然过期"的新版本。

避免方法：

1. 调度器严格按拓扑序选择"第一个不能跳过的节点"；
2. 或者在 `CanSkip` 里把 `StaleReasons` 也附在 `Shortfall` 后面，让调用方同时看到两种问题；
3. 或者在节点执行前检查输入新鲜度（L2 的 `staleInputs` 就是这么做的）。

## checkpoint 的简要答案

- **为什么不能归到成功/失败**：整体失败会丢掉已完成部分；整体成功会掩盖缺口。
- **Shortfall 进信封**：`NewArtifact` 在产物创建时调用 `Partial.Shortfall()`，把结果固化到信封。
- **三种状态**：Missing 去跑；Incomplete 补缺口；Stale 先重做上游。
- **完成判定由代码做**：模型只说"下一步"，系统状态必须由代码检查。
- **Shortfall 不表达**：完全没有、数量不对、没做。
- **Partial 可选**：大多数产物不会残缺；可选能力避免接口变胖。
- **只加字段不接判断**：缺口会被静默忽略，系统误判完成。
