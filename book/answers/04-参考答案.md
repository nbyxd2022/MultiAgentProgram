# 第 4 章 参考答案

## 练习：写一个消息校验器

下面是一个严格版本。它比真实服务端更严格：只要协议出现"半截"，就报错。这样更适合用在测试里。

```go
package messagecheck

import (
    "fmt"
    "sort"

    "multiagent/internal/message"
)

func Validate(messages []message.Message) error {
    if len(messages) == 0 {
        return fmt.Errorf("消息列表为空")
    }

    // 当前这条 assistant 消息里，还没有拿到结果的 tool_call ID。
    pending := map[string]bool{}

    for i, m := range messages {
        switch m.Role {
        case message.RoleSystem:
            if i != 0 {
                return fmt.Errorf("第 %d 条: system 只能出现在最前面", i+1)
            }

        case message.RoleUser:
            if len(pending) > 0 {
                return fmt.Errorf("第 %d 条: 还有未完成的 tool_call %v", i+1, sortedKeys(pending))
            }

        case message.RoleAssistant:
            if len(pending) > 0 {
                return fmt.Errorf("第 %d 条: 上一条 assistant 的 tool_call 还没有结果 %v", i+1, sortedKeys(pending))
            }
            for _, tc := range m.ToolCalls {
                if tc.ID == "" {
                    return fmt.Errorf("第 %d 条: tool_call 缺少 id", i+1)
                }
                if pending[tc.ID] {
                    return fmt.Errorf("第 %d 条: tool_call id %q 重复", i+1, tc.ID)
                }
                pending[tc.ID] = true
            }

        case message.RoleTool:
            if m.ToolCallID == "" {
                return fmt.Errorf("第 %d 条: tool 消息缺少 tool_call_id", i+1)
            }
            if !pending[m.ToolCallID] {
                return fmt.Errorf("第 %d 条: tool_call_id %q 没有对应的 tool_call（孤儿结果）", i+1, m.ToolCallID)
            }
            delete(pending, m.ToolCallID)

        default:
            return fmt.Errorf("第 %d 条: 未知角色 %q", i+1, m.Role)
        }
    }

    if len(pending) > 0 {
        return fmt.Errorf("对话结束时仍有 tool_call 没有结果: %v", sortedKeys(pending))
    }
    return nil
}

func sortedKeys(m map[string]bool) []string {
    out := make([]string, 0, len(m))
    for k := range m {
        out = append(out, k)
    }
    sort.Strings(out)
    return out
}
```

### 几处设计取舍

- **严格模式**：只要出现"下一条 assistant/user 之前还有未完成 tool_call"，就报错。真实服务端有时允许更松的顺序，但学习阶段用严格模式更容易抓 bug。
- **system 只允许第一条**：有些服务商允许多条 system，这个校验器不支持。它教的是"最常见、最安全的形态"，不是完整规范。
- **不检查内容是否为空**：空的 assistant 消息在工具调用场景是合法的（`content: null`），所以不能在通用校验器里一律拒绝。
- **纯函数**：不依赖网络和模型，最适合写单测，也适合放在工具执行前的防御层。

## 4.1 的错误列表为什么失败

那条消息列表里，工具结果用了 `user` 角色，所以校验器会走到 `RoleUser` 分支。此时 `pending` 里还有 `call_bj`，于是报：

```text
第 3 条: 还有未完成的 tool_call [call_bj]
```

即使把角色改成 `tool`，如果漏掉 `tool_call_id`，会报"tool 消息缺少 tool_call_id"。

正确的列表应该是：

```text
system
user
assistant(tool_calls: call_bj)
tool(tool_call_id: call_bj)
assistant(content: 最终回答)
```

## 嵌套格式与扁平格式的转换

线格式（OpenAI）：

```json
{
  "id": "call_bj",
  "type": "function",
  "function": {
    "name": "get_weather",
    "arguments": "{\"city\":\"北京\"}"
  }
}
```

领域模型（仓库的 `message.ToolCall`）：

```go
message.ToolCall{
    ID:        "call_bj",
    Name:      "get_weather",
    Arguments: `{"city":"北京"}`,
}
```

转换时只做三件事：

1. 取出 `id`；
2. 取出 `function.name`；
3. 取出 `function.arguments`，**保持字符串**，不要在这里 `json.Unmarshal`。

为什么不在适配器里解析参数？因为"参数怎么解析"是具体工具的知识，不是模型客户端的知识。适配器只负责搬运协议，工具自己负责解析自己的参数。

## 上下文计算的参考答案

一个 10 步任务，每步 2 个工具调用：

- 消息条数：1 system + 1 user + 10 assistant + 20 tool = 32 条。
- 如果每条 tool 结果是 2,000 token，20 条就是 40,000 token。
- 每轮都要重发历史，所以输入 token 的总量会远大于 40,000；具体取决于每一轮的历史长度。

这个计算不是精确账单，而是让你建立直觉：**工具结果的体积，会直接变成上下文成本和延迟。** 后面的产物引用（`key@version`）就是为了把"完整内容"留在黑板里，只在上下文里传一个短引用。

## checkpoint 的简要答案

- **为什么不能用 user？** 模型会把工具结果当成用户的新指令，而不是"某个调用的观察结果"。
- **3 个 tool_call 要几条 tool 消息？** 3 条，每个 ID 一条，建议保持原顺序。
- **为什么分领域模型和线格式？** 隔离厂商差异，换服务商只改适配器；代价是多一层转换和测试。
- **五条不能丢的东西？** system、当前目标、最近一次工具结果、与它配对的 assistant tool_calls、协议完整性。
- **为什么是预算问题？** 上下文每轮重发，工具结果越大、轮次越多，输入 token 和费用增长得越快。
