# 第 8 章 参考答案

## 练习 1：把一段 prose 变成 struct

一个可用的形状：

```go
type Finding struct {
    Claim    string `json:"claim"`              // 结论本身，必填
    Evidence string `json:"evidence"`           // 支撑证据，必填
    Source   string `json:"source,omitempty"`   // 来源，可为空，但空要被标记
    Metric   string `json:"metric,omitempty"`   // 指标名，例如 "渗透率"
    Value    string `json:"value,omitempty"`    // 指标值，例如 "35%"
}

type Research struct {
    Findings []Finding `json:"findings"`
}

func (r Research) Validate() error {
    if len(r.Findings) == 0 {
        return fmt.Errorf("research.findings 不能为空")
    }
    for i, f := range r.Findings {
        if strings.TrimSpace(f.Claim) == "" {
            return fmt.Errorf("findings[%d].claim 不能为空", i)
        }
        if strings.TrimSpace(f.Evidence) == "" {
            return fmt.Errorf("findings[%d].evidence 不能为空", i)
        }
        // Source 允许为空，但下游必须能看出它没有来源。
        // 这里不直接拒绝，是因为调研早期经常先有结论、后补来源；
        // 但"没有来源"必须是一个显式状态，而不是静默通过。
    }
    return nil
}
```

设计取舍：

- `Claim` 和 `Evidence` 必填：没有结论或没有证据的条目，下游无法使用；
- `Source` 可以为空，但空意味着"未经证实"，下游不能把它当成事实引用；
- `Metric` / `Value` 可选：不是所有结论都是数字。

如果你把 `Source` 也设成必填，系统会更严格，但可能让调研在早期无法提交。**约束的松紧，取决于你希望系统在什么地方失败。**

## 练习 2：补上 `field` 的非空校验

在 `internal/agents/critic.go` 的 `submitReview.Execute` 里，`fix` 校验之后加：

```go
field := strings.TrimSpace(raw.Field)
if field == "" {
    return "", fmt.Errorf(
        "issues[%d].field 不能为空：没有定位，生成器不知道改哪里", i)
}

issues = append(issues, schema.Issue{
    Level:   level,
    Field:   field,
    Message: message,
    Fix:     fix,
    Source:  schema.SourceCritic,
})
```

注意：`field` 在 schema 里是 `Required: true`，但那只是给模型的提示；**服务端不会替你校验业务字段**。真正的校验必须在你自己的 `Execute` 里。

## 练习 3：让模型提交一个缺字段的 JSON

如果提交的是：

```json
{"issues":[{"level":"major","message":"第二条太空","fix":"补数据"}]}
```

`json.Unmarshal` 不会报错，`Field` 只是空字符串。

- 当前代码（未打练习 2 的补丁）：会接受这条 issue，`field=""`，生成器拿到一条无法定位的反馈。
- 打了补丁后：`Execute` 返回 `"issues[0].field 不能为空"`，Agent 把错误回灌给模型。
- 如果 Mock 只返回一次（不根据错误重试），`a.Run` 会走到最大步数或返回错误；`reviewSoft` 返回 error，`Review` 把报告标记为 `Incomplete`，不会当成"评审完成"。

这就是 `submitted` 和 `Incomplete` 两层保护的价值：**即使模型没交对，系统也不会误判为"没问题"。**

## 练习 4：模型摘要 vs 代码摘要

产物：

```json
{"pages":[{"title":"趋势","bullets":["渗透率 35%","成本下降 40%"]}]}
```

模型可能写：

```text
本报告共 3 页，涵盖趋势、成本与基础设施。
```

实际只有 1 页。模型不是故意撒谎，它是在"补全一个看起来合理的摘要"。

代码派生：

```go
summary := fmt.Sprintf("%d 页；第一页：%s（%d 条要点）",
    len(pages), pages[0].Title, len(pages[0].Bullets))
```

得到：

```text
1 页；第一页：趋势（2 条要点）
```

代码摘要不会"觉得应该有三页"。它可能不够漂亮，但它**不会说谎**。

结论：摘要可以作为模型上下文的一部分，但**权威摘要必须由代码从结构化字段派生**。模型摘要只能作为辅助描述。

## 练习 5：设计一个 `submit_outline`

一个可用的参数形状：

```go
tool.Parameter{
    Name:     "pages",
    Type:     tool.TypeArray,
    Required: true,
    Description: "大纲页列表，必须正好 3 页",
    Items: &tool.Parameter{
        Name: "page",
        Type: tool.TypeObject,
        Properties: []tool.Parameter{
            {
                Name: "title", Type: tool.TypeString, Required: true,
                Description: "这一页的标题",
            },
            {
                Name: "bullets", Type: tool.TypeArray, Required: true,
                Description: "这一页的 3 到 5 条要点",
                Items: &tool.Parameter{
                    Name: "bullet", Type: tool.TypeString,
                    Description: "单条要点文本",
                },
            },
        },
    },
}
```

为什么用对象数组，而不是三个平行数组？

```json
// 不推荐
{"titles":["A","B","C"], "bullets":[["a1","a2"],["b1","b2"],["c1","c2"]]}
```

平行数组把"对齐"的责任推给了模型：

- 两个数组长度不一致时，`titles[2]` 可能配到 `bullets[1]`；
- 没有任何 schema 能表达"这三个数组必须一一对应"；
- 错误是静默的，不会在解析时报出来。

对象数组把同一页的字段放在一起：

```json
{"pages":[{"title":"A","bullets":["a1","a2"]}, ...]}
```

字段的对齐关系由结构保证，不需要约定下标。这正是仓库补 `tool.TypeObject` 的理由（`internal/tool/tool.go:22`）：**协议层表达力不足时，扩展协议，而不是让业务去将就。**

## checkpoint 的简要答案

- **四种损失**：字段丢失、字段漂移、字段虚构、定位丢失。
- **只有 JSON 不够**：会包裹、截断、缺字段；解析成功不等于语义正确；没有提交点，无法区分"没检查"和"没问题"。
- **submit_review 的四样保障**：schema 契约、明确提交点、语义校验、错误回灌。
- **区分空结论与没提交**：前者是"检查过了没问题"，后者是"根本没检查"，两者不能混。
- **Submitted / Overwrites**：前者判断是否真的提交过；后者让"覆盖了上一份"这件事可见、可统计。
- **只传 ref+summary**：省 token，避免下游复述全文导致漂移；要全文的人自己取。
- **Summary 由代码派生**：模型摘要可能说谎；代码从结构体投影不会。
