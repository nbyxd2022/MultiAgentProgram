# 第 28 章 精读参考实现：哪些能抄，哪些不能

失败有了名字，可还得判断哪些做法值得学、哪些只是别人的业务。这一章读参考实现。

## 28.1 两个系统根本不一样

参考实现（`beautifulagent-go`）是：

- Eino 之上的生产服务；
- Redis / Mongo / OTel / Prometheus / gin；
- 多实例、真并发；
- 有真实业务表。

本仓库是：

- 教学实现；
- 标准库 + 零框架；
- CLI 单进程、图串行；
- 业务表是演示用的。

所以"逐文件对齐"没有意义——它们没有对应的文件。

有意义的比法是：逐个"我们关心的事"，同一件事两家各怎么做。

`docs/09-与参考实现的差异审计.md` 的开头就写了这条射程：

> 本次审计的射程 = 那份 14 次对照的清单。清单之外还有没有差异，本文不保证。

一个"看起来已经审计完了"的文档，比"没有审计"更容易骗人。

## 28.2 三分法：缺陷、欠账、取舍

判据只有一句：

> **能不能写出一条今天就会失败的测试？**

| 类别 | 判据 | 处置 |
|---|---|---|
| 缺陷 | 能写，而且依赖存在 | 改 |
| 欠账 | 能写，但依赖还不存在（没有指标/真实模型） | 登记 + 触发条件 |
| 取舍 | 写不出——只能主张"它那样更好" | 保留，把理由摆出来 |

为什么这条判据好用？它把"我觉得它那样更好"换成了一个可验证的句子。

- "Runner 的 ctx 检查永远不会触发"——写得出会失败的测试 → 缺陷；
- "滑动窗口比累计上限更专业"——写不出（累计上限同样拦得住）→ 取舍。

## 28.3 哪些能抄：形状

### 1. 边界上的 panic 恢复

参考实现在三个边界做 recover：goroutine、HTTP、外部调用。

共同点三样：

- `crash: true` 是显式的结构化字段；
- 带 stack；
- 不静默。

本仓库抄的是形状，不是位置：只在节点调用这一处 recover。

因为工具、模型、schema 断言全在节点里面，包住这一处就包住了全部。

> 不是"哪里可能 panic 就包哪里"，而是"我们的边界在哪"。

### 2. 超时必须有人生产

参考实现有 45+ 处 `WithTimeout`，本仓库原来 0 处。

而 `Runner.drive` 一直有一个 `ctx.Err()` 检查——没有生产者，它永远不会触发。

抄法：在 `cmd/l3` 加 `-timeout`，由 `runCtx()` 一处产生，主流程和 `-verify` 共用。

教训：

> 声明 ✅ 实现 ✅ **生产 ❌** —— 这比"没实现"更隐蔽。

### 3. 错误分类的"形状"

参考实现有一张 25 个常量的错误表，两个消费者（Prom label + 日志字段）复用它。

本仓库抄的是：

- 常量 + `Classify` 函数 + 明确的优先级；
- 结构化优先，字符串兜底；
- 有兜底值。

但只保留两个类（Retryable / Permanent），因为只有一个消费者：重试。

> 类的数量由消费者的数量决定，不由"错误的丰富程度"决定。

### 4. 重试与退避

参考实现有 fallback 链和 `ShouldFallback`；本仓库有 `retry.Do`：

- 带 ctx；
- 带退避；
- `canRetry` 是回调（机制不认识策略）；
- `Error` 带尝试次数和 `Unwrap`。

这些是分布式系统的通用形状，值得抄。

### 5. 原子写盘

`temp → fsync → rename → fsync dir`，Windows rename 重试。

这是"状态要么旧完整、要么新完整"的标准做法，直接抄。

### 6. 端口-适配器

`llm.Client` / `checkpoint.Store` / `observ.Tracer` / `budget.Guard`。

框架、存储、观测、预算都应该是端口，具体实现由最外层注入。

### 7. 结构化错误

"期望 X，实际 Y"；"哪一维超了"；"缺哪个字段"。

这是可行动的反馈，不是"出错了"。

## 28.4 哪些不能抄：业务与前提

### 1. 业务表

参考实现的 25 个错误类型是它业务的。抄过来毫无意义。

要抄的是形状：一组常量 + 一个分类函数 + 优先级 + 兜底。

`docs/10-L4复盘.md` 把这个错误反过来讲了一次：

> 抄了形状，而那张表是它业务的 → 对；
> 抄了形状，而它要表达的事实没人产生 → 空壳。

### 2. 滑动窗口

参考实现用 60 桶滑动窗口 + CAS 做限流。

那是速率问题（同一秒 1000 次 vs 一分钟 1000 次）。

预算是总量问题（一秒花完 100 万和一年花完 100 万，前者同样超）。

在 CLI 单进程、没有突发流量的场景，累计上限够了。

### 3. `Remaining` 取 min

参考实现的 `CompositeLimiter` 取 `min(Remaining)`，因为它的多个窗口单位相同（都是次数）。

本仓库五维单位不同（步数 / token / 厘 / 纳秒）——取 min 是把不同量纲的数比大小。

### 4. TOCTOU 注释

参考实现说"Allow/ReportUse 分离有 TOCTOU 窗口，高并发可能多放一次"。

那对它是事实（HTTP 服务，真并发）。

本仓库是 CLI 单进程、图串行，`Allow` 之后必然先 `ReportUse` 才轮到下一个——窗口不存在。

> 错的不是那句注释，是"照抄"这个动作。
> 照抄一条不成立的代价说明，比不写更糟：它会让下一个人以为"这个问题我们已经考虑过了"。

### 5. OTel / Prometheus

L4 的重点是"观测模型"，不是"接哪个后端"。

端口定好之后，写适配器是机械工作。提前接，会造一个没有消费者的能力。

### 6. 框架胶水与业务 Prompt

Eino 的 `AgentWithDeterministicTransferTo`、具体的 Prompt 措辞、业务 schema，都不能直接搬。

它们解决的是"那个框架/那个业务"的问题。

## 28.5 空壳：抄了形状，没人生产

`docs/10-L4复盘.md` 列了 11 个"声明 ✅ 实现 ✅ 生产 ❌"，其中两个最典型：

- `Usage.CostMilli`：字段、类型、校验都在，但没有一处赋过非零值；
- `KindReconcile`：常量、契约表、注释都在，但没有一处 emit。

这不是"抄错了形状"，是"抄了形状，而它要报告的那件事在我这里没有人看得见"。

> **抄一个机制时，要问的不只是"它的形状对吗"，而是"它要报告的那件事，我这儿有没有人看得见"。**

这也解释了为什么"框架型代码"的失效方式不是"跑错了"，而是"它存在，而没人用"。

## 28.6 怎么抄：五步

1. 读 why：先读它的注释/调用点，弄清它防的是什么故障；
2. 写一条会失败的测试：如果写不出，它可能只是风格；
3. 抄形状，不抄表：接口、优先级、兜底、边界；
4. 用注入验证：证明它真的在作用，而不是"接了但没通电"；
5. 记录触发条件：暂时不抄的，写清"什么情况下该抄"。

这五步比"照着写一遍"慢，但它产出的是判断力，不是复制品。

## 28.7 练习

先自己做，再看 `answers/28-参考答案.md`。

### 练习 1：分类三条差异

从 `docs/09` 里挑三条：

- 一条缺陷；
- 一条欠账；
- 一条取舍。

分别说明：为什么它属于那一类？能不能写出一条今天会失败的测试？

### 练习 2：找一条会失败的测试

挑一条你认为的"缺陷"，写出测试的名字和它会断言什么。

例如：

```go
func TestOpenAI429IsRetryable(t *testing.T)
```

### 练习 3：找一个空壳

在本仓库里找一处"有字段/有常量/有注释，但没有生产者"的东西。

提示：`CostMilli`、`KindReconcile`、`Layers()` 的并行、`LocalAndRemote` 的生产接线。

回答：

- 它要报告的事实是什么？
- 谁应该生产它？
- 没有它会导致什么？

### 练习 4：判断一条注释能不能抄

找一条参考实现的注释，问：

- 它成立的前提是什么？
- 我们的前提一样吗？
- 如果不一样，照抄会导致什么误解？

### 练习 5：给自己定一条"不抄清单"

写下三条你不会从参考实现抄的东西，并给出理由。

## 28.8 小结与自检
合上书，回答：

- 为什么不能逐文件对齐？
- 三分法的判据是什么？
- 哪些"形状"值得抄？举三个。
- 为什么不能抄 25 个错误类型？
- 为什么滑动窗口、`min(Remaining)`、TOCTOU 注释不能直接抄？
- 什么是"空壳"？为什么它比"没实现"更危险？
- 抄一个机制的五步是什么？

能答出五题以上，再进下一章。

## 28.8 拓展：先写三行，再决定抄不抄

从参考实现里挑一条你最想抄的机制，先别抄代码。写下三行：

1. 它防住的故障是什么？
2. 它的代价是什么？
3. 我的系统里，有没有产生它所需数据的那一层？

三行都写不出来，就先别抄。第四行可以写：“等我有了 __，再回来。”
