# 第 18 章 坏图的五种形态：构建期校验

边推导出来了，可一张图能建出来，不代表能跑。这一章看构建期应该拒绝哪些坏图。

## 18.1 一张能建出来、但跑不动的图

你写了一个节点：

```go
func (n *Outline) Needs() []schema.Kind {
    return []schema.Kind{"outline"} // 手滑，写成了自己
}
```

图建出来了。Runner 按拓扑序跑，发现：

- `outline` 依赖 `outline`；
- 它自己还没产出；
- 所以它永远不能开始。

或者你写了两个节点，都产出 `outline`。图建出来了。运行时：

- 第一个节点写 `outline@1`；
- 第二个节点写 `outline@2`；
- 下游 `Get("outline")` 拿到的是第二个；
- 但 `Get("outline@1")` 拿到的是第一个。

版本语义还在，但"outline 是谁产的"变得含糊。

这些错误的共同点是：建图时看不出来，运行时才变成怪事。

所以 `BuildGraph` 在建图期拒绝它们。

## 18.2 为什么必须在建图期

三个理由：

1. 离错误来源最近：配置写错的地方就在 `Needs()` / `Kind()` 里，建图时就能指出来；
2. 运行期失败很贵：可能已经跑了几轮、花了几万 token，才发现某个前置永远不会就绪；
3. 确定性：建图是纯计算，不依赖模型、不依赖磁盘；同样的 spec 一定得到同样的结果。

这和 L2 的构造期校验、checkpoint 的写盘前自检是同一条：

> **错配是本程序的 bug，越靠近它的来源发现越便宜。**

## 18.3 五种主形态

`BuildGraph`（`graph.go:312`）的注释列了五种。下面逐条说：如果不拦，会发生什么。

### 形态一：节点名为空或重复

```go
if name == "" { ... }
if _, dup := nodes[name]; dup { ... }
```

如果不拦：

- 空名字的节点无法被 `Next` 或日志引用；
- 重复名字的节点会在 map 里互相覆盖，其中一个静默消失。

静默消失比报错更糟：你以为图里有 4 个节点，实际只有 3 个。

### 形态二：Kind 不合法

```go
if !n.Kind().Valid() { ... }
```

`Kind` 是受控词表（`topic/research/outline/design/render`）。它同时是黑板 key 和边的端点。

如果不拦：

- 黑板会出现一个"谁都不认识"的 key；
- `Decode` 无法根据 Kind 找到具体类型；
- 下游的 `Needs` 写的是合法 Kind，永远匹配不上这个脏 Kind。

脏数据不能进系统。这是原则一（确定性兜底）在协议层的落地。

### 形态三：两个节点产出同一个 Kind

```go
if owner, dup := kinds[n.Kind()]; dup {
    return fmt.Errorf("节点 %s 与 %s 都产出 %q：它们会抢同一个黑板 key", ...)
}
```

如果不拦：

- 两个节点都往 `outline` 这个 key 写；
- 版本号交替递增：A 写 @1，B 写 @2，A 再写 @3……
- 下游 `Get("outline")` 拿到的是"最后写的那个"，不一定是它以为的那个；
- `Get("outline@2")` 取到的是 B 的产物，但下游可能以为是 A 的。

更隐蔽的是：两个产物Kind 相同，所以 `Decode` 的双向校验也发现不了错位。它只会安静地返回一份"类型正确、内容来源错误"的产物。

一个 key 只能有一个产出者。 这条规矩没有例外。

### 形态四：依赖没有生产者

```go
if _, ok := kinds[dep]; ok { continue }
if presets[dep] { continue }
return fmt.Errorf("节点 %s 依赖 %q，但没有节点产出它、它也不在预置输入里 —— 这条前置永远不会就绪", ...)
```

如果不拦：

- Runner 每次问 `Next`，都会选中这个节点；
- 它的 `CanSkip` 永远返回 false（前置不存在）；
- 它永远跑不起来；
- 最后只能靠 `MaxSteps` 强制终止。

而错误信息会是"达到最大步数"，不是"你少写了一个节点"。报错了对象，排查会被引向错误的方向。

### 形态五：有环

```go
order, err := topoSort(nodes, presets)
```

如果不拦：

- 拓扑排序失败；
- 如果强行跑，节点会互相等待，永远不满足；
- 或者调度器无限循环。

`topoSort` 用三色标记检测环，并打印完整路径：

```text
图里有环：a → b → c → a
```

只说"有环"不够——你需要知道是哪几个节点咬住了。

## 18.4 一个容易忽略的变体：预置输入冲突

```go
if owner, clash := kinds[k]; clash {
    return fmt.Errorf("预置输入 %q 同时被节点 %s 产出 —— 它是输入还是产品？两者只能选一个", ...)
}
```

`Presets` 是"图开始之前已经在黑板上的产物"，比如 `topic`。

如果某个节点也产出 `topic`：

- `topic@1` 是输入；
- 节点又写出 `topic@2`；
- `StaleReasons` 会把"用户改了主题"和"节点产出了新主题"混在一起；
- 你无法区分"输入变了"和"下游重写了输入"。

一个 key 只能有一个来源。 输入和产品不能共用。

## 18.5 环检测的细节

`topoSort`（`graph.go:617`）用三种颜色：

- white：没访问；
- gray：在栈上；
- black：访问完。

遇到 gray，说明找到了一个回边，`cyclePath` 从栈里截出环：

```go
func cyclePath(stack []string, back string) []string {
    for i, name := range stack {
        if name == back {
            return append(append([]string(nil), stack[i:]...), back)
        }
    }
    ...
}
```

输出形如 `a → b → c → a`。

注意：拓扑排序的起点按名字排序，每个节点的依赖也排序。所以同样的图，两次建图得到的 `Order()` 和 `Edges()` 完全一致。

确定性不是"碰巧"，是排序保证的。

## 18.6 BuildGraph 不检查什么

它只检查结构，不检查：

- payload 的业务语义（`Research` 有没有 findings）；
- 节点的行为（`Run` 会不会返回错误）；
- 运行期的数据新鲜度（`CanSkip` / `StaleReasons`）；
- 并行安全（`Runner` 目前串行）；
- 资源预算（那是 `budget` 的事）。

建图期能挡的和运行期才能挡的，必须分开。 试图在建图期检查一切，会让 `BuildGraph` 变成一个依赖业务知识的上帝函数。

## 18.7 预置输入为什么要当产物

`topic` 不是节点产出的，但它是 `research.Needs()` 的依赖。

如果把输入特殊对待：

- "输入变了要不要重做"要单独写一套逻辑；
- 根节点的新鲜度没有上游可比；
- `StaleReasons` 要加一个"根节点特例"。

把它当普通产物（`topic@1`）之后：

- 根节点也有上游；
- 主题变化会让 `research` 自动过期；
- `StaleReasons` 一路通用，没有特例。

`BuildGraph` 只做一件事：确保预置输入不被节点重复生产。

## 18.9 拓展：只看错误信息复原一张图

自己造一个环：A 依赖 B，B 依赖 C，C 又依赖 A。观察 `BuildGraph` 打印的路径。

然后合上代码，只凭错误信息把这张图重新画出来。画不出来，说明错误信息还不够可执行；画得出来，你就知道为什么 `cyclePath` 不能省。
