# 第 6 章 ReAct 循环：为什么必须循环，什么时候停

工具、消息、循环三样零件都在了。现在回到循环本身：它为什么必须循环、什么时候停、什么时候会被模型“骗”。

## 6.1 一次调用为什么不够

假设任务是：

> 搜索新能源汽车的最新数据，整理成三条结论，再生成一页幻灯片。

一次模型调用能完成吗？

不能。因为模型在一次调用里看不到工具的执行结果。它最多能说"我想调用 web_search 和 render_slide_html"，但工具还没跑，结果还不存在。它必须等运行时执行完、把结果放回上下文，再进行下一次调用。

所以最小流程至少是：

```text
调用模型 → 模型请求搜索
执行搜索 → 把结果放回上下文
调用模型 → 模型根据结果请求渲染
执行渲染 → 把结果放回上下文
调用模型 → 模型给出最终回复
```

三次模型调用，两次工具执行。**这个"调用—执行—回灌—再调用"的重复，就是循环存在的原因。**

## 6.2 ReAct 到底是什么

ReAct 的原意是 Reasoning + Acting：模型先推理，再行动，再根据观察继续推理。

它有两种常见实现形态：

### 形态一：显式文本协议

提示词要求模型输出：

```text
Thought: 我需要先查一下最新的渗透率数据。
Action: web_search
Action Input: {"query":"新能源汽车 渗透率 2026"}
Observation: ...
```

运行时要解析 `Action` 和 `Action Input`，执行工具，再把 `Observation` 拼回去。

优点：不依赖模型的 function calling 能力，任何文本模型都能用。
缺点：解析脆弱；模型可能不按格式写；推理文本可能是事后编的。

### 形态二：原生工具调用（本仓库的做法）

模型直接返回结构化的 `tool_calls`，运行时不解析自然语言：

```json
{
  "role": "assistant",
  "content": "我先查一下最新数据。",
  "tool_calls": [
    { "id": "call_1", "type": "function", "function": { "name": "web_search", "arguments": "{\"query\":\"新能源汽车 渗透率 2026\"}" } }
  ]
}
```

优点：协议稳定、可校验、模型厂商原生支持。
缺点：依赖模型的 function calling 能力；推理文本可能为空，过程不如显式 ReAct 可读。

仓库用的是形态二。 所以严格说，它是一个 tool-calling loop，而不是教科书里那种带 `Thought/Action/Observation` 的 ReAct。工程上大家常把两者都叫 ReAct，但面试时你要能说清区别——这会让面试官知道你读过原始概念，而不是只背了名词。

## 6.3 循环的四条不变量

不管叫什么名字，一个正确的循环必须满足四条不变量：

1. 每一轮只发起一次模型调用。 不要把多个模型调用混在一轮里，否则 token 记账、重试和事件都会乱。
2. **模型请求的所有工具，都要在下一轮之前执行完。** 一个 assistant 消息里有 3 个 `tool_call`，就要有 3 条 `tool` 消息。
3. 所有工具结果都要回到上下文。 少一条，模型就看不到那次观察。
4. **终止只有两种：自然终止（没有 tool_calls）和硬终止（达到最大步数）。** 不能有第三种"悄悄退出"。

第 4 条尤其重要。很多实现会在工具报错时直接 `return`，看起来是"错误处理"，实际上是跳过了终止协议：模型没有收到错误，用户只看到一句"运行失败"。仓库的做法是把错误变成 `ok=false` 的结果，继续循环，让模型自己决定下一步。

## 6.4 仓库里的循环与三个关键位置

打开 `internal/agent/agent.go`，从 `RunWithMessages`（大约第 213 行）开始看。核心结构和第 3 章一样，但有三个位置值得单独说。

### 位置一：重试只包住模型调用

```go
_, err := retry.Do(ctx, a.retry, func(ctx context.Context) error {
    resp, genErr = a.Client.Generate(ctx, llm.Request{...})
    ...
})
```

`retry.Do` 包的是**一次 `Generate`**，不是整个 `for` 循环。

这个位置不是随便选的：

- 重试这一次调用：上下文不变，模型重新回答一次，工具不会重跑。
- 重试整个循环：已经执行过的工具会被再执行一遍。如果工具写文件、发请求、扣款，副作用就会重放。

工具不可能都保证幂等。所以重试必须放在"最内层、没有副作用"的那一层。

### 位置二：每次成功调用都记一条明细

```go
a.emit(llmCallEvent(a.Name, resp))
a.guard.ReportUse(budget.Usage{...})
```

这两行在 `retry.Do` 的 `fn` 里面，所以每一次成功的调用都会记一条事件、记一笔 token。

如果只记"最后一次成功"，重试花掉的钱在账上就不存在。第 25 章会把这件事展开：总量只能有一份明细。

### 位置三：最大步数的错误要带上下文

```go
return "", fmt.Errorf("%s: 达到最大步数 %d 仍未收敛，已强制终止（已调用工具 %d 次）",
    a.Name, a.MaxSteps, a.Stats().ToolCalls)
```

只报"达到最大步数"没有用。你要知道它调了多少次工具、卡在哪一类动作上。错误信息是给排查的人看的，不是给日志凑字数。

仓库的 `MaxSteps` 默认是 8（`internal/agent/agent.go:141`）。这个数字不是真理，是一个成本与成功率的折中：

- 太小：复杂任务做不完；
- 太大：模型打转时烧钱更多。

真实项目里应该用评测数据来定，而不是拍脑袋。第 26 章会把这件事变成可测量的。

## 6.5 "模型说完成了"不等于"任务完成了"

自然终止的条件是"模型不再请求工具"。这只是一个模型判断，不是事实判断。

模型可能：

- 任务没做完就停（比如只搜了资料，没生成幻灯片）；
- 任务做错了还停（生成的幻灯片缺了关键字段）；
- 一直不停（反复调用同一个工具）。

所以，仅靠循环本身，无法保证任务完成。你需要在循环之外加完成判定：

- L2 的 Supervisor 会检查：产物是否齐全、是否有 `Shortfall`、是否 `Stale`（第 16 章）；
- L3 的图会在节点产出后检查：`Kind` 对不对、依赖是否满足（第 19 章）；
- L4 的评测会检查：最终产物是否满足硬判据（第 26 章）。

**这是从"单 Agent"走向"多 Agent/图编排"的真正动机**：不是"多几个角色更酷"，而是"模型的自我判断不可靠，需要代码来兜底"。

最大步数是另一层兜底：它不保证任务完成，只保证不会无限花钱。两者不能互相替代。

## 6.6 什么时候需要显式推理

你可能会问：既然原生工具调用就够了，为什么还要让模型写 `Thought`？

三种情况值得考虑：

1. **模型不支持 function calling。** 只能用文本协议，这时显式 ReAct 是唯一选择。
2. 任务需要长链条规划。 显式写出"先做什么、再做什么"可能提高一致性，但代价是 token 和格式不稳定的风险。
3. 需要审计推理过程。 人要能看懂模型为什么这么做。

但要记住：显式推理文本不等于真实推理。 模型可以事后编一段看起来合理的 `Thought`。它可以作为调试线索，不能当作正确性的证据。

仓库选择了原生工具调用 + 结构化产物，而不是解析思维链。这是一个偏工程可靠性的选择：**能校验的结构化字段，优先于不可校验的自然语言。**

## 6.7 坏循环与好循环

| 维度 | 坏循环 | 好循环（仓库） |
|---|---|---|
| 终止 | 只靠模型停 | 自然终止 + 最大步数 |
| 工具错误 | 直接返回错误 | 结构化回灌，让模型自愈 |
| 重试 | 重跑整个循环 | 只重试单次模型调用 |
| 工具结果 | 可能漏掉某条 | 所有结果都回灌 |
| 用量 | 不记录 | 每次调用记 token 与事件 |
| 完成判定 | 模型说完成就完成 | 循环外还有产物/依赖检查 |

这张表不是让你背，而是让你在写自己的循环时逐条对照。**每一条"好"的背后，都有一个具体的故障场景。**

## 6.8 练习

先自己做，再看 `answers/06-参考答案.md`。

### 练习 1：给第 3 章的 Agent 加统计

在 `book/code/ch03` 的 `Agent` 里加：

```go
type Stats struct {
    Steps     int
    ToolCalls int
    PromptTokens int
    CompletionTokens int
}
```

要求：

- `Steps` 数的是真正发起的模型调用次数，不是循环轮次；
- `ToolCalls` 数的是执行过的工具次数；
- 每次 `Generate` 成功后累加 token。

然后和仓库的 `Stats()`（`internal/agent/agent.go:189`）对比：它为什么从事件里数，而不是另存一份？

### 练习 2：制造一次"提前终止"

写一个 Mock：第一次返回一个 `tool_call`，第二次（即使工具结果还没回灌）直接返回最终回复。

观察：任务真的完成了吗？产物存在吗？

这个练习的目的是让你看到：**自然终止只代表模型不想再调用工具，不代表任务目标达成。**

### 练习 3：给循环加一个完成判定

在第 3 章的 Agent 返回最终回复之前，加一个检查：

```go
if _, err := os.Stat("out/note-天气笔记.md"); err != nil {
    return "", fmt.Errorf("任务未完成：笔记文件不存在")
}
```

再跑一次"提前终止"的 Mock。观察它现在会不会报错。

这就是"完成判定"的最小版本。第 19 章会把它升级成图节点的产物检查，第 26 章会把它升级成评测判据。

### 练习 4：重试位置实验

写一个会失败一次的 `Client` 包装器，然后做两次实验：

1. 只重试 `Generate`：观察工具执行了几次；
2. 把整个 `Run` 包在重试里：观察工具执行了几次。

用一个带计数器的工具（比如每次调用写一行日志）来观察。你会看到：重试放错位置，副作用会重放。

## 6.9 拓展：让重试判据自己停下来

写一个节点，让它永远返回 `Next = 自己`，观察它在第几次被上限拦住。然后把判据改成“素材少于 3 条才重试”，再看它能不能自己停。

两次运行的差别，就是“有界重试”和“无界重试”的差别。前者是一个策略，后者只是把问题推给预算。
