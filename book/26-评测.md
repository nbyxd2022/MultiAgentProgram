# 第 26 章 评测：可观测不等于可评测

系统能停下来了，可停下来之后，你怎么知道这一版比上一版好？这一章看评测。

## 26.1 自比与他比

L0~L3 把"可观测"做起来了：事件流、录播、行为投影。

`-verify` 比较的是"两次运行是否相同"——这是自比。

而"改了 Prompt 之后是变好还是变坏"，需要的是他比：

```text
一次运行 vs 一个期望
```

期望从哪来？只能人写。

> `-verify` 比的是两次运行是否相同（自比）；
> 评测比的是运行 vs 期望（他比）。
> 这两件事的判据不一样，虽然都会用到事件流。

## 26.2 用例与期望

`Case`（`eval/case.go:43`）：

```go
type Case struct {
    ID    string
    Topic string
    Hints map[string]string
    Tags  []string
    Expect Expectation
}
```

`Expectation` 是硬判据：

- `MustHaveKinds`：必须产出的产物种类；
- `MinFindings`：研究素材最少几条；
- `Pages`：期望页数；
- `MaxSteps` / `MaxTokens` / `MaxWall`：上界；
- `MustContain` / `MustNotContain`：最终产物里必须/不许出现的话。

零值 = 这一条不检查。

这与 `budget.Limits` 的 fail-closed 契约相反，源码里专门写了：

> 期望是**人写的**，而"人没写的那些"本来就是"他没要求"。
> 要求"没写就必须为 0"会让每个用例都必须写全八条——而那样最大的可能是有人随手填一个 0，于是那个用例永远过不了。

### 一条最重要的校验

`CaseSet.Validate` 强制每个用例至少有一条硬判据。

否则：

- 一个"期望全空"的用例永远会过；
- 它绿着，没人去看它；
- 而它什么都没验证。

> **一个永远绿的用例，是一种伪装成保障的空白。**

用例集还有：

- ID 唯一；
- Topic 非空；
- 空行和 `//` 注释会被跳过；
- JSONL 一行一个用例，坏一行报行号。

## 26.3 硬判据

`Case.checks`（`eval/run.go:157`）会跑全部判据，而不是遇到第一个失败就返回。

为什么？

> 判据是免费的，运行不是。

一次只报一条失败，会让人修一条、再跑一次、再看到下一条——每次都要花一次运行的代价。

每个 `check` 都渲染成：

```text
pages：期望 5，实际 3
```

三个字段缺一不可：名字、期望、实际。只说"失败"，排查的人要自己去算。

几个细节：

### `must_have_kinds` 只报缺的，不报多的

"多产出了 design"不是失败——那是流程的自由度，不是回归。

### `MustContain` 查的是 `Rendered`，不是 `Board`

`Board` 是中间产物（大纲、版式、素材）；`Rendered` 是用户最终看到的东西。

问错对象会得到一个恒真的判据——中间产物里当然有大纲里的词。

### `countIn` 解不出来时返回 error，不是 0

"真的 0 条素材"和"读不出来"在表里都是 0，但它们要去看的地方完全不同：

- 真的 0 条 → 去看角色为什么没产出；
- 读不出来 → 去看产物本身（信封/payload kind 不一致、JSON 坏了）。

> 判据说错方向，比不说更贵——它让人去错地方。

## 26.4 指标：`Steps` 与 `AgentSteps` 是两个问题

`Metrics`（`eval/run.go:87`）：

```go
type Metrics struct {
    Steps            int // 图跳数
    AgentSteps       int // 所有角色的 ReAct 迭代总数
    PromptTokens     int
    CompletionTokens int
    Wall             time.Duration
}
```

为什么两个步数？

第一次跑真实用例时，`max_steps` 报"期望 ≤12，实际 30"，而那一轮只有 4 个节点。

多出来的 26 从哪来？

**`KindStart` 有两层都在发**：

- 图层：每个节点发一次 → 4 条；
- agent 层：每个角色每轮 ReAct 迭代发一次 → 若干条。

`Count(KindStart)` 把两层混在了一起。

> 这不是"指标算错了"，是"步数"这个词在两个问题下含义不同：
> 图层的"一步" = 跑了一个节点；agent 层的"一步" = 一轮 ReAct 迭代。

而 `Expectation.MaxSteps` 问的是前者。

修法：`metricsOf` 按 `Layer` 分流。

```go
case e.Kind == observ.KindStart && e.Layer == observ.LayerGraph:
    m.Steps++
case e.Kind == observ.KindStart:
    m.AgentSteps++
```

这是一个很好的教训：**同一个词在不同层含义不同——用之前先说清是哪一个。** `Event.Layer` 正是为这件事存在的。

## 26.5 跑不完 ≠ 判据没过

`Verdict`（`eval/run.go:306`）：

```go
type Verdict struct {
    CaseID  string
    Passed  bool
    Failed  []string
    Metrics Metrics
    Err     error
    Judgement *Judgement
    JudgeErr  error
}
```

- `Failed`：跑完了，但判据没过；
- `Err`：根本没跑完（模型失败、预算、图错误）。

为什么分开？因为处置完全不同：

- 判据没过 → 去看产物；
- 跑不完 → 去看错误。

合并成一个"失败"会让人去错地方。

`Summarize` 的平均值只对跑完的用例算：

- 一个跑不完的用例，它的耗时/token 不是有意义的样本；
- 把它算进平均会把均值拉向一个假的位置。

而成功率的分母是全部用例——跑不完的也算不成功。这两个口径不同，不能混。

## 26.6 软判据：线索，不是判据

`Judge` 是一个端口：

```go
type Judge interface {
    Judge(ctx context.Context, prompt string) (string, error)
}
```

它收 prompt，返回文本。为什么收 prompt 而不是 `Case`？

因为"问什么"是判据的一部分：

- 问"这份 PPT 完整吗"和"这份 PPT 有没有创意"是两个完全不同的判据；
- 让实现自己造 prompt，等于把判据定义藏进实现里。

`Judgement` 有三个维度：`faithful`、`complete`、`readable`，每个 0~10 分，必须给理由。

`Validate` 检查：

- 分数在 0~10；
- 理由非空；
- 不自创维度。

prompt 是请求，校验是保证。

### 最关键的决定：软判据不参与 Passed

让一个概率值决定"通过/失败"，就是让评测开始 flake。

而 flake 的评测比没有评测更坏——它会训练人忽略红色。

所以软判据只进报告，不进判定。它是"给人看的第二列信息"：

> "这次硬判据全过，而 `complete` 从 4 分掉到 2 分"——那是一条线索。

### 自愈 ≠ 重试

`judgeOne` 在输出不合法时会回灌自愈：

- `retry`：同一个请求再发一次，治网络抖动；
- 自愈：改了输入再发一次，治输出格式不对。

把后者当成前者，会得到"同一个坏格式被要了三遍"——三次都会是坏的。

自愈上限是 2 次（重试 1 次）：格式错通常一次就能改对；改不过来的模型再问十次也不会。

## 26.7 诚实的射程

当前评测集只有 3 条用例（`internal/eval/cases.jsonl`）：

1. `baseline-3p`：完整流程、3 页、至少 1 条发现、含"行业现状"；
2. `expect-mismatch`：故意期望 5 页——用来证明判据会红；
3. `short-topic`：短主题、不含 panic/undefined。

模型是离线替身，Judge 是替身（按内容长度给分）。

所以：

- 它测的是骨架：流程有没有走完、产物齐不齐、成本/步数有没有漂；
- 它测不出"这句 Prompt 写得更好"——那需要真实模型；
- 它测得出"改了 Prompt 之后，流程与成本变了"。

`go run ./cmd/l4` 默认会退出 1，因为 `expect-mismatch` 是故意的失败。

`go run ./cmd/l4 -tag=smoke` 只跑两条 smoke 用例，应该 2/2 通过。

> 一个永远 100% 的评测，和一个永远 0% 的评测一样可疑。
> 保留一条"必红"的自测用例，证明汇总真的在算。

## 26.8 对照 Eino / 框架

框架通常不提供评测：

- LangSmith / Langfuse 提供 trace 和数据集；
- Eino 有评估相关能力，但判据仍然要你写；
- "什么算通过"永远是业务问题。

评测框架能给你：

- 数据集管理；
- 指标聚合；
- 报告。

但它不能替你回答：

- 期望是什么；
- 硬判据和软判据怎么分工；
- 软判据要不要影响 pass/fail；
- 跑不完的用例算不算失败。

先自己做，再看 `answers/26-参考答案.md`。


```powershell

```

- 它通过了吗？
- 如果失败，是哪一个判据？
- 报告里有没有说清期望和实际？

### 练习 2：空期望

加一条 `expect:{}` 的用例。

回答：

- `Validate` 会拒绝吗？
- 如果不拒绝，会发生什么？
- 为什么"永远绿"比"永远红"更危险？

### 练习 3：注入失败用例

```powershell
$env:L4_BAD_CASE="1"; go run ./cmd/l4
```

回答：

- 成功率从多少变成多少？
- 这个注入证明了什么？
- 为什么"临时注入"比"常驻一条必红用例"更强？

### 练习 4：软判据自愈

```powershell

```

回答：

- 第一次软判据输出了什么？
- 自愈后有没有成功？
- 如果只在最终输出看，你怎么知道它自愈过？

### 练习 5：步数口径

把 `metricsOf` 里的 `Layer` 过滤去掉，只数全部 `KindStart`。

跑一次 `go run ./cmd/l4 -tag=smoke`。

回答：

- `max_steps` 会报多少？
- 为什么和"4 个节点"对不上？
- 这个 bug 应该在哪一层修（指标、事件、还是期望）？

## 26.10 拓展：加一条空期望

给 `cases.jsonl` 加一条 `expect:{}` 的用例，看 `Validate` 怎么拒绝。然后把它删掉。

这个实验能让你记住：一个永远绿的用例，比一个永远红的用例更危险。红会被修，绿会被信任，而它什么都没验证。
