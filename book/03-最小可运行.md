# 第 3 章 最小可运行：150 行 Agent

上一章只发了一次请求。真实任务通常要走几步：查完再写，写完再改。这一章把一次调用变成循环，并且只保留最必要的零件。

## 3.1 目标

上一章我们停在"只调用一次"的坏版本：模型请求了工具，程序执行了，但没有把结果放回去。

这一章补上循环，得到一个真正能完成多步任务的 Agent。验收标准只有三条：

1. 模型可以连续请求多个工具；
2. 每次工具结果都能回到上下文；
3. 循环有明确的终止条件，不会无限跑。

配套代码在 `book/code/ch03/`。整个目录约 560 行，其中真正决定行为的核心循环不到 70 行。剩下的都是类型定义、两个工具和一个用来演示的 Mock。

## 3.2 文件地图

先看目录，不要急着读全部：

| 文件 | 作用 | 建议阅读顺序 |
|---|---|---|
| `agent.go` | 核心循环：调用模型、执行工具、回灌结果、终止 | 1 |

## 3.3 核心循环

下面是 `book/code/ch03/agent.go` 的骨架，去掉日志和错误包装：

```go
history := []Message{{Role: "user", Content: input}}

for step := 1; step <= a.MaxSteps; step++ {
    resp, err := a.Client.Generate(ctx, LLMRequest{
        Messages: history,
        Tools:    a.Tools.Definitions(),
    })
    if err != nil {
        return "", err
    }
    if resp.FinishReason == "length" {
        return "", fmt.Errorf("输出被截断")
    }

    if len(resp.ToolCalls) == 0 {
        return resp.Content, nil
    }

    history = append(history, Message{
        Role:      "assistant",
        Content:   resp.Content,
        ToolCalls: resp.ToolCalls,
    })

    for _, tc := range resp.ToolCalls {
        result, execErr := a.Tools.Execute(ctx, tc.Function.Name, tc.Function.Arguments)
        if execErr != nil {
            result = fmt.Sprintf(`{"ok":false,"error":%q}`, execErr.Error())
        }
        history = append(history, Message{
            Role:       "tool",
            ToolCallID: tc.ID,
            Name:       tc.Function.Name,
            Content:    result,
        })
    }
}

return "", fmt.Errorf("达到最大步数 %d", a.MaxSteps)
```

逐段解释：

### 第一段：历史从一条 user 消息开始

```go
history := []Message{{Role: "user", Content: input}}
```

模型没有记忆。`history` 就是它这次能看到的全部上下文。后面每执行一次工具，`history` 都会变长——这就是"上下文会增长"的物理原因。

### 第二段：调模型，拿"下一步"

```go
resp, err := a.Client.Generate(ctx, LLMRequest{Messages: history, Tools: a.Tools.Definitions()})
```

注意每次调用都重新传 `history` 和 `Tools`。模型不会记得上一轮，它只是基于你这次给它的全部消息，决定下一步。

### 第三段：先处理"截断"

```go
if resp.FinishReason == "length" {
    return "", fmt.Errorf("输出被截断")
}
```

这一步很容易被忽略。`finish_reason=length` 意味着模型说到一半被截断了，后面的 JSON 很可能不完整。如果你不在这里拦住，它会伪装成"模型不会写 JSON"，让你在错误的方向上排查很久。

### 第四段：自然终止

```go
if len(resp.ToolCalls) == 0 {
    return resp.Content, nil
}
```

模型不再请求工具，说明它认为可以给最终答案了。这是自然终止。

### 第五段：把 assistant 的请求放回历史

```go
history = append(history, Message{Role: "assistant", Content: resp.Content, ToolCalls: resp.ToolCalls})
```

这一行是第 2 章练习 3 的答案。没有它，后面的 `tool` 消息就没有"对应的请求"，协议就断了。

### 第六段：执行工具，把错误变成数据

```go
result, execErr := a.Tools.Execute(...)
if execErr != nil {
    result = fmt.Sprintf(`{"ok":false,"error":%q}`, execErr.Error())
}
```

工具报错时，程序不崩，而是把错误包成一条 JSON 结果，回灌给模型。模型看到 `ok=false` 和 `error`，有机会自己修正参数。

这是一个很重要的设计选择：错误是数据，不是异常。 第 7 章会讲哪些错误该回灌、哪些不该。

### 第七段：追加 tool 消息

```go
history = append(history, Message{
    Role:       "tool",
    ToolCallID: tc.ID,
    Name:       tc.Function.Name,
    Content:    result,
})
```

`tool_call_id` 必须和模型请求的 ID 一致。一个 assistant 消息里可能有多个 tool_call，每个结果都要带自己的 ID，否则模型会配错。

### 第八段：硬上限

```go
for step := 1; step <= a.MaxSteps; step++ { ... }
return "", fmt.Errorf("达到最大步数 %d", a.MaxSteps)
```

自然终止是"模型说完了"；硬上限是"模型没说够，但我不让你继续了"。

两者不是一回事。 自然终止是正确性；最大步数是成本与死循环的保险。不能拿最大步数当正确性保证，也不能因为有了自然终止就不要保险。

## 3.4 三个边界，缺一不可

### 边界一：最大步数

如果没有最大步数，而模型一直请求工具，会发生什么？

- 循环永远不结束；
- 每一次都花钱；
- 如果工具还有副作用（写文件、发请求），副作用会不断重复。

在 Mock 里你可以安全地试：把 Mock 改成永远返回一个 tool_call，再把 `MaxSteps` 设成 0（代码里会归一成 6），观察它跑到第 6 步报错。真实模型上不要做这个实验，除非你盯着账单。

### 边界二：工具错误

如果工具错误直接 `panic` 或向上抛，用户会看到什么？

- 整个任务失败；
- 模型没有机会修正参数；
- 你失去了"模型自愈"这个能力。

但也不是所有错误都该回灌。比如 API Key 错了、工具根本没注册，这些是运行时/配置错误，回灌给模型它也无能为力，反而会让它反复重试。第 7 章会给出一条可操作的分类。

### 边界三：输出截断

`finish_reason=length` 不是"模型不会写"，是"输出没写完"。

这两者的修复方式完全不同：前者要改提示词或换模型，后者要加长 `max_tokens` 或让它分段输出。不区分，就会一直在错误的地方修。

## 3.5 跑起来

### 先跑 Mock

```powershell
go run ./book/code/ch03
```

不需要 API Key。预期输出：

```text
模型: mock（离线，无需 API Key）

--- step 1 ---
tool get_weather({"city":"北京"})
  -> {"city":"北京","condition":"晴","ok":true,"temperature":22}
tool get_weather({"city":"上海"})
  -> {"city":"上海","condition":"多云","ok":true,"temperature":26}

--- step 2 ---
tool save_note({"title":"天气笔记","content":"北京 22 度晴；上海 26 度多云。"})
  -> {"file":"out/note-天气笔记.md","ok":true}

--- step 3 ---

===== 最终回复 =====
已完成：查询了北京和上海的天气，并保存为 out/note-天气笔记.md。
```

注意 step 1 里**一个 assistant 消息带了两个 tool_call**。这不是两次模型调用，是一次调用返回了两个请求。运行时逐个执行，然后一次性把两条 `tool` 消息放回去。

打开 `out/note-天气笔记.md`，你应该能看到刚才保存的内容。

### 再跑真实模型

```powershell
$env:MULTIAGENT_LLM="openai"
$env:OPENAI_API_KEY="sk-..."
go run ./book/code/ch03
```

真实模型的行为可能和 Mock 不一样：

- 它可能先查北京，再查上海，分成两步；
- 它可能跳过 `save_note`，直接回答；
- 它可能把 `city` 写成 "Beijing"；
- 它可能调用一个不存在的工具。

这些差异才是真实的。 Mock 只能验证代码路径，不能验证 Agent 好不好用。第 26 章会把这件事变成可量化的评测。

## 3.6 对照仓库的 L0

现在打开 `internal/agent/agent.go`，找到 `RunWithMessages`（大约在第 213 行）。你会看到同一个骨架：

- `history` 从传入的消息开始；
- `for step := 0; step < a.MaxSteps; step++`；
- 调 `a.Client.Generate`；
- 没有 tool_call 就返回；
- 有 tool_call 就执行、追加、继续。

仓库的版本多了四样东西：

| 多出来的东西 | 位置 | 为什么 |
|---|---|---|
| 重试 | `internal/agent/agent.go:257` | 模型调用失败可能是一次网络抖动，重试这一次调用，而不是重跑整个循环 |
| 事件 | `internal/agent/agent.go:230`、`306` | 让外部能看见每一步发生了什么 |
| 预算上报 | `internal/agent/agent.go:268` | 每次模型调用后把 token 记到账上 |
| 统计派生 | `internal/agent/agent.go:189` | `Stats()` 从事件里数，而不是另存一份 |

它没有多出来的核心逻辑：循环还是那个循环。仓库之所以看起来复杂，是因为它在循环外面加了工程能力，而不是因为循环本身有魔法。

再看三处：

- `internal/tool/tool.go:60`：`Tool` 接口只有 `Definition` 和 `Execute` 两个方法。
- `internal/message/message.go:28`：消息模型只有四个角色和两个工具字段。
- `cmd/l0/main.go:44`：L0 的装配就是一个 Registry、一个 Client、一个 Agent。

**你现在写的这一版，和仓库的 L0 是同一个东西的不同工程化程度。** 这句话很重要：后面看到更复杂的模块时，不要被吓住，先找它的"核心循环"在哪里。

## 3.7 这一版还缺什么

这不是一个"完整"的 Agent。它缺的东西，正好是后面每一章的主题：

| 缺什么 | 会在哪一章补 | 现在没有会导致什么 |
|---|---|---|
| 重试、超时、错误分类 | 第 7 章 | 一次网络抖动就让整个任务失败 |
| 结构化产物 | 第 8 到 11 章 | 多角色交接时丢字段 |
| 多 Agent 编排 | 第 12 到 16 章 | 只能一个人干完所有事 |
| 图编排、HITL、持久化 | 第 17 到 22 章 | 长任务无法恢复，无法让人确认 |
| 事件、脱敏、预算、评测 | 第 23 到 27 章 | 不知道花了多少钱，也不知道改得好不好 |

不要现在就把它们全加上。 每加一个，你都要能说出"它解决了当前版本的哪个具体故障"。说不出来，就说明还没到需要它的时候。

## 3.8 关于"ReAct"这个名字

仓库把这个循环叫 ReAct。严格说，这一版更像 tool-calling loop：模型返回工具请求，运行时执行，循环继续。

ReAct 的原意是 Reasoning + Acting：模型先写出推理，再采取行动，再根据观察继续推理。工程上，很多"ReAct"实现并不强制模型输出显式的推理文本，只要有"行动—观察—再行动"的循环，就被叫作 ReAct。

这个区别不影响你现在写代码，但会影响你面试时的表述。第 6 章会把两种模式拆开讲：**什么时候需要显式推理，什么时候只需要工具调用。**

### 练习 1：加第三个工具

给 `book/code/ch03/tools.go` 加一个 `word_count` 工具：

- 输入：`{"text": "..."}`
- 输出：`{"ok":true,"characters":N,"words":M}`

然后在 `main.go` 注册它，把用户输入改成"统计'多智能体系统'这几个字的长度，并保存成笔记"。

观察：模型会不会主动调用它？它是在 `save_note` 之前还是之后调用？

### 练习 2：把最大步数改成 1

把 `MaxSteps` 改成 1，再跑 Mock。会发生什么？

提示：第 1 步会执行工具，但循环在第 1 步结束，模型没有机会给出最终答复。

这个练习的目的是让你分清："执行了工具"不等于"完成了任务"。

### 练习 3：让工具报错

把用户输入改成"查火星的天气"，再跑真实模型（Mock 不会理解错误）。

观察：

- 模型看到 `ok=false` 后，会修正参数、换城市，还是重复调用？
- 它重复了几次？
- 如果一直重复，最大步数有没有拦住它？

这个练习没有标准答案，但它是第 7 章"错误回灌与重试"的引子。

### 练习 4：打印完整历史

在 `Agent.Run` 返回之前，把 `history` 逐条打印出来（role、content 前 80 字、tool_call_id）。数一数：

- 一共几条消息？
- 其中几条是 assistant，几条是 tool？
- 如果任务有 10 步，历史会有多长？

这个数字会在第 4 章和第 7 章反复出现。

## 3.10 拓展：让循环少一步

把 `save_note` 的调用从 Mock 里删掉，只保留天气查询，再跑一次。循环仍然会结束，但产物没了。

这说明“循环结束”和“任务完成”不是一回事。这一章先不修它；第 16 章会用 `Shortfall` 正式处理“做了一半”的情况。现在你只要记住：模型不再请求工具，只代表它不想再调工具了。
