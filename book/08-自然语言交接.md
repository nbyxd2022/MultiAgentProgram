# 第 8 章 自然语言交接为什么会丢字段

单个 Agent 的错误边界补上了，两个角色之间的问题却不一样：上游的话传到下游，还是原来的意思吗？

## 8.1 一个丢字段的场景

假设你有两个角色：

- `research`：查资料，输出研究结论；
- `outline`：根据研究结论，生成三页大纲。

`research` 返回了一段很自然的总结：

```text
我找到了三条趋势：
1. 新能源汽车渗透率已达 35%，预计 2027 年突破 50%；
2. 动力电池成本两年内下降 40%，进入 0.5 元/Wh 区间；
3. 公共充电桩保有量同比增长 46%，但区域分布不均。
```

`outline` 的 Prompt 是："根据上游研究，生成三页大纲。"

它可能输出：

```text
第一页：行业趋势
第二页：成本变化
第三页：基础设施
```

三个数字全没了，还多了一个"基础设施"这种模糊概括。

这不是模型"不听话"。这是自然语言交接的必然结果：

1. 上游没有规定字段，所以下游不知道哪些信息必须保留；
2. 下游要做压缩，而压缩就会丢细节；
3. 没有任何代码能检查"三个数字是否都还在"。

如果这是一次性写作，丢一点细节无所谓。但多 Agent 系统里，`outline` 的产物会继续传给 `designer`、`renderer`，每传一次都可能再丢一层。**错误会沿着链路累积，而没有任何一层能发现。**

## 8.2 自然语言交接的四种损失

### 损失一：字段丢失

上游有 `penetration=35%`，下游只写了"渗透率提升"。字段没了。

### 损失二：字段漂移

上游写"同比增长 46%"，下游写成"增长接近一半"。数值被改写，精度丢了。

### 损失三：字段虚构

上游没有"基础设施"这个结论，下游为了凑三页，自己编了一个。这是最危险的一种：它看起来合理，但无法追溯来源。

### 损失四：定位丢失

评审说"第二条有点空"，但生成器重新生成后，"第二条"可能已经变成另一条。反馈无法定位到具体字段，返工就变成"再写一版看看"。

这四种损失，靠"把 Prompt 写得更严格"只能缓解，不能根治。因为自然语言没有 schema，也没有提交点。

## 8.3 只让模型输出 JSON，还不够

很多人的第一反应是："那我让它输出 JSON 不就行了？"

这比自然语言好，但还不够。你会遇到：

- 模型用 Markdown 代码块包住 JSON；
- 字符串里有未转义的引号；
- 输出被 `max_tokens` 截断，JSON 不完整；
- 字段名拼错、少一个必填字段；
- 模型在 JSON 前后加一句"这是结果："；
- 模型把数组写成字符串。

这些问题，第 9 章的 `llmjson` 会处理一部分（提取、修复），但解析成功不等于语义正确。一个 `{"issues": []}` 可能是"检查过了，没问题"，也可能是"我根本没检查"。

所以仓库用了更强的一层：用工具收结论。

## 8.4 L1 的答案：`submit_review`

打开 `internal/agents/critic.go`。

Critic 不让模型"在最终回复里写评审结论"，而是给它一个工具：

```go
registry.Register(newSubmitReview(collector))
```

工具定义在 `internal/agents/critic.go:239`：

```text
submit_review
  issues: [
    { level: "major" | "suggestion",
      field: "bullets[2]" | "title",
      message: "错在哪",
      fix: "怎么改" }
  ]
```

模型必须调用这个工具，把结论放进 `issues`。代码拿到的不是一段文本，而是：

```go
[]schema.Issue{
    {Level: "major", Field: "bullets[1]", Message: "...", Fix: "..."},
}
```

这带来四个好处：

### 好处一：字段名和类型是契约

`level` 只能是 `major` 或 `suggestion`；`field`、`message`、`fix` 都是必填。模型不能再"自由发挥"。

### 好处二：有明确的提交点

`reviewCollector` 有一个 `submitted` 标志（`critic.go:227`）。评审结束后，代码检查：

```go
if !collector.submitted {
    return ..., fmt.Errorf("模型没有调用 submit_review，评审未完成")
}
```

这条检查解决了一个非常危险的问题：把"没发现问题"和"没做检查"混为一谈。

如果只看最终文本，模型说"整体不错"，你无法判断它是真的检查过，还是根本没看。`submitted` 把这两种情况分开了。

### 好处三：语义校验可以在代码里做

`submitReview.Execute`（`critic.go:299`）做了三件事：

1. `level` 必须是合法值，拼错会被拦住；
2. 拒绝 `blocker`：致命问题只能由硬判据产出，模型不能自己升级严重度；
3. `message` 和 `fix` 不能为空：没有"错在哪"和"怎么改"，这条反馈就不可执行。

这些校验如果只写在 Prompt 里，模型迟早会违反；写在代码里，违反会变成一条错误回灌，模型有机会修正。

### 好处四：反馈可以被定位

`field` 字段让"第二条有点空"变成 `bullets[1]`。生成器拿到的是可定位的修改指令，而不是一段需要重新理解的散文。

> 注意：`field` 目前在 schema 里是必填，但 `Execute` 只做了 `strings.TrimSpace`，没有拒绝空字符串。这是一个真实的小缺口，第 8.7 节的练习会让你补上。

## 8.5 从 L1 到 L2：提交口的通用化

L1 的 `submit_review` 只服务 Critic。到了 L2，四个角色（research / outline / designer / renderer）都需要提交结构化产物。

仓库没有复制四份 `submit_review`，而是抽出了 `internal/agents/submit.go`：

- `SubmitSpec`（`submit.go:34`）：工具名、描述、参数、解码函数；
- `SubmitTool`（`submit.go:50`）：收 JSON → 校验 → 交给调用方；
- `Submitted()`：区分"提交了空结论"和"从没提交"；
- `Overwrites()`：记录"新结论替换旧结论"的次数。

四个角色共用一套提交纪律，差异只在 `SubmitSpec`。这就是"把差异压成数据"。

再往上，是 `schema.Artifact` 信封（`internal/schema/artifact.go:165`）：

```go
type Artifact struct {
    Key        string
    Kind       Kind
    Version    int
    ProducedBy string
    Summary    string
    Shortfall  []string
    BasedOn    []Basis
    Payload    json.RawMessage
}
```

它解决的是下一层问题：产物怎么在黑板里流转、怎么带版本、怎么表达缺口、怎么记录血缘。第 10 章会专门讲。

这里先记住一个原则（`artifact.go:21`）：

> **handoff 只传 `{ref, summary}`，不传 payload 全文。**

上下文里只放"决策所需的最小信息"；要全文的人，自己拿 ref 去黑板取。这既省 token，也避免"每个下游都复述一遍全文"导致的漂移。

而 `Summary` 是代码派生的，不是模型自述的（`Payload.Summarize`）。模型写的摘要可能说谎，代码从结构化字段投影出来的不会。

## 8.6 "结构化"的真正含义

三种交接方式，强度不同：

| 方式 | 可解析 | 可校验 | 有提交点 | 失败可回灌 |
|---|---|---|---|---|
| 自然语言 | 否 | 否 | 否 | 否 |
| 文本 JSON | 有时 | 靠代码 | 否 | 解析失败可以 |
| 工具 + schema | 是 | 是 | 是 | 是 |

所以"结构化 handoff"不是"让模型输出 JSON"这么简单，它至少包含：

1. 一个 schema：字段名、类型、必填、枚举；
2. 一个提交点：模型必须显式调用工具，代码才知道"它交了"；
3. 一层校验：类型之外，还要检查语义（level 合法、message 非空）；
4. 一条回灌通道：校验失败时，把错误告诉模型，让它改。

少了第 2 条，你无法区分"没检查"和"没问题"；少了第 3 条，合法 JSON 也可能是脏数据；少了第 4 条，模型第一次写错就永远错了。

## 8.7 对照 Eino / LangGraph

你用过 Eino 的 State，应该见过"节点之间传一个 typed struct"。LangGraph 也鼓励用 TypedDict / Pydantic 定义 State。

但框架只提供放类型的位置，不强制你使用它。你仍然可以：

- 在 State 里放一个 `string` 字段，让下游自己解析；
- 让模型在节点里输出一段自然语言，再塞进 State；
- 跳过校验，直接把模型输出当结构体用。

所以，框架解决的是"状态怎么传"，不解决"状态里放什么"。**后者才是多 Agent 系统真正的设计工作。**

一个可以带走的判断：

> 如果两个角色之间的接口，无法用一个 struct 写出来，那说明你还没想清楚要传什么。

## 8.8 练习

先自己做，再看 `answers/08-参考答案.md`。

### 练习 1：把一段 prose 变成 struct

把 8.1 的研究结论变成一个 Go struct：

```go
type Research struct {
    Findings []Finding
}
```

要求：

- 每条 finding 至少包含 `claim`、`evidence`、`source`；
- 数字类结论必须有 `metric` 和 `value`；
- 哪些字段必填？哪些可以空？
- 如果上游没有来源，应该允许空，还是直接拒绝？

先写 struct，再写一个 `Validate` 函数。不要急着写 Prompt。

### 练习 2：补上 `field` 的非空校验

`submit_review` 的 schema 说 `field` 必填，但 `Execute` 里没有拒绝空字符串。

在 `internal/agents/critic.go` 的 `Execute` 里补上：

```go
field := strings.TrimSpace(raw.Field)
if field == "" {
    return "", fmt.Errorf("issues[%d].field 不能为空：没有定位，生成器不知道改哪里", i)
}
```

然后构造一条 `field: ""` 的提交，确认它会被拒绝并回灌。

### 练习 3：让模型提交一个缺字段的 JSON

用 `ScriptedClient` 或手写一个 Mock，让 `submit_review` 收到：

```json
{"issues":[{"level":"major","message":"第二条太空","fix":"补数据"}]}
```

缺 `field`。观察：

- `Execute` 会报什么错？
- 错误回灌后，模型有没有机会补上？
- 如果没有机会（Mock 只返回一次），系统最后是"评审完成"还是"评审未完成"？

### 练习 4：模型摘要 vs 代码摘要

假设产物是：

```json
{"pages":[{"title":"趋势","bullets":["渗透率 35%","成本下降 40%"]}]}
```

让模型写一句摘要，再让代码从结构体生成摘要：

```go
fmt.Sprintf("%d 页：%s", len(pages), pages[0].Title)
```

构造一个"模型摘要说谎"的例子（比如它说"3 页"，实际只有 1 页），说明为什么 `Summary` 要由代码派生。

### 练习 5：设计一个 `submit_outline`

给 `outline` 角色设计提交工具：

- 3 页，每页有 `title` 和 `bullets`；
- `bullets` 是字符串数组，不能是"平行数组"；
- 页数不对要报错；
- 每页标题不能为空。

写出 `[]tool.Parameter` 的形状，并说明：为什么用"对象数组"，而不是三个平行数组？

## 8.9 拓展：把两次交接并排看

让两个角色先用一段自然语言交接，再把同一份内容改成 struct。把两次的最终产物并排贴出来，圈出丢掉的字段。

这个对比不用跑模型也能做：你手写两版中间产物即可。做完你会更清楚，“结构化”不是为了好看，而是为了让丢字段这件事能被发现。
