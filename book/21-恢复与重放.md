# 第 21 章 中断恢复：decision 重放与幂等

中断存下来了，可恢复不是“从游标往后跑”，而是“再读一次状态”。这一章看 decision 重放、幂等和版本兼容。

## 21.1 三个崩溃窗口

人在 HITL 里回答了"修改第二页"，系统开始重做。假设进程在这三个时刻崩掉：

```text
A. 回答刚收到，还没落盘
B. 回答已落盘，还没开始执行
C. 已经开始执行，还没跑完
```

分别会发生什么？

### 窗口 A：回答没落盘

磁盘上还是"未回答"。重启后系统会再问一遍。

这是最差的一种，但无法完全避免——除非落盘本身成功。`Resume` 的第一步就是落盘，正是为了把窗口缩到最小。

### 窗口 B：已回答，未消费

磁盘上是"已回答未消费"（`Pending.Decision` 非 nil）。

重启后 `Run` 会自动读到这个决定，重放它。用户不会被再问一遍。

### 窗口 C：执行到一半

这是最微妙的一种。

`drive` 在开始执行前，会把内存里的 `Pending` 清掉；但落盘发生在节点执行之后。所以如果节点执行到一半崩了：

- 磁盘上仍然是"已回答未消费"；
- 重启后会重放这个决定；
- 那个节点会被再执行一遍。

> **恢复是 at-least-once，不是 exactly-once。**

这是本章最重要的一句话。理解它，你才知道哪些操作可以放心重放，哪些必须自己做幂等。

## 21.2 "重放"不是额外机制

`Resume`（`runner.go:347`）的顺序：

```text
① 读 checkpoint，检查还能不能恢复
② 校验回答
③ 把回答写进 Pending.Decision，落盘
④ drive
```

`drive` 一开头：

```go
if st.Pending != nil && st.Pending.Decision == nil {
    return StatusInterrupted
}
st.Pending = nil
```

它只清内存；磁盘上的 Pending 要等下一次 persist 才消失。

如果这期间崩了，磁盘上仍是"已回答未消费"，下次 `Run` 再读一次，继续重放。

所以源码里说：

> **"重放"不需要任何额外机制——它只是"再读一次状态"。**

没有"恢复队列"、没有"事件回放器"、没有单独的 resume 状态机。状态本身就是恢复的依据。

## 21.3 三种意图的重放语义

### confirm

confirm 是无副作用的。

中断的那一跳已经把产物写进黑板了；confirm 之后，`CanSkip` 跳过它，调度往下走。

重复重放 confirm，结果一样。这是最安全的一种。

### revise

revise 会强制重做中断的那一跳，并把 Note 交给它。

如果重做跑到一半崩了，重启会再重做一遍：

- 节点可能产出新版本；
- 如果节点内部有副作用（写文件、发请求、扣款），副作用会重放；
- 仓库没有通用的幂等键机制。

所以 revise 的重放安全，取决于节点是否幂等。

### abort

abort 只是停止推进，重复执行也没有副作用。

## 21.4 幂等由谁负责

Runner 不提供通用的"去重"能力。它只保证：

- 已完成的节点会被 `CanSkip` 跳过；
- 中断决策会被重放；
- 每个节点跑完后落盘。

它不保证：

- 节点内部副作用只执行一次；
- 重放时不会产生重复版本；
- 外部系统不会收到重复请求。

所以：

> **能在节点内部做成幂等的，就在节点内部做；不能的，要在业务上接受"至少一次"。**

例如：

- `render_slide_html` 写同名文件，重复写是覆盖，近似幂等；
- 发邮件、扣款、创建订单，不是幂等的，需要业务侧的幂等键；
- 纯计算节点，天然幂等。

这不是仓库的缺陷，而是分布式系统的常识：**exactly-once 很难，at-least-once + 幂等更现实。**

## 21.5 输入一致性：同一个 run id 不能配两个输入

`load`（`runner.go:742`）会检查：

- checkpoint 里的 topic 与本次调用的 topic 一致；
- hints 一致（从 v2 起）。

如果不一致：

```text
run l3-demo 记录的主题是 "A"，但这次调用传的是 "B" ——
同一个 run id 配不同的输入等于两件事共用一个身份（血缘会串）。
```

为什么不能"自动接受新主题"？

- 黑板上会混着两次不同输入产生的产物；
- 血缘判据会认为它们是同一条链；
- 你无法区分"上游更新了"和"换了一个任务"。

正确做法是**在图上新增一版 `topic`**，让 `StaleReasons` 把下游标脏——而不是换一个调用参数。

### v1 的兼容窗口

v1 的快照没有 `hints` 字段。`load` 不会拿 v2 的规则去校验它，而是发一条 `KindNotice`：

```text
这份快照是 v1（没有 hints 字段）—— 本次不做输入一致性校验。
```

为什么不迁移（给 v1 补上本次 hints）？

因为那会把"我们不知道它之前用的是什么"变成"我们编一个值"，而血缘判据会从此认为全部产物都基于这套 hint——那是一个永久的谎。

**拒绝 ≠ 正确，但它把静默错误变成了显式错误。**

## 21.6 恢复失败的六种分类

`ResumeErrorKind`（`interrupt.go:512`）：

| Kind | 谁的问题 | 处置 |
|---|---|---|
| `not_found` | 对方（引用错了） | 重新开始 |
| `expired` | 时间（业务过期） | 重新开始，但告诉人是过期 |
| `corrupt` | 我们（磁盘/代码） | 重新开始 + 告警 |
| `too_old` | 我们（协议演进） | 重新开始 |
| `from_future` | 我们（部署） | **重试到新实例** |
| `bad_decision` | 对方（答案不对） | **让人改答案，重试** |

为什么分这么细？因为处置完全不同。

把 `from_future` 当成不可重试，会让滚动发布期间的用户看到"请重新开始"，而他其实只需要再点一次。

把 `corrupt` 归成 `bad_decision`，会让一个磁盘故障看起来像用户误操作——于是没有人去查磁盘。

**错误分类不是为了好看，是为了让调用方能选对动作。**

## 21.7 恢复不是"从游标往后跑"

`drive` 里没有游标。恢复时：

```go
if next == "" {
    next = r.graph.Next(st)
}
```

`Graph.Next` 按拓扑序找第一个 `CanSkip` 不通过的节点。

所以恢复后的 `Ran` 列表通常很短——大部分节点被跳过。这是"位置由产物推导"最直观的证据。

`skipped` 还会发一条事件：

```text
已就绪、跳过：research、outline
```

注意它排除了 `plan.Force`（revise 要强制重做的那一跳），否则会打出一句"跳过 outline"，紧接着 outline 就跑了——一句话与行为互相打脸，比没有这句话更糟。

## 21.9 拓展：在两个时刻杀进程

先做一次 confirm，然后在 `Resume` 落盘 decision 之后、`drive` 执行之前杀掉进程；重启，看它会不会重放。再换成 revise，重复一次，看副作用执行了几次。

两次实验的差别，就是“重放决定”和“重放副作用”的差别。前者是设计保证的，后者要靠节点自己做幂等。
