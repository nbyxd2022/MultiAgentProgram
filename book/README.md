# 从零重建一个多 Agent 运行时

> 以 `MultiAgentProgram` 为参考答案，把 L0 到 L4 一层层拆开、重写、验证。
>
> **状态：30 章修订版完成。** 每章都有开场衔接、练习、自检、拓展和下一章过渡；答案在 `answers/`。

## 这本书为谁写

你会 Go，能看懂基本的 HTTP 和 JSON，但没有写过 Agent。你不需要懂 LLM 的内部原理，也不需要先学某个框架。你可能已经把这个仓库跑起来过，甚至读过一部分代码，但合上文件之后，仍然说不清：

- 为什么模型会"调用工具"？它真的执行了工具吗？
- 为什么需要 ReAct 循环？一次调用不够吗？
- 为什么多 Agent 要引入黑板、产物版本、失效传播？
- 为什么图编排比"让模型自己决定"更可靠？
- 为什么断点恢复不能靠一个"当前节点"的游标？

这本书假设你一个都答不上来。它不要求你先读完全部源码；相反，它要求你**先写，再对照**。

> 如果你的情况是"用过 Eino/LangGraph、每天 1 小时"，走 [学习路径 C](./学习路径-C-每天1小时.md)：第 2 章速读，第 3 章精做，后面按 7 周节奏推进。

## 方法只有一条

**不要读仓库，重建仓库。**

仓库是参考答案，不是教材。读答案会产生"我懂了"的错觉；只有自己写出一版会坏的代码，再让它失败，你才会真正需要那个机制。

## 三条原则

1. **先写后读**：每一章先给你一个能跑但有缺陷的版本，你亲手让它失败，再引入机制，最后才看仓库怎么实现。
2. **一次只加一个机制**：每加一个东西，你必须能说出"它解决了上一版的哪个具体故障"。说不出来，就说明还没到需要它的时候。
3. **用真实模型验收**：单测可以用 mock，但每一部分结束必须用真实模型跑一次。mock 只能证明代码路径通，不能证明 Agent 好用。

## 每一章的结构

1. **一个具体故障**：不从概念定义开始，从一个会坏掉的场景开始。
2. **坏版本**：10 到 30 行，能跑，但有缺陷。
3. **让它失败**：用测试或真实模型，把缺陷暴露出来。
4. **机制**：为什么必须这样、代价是什么、否掉了哪些替代方案。
5. **对照仓库**：精确到 `file:line`，看参考实现怎么处理。
6. **练习**：2 到 3 个，其中一个是"删掉这个机制会发生什么"。
7. **小结与自检**：能白板讲清，或能通过一个具体测试。
8. **拓展**：把这一章的机制换一个场景再用一次。不是必做；第一遍可以只读，第二遍再做。
9. **下一章**：指出这一章留下的问题，以及下一章为什么必须存在。

## 环境准备

- Go 1.21 或更高版本。
- 一个 OpenAI 兼容服务的 API Key。第 1 到 2 章不需要；第 3 章开始用它做验收。
- 本书命令以 **PowerShell** 为准。如果你用 Git Bash，把 `$env:X="v"` 换成 `export X=v`。
- 一个记录"我哪里卡住了"的 Markdown 文件。只记结论没有用，要记你当时相信了什么、后来被什么推翻。

设置环境变量的例子（PowerShell）：

```powershell
$env:OPENAI_API_KEY="sk-..."
$env:OPENAI_BASE_URL="https://api.openai.com/v1"   # 用第三方兼容服务时改成对应地址
$env:OPENAI_MODEL="gpt-4o-mini"
```

## 约定

- `file:line` 指向仓库里的真实位置。行号会随代码变化，找不到时按函数名搜索。
- "坏版本"是故意写错的，不要直接用于生产。
- 每章末尾有练习、自检和拓展。参考答案在 `answers/`，先自己做，再对照；拓展没有标准答案。
- 仓库注释不全是真理。我们已经发现过注释与实现矛盾的地方；书里会教你怎么验证，而不是让你背结论。
