# 第 4 章 消息协议：角色、顺序与上下文

循环能跑起来，但消息顺序一直没有被认真检查过。一旦工具结果写错角色，模型就会把“观察”当成“新指令”。这一章把消息协议拆开。

## 4.1 一个真实的 bug

假设你在写一个天气 Agent，消息列表长这样：

```json
[
  { "role": "system", "content": "你是一个天气助手。" },
  { "role": "user", "content": "北京今天天气怎么样？" },
  {
    "role": "assistant",
    "content": "",
    "tool_calls": [
      {
        "id": "call_bj",
        "type": "function",
        "function": { "name": "get_weather", "arguments": "{\"city\":\"北京\"}" }
      }
    ]
  },
  { "role": "user", "content": "{\"temperature\":22,\"condition\":\"晴\"}" },
  { "role": "assistant", "content": "北京今天 22 度，晴。" }
]
```

看起来"对话很顺"，但协议是错的：工具结果被写成了 `user` 消息。

模型会怎么理解？它看到的是"用户又发了一条消息，内容是 `{"temperature":22}`"。它可能：

- 把这段 JSON 当成用户的新指令；
- 问"你给我的这串数据是什么意思"；
- 或者勉强猜出这是天气结果，但下一次就不一定了。

正确的写法是把这条消息的 `role` 改成 `tool`，并带上 `tool_call_id`：

```json
{
  "role": "tool",
  "tool_call_id": "call_bj",
  "name": "get_weather",
  "content": "{\"temperature\":22,\"condition\":\"晴\"}"
}
```

这个 bug 的危险之处在于：它有时候能跑通。 模型很擅长"猜"，所以你可能在一个简单任务上看不出问题；换个复杂任务，它就会把工具结果和用户指令混在一起。

## 4.2 四种角色，分别是谁在写、谁在读

| 角色 | 谁写 | 谁读 | 关键点 |
|---|---|---|---|
| `system` | 运行时/开发者 | 模型 | 设定身份、约束、工具使用规则；不展示给最终用户 |
| `user` | 用户或上层运行时 | 模型 | 表达"这次要做什么" |
| `assistant` | 模型 | 运行时/模型 | 可能带 `tool_calls`；运行时负责执行 |
| `tool` | 运行时 | 模型 | 必须带 `tool_call_id`，与某次调用配对 |

角色不是 UI 标签，是协议字段。 模型靠它判断"这句话是谁说的、该不该当成指令"。

一个常见的误区：把工具结果写成 `assistant` 消息，觉得"这是系统自己说的话"。这同样会破坏协议：模型会以为"我刚刚已经说过这个结果了"，从而跳过对结果的引用。

## 4.3 五条顺序规则

这五条不是 OpenAI 独有的，绝大多数 function calling 协议都类似。记住它们，后面调试会快很多。

### 规则一：`system` 放在最前

可以有零条或一条。放在最前，模型才能把它当成"全局设定"，而不是"对话中的某一句话"。

### 规则二：`tool` 消息必须跟在那条 assistant 之后

模型发出 `tool_calls` 的那条 assistant 消息，必须先出现在历史里；工具结果才能跟在它后面。

如果你把 assistant 消息省掉，只放一条 `tool` 消息，协议就断了：模型不知道这个结果对应哪个请求。

### 规则三：每个 `tool_call` 都要有且只有一条结果

一个 assistant 消息里可以有多个 `tool_call`：

```json
{
  "role": "assistant",
  "tool_calls": [
    { "id": "call_bj", "function": { "name": "get_weather", "arguments": "{\"city\":\"北京\"}" } },
    { "id": "call_sh", "function": { "name": "get_weather", "arguments": "{\"city\":\"上海\"}" } }
  ]
}
```

你必须返回两条 `tool` 消息，每条带自己的 `tool_call_id`。少一条，下一轮协议就不完整；多一条没有对应调用的，就是"孤儿"。

建议保持与 `tool_calls` 相同的顺序。虽然很多服务端只按 ID 配对，不强制顺序，但保持顺序能让日志和调试更简单。

### 规则四：`tool_call_id` 必须严格一致

不要自己生成 ID，也不要把 ID 截断、转小写、加前缀。ID 是模型和服务端用来配对的，改一个字符就可能配错。

如果你的系统里有多轮并发调用，ID 还可能重复出现在不同轮次里。配对时要看"当前这条 assistant 消息里的 ID"，不能全局搜。

### 规则五：不要把工具结果写成 `user` 或 `assistant`

这是 4.1 的 bug。工具结果只有一个合法角色：`tool`。

如果你确实想对模型说一句"这是工具结果，请基于它回答"，那应该放在 `content` 里，而不是改变角色。角色是协议，不是语气。

## 4.4 领域模型 vs 线格式

现在打开仓库里的两个文件：

- `internal/message/message.go:29`：`Message` 结构体。
- `internal/llm/openai.go:121`：把 `message.Message` 转成 `oaiMessage`。

你会看到两套很像、但不完全一样的类型。

### 领域模型（domain model）

```go
type Message struct {
    Role       Role       `json:"role"`
    Content    string     `json:"content,omitempty"`
    ToolCalls  []ToolCall `json:"tool_calls,omitempty"`   // 扁平：ID / Name / Arguments
    ToolCallID string     `json:"tool_call_id,omitempty"`
    Name       string     `json:"name,omitempty"`
}
```

这是整个系统内部使用的消息模型。它的特点是扁平：`ToolCall` 直接有 `ID`、`Name`、`Arguments`。

### 线格式（wire format）

```go
type oaiMessage struct {
    Role       string        `json:"role"`
    Content    string        `json:"content,omitempty"`
    ToolCalls  []oaiToolCall `json:"tool_calls,omitempty"`
    ToolCallID string        `json:"tool_call_id,omitempty"`
}
```

而 `oaiToolCall` 是嵌套的：

```go
type oaiToolCall struct {
    ID       string `json:"id"`
    Type     string `json:"type"`
    Function struct {
        Name      string `json:"name"`
        Arguments string `json:"arguments"`
    } `json:"function"`
}
```

### 为什么要分成两套？

三个理由，每个都很实际：

1. 换服务商时，只改适配器。

OpenAI 的工具调用是嵌套的 `function` 对象；Anthropic、Gemini 的形状不同。如果领域模型直接长成 OpenAI 的样子，换服务商时你会改遍整个系统。

2. 领域模型可以表达"更稳定的概念"。

领域模型关心的是"谁说了什么、要调哪个工具、参数是什么"；线格式关心的是"某个厂商的 JSON 怎么摆"。两者的变化频率不同，应该分开。

3. 空值和缺失值需要适配。

OpenAI 在工具调用时可能返回 `content: null`；Go 的 `string` 表达不了 `null`，`omitempty` 会直接省略这个字段。大多数兼容服务接受省略，但少数服务要求显式 `null`。这类细节必须由适配器处理，不能污染领域模型。

### 代价是什么？

多一层转换，就多一处可能出错的地方。

仓库的 `internal/llm` 覆盖率明显偏低（我上一次实测是 15.7%，你可以本地复测），这是全书里最值得补测试的包之一。因为它的错误不是"逻辑不对"，而是"协议没对上"：`arguments` 没转、tool_calls 丢了、`finish_reason` 没传出来。**这类错误在单测里最容易抓到，在真实调用里最难查。**

> 你用过 Eino，应该见过它的 `schema.Message` 和各种 `Model` 适配器。那就是同一个模式：**领域模型稳定，适配器隔离厂商差异。**

## 4.5 上下文是怎么变长的

每执行一个工具，历史里就多两条消息：

```text
assistant(tool_calls) + tool(result)
```

一个 10 步的任务，如果每步调用 2 个工具，历史至少有：

```text
1 条 system + 1 条 user + 10 条 assistant + 20 条 tool = 32 条消息
```

而且 `tool` 消息的 `content` 可能很大：一整页 HTML、一份完整 JSON、一段搜索结果。下一轮调用时，这些内容会全部重新发给模型。

粗略算一笔账：

- 每条工具结果 2,000 token；
- 20 条就是 40,000 token；
- 如果每一轮都重发，10 轮就是 400,000 token 的输入。

这就是为什么后面需要：

- 预算守卫（第 25 章）：知道花了多少，什么时候该停；
- 产物引用（第 14 章）：黑板里存完整内容，上下文里只传 `key@version`；
- 上下文裁剪（第 7、22 章）：哪些消息可以丢，哪些绝对不能丢。

### 裁剪的五条底线

1. `system` 不能丢。
2. 当前用户目标不能丢。
3. 最近一次工具结果不能丢——模型正在用它。
4. 与最近工具结果配对的 assistant `tool_calls` 不能丢。
5. 不能留下"有调用、没结果"的半截协议。

在这五条之外，旧的工具结果可以摘要、可以替换成引用、可以丢弃。先保证协议完整，再谈省 token。

## 4.6 练习：写一个消息校验器

这一章不写新 Agent，写一个校验器。它会在你后面调试多 Agent 交接时反复救命。

函数签名：

```go
func Validate(messages []message.Message) error
```

至少检查：

1. `role` 只能是 system / user / assistant / tool；
2. `tool` 消息必须有 `tool_call_id`；
3. 每条 `tool` 消息必须能匹配到"当前未完成"的某个 `tool_call`；
4. 每个 `tool_call` 最终都要有结果；
5. 在进入下一条 assistant/user 消息之前，未完成的 tool_call 必须清零（严格模式）。

这个校验器不需要接模型，纯函数，最适合写单测。

写完之后，拿 4.1 的错误消息列表跑一遍，确认它能报错；再拿正确的列表跑一遍，确认它能通过。

参考答案在 `answers/04-参考答案.md`。

## 4.7 对照 Eino：框架替你做了什么

你用过 Eino，可以带着这个问题读：

> Eino 的 `schema.Message` 和它的 OpenAI 适配器，分别对应仓库里的哪两个类型？它有没有替你检查 tool_call 的配对？

大概率是：

- 有领域模型（`schema.Message`）；
- 有适配器（把领域模型转成厂商格式）；
- 但配对检查、上下文裁剪、工具结果保留策略，仍然是你（或你的编排层）的责任。

框架能保证"协议不出错"，但不能保证"上下文不爆"。这两件事要分开看。

## 4.8 拓展：角色是最便宜的约束

把一条 `tool` 消息的角色改成 `user`，接真实模型跑一次，看看它把这段内容当成“工具结果”还是“用户的新指令”。没有 API Key 也没关系：写一个 20 行的校验器，专门拦“孤儿 tool 消息”，效果一样。

这个实验比读十遍协议更能让你记住：角色不是 UI 标签，是模型判断“谁在说话”的依据。
