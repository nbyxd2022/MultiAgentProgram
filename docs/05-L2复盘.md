# 05 · L2 复盘：多 Agent 编排的问题、风险与改进方向

> 这是"教学循环"的第 ③ 步：**复盘**。
> 对象是刚刚跑通的 L2：
> `cmd/l2` + `internal/agents/{subagent,supervisor,submit,research,outline,designer,renderer}.go`
> + `internal/schema/artifact.go` + `internal/state/blackboard.go`。
>
> 目的不是否定它，而是回答一个问题：
> **一个"能让四个角色协作、并且只传引用不传正文"的系统，离"敢让它跑在真实需求上"还有多远？**

---

## 0. 先看它做对了什么

复盘容易只盯着缺点，但要先确认哪些决策是**对的**，因为它们是后面所有阶段的地基：

| 决策 | 位置 | 为什么正确 |
|---|---|---|
| **Agent 之间只传 `{ref, summary}`，正文不进上下文** | `schema.Handoff` / `subagent.go` | 直接废掉企业仓库 A2/A3 那条路：**编排者即使想搬数据，也无处可搬** |
| **每个角色暴露成一个工具** | `subagent.go` `subAgentTool` | "路由"= 从有限集合选一个动作 = 工具调用。**路由合法性、结构化决策、确定性回传，三样全白拿** |
| **依赖由 `Needs()` 声明、由代码强制** | `subagent.go` `missingNeeds` | P3 的治本：顺序约束**想违反也违反不了**（已用 `L2_SKIP_ORDER` 实证） |
| **黑板追加不覆盖 + `key@version` 引用** | `state/blackboard.go` | 引用**不可变**；返工/重试/回放才有意义 |
| **黑板进出深拷贝** | `blackboard.go` `cloneArtifact` | 它是唯一的跨 Agent 可变共享状态，不拷贝必出"我明明没改它"的幽灵 bug |
| **提交出口统一（`SubmitTool`）：没提交 ≠ 没问题** | `agents/submit.go` | 与 L1 的 `Critic` 同一条底线；且覆盖不累加，避免分数虚高 |
| **无来源的断言进不来** | `agents/research.go` `decodeResearch` | L1-5 的落点：**可验证性是数据结构问题，不是 Prompt 问题** |
| **版式是枚举，目录是唯一真相来源** | `schema/layout.go` | 自由文本进不来；加一个版式 = 加一行，校验与 Prompt 自动同步 |
| **renderer 不调模型** | `agents/renderer.go` | 零 token、确定性、可复现；**内容只被压缩一次** |
| **渲染并发但结果按索引写回** | `renderer.go` `renderAll` | 并发不乱序 → 输出稳定、可 diff、可回归 |
| **"部分成功"是合法产物 + 写盘前预检** | `schema.RenderResult` / `checkFileConflicts` | 交付能交付的 + 说明为什么缺；有副作用就先预检 |
| **事件形状与 L0 完全一致** | `renderer.go` `emit` | `internal/agent` 从 L0 之后**一行未改**，L1/L2 全程复用 |

**记住这些。** 它们是从 L2 到 L4 要一直保留的骨架。

## 0.5 一个被实验推翻的假设（方法论）

写这份复盘时，我先读代码提出过一个"真 bug"假设：

> `agent.go` 里 `a.stats.Steps = step + 1`（**覆盖**），而 `a.stats.PromptTokens += ...`（**累加**）
> → 两个字段语义不一致 → `supervisor.go` 的 `total = addStats(total, sup.Stats())`
> 在第二轮会把第一轮的 token **重复累加一次**。

推理看起来无懈可击。于是我写了一个临时测试实测：

```
Run #1 之后: {Steps:1 ToolCalls:0 PromptTokens:64 CompletionTokens:16}
Run #2 之后: {Steps:1 ToolCalls:0 PromptTokens:64 CompletionTokens:16}
```

**PromptTokens 还是 64，不是 128。** 因为 `RunWithMessages` 开头有一行：

```go
	a.stats = Stats{}     // agent.go:112
```

**每次 Run 重置统计** —— `Stats()` 的语义（"最近一次运行"）是自洽的，`supervisor` 的累加是对的。

> ### 教训
> **从局部代码片段读出来的结论，必须回到完整上下文验证。**
> 我读到了 `+=` 却没读到前面那行 `= Stats{}` —— 因为它们隔了 40 行。
>
> 而且这个错误有个**具体的代价**：如果我没做实验，这份复盘里会多出一条
> **不存在的 bug**，后续会花时间去"修"一个没坏的东西，甚至把正确的代码改坏。
>
> → 从现在起，复盘里每一条"真 bug"都必须**附上复现证据**（日志 / 测试 / 输出），
> 没有证据的降级为"待验证的怀疑"。

## 1. 问题清单

### L2-1 · ⭐ 核心问题：黑板缺少"新鲜度/血缘"概念——产物可能早已过期，但没人知道

这是本轮挖到的**最重要、也最隐蔽**的问题。它不是一个"写错了"的 bug，而是**语义缺口**。

#### 现象

看 `subagent.go` 的装配输入：

```go
// collectInputs 把已就绪的前置产物收成 handoff 列表（只有 ref + summary）。
func (t *subAgentTool) collectInputs() []schema.Handoff {
	needs := t.sub.Needs()
	out := make([]schema.Handoff, 0, len(needs))

	for _, k := range needs {
		a, err := t.board.Get(string(k)) // ← 取最新版
		if err != nil {
			continue
		}
		out = append(out, schema.HandoffOf(a))
	}
	return out
}
```

`board.Get(string(k))` 语义是 **"取该 key 的最新版"**（`ParseRef` 里 `version == 0` 就是"最新"）。

于是这个场景是通的：

```
第 1 轮：outline@1 ──> design@1（design@1 的版式是按 outline@1 的页面做的）
                     └─> render@1

（用户说"第 2 页标题不对，重来"）

第 2 轮：outline 重跑 ──> outline@2   ← 页数没变，但内容变了

现在再调 renderer：
  collectInputs() 取到：outline@2 + design@1
                              ↑            ↑
                        最新的          基于 outline@1 做的（已经过期）

  renderer 的校验：len(design.Pages) == len(outline.Pages)  →  3 == 3  →  通过 ✅
```

**结果：渲染出"outline@2 的内容 + 按 outline@1 意图设计的版式"，而且没有任何一层能发现。**

#### 为什么现有机制拦不住

| 现有机制 | 为什么拦不住 |
|---|---|
| `RenderResult` 校验页数一致 | 只验**数量**，不验**内容血缘**。页数相同就通过 |
| `schema.Decode` 的双向 Kind 校验 | 只验**类型**对不对，不验**版本**新旧 |
| `Artifact.Version` / `RefOf` | 提供了"带版本的引用"，但**装配时用的是不带版本的那种写法** |
| `missingRequired()` | 只问"有没有"，不问"新不新" |

**最讽刺的一点**：我们花了一整个 `blackboard.go` 的注释去强调"带版本引用是不可变的"，
结果在**唯一真正消费引用的地方**（`collectInputs`）把它降级成了"取最新"。
**不可变引用的价值，被装配方式抵消了。**

#### 根因

> **黑板只有"存在性"（有没有）和"可追溯性"（哪一版），缺了"新鲜度"（这一版还是不是最新的依据）。**

一份产物是否"有效"，取决于**它的依据链是否仍然指向当前最新版**。
而我们没有任何地方表达"我依据了谁"。

#### 改进方向

**让"血缘"进数据**（放在信封上，因为它不是业务属性，是**产生这份产物的那次运行的属性**）：

```go
type Artifact struct {
	Key        string
	Kind       Kind
	Version    int
	ProducedBy string
	BasedOn    []string   // ← 新增：我依据了哪些 ref（形如 outline@1）
	Summary    string
	Payload    json.RawMessage
}
```

填充它几乎不要钱 —— `subAgentTool.Execute` 里**本来就有** `collectInputs()` 的返回值：

```go
	inputs := t.collectInputs()
	...
	a, err := schema.NewArtifact(...)
	a.BasedOn = refsOf(inputs)      // 两行
```

于是消费方可以自查：

```
renderer 拿到 design@1 与 outline@2
  design@1.BasedOn == ["outline@1"]
  但上游实际是 outline@2  →  不一致  →  拒绝（或要求先重跑 design）
```

由此可以提炼一条更一般的判据，它就是 L2 版本的 `Deliverable()`：

> ### 判据：新鲜度（Freshness）
> 一份产物**有效**，当且仅当：
> ① 它存在；
> ② **它的 `BasedOn` 链全部指向当前最新版**。

#### 企业仓库对照

企业仓库**没有这个问题** —— 因为它把一次流水线的输入（`PipelineInput.OutlineItems`）
在一次 Run 内**冻结**了，`OutlineItems` 是谁传进来的就是谁，中途不可能变。
要变就整体重跑。

**换句话说：它的简单性来自"没有共享可变状态"，而不是因为它解决了这个问题。**
我们引入黑板（为了支持续跑/返工）才**第一次**面对它 —— 这是"能力换复杂度"的典型案例。

> **判断力**：这不是"我们做错了"。黑板带来的续跑/返工能力，是 L3 的必需品。
> 但要清楚：**每一步能力的引入，都会带来一个必须补上的语义**。

### L2-2 · 【真 bug】"产物存在" ≠ "产物完整"（L1-3 的同构变体）

#### 现象

`renderer` 明确支持"部分成功"：

```go
type RenderResult struct {
	Files  []string      `json:"files"`
	Failed []PageFailure `json:"failed,omitempty"`
}
```

但**编排者的终止判断**从来没读过它：

```go
// supervisor.go
func (s *Supervisor) missingRequired() []schema.Kind {
	var missing []schema.Kind
	for _, k := range s.required {
		if s.board.Versions(string(k)) == 0 {   // ← 只看"有没有"，不看"完不完整"
			missing = append(missing, k)
		}
	}
	return missing
}
```

**实测证据**（用 `grep` 全仓搜 `.Failed` 的读取点）：

```
internal/agents/renderer.go     ← 自己构造它
cmd/l2/main.go                  ← 只用来"打印"
```

**全仓没有任何一处"判断逻辑"读 `Failed`。** 它只被打印，不被决策。

#### 后果

```
3 页渲染 → 2 页成功 + 1 页写盘失败
  → render@1 入库（含 Failed）
  → missingRequired() 看到 Versions("render")==1  →  认为 render 已完成
  → Result.Complete() == true
  → cmd/l2 打印「必需产物齐全」
```

**用户拿到一个"齐全"的结论，但少了一页。**

#### 为什么这是"最危险的一类 bug"

因为它的表现是**一切正常** —— 除了少一页。
这和我们刚在 L1-3 修掉的那个 bug **结构完全一样**：

| | L1-3 | L2-2 |
|---|---|---|
| 表面 | "评审通过" | "必需产物齐全" |
| 实际 | 语义质量**从未被检查** | 一页**从未被渲染** |
| 根因 | 把"没做检查"当成了"没问题" | 把"有产物"当成了"产物完整" |
| 共性 | **用了一个更弱的判据，去代替一个更强的判据** | 同 |

> ### 提炼
> **"存在"、"沉默"、"没有报错" —— 这三样都不是"完成"。**
> 凡是"默认通过"的设计，都藏着一个假阴性。

#### 改进方向

让**产物自己知道它完不完整** —— 这与 `Kind()` / `Summarize()` 是同一个理由
（"我是什么"、"我该怎么被摘要"、"我完不完整"都是**产物自己的知识**）。

```go
// Partial 是可选能力：产物知道自己有没有留下缺口。
//
//	不实现它  = 产物要么完整、要么不存在（Research / Outline / Design 都是这一类）
//	实现它    = 产物可能"部分成功"，调用方必须知道缺口在哪
type Partial interface {
	// Shortfall 返回未完成的部分（空 = 完整）。
	Shortfall() []string
}
```

`RenderResult` 实现它；`Supervisor` 在 `missingRequired` 之外再查一次；
`Result.Complete()` 两个条件都要满足。

**注意这是一个"可选能力"** —— 和 `statsReporter`（`cmd/l2` 里那个）一样，
用类型断言探测，**不要往 `Payload` 主接口里塞**（接口要小，见 R23 ⑥）。

### L2-3 · 成本会**少算**：子 Agent 的统计只留最后一次运行

#### 现象

```go
// research.go / outline.go / designer.go 都是同一个写法
	if _, err := a.Run(ctx, prompt); err != nil { ... }
	r.lastStats = a.Stats()          // ← 覆盖
```

而 `agent.Stats()` 的语义是**最近一次运行**（`agent.go:112` 每次 Run 重置）。

`cmd/l2` 的成本汇总在**最后**统一读一次：

```go
	for _, s := range subs {
		if r, ok := s.(statsReporter); ok {
			st = r.Stats()          // ← 只拿到"最后一次"
		}
		...
	}
```

#### 后果

如果某个角色**跑了两遍**（编排者补缺、返工、重试），它的 token **只算最后一遍**。

> **这个 bug 恰好会在"需要返工"的时候最严重** ——
> 也就是成本最高的那一次运行，我们反而算得最少。

#### 为什么算是"真 bug 而不是设计选择"

因为 **supervisor 那一行是累加的**（`total = addStats(total, sup.Stats())` 每轮都加），
而子 Agent 这一行是覆盖的。**同一个成本汇总表里，两行用两种口径。**

#### 改进方向

统一口径：**要么都记"最近一次"，要么都记"累计"**。
正确做法显然是**累计**（成本是"这一趟总共花了多少"），
所以应当把累加逻辑收进 Agent 内部（加一个 `TotalStats()`，
或者让 `Stats()` 返回累计 + 另给 `LastRunStats()`）。

**根因**：`Stats` 的语义没有在**类型层面**被钉死，只写在注释里。
→ 与 L1-2 的根因同类：**语义只存在于人的脑子里，代码就无法自洽。**

---

### L2-4 · 【潜在 race】各 SubAgent 的 `lastStats` 没有并发保护

`ResearchAgent` / `OutlineAgent` / `Designer` 的 `lastStats` 字段
被 `Run` 写、被 `Stats()` 读，**没有任何锁**。

当前**不会**出事 —— 因为编排者是串行的（一次只派一个角色）。
但两个很近的将来会踩到：

1. **P12 的下一步**：让编排者一次并行派多个无依赖角色；
2. `subAgentTool` 是**共享实例**（同一个 tool 对象被注册一次、被反复调用）。

（`Renderer` 有锁，但那是为了 `observer` 的并发安全，不是为 `lastStats`。）

**改进方向**：把统计收进 `internal/agent`，用 `atomic` 或锁保护；
或者在 `SubAgent` 层面定义"每次 Run 返回自己的 Stats"，**从设计上取消共享可变字段**（更优）。

### L2-5 · 编排者**跨轮没有记忆**

`agent.Agent.RunWithMessages` 每次都 `history := make(...)`（新的）。
所以 `supervisor.go` 里这个循环：

```go
	for round := 1; round <= supervisorRounds; round++ {
		prompt := taskPrompt(topic)
		if missing := s.missingRequired(); len(missing) > 0 {
			prompt = reminderPrompt(topic, missing)
		}
		sup.Run(ctx, prompt)
	}
```

**第 2 轮开始时，编排者完全不记得第 1 轮做过什么** —— 它只知道"缺什么"。

#### 这是优点还是缺点？

**两面都有，必须说清楚：**

| 好的一面 | 坏的一面 |
|---|---|
| 天然缓解 P1（上下文不跨轮膨胀） | 模型无法从"上一轮为什么失败"中学到东西 |
| 每轮状态都从**黑板**重建 → 不存在"上下文与真实状态不一致" | 如果某轮失败的原因是"顺序搞错了"，第 2 轮很可能**再错一次** |

#### 结论

这是一个**可接受的设计**（黑板是唯一真相来源，比"上下文里记一份、黑板里记一份"安全得多），
但要意识到代价：**跨轮的"经验"没有任何载体**。

→ 改进方向（L4 的老问题）：把"失败原因"也写进黑板（`Failure` 产物 / `Issue`），
让下一轮能读到 —— 这样既保持"上下文从黑板重建"的干净，又不丢经验。

### L2-6 · 没有 HITL：用户中途既看不到、也改不了

#### 现象

一次 `go run ./cmd/l2` 从头跑到尾，用户**唯一能干预的时刻是"之前"（给主题）和"之后"（看结果）**。
典型场景完全做不到：

- "大纲给我看一眼，第 3 页换成建议";
- "版式别用 data，换成 comparison";
- "素材不够，再搜两轮"。

而 L2 恰恰产出了**最适合人工确认的中间产物**（3 页大纲、3 个版式）——
只要一个"暂停/确认"机制，产品的可用性会完全不同。

#### 企业仓库对照：`tools/localtools/follow_up.go`（R7，本轮精读）

它的做法**非常值得学**，而且和我们的两条既有原则高度一致：

```go
func FollowUp(ctx context.Context, input *FollowUpToolInput) (string, error) {
	wasInterrupted, _, storedState := tool.GetInterruptState[*FollowUpState](ctx)

	if !wasInterrupted {
		info := &FollowUpInfo{Questions: input.Questions}
		state := &FollowUpState{Questions: input.Questions}
		return "", tool.StatefulInterrupt(ctx, info, state)      // ← 中断
	}

	isResumeTarget, hasData, resumeData := tool.GetResumeContext[*FollowUpInfo](ctx)
	if !isResumeTarget {
		return "", tool.StatefulInterrupt(ctx, info, storedState)
	}
	if !hasData || len(resumeData.UserAnswers) == 0 {
		return "", fmt.Errorf("tool resumed without a user answer")   // ← ★ 见下
	}
	...
}
```

**四处值得记住：**

| # | 观察 | 与我们的关系 |
|---|---|---|
| 1 | **中断被表达成"工具的返回"**，不是异常、不是特殊控制流 | 与我们的"错误也是数据"同源：**中断也是一种数据** |
| 2 | **同一个函数被调用两次**：第一次抛出中断并存 state，恢复时重进同一函数 | "恢复"不是重放，而是**带着答案重进同一跳** —— 幂等键就是"位置"本身 |
| 3 | `schema.Register[*FollowUpInfo]()` —— 序列化要**注册具体类型**（Go 接口反序列化的硬需求） | 这正是 01 索引里 **F1** 隐患的来源：**类型改名 → 旧 checkpoint 无法恢复** |
| 4 | **恢复了但没有答案 → 直接报错**，而不是把空答案当合法输入 | ⭐ 与 L1-3 一模一样的底线：**"恢复到一半" ≠ "用户确认了"** |

第 4 条特别值得注意：**企业仓库在这件事上做对了**（fail loud），
而我们 L1 曾经在这里栽过一次（L1-3）。值得记住这个正面样本。

#### 我们的差距 + 难度

我们**没有任何中断/恢复机制**：

- 没有"可以暂停的位置"概念（一次 Run 是一个黑盒）；
- 黑板在内存里，进程一停就没了（→ L2-7）；
- 没有"恢复时的输入通道"。

**这不是小改动** —— 它需要 ① 持久化 ② 恢复语义 ③ 中断的表达。
→ **L3 的核心目标**。

### L2-7 · 黑板在内存里；磁盘上仍然同名覆盖

- **黑板**：`byKey map[string][]Artifact`，纯内存。**进程一挂，四份产物全丢。**
  而"多 Agent + 多轮"恰恰意味着"跑到一半的损失更大"（L1 时只丢一页，L2 丢整条链）。
- **磁盘**：`out/l2/slide-<标题>.html` 仍是同名覆盖。
  L2 只是把目录隔离了（挡住 L0/L1 互相覆盖），**没有解决"同一角色重跑覆盖"**。

#### 我们的临时补丁与它的边界

L1 交付时"把 best-so-far 重渲染一遍"来保证"交付版本 = 磁盘版本"。
L2 **连这个补丁都没有** —— 如果 `renderer` 跑两遍，磁盘上只剩第二遍的结果，
而黑板上的 `render@1` 声明的却是第一遍的文件路径（**路径相同，内容已换**）。

> 这里又出现一次"无名的不一致"：**黑板说的文件 ≠ 磁盘上的文件**。
> 与 L2-1（内容与版式错配）是**同一类问题：我们的引用能力，跑在了存储能力前面。**

→ L3：checkpoint 持久化 + 版本化文件名 / 幂等键。

### L2-8 · 编排是"中心化串行"，表达不了并行与条件

#### 现象

一次只有一个角色在跑。但 L2 的产物依赖图里其实**本来就有可并行的部分** ——
比如 `designer` 与（若存在的）"配图/文案"角色都可以只依赖 `outline`。

更要紧的是**条件边**表达不了：

```
素材不足 → 回头再搜一轮
版式与页数不匹配 → 重跑 designer
渲染失败 → 只重跑失败的那一页
```

这些**今天全靠 Prompt 里的"请继续调度对应角色"**（一句建议）。

#### 企业仓库对照

它有**两套**编排范式并存：

| 范式 | 位置 | 特点 |
|---|---|---|
| Supervisor（自主路由） | `agent_helper/supervisor.go` | 灵活，但顺序不可保证、不可测 |
| Graph（确定性 DAG） | `v5_html_ppt_agent/graph.go` | `classify → (plan ∥ style) → render`，**边由代码连** |

而且这正是 01 索引里 **G** 记的隐患：**两套范式并存，缺统一抽象**。

**结论**：我们迟早也要有"图"。区别是我们**已经知道为什么需要它**（条件边 + 并行 + 可测），
而企业仓库是"长出来的"。→ **L3 的核心目标之二**。

### L2-9 · Mock 更自欺了

L0 的 Mock：损失"Prompt 质量验证"。
L1 的 Mock：损失"评审能力验证"（Critic Mock 在做字符串匹配）。
L2 的 Mock：**多了一层"编排合理性"的损失**。

具体来说，这个 Mock：

```go
		case hasTool(req, nameResearch) && hasTool(req, nameRenderer):
			return supervisorTurn(req)
```

它按**工具集**判别角色 —— 这验证了"角色 = 人格 + 工具集"这个机制，
但**完全无法验证**：

- 真实模型会不会**选错角色**（该搜不搜就渲染）？
- 真实模型会不会**乱序**（L2_SKIP_ORDER 是我们手写的，不是在观察它）？
- 真实模型在收到"前置产物未就绪"之后，**会不会真的纠正**？

第 3 条尤其关键 —— 那是 P3 治本能否成立的**唯一验证点**，而我们的 Mock 是"我告诉它要纠正"。

#### 改进方向

① 至少跑一次真实模型，记录"它有没有按顺序来"；
② 做**失败注入**：让 Mock 在被拒绝后**故意不纠正**（模拟"模型学不会"），
观察 `supervisorRounds` 与最终交付语义是否仍然正确 —— 这是 L4 评测的雏形。

---

### L2-10 · 编排没有总预算

一次编排最多可能发生：
`supervisorRounds(3) × supervisor MaxSteps(12) × 4 个角色各自的 MaxSteps(4~6)` 次模型调用。
**没有任何总步数 / 总 token / 总时长 / 总成本的上限。**

L2 已经比 L1 更危险一档：L1 最坏是 8×，L2 的乘数结构是**嵌套的**。

（我们 **有** 成本汇总 —— 这是 L1-6 的成果。但 **统计 ≠ 限制**。）

**企业仓库对照**：01 索引 **C1** —— 它也**没有**全局预算
（`RunnerConfig` 无 `MaxStep`，`controller/chat.go:275` 循环无上限），
并且已经出现了对应的现象（S3：请求卡死 / 计费暴涨）。

**→ 这是 L4 的核心目标，而且我们比企业仓库更有条件做对**（我们已经有统一的 `Stats`）。

---

### L2-11 · 二次提交被**静默**覆盖

`submit.go` 的约定是"覆盖而非累加"（R8 定下的，为了防止同一问题算两遍）。
这个取舍本身是对的，但：

```
模型第 1 次提交：5 条发现
模型第 2 次提交：2 条发现（它以为在"补充"）
  → 最终只存 2 条，**没有任何提示**
```

**"覆盖"是一个决策，不该是一次事故。** 至少应该：

- 要么**拒绝**第二次提交并说明"已经提交过了"（回灌，模型可自愈）；
- 要么**接受并记录**"本次覆盖了 N 条"（可观测）。

**这与 L1-3 是同一条**：不要让一个重要的事实只存在于"没发生"里。

## 5. 决策：L2 阶段"现在改"还是"留到后面改"

**不要现在全改。** 但有两类必须立即处理：

### 立即改（真 bug / 极低成本）

| 编号 | 改什么 | 成本 | 状态 |
|---|---|---|---|
| **L2-2** | `Artifact` 增加可选 `Partial` 能力；`Supervisor.Complete()` 同时看"存在"与"完整"；`RenderResult` 实现它 | 很小（一个可选接口 + 两处判断） | ✅ **R25** |
| **L2-3** | 统一 Stats 口径（累计），并让 `cmd/l2` 的成本汇总与之自洽 | 小 | ✅ **R25** |
| **L2-11** | `SubmitTool` 的二次提交：接受，但**让事实可见**（回执 + 计数） | 小 | ✅ **R25** |

> 实现时对 L2-11 的方案做了**微调**：复盘里给的是"要么拒绝、要么记账"，
> 实际选定"**接受 + 可见**"。理由是：拒绝会让"修正"这条合理路径死掉，
> 而我们**分不清**"补充"与"修正"（`Execute` 看到的是一样的）。
> **分不清意图时，"可见"优于"禁止"。**（详见 R25 ④.4）

### 顺带改（④ 改进的核心目标）

| 编号 | 改什么 | 为什么是核心 | 状态 |
|---|---|---|---|
| **L2-1** | `Artifact.BasedOn []Basis`（血缘进信封）+ 消费方/编排方的**新鲜度校验** | 它是 L2 唯一一个"语义缺口"级别的问题；**不解决它，L3 的返工就是在制造静默错配** | ✅ **R26** |

> 实现时对方案做了两点调整（详见 R26 ③）：
> ① `BasedOn` 用 **key+version 的结构**而不是 `"outline@1"` 字符串 ——
>    字符串要先解析再比较，而"格式"与"解析"分处两地必然漂移；而且漂移的方式是
>    "永远认为新鲜"，即**永远不报错**；
> ② 遍历改成**后序**（先深入上游、再报自己），让输出列表**天然就是可执行的修复顺序** ——
>    第一版"查到就报"的顺序会导致模型先做一件注定被拒的事。

### 留到对应阶段

| 编号 | 阶段 | 说明 |
|---|---|---|
| L2-4 / L2-5 / L2-10 | **L4** | 并发统计、跨轮经验、预算 |
| L2-6 / L2-7 / L2-8 / L2-12 | **L3** | HITL、持久化、图编排 |
| L2-9 | 立即（非代码） | **接一次真实模型，记录它有没有按顺序来** |
| P1（被放大） | L2/L4 | 精读 R2 `buildSupervisorHistoryRewriter` 后再定 |

### 一个"要不要现在接 Critic"的判断

L1 做了 Critic，L2 **没有把它接进链路**。为什么先不接？

1. L2 的目标是**编排机制**，不是质量——混在一起会让两边都说不清；
2. L2 的产物是**结构化的**（`Slide` / `Outline` / `Design`），
   而 Critic 目前只认 `Slide`；
3. 更要紧的是：**在 L2-1（血缘）没修之前接 Critic，评审的可能是一份"错配"的产物** ——
   先修地基。

→ **接 Critic 放在 L3**（和返工一起，那时才真的需要它）。
