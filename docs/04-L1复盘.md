# 04 · L1 复盘：评审-返工闭环的问题、风险与改进方向

> 这是"教学循环"的第 ③ 步：**复盘**。
> 对象是刚刚跑通的 L1 Demo：
> `cmd/l1` + `internal/agents/critic.go` + `internal/schema/*` + `internal/tools/layout_check.go`。
>
> 目的不是否定它，而是回答一个问题：
> **一个"能自己发现问题并返工"的系统，离"值得信任"还有多远？**

---

## 0. 先看它做对了什么

复盘容易只盯着缺点，但要先确认哪些决策是**对的**，因为它们是后面所有阶段的地基：

| 决策 | 位置 | 为什么正确 |
|---|---|---|
| **硬判据交给代码，软判据才交给 LLM** | `tools/layout_check.go` / `agents/critic.go` | LLM 只做它不可替代的那部分；机械判断零成本、确定性、可测 |
| **评审结论是结构化清单，不是分数** | `schema/issues.go` | 分数不可执行、会被刷分；清单可执行、可计数、可排序 |
| **硬判据由代码采集并注入，不让模型搬运** | `critic.go` `Review` / `buildReviewPrompt` | 直接规避企业仓库 A2/A3 的坑 |
| **用工具收结论**（`submit_review`） | `critic.go` | 把"结构化"从文本约定升级为**契约约定**；解析失败还能回灌自愈 |
| **"没做检查" ≠ "没问题"** | `critic.go` `reviewSoft` | 拒绝把"沉默"当作"通过" |
| **best-so-far，而不是最后一版** | `schema/issues.go` `Best[T]` | 返工可能震荡，最后一版经常不是最好版 |
| **超限 ≠ 失败**（降级交付 + 说明） | `cmd/l1` `deliver` | 保住已经算出来的成果，不因超限全盘丢弃 |
| **约束只有一个来源**（`schema` 常量） | `schema/slide.go` | Prompt / 工具描述 / 检查器三处同源，不可能自相矛盾 |
| **产物由工具交出**（`LastSlide`） | `render_slide.go` | 同样是"不让模型搬数据"，且是 L2 黑板的最小版本 |

**记住这些。** 它们是从 L1 到 L4 要一直保留的骨架。

## 1. 问题清单

### L1-1 · 返工粒度太粗：一条要点有问题，整页重写 ⭐核心问题

- **现状**：`reworkPrompt` 要求 Generator 重新调用 `render_slide_html`，**输出完整的一版**。
- **后果**：
  1. **浪费**：改 1 条要点，重生成 5 条；
  2. **可能改坏**：原来对的 4 条被重新采样，可能变差（**回归**）。
     `best-so-far` 只能兜住"整体变差"，兜不住"局部被打坏"；
  3. **震荡的根源**：每轮都在重新掷骰子，而不是"定点修复"。
- **关键观察**：我们的 `Issue` 里**已经有 `Field`**（`bullets[2]` / `title` / `bullets`）——
  也就是说，"哪些问题是可定位的"这个信息我们已经拿到了，却没用上。
- **改进方向**：**按"可定位性"分流**：
  - 有精确定位的（`bullets[2]`）→ **局部修复**（改那一条，其余原样保留）
  - 只有整体定位的（`bullets` / 空）→ 整体重写
- **企业仓库对照**：`layout_guard_quickfix.go`（确定性局部修复）vs `layout_guard_repair.go`（LLM 修复）——
  它也在问同一个问题：**什么时候用便宜的确定性修复，什么时候才动用昂贵的 LLM 修复。**

### L1-2 · 【真 bug】停止条件判"停滞"时丢掉了严重度，"假停滞"会提前终止 ⭐

看这段代码：

```go
// cmd/l1/main.go
switch {
case !rep.HasHardIssue():
	stopReason = "已没有致命/严重问题"
case prev != nil && rep.HardCount() >= prevReport.HardCount():
	stopReason = fmt.Sprintf("严重问题数没有下降（%d → %d），判定为停滞", ...)
}
```

`HardCount()` 只数 `blocker + major` **的条数**，把严重度丢了。于是：

| 上一轮 | 这一轮 | HardCount 比较 | 实际 |
|---|---|---|---|
| 3 × blocker（总分 9） | 3 × major（总分 6） | 3 >= 3 → **判停滞** | **明明是巨大进步** |

**致命问题全部消灭、总分 9→6，却被判成停滞，直接停止返工。**

- **根因**：我们**有**正确的比较函数 `schema.Report.BetterThan()`（先比加权总分，再比硬问题数），
  但编排层没用它，改用了一个更弱的自造判据。
  → **"造了正确的工具，却在调用处用错了"**，这是最典型的架构级失误。
- **修法**：直接用 `rep.BetterThan(prevReport)`，或者更稳妥地改成
  **"连续 K 轮 best 没有被刷新"** 才判停滞（比较对象从"上一轮"换成"历史最好"）。

### L1-3 · 【真 bug】评审失败的"静默降级"——刚立的规矩在编排层被打破 ⭐

`Critic.Review` 的约定是：**评审失败时返回 (只含硬判据的报告, error)**。
`cmd/l1` 的处理是：打印一行警告，然后**照常继续用那份报告做判断**。

于是这条路径是通的：

```
Critic 超时 / 模型报错
  → rep 只含硬判据（恰好没有硬问题）
  → !rep.HasHardIssue() == true
  → 停止原因："已没有致命/严重问题"
  → 交付！
```

**结果：一个"语义质量从未被检查过"的产物被当成合格品交付，而日志里只有一行警告。**

- **讽刺之处**：我们在 R8 里刚刚立下规矩——**"没发现问题"和"没做检查"必须区分**——
  结果在 R9 的编排层就把它破坏了。**边界约定不传播，规矩就只在自己那一层生效。**
- **修法**：让"评审不完整"成为**可传播的一等状态**（例如 `Report.Incomplete` / `ReviewIncomplete bool`），
  并在交付结论里明确写出来；而不是靠一行 print。
- **更深一层的教训**：**凡是"错误被降级成日志"的地方，都会变成静默假阴性。**

### L1-4 · Critic 与 Generator 同模型 → 相关盲区，事实错误拦不住

- **现状**：两个 Agent 用的是**同一类模型**（Demo 里甚至就是同一套 Mock 思路）。
- **后果**：同模型 = 同训练数据 = **同一个知识盲点**。
  Generator 编了"渗透率已达 35%"，Critic **会倾向于认为它合理**（因为它也会编同样的数）。
- **准确的能力边界**：L1 的 Critic 能拦 **格式 / 结构 / 措辞 / 空洞**，
  **拦不住事实性幻觉**。这不是实现缺陷，是**同模型评审的结构性上限**。
- **改进方向**：分级评审（代码规则 → 同模型 → 异模型），只在关键路径上花异模型的钱。

### L1-5 · 产物里的每个断言都没有"锚点"，无法核对来源

- **现状**：`Slide` 里只有 `Title` 和 `Bullets` 两串文本，**没有来源**。
- **后果**：Critic 即使想核对，也无从下手——它只能凭"感觉像不像真的"。
- **改进方向**：让断言**可引用**（claim → source）。不一定现在做，但要想清楚：
  **"可验证性"不是一个 Prompt 问题，是一个数据结构问题。**
  这也是为什么企业仓库会做"边界检测服务"，而不是靠 Prompt 叮嘱模型。

### L1-6 · 成本链路在 L1 断了：Critic 的 token 没有汇总，也没有预算

- **现状**：L0 会打印 `PromptTokens / CompletionTokens`；
  L1 里 `generator.Stats()` 与 `critic.Stats()` 各算各的，`cmd/l1` **一个都没打印**。
- **后果**：最坏成本从 L0 的 1× 变成 **4 轮 × 2 个 Agent = 8×**，
  而我们**连花了多少都不知道**。
- **改进方向**：先汇总（一行代码的事），L4 再做四维预算。
  **"先能看见，才能管住"** —— 统计先于限制。

### L1-7 · 失败计数与升级链（P6）仍然没有落地

- **现状**：模型提交非法 `level` → 回灌 → 它可能用**完全相同的参数**再试一次 → 直到 `MaxSteps`。
- **后果**：烧步数、烧 token，且没有任何降级动作。
- **此前承诺**：R5 里说 L1 要"顺带落地 P6"，实际**没做** —— 计划与实现脱节，记录在此。

### L1-8 · 返工轮不保证重新搜索（P3 的变体）

- **现状**：Prompt 里写着"先搜索"，但返工轮**没有任何机制**保证它真的搜了。
- **后果**：返工版可能变成"凭空改"，产出比原版更没有依据。
- **本质**：和 P3 一模一样 —— **顺序约束写在哪都不算数，只有代码/图能强制**。→ L3。

### L1-9 · 离线 Mock 更自欺了：Critic Mock 根本不在评审

- **现状**：`newCriticMock` 判断"这一版是不是缺陷版"的方法是
  **看 Prompt 里有没有 `defectBullets[0]` 这段文本**。
- **后果**：我们验证的是"循环接得对不对"，**完全没验证"评审有没有判断力"**。
- **比 L0 更严重**：L0 只损失了"Prompt 质量验证"，L1 损失的是**核心能力本身的验证**。
- **改进方向**：① 至少接一次真实模型并记录结果；② 做**失败注入**：
  让 Mock 故意报假问题，观察系统会不会无限返工 / 会不会正确停住。

### L1-10 · "爆版"是文本层近似，不是真实版面

- **现状**：`layout_check` 检查的是**文字长度**，不是渲染后的**真实排版**。
- **后果**：字数合规 ≠ 版面不溢出（字体、行高、中英混排都会变）。
- **企业仓库对照**：它有独立的"边界检测服务"（`layout_guard_*`），
  我们是"用字数近似布局" —— 便宜、快、会漏。

### L1-11 · 无持久化：崩溃即全丢，且磁盘上只剩最后一版

- **现状**：同名覆盖（`slide-<title>.html`）。
- **后果**：best-so-far 存在内存里 —— **进程一挂，最好的那一版就没了**，
  磁盘上留下的反而是最后的（可能更差的）那一版。
- **我们的临时补丁**（交付时重渲染 best）只解决"本次运行内"的一致性问题，**跨进程无效**。→ L3。

## 3. 主流改进对照

| 我们的问题 | 主流做法 | 对应开源 / 企业实现 |
|---|---|---|
| L1-1 返工粒度粗 | **分级修复**：确定性局部修复 → LLM 局部修复 → 整体重写 | 企业仓库 `layout_guard_quickfix.go` / `layout_guard_repair.go` |
| L1-2 假停滞 | 用**单调性 + 加权分**判收敛；"连续 K 轮 best 未刷新"更稳 | 通用迭代优化实践 |
| L1-3 静默降级 | 把"未完成"做成一等状态，**禁止 error→log 降级** | 通用工程实践（fail loud） |
| L1-4 同模型盲区 | 异模型二次校验 / LLM-as-judge 与生成器解耦 | OpenAI Evals / MetaGPT 评审角色 |
| L1-5 断言无锚点 | 产物带**引用 / 溯源字段**（claim → source） | MetaGPT `artifact repository`；企业仓库边界服务 |
| L1-6 成本失控 | 四维预算 + 成本汇总 | OpenAI Agents SDK guardrails |
| L1-7 无升级链 | retry / fallback / circuit breaker | 企业仓库 `ModelRetryConfig` + fallback 模型 |
| L1-8 流程靠 Prompt | 顺序交给**图编排 / 工具动态授权** | LangGraph；企业仓库 `v5_html_ppt_agent/graph.go` |
| L1-9 Mock 自欺 | 契约测试 + 真实模型冒烟 + **失败注入** | 通用工程实践 |
| L1-10 近似版面 | 渲染后真实几何检测 | 企业仓库 `layout_guard_*` |
| L1-11 无持久化 | checkpoint + 版本化文件名 / 幂等键 | 企业仓库 `store/checkpointstore/` |

## 5. 决策：L1 阶段"现在改"还是"留到后面改"

**不要现在全改。** 但有两个是**真 bug**，必须马上修：

| 立即改（真 bug / 成本极低） | 顺带改（本轮改进核心） | 留到对应阶段 |
|---|---|---|
| **L1-2** 停止条件改用 `BetterThan` / best 单调性 | **L1-1** 分级修复（局部 vs 整体） | L1-4/L1-5 事实锚点 → **L2** |
| **L1-3** "评审未完成"作为一等状态向上传播 | | L1-6 成本汇总 → **L1 顺手 / L4 预算** |
| | | L1-7 失败升级链 → **L4** |
| | | L1-8 流程强制 → **L3** |
| | | L1-11 持久化 → **L3** |

**下一步（④ 改进）的核心目标**：解决 **L1-1（返工粒度）**——
把"整页重写"升级为"**按 `Field` 分流的局部修复**"。
在这个过程中，L1-2 / L1-3 作为 bug 一并修掉。

## 6. 本轮要你回答的问题

1. **L1-2 里我们明明写了 `BetterThan()`，为什么编排层没用它？**
   这类"工具写对了、调用处用错了"的失误，在一个真实项目里应该用什么机制来防？
2. **L1-3 说"凡是错误被降级成日志的地方，都会变成静默假阴性"。**
   请对照 L0 的 `formatToolError`（工具错误**回灌**给模型）——同样是"错误不向上抛"，
   为什么那里是对的，这里就是错的？**区别到底在哪？**
3. **L1-1 的改进方向是"按 `Field` 能不能精确定位来分流"。**
   那么"局部修复"应该由**谁来执行**？是让 Generator 再跑一次 Agent（带着"只改第 2 条"的指令），
   还是**代码直接改**？各自的代价是什么？
