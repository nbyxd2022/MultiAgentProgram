## 1. 🔴 已改（2 条）

### 1.1 节点的 panic 会**杀掉整个进程**（`recover()`：我们 0 处，它 6 处）

**它的做法**（三处边界，同一个形状）：

```go
// internal/grqueue/gr.go —— 协程边界
func RunGrFn(ctx *common.Context, fn func()) {
	go func() {
		defer func() {
			if err := recover(); err != nil {
				stack := util.Stack(3)
				ctx.Logger.WithFields(log.Fields{"crash": true, "stack": string(stack)}).Error(err)
			}
		}()
		fn()
	}()
}

// internal/middleware/recovery.go —— HTTP 边界
	stack := util.Stack(3)
	httprequest, _ := httputil.DumpRequest(c.Request, true)
	ctx.Logger.WithFields(log.Fields{"crash": true, "request": ..., "stack": ...}).Error(err)
	c.AbortWithStatus(500)

// internal/api/api_ai_gateway/api.go:337 —— 外部调用边界
```

**共同点三样**：`crash: true` 是**显式的结构化字段**（不用去 grep "panic" 这个词）、
**带 stack**、**不静默**。

**我们的问题**：全仓 `recover()` = **0 处**。一个节点的 panic
（schema 断言、索引越界、除零）→ **整个 `cmd/l3` 进程崩**。

**为什么在我们的语境下更要紧**：L3 的核心资产恰恰是 **checkpoint** ——
它保证"进程死了能接着跑"。可用户看到的是**一屏栈**，
而不是"第 3 步失败了（这是个 bug），产物都在，可以重试"。

> **能力在，但没人把它翻译成人话。**

**修法**（`internal/graph/runner.go` 的 `callNode`）：recover **只放在一处** ——
**节点调用**。因为工具、模型、schema 断言全都跑在节点**里面**，包住这一处就包住了全部。

⭐ 这一处也说明"家"的选址逻辑（R36 立的判据）：
**不是"哪里可能 panic 就包哪里"，而是"我们的边界在哪"。**

**实证**：

```
$ L3_PANIC=outline L3_RUN=l3-r42 go run ./cmd/l3
[失败] 运行失败: 节点 outline 执行失败（第 1 次）:
       节点 outline 发生 panic（这是一个 bug，不是外部故障；产物与状态未受影响，可以直接重跑）:
       故障注入：这个节点故意 panic 了
goroutine 1 [running]:
panic({0x7ff6fb5210a0?, 0x7ff6fb58b480?})
	C:/Program Files/Go/src/runtime/panic.go:860 +0x13a        ← 栈保留

$ go run ./cmd/l3                                             # 同一个 run，接着跑
      已就绪、跳过：research                                   ← ★ checkpoint 自洽
状态        ：interrupted
```

**② 才是修复的意义** —— panic 发生在节点内，而**状态写入全部由 Runner 控制**
（节点只能读黑板，产出走 `Outcome`），所以崩过一次的 run **仍然能正确地接着跑**。

### 1.2 `Runner` 的 `ctx.Err()` 检查**没有生产者**（`WithTimeout`：我们 0 处，它 45+）

**它的做法**：45+ 处 `WithTimeout` —— 每次模型调用、每次外部请求、每次存储访问；
而 `internal/common/context.go` 把 `WithTimeout` 做成了 `Context` 的**一等方法**。

```go
// agents/v5_html_ppt_agent/single_page_outline_gen_multi.go
	llmCtx, cancel := cctx.WithTimeout(singlePageOutlineGenTimeout)
```

**我们的问题**：`Runner.drive` **一直有**这个检查：

```go
	for {
		if err := ctx.Err(); err != nil {
			return Result{...}, fmt.Errorf("图执行被 context 打断（已完成的产物都在磁盘上，可以直接 Run 恢复）: %w", err)
		}
```

而**全仓 `WithTimeout` / `WithDeadline` = 0 处** ——
也就是说：**那个检查永远不会触发。**

> ⚠️ 这与 L3 复盘抓到的那 6 个半成品是**同一个形状**：声明 ✅ 实现 ✅ **生产 ❌**。
>
> 而它比之前那些**更隐蔽** —— 因为 `context.Context` 是一个**标准接口**，
> 看起来"当然有人会给它一个 deadline"。

我们**只**有 `llm.OpenAIClient` 自己的 HTTP `Timeout`（默认 60s）——
那覆盖了"**单次调用**不返回"，但**不覆盖"整轮跑不完"**：

| | 我们 | 它 |
|---|---|---|
| 单次调用不返回 | ✅ HTTP client 60s | ✅ `WithTimeout` |
| **整轮跑不完** | ❌ —— 只能靠 `MaxSteps`（8 步）兜 | ✅ |

**两者都要有**：`MaxSteps` 防**打转**（步数的界），超时防**慢**（时间的界）。

**修法**（`cmd/l3/main.go`）：加 `-timeout`（默认 5m），并由 `runCtx()` **一处**产生 ——
两条调用路径（主流程 + `-verify`）共用。

约定与 `budget.WithWall` / `InterruptTTL` 一致：**零值 ≠ 不限**，"不限"要显式（写负数）。

**实证**：

```
$ go run ./cmd/l3 -timeout=1ns
[失败] 运行失败: 图执行被 context 打断（已完成的产物都在磁盘上，可以直接 Run 恢复）: context deadline exceeded

$ go run ./cmd/l3 -timeout=-1s
状态        ：completed
```

```go

// V5 HTML PPT 错误分类标准常量，作为**全项目唯一错误类型定义源**。

	// C 类 — 生成结果类
	ErrTypeZeroSuccessPages / ErrTypeSlotGenLLMFail / ErrTypeSlotParseFail / …

// **Controller 层 Prom 上报和 Agent 层日志结构化字段均复用此函数。**
//
// 分类优先级：
//  1. api_ai_gateway.GatewayError 类型判定     ← 最可靠
```

**两件事值得学**：
① **分类是一个一等公民，有一个唯一的函数**，两个消费者（Prom label + 日志字段）**复用它**；
② 分类有**明确的降级顺序**，且**有兜底** —— 而不是"猜不出来就算了"。

**我们**：除了 `graph.ResumeErrorKind`（3 种）之外，**全是裸 `fmt.Errorf`** ——
失败**无法按类型聚合**（"失败率 12%" 回答不了"哪一类最多"）。

**触发条件**：**L4 的评测集/指标落地时**。那时"按 error_type 切片"才第一次有消费者 ——
现在做，就又是一个"没有消费者的能力"。

## 3. 🟢 有理由的偏离 —— **保留**（5 条，附裁决请求）

> ⚠️ 这一节**不是"拒绝改"**。每一条都给出**判据为什么写不出会失败的测试**，
> 如果你判断该改，改它 —— 但理由要一起改掉，别让代码和注释互相打脸。

### 3.1 预算是**累计上限**，不是**滑动窗口**

| | 它 | 我们 |
|---|---|---|
| 模型 | 60 桶滑动窗口 + CAS | 累计上限 |
| 判据 | **时间是不是判据的一部分** | |

**限流**关心**速率**（同一秒 1000 次 vs 一分钟 1000 次，前者要拦）；
**预算**关心**总量**（一秒花完 100 万 和 一年花完 100 万，**前者同样超**）。

> **写不出会失败的测试**：照抄滑动窗口之后，`TestNoLimitMeansUnbounded`
> 之类的用例**照样通过** —— 因为累计上限同样拦得住。差别只在"突发 vs 持续"，
> 而**我们不是服务，没有突发流量**。

### 3.2 观测出口**不挂 ctx**，走显式传参

它的 `tasklog.WithContext(ctx, collector)` 让任意深度的代码取用收集器；
我们一路显式传 `Tracer`。

**判据：谁需要发事件？**
装配层知道的对象（Runner / Node / LLM Client）→ 显式传 ✅（现状）
任意深度的库代码 → 需要通道。

**我们的观测点恰好全是前者** —— 而显式传保住了"数据流可见"（本项目的核心原则）。
**触发条件**（已写在 `observ/tracer.go`）：出现"深层库代码也要发事件"的真实需求时。

### 3.3 不接 OTel / Prometheus

L4 的重点是"**观测模型**"，不是"接哪个后端"。
端口（`observ.Tracer`）定好之后，写适配器是机械工作。

**写不出会失败的测试**：接上它之后，我们的测试**一条都不会变**。

### 3.4 `Decision.Remaining` 不给"最紧的一维"

它的 `CompositeLimiter` 取 `min(Remaining)` —— **但它多个窗口单位相同**（都是"次数"）。
我们的四维单位不同（步数 / token / 厘），**取 min 是把不同单位的数比大小**。

### 3.5 "存在 TOCTOU 窗口"那句话**对我们是照抄**

它的注释说得很对（**对它是事实**）；而我们是 CLI 单进程 + **串行**的图
（`Runner.drive` 是一个 `for` 循环）—— `Allow` 之后**必然**先 `ReportUse` 才轮到下一个。

> **窗口不存在。** 而错的不是那句注释，是"**照抄**"这个动作 ——
> 照抄一条不成立的代价说明，比不写更糟：它会让下一个人以为"这个问题我们已经考虑过了"。
