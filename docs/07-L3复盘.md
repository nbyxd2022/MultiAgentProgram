## 0. 一句话结论

> **机制是对的，但"能力"有三分之一是空的** —— 声明了、检查了、测了，
> 而**没有任何生产代码去生产它或消费它**。

本轮 13 个问题里，**6 个属于同一类**：`Hint` / `ExpiresAt` / `Retryable()` /
`Store.List()` / `ask_user` / `Stats`。它们的共同形状是：

| | 声明 | 检查/实现 | 测试 | **生产者** | **消费者** |
|---|---|---|---|---|---|
| `ExpiresAt` | ✅ | ✅ | ✅ | ❌ | ✅ |
| `Retryable()` | ✅ | ✅ | ✅ | ✅ | ❌ |
| `Store.List()` | ✅ | ✅ | ✅ | ✅ | ❌ |
| `Hint` | ✅ | ❌ | ✅ | ✅ | ✅（但**没被记录**） |
| `Stats` | ✅(L2) | — | — | ✅ | ❌（**L3 丢了**） |

> ### 这就是本轮复盘的核心结论：
> **"写了"不等于"通了"。一个能力要成立，需要 5 个位置都有东西** ——
> 声明 / 实现 / 生产 / 消费 / 测试。
> **缺任何一个，它就是一个看起来很像能力的装饰。**

而这一类的发现手段**不是读代码想出来的**，是**审计出来的**（见 §1）。

## 1. 本轮复盘的方法：**"声明了但没人用"审计**

L2 复盘时我用 `grep` 抓到了一个真 bug（`RenderResult.Failed` 全仓无人读取 → L2-2）。
本轮把那个手法**系统化**了：

```
① 列出 L3 新增的全部"对外承诺"（导出的类型 / 字段 / 方法 / 事件常量）
② 对每一个，grep 它的"生产点"与"消费点"
③ 生产点 = 0 → 它是"没有源头的检查"（ExpiresAt）
   消费点 = 0 → 它是"没有出口的能力"（Retryable / List）
④ 剩下那些"只有测试在调用"的，**一律当成可疑**
```

**为什么这个方法有效**：它不需要理解代码的意图，只需要数**引用**。
而"意图"恰恰是最容易骗到人的东西 —— 写代码的人（我）清楚地记得**为什么**加它，
于是**不会去问"谁在用"**。

> ### 判据
> **一个导出的东西，如果只有测试在用它，那它就不是能力，是文档。**
>
> （测试是"规格"，不是"用户"。规格可以描述一个没人用的功能。）

实测数据：

| 符号 | 生产消费点 | 判定 |
|---|---|---|
| `Interrupt.ExpiresAt` | **0** | 🔴 没有生产者的检查 |
| `ResumeErrorKind.Retryable()` | **0** | 🟡 没有消费者的能力 |
| `checkpoint.Store.List()` | **0** | 🟡 没有消费者的能力 |
| `Graph.Layers()` | 1（`Describe`） | 🟡 只有打印 |
| `KindAskUser` / `KindChooseOption` | **0** | 🟡 没有生产者 |
| `StatsReporter`（在 L3） | **0** | 🔴 L2 的能力在 L3 丢了 |
| `Interrupt.Payload` / `Options` | 0 | 🟡 |

## 2. L3 的问题清单

### A 类：真问题（能力是假的）

#### ⭐⭐ L3-1 `Hint` 是节点的**输入**，但它不在状态里、不在黑板里、也不会被发现变了

```go
// runner.go:179
	hints: opt.Hints,
// runner.go:385
		Hint:    r.hints[name],
```

`Hint` 从 `RunnerOptions`（**装配期参数**）读，然后交给节点。它是**指令**（L2 的原话）。

而 `load()` 里只检查了 `Topic`：

```go
	// runner.go:496
	// ⚠️ 输入必须一致。
	//	同一个 run id 配着不同的主题，等于**两件事共用一个身份** …
	if got, err := st.Topic(); err != nil { … } else if got != r.topic { … 报错 … }
```

**没有对 `Hints` 的同类检查。**

**后果具体**：

```
进程 A：go run ./cmd/l3                      → 中断（Hint = "控制在 3 页"）
进程 B：go run ./cmd/l3 -hint="不限页数"     → 恢复成功，**没人发现输入变了**
        ↓
outline 拿到的是**另一条指令**，产出的 outline@2 血缘上仍然写着 BasedOn=[research@1]
        ↓
**血缘判据会认为这条链是新鲜的** —— 因为"输入变了"这件事在数据上不存在
```

**这与 R30 的 `State.Topic`、L2-1 是同一个形状的第三次**：

| | 表现 | 为什么没有一层能发现 |
|---|---|---|
| L2-1 | 上游重跑 → 下游静默用旧版 | 产物没有"我依据了谁"的记录 |
| R30 `State.Topic` | 主题改了 → 字段停在旧值 | 字段是黑板的副本，**副本不会自己更新** |
| **L3-1 `Hints`** | **Hint 换了 → 没有任何痕迹** | **它根本不在状态里** |

> **规律（三次了）：**
> **任何"输入"如果不进状态/不进黑板，它变了就没人知道。**
>
> 而 `Topic` 之所以现在安全，不是因为"检查了它"，而是因为
> **它是一份黑板产物（`topic@1`）** —— 检查只是第二道防线。

**修法（④ 改进第一批）**：把 `Hints` 也变成**输入产物**（`hint:<node>@1`），
或者至少进 `State` 并像 `Topic` 一样比对。

Hmm —— 两个方案有真差别：

| 方案 | 好处 | 代价 |
|---|---|---|
| **进 `State` 并比对**（与 `Topic` 一样） | 一行代码 | 换 Hint 会被**拒绝**，而不是"正确地重做" |
| **做成产物**（`hint@1`） | 换 Hint → `StaleReasons` 自动让**那一个节点**重做 | 要动 `Needs()`（节点得依赖它） |

**倾向第二个** —— 因为 `Topic` 的教训就是"**比对只能拒绝，进产物才能正确重做**"。
而这需要先想清楚"Hint 该被哪些节点依赖"（答案：只有被它指向的那个）。

#### ⭐ L3-2 `ExpiresAt` 永远为零值 —— 过期检查是**装饰**

```go
// interrupt.go:299
	// ExpiresAt 是**业务上的**过期时刻；零值表示不过期。
	ExpiresAt time.Time `json:"expires_at,omitempty"`

// interrupt.go:710
	if !in.ExpiresAt.IsZero() && now.UTC().After(in.ExpiresAt) {
		return &ResumeError{Kind: ResumeExpired, …}
	}
```

**全仓搜索的结果**：

| 位置 | 内容 |
|---|---|
| `interrupt.go:299/311` | 声明 |
| `interrupt.go:710/713` | 检查 |
| `interrupt_test.go:463/554/659` | **测试设置它** |
| `cmd/l3` / `runner.go` / `agents/node.go` | **零设置** |

**没有任何生产代码写过它。** 于是：

> 那条过期检查**永远不触发** —— 中断可以无限期恢复。
> 而我在 R29 花了整整一节论证"**业务过期必须写进数据，不能靠存储 TTL**"。
>
> **我论证了一个没有实现的机制。**

这是 L2-2 的形状（`RenderResult.Failed` 声明了、没人读）**的镜像**：那次是没消费者，这次是没生产者。

**为什么它对 CLI 无害，但仍然要修**：
- CLI 里"中断永远有效"是合理的（用户明天回来接着做）；
- **但"能力是假的"这件事本身有害** —— 下一次有人依赖它（比如"超过 24h 的中断自动放弃"），
  他会以为已经做了。

**修法**：`NewInterrupt` 加一个显式的 TTL 参数（或 `RunnerOptions.InterruptTTL`），
由调用方决定 —— **默认给一个值，比默认是零值好**。

#### ⭐⭐ L3-3 **成本统计在 L3 完全丢失** —— 而且是"可选能力被适配器吞掉了"

L2 的 R25（L2-3）花了一整轮统一成本口径（**必须是"累计"，不是"最近一次"**）。
到了 L3：

| 位置 | 对 `Stats` / `StatsReporter` 的引用 |
|---|---|
| `cmd/l0/main.go` | ✅ `a.Stats()` |
| `cmd/l1/main.go` | ✅ `generator.Stats()` / `critic.Stats()` |
| `cmd/l2/main.go` | ✅ 类型断言 `s.(agents.StatsReporter)` |
| **`cmd/l3/main.go`** | ❌ **0 次** |
| **`internal/graph/runner.go`** | ❌ **0 次** |
| **`internal/agents/node.go`** | ❌ **0 次** |

**三层都断了**：

```
① SubAgentNode 没有把 StatsReporter 转发出去
      → 调用方拿到 []graph.Node，断言 StatsReporter 全部失败
      → **看起来像"这一层没有用量"，而不是"我没接出来"**

② graph.Result 里没有 Stats 字段
      → 就算 Runner 想聚合，也**没有地方放**

③ cmd/l3 不打印
      → 图驱动下的成本对用户**完全不可见**
```

**根因是一条我没意识到的规律**：

> ### 适配器会**静默吞掉**它没转发的能力。
>
> L2 的取舍是"能被调度"与"能报用量"是两件事 → 用**可选能力 + 类型断言**
> （`schema` 的注释原话："接口要小，能力要可探测"）。
>
> 而 L3 加了一层适配器（`SubAgent → Node`），**那一层没有转发** ——
> 于是"可探测的能力"**探测不到了**。
>
> **类型断言的好处是"不用改接口"；代价是"每一层都要记得转发"。**
> 这正是 R23 那条教训的又一次现身：**"每个调用点都要记得做同一件事"的设计，迟早会漏掉一次。**

**修法**（④ 改进第一批）：
1. `SubAgentNode` 实现 `StatsReporter`（转发给 `n.sub`）；
2. `graph.Result` 加 `Stats`（由 Runner 在 `step` 之后断言累加）——
   **或者在 `RunnerOptions` 里接收一个 `[]NamedStats` 让调用方自己算**（更少的耦合）。

**取舍**：方案 1 + 让 `cmd/l3` 像 `cmd/l2` 一样自己遍历 roles 累加 ——
**不改 `graph` 包一行**，代价是"统计"这件事仍然在图之外。
（L4 做预算守卫时会需要"图内的成本视图"，那时再往上抬。）

### B 类：声明了但没人用（"死能力"）

#### L3-4 `ResumeErrorKind.Retryable()` 没有生产消费者

```go
// interrupt.go:583
func (k ResumeErrorKind) Retryable() bool { … }
```

调用点：`interrupt_test.go`（2 处）、`state_test.go`（1 处）。**生产代码零调用。**

它的本意是"给调用方做行为分支"。而唯一的调用方 `cmd/l3` 是这样的：

```go
	if runErr != nil {
		printStop(res)
		fail("运行失败: %v", runErr)      // ← 所有错误一视同仁
	}
```

**后果具体**：`from_future`（语义：**重试到新实例**）与 `corrupt`（语义：**查磁盘**）
在 CLI 里**表现完全一样** —— 都是打印 + `os.Exit(1)`。

**但它不完全是"没想到"**：CLI 只有一个实例，"重试到新实例"**确实无处可去**。
所以这是一个"**能力为 HTTP 场景准备，当前唯一调用方用不上**"。

**处置**：不改代码，但**在 `cmd/l3` 里用它**（哪怕是打印一句"这是可以重试的"）——
让它从"死能力"变成"**活的可观测**"。因为不这么做的后果是：
**下一个人会以为 `Retryable()` 是错的（因为没人用）而删掉它。**

#### L3-5 `checkpoint.Store.List()` 没有生产消费者（且与"不加 `Delete`"自相矛盾）

```go
// store.go
	List() ([]string, error)   // 返回全部**完好**的 run id
```

调用点：`file_test.go`（4 处）。**生产代码零调用。**

⚠️ **而我在 R32 明确写了**：

> "关于'要不要加 `Delete`'：**L3 不加**。L3 的每一轮都留着自己的 checkpoint……
> 『什么时候可以清理』是一个**运维策略**问题，现在没有输入条件。"

**`List` 与 `Delete` 是配套的**（列出才能选择删除）。我拒绝了后者却留下了前者 ——
**这不是"想过了"，这是"标准接口长这样所以我也这么写"**。

更尴尬的是：**`cmd/l3` 明明需要它**。
它现在的行为是"如果有 checkpoint 就从它恢复"，但**从不告诉用户"存在哪些 run"**。
而一个真实的用户会问的第一个问题就是："**我上次那个跑到一半的，还在吗？**"

**处置**：`cmd/l3` 加一句"磁盘上有 N 个 run：…"（用它）。**让能力有出口，或者删掉它。**

#### L3-6 `ask_user` / `choose_option` 有完整规则，但没有节点会创建它们

`interrupt.go` 的目录里声明了三种，其中两种（`ask_user` / `choose_option`）：

| 有的 | 内容 |
|---|---|
| 声明 | ✅ 目录表 |
| 校验 | ✅ `NeedsOptions` / `RequiresNote`（R34 专门加的） |
| 测试 | ✅ 多例 |
| **生产者** | ❌ **零** |

**这一条与 L3-2 不同**：协议表**可以先于实现存在**（那是"接口先定义"）。
我在 R34 论证过"目录里宣称三种、只实现一种会让目录说谎"，当时的解法是**实现 `Answer` 回传**
（已实现 ✅）—— 所以现在**它们是可以用的**，只是没有节点用。

**处置**：**保留**，但把触发条件写进看板：
"当出现一个'不问就无法开始'的节点时"。**这是"想过了"**，证据是 `Answer` 回传已就位。

### C 类：做到了可验证，但没兑现

#### L3-7 `Layers()` 只有 `Describe()` 在调 —— 图**全串行**

```go
// graph.go:500
func (g *Graph) Layers() [][]string    // 同层互不依赖 = 可并行的候选
```

调用点：`graph.go:579`（`Describe` 打印）、`graph_test.go`（2 处）。**Runner 不用它。**

我在 L2 复盘的结尾写过一句很得意的话：

> "加一个只依赖 `outline` 的配图角色，它会自动和 designer 排成同一层，
> **不需要谁去说这两个可以并行。**"

L3 的 `Layers()` + `TestLayersRevealParallelOpportunities` **证明了这句话**。
但：**没有任何东西真的并行。** `Runner.drive` 是一个 `for` 循环，一次一个节点。

**诚实评估**：这不是 bug。L3 的目标是"跨进程"，不是"并行"。
但它是 **L2-8（"表达不了并行"）的后半段**：
L2 的问题是"表达不了"，L3 解决了表达 —— **但没有兑现执行**。

**风险**：`Layers()` 现在是一个"看起来准备好了"的接口。
下一个人看到它会以为"并行已经支持，只要打开开关"。**那是一个谎言。**

**处置**：`Layers()` 的注释里**明确写"这只是候选，Runner 尚未并行"**（一行注释，消除误解）。
真的并行 → L4（它需要：并发安全的黑板写入、并发下的失败隔离、以及一个**真正需要它的场景**）。

> 对照：企业仓库**真的并行**，用的是 `grqueue.NewGrQueue(v1MaxConcurrency)` + 有序交付。
> 而它为此付出的复杂度是 `EarlyRendered` / `EarlyFailed` / `DesignTokensReady` /
> `DynamicSkipIndices` 这一整套协调机制（R31/R34 精读）。
>
> **这就是"兑现并行"的账单。** 我们暂时不付 —— 但要知道它有多贵。

### D 类：已知 + 有触发条件（复核触发条件是否仍然成立）

#### L3-8 `maxRunsPerNode` 不跨进程（R33 标注）

理由：一次 `Run` 的边界是"进程活着的一段时间"，跨恢复的重试意味着**人在反复同意**。

**复核**：仍然成立。而且 L3 的实测里"revise 之后会再问一次"是**预期行为** ——
用户每答一次，就多一次机会说"还是不对"。**这是人在驱动，不是死循环。**

#### L3-9 无分布式锁（R28 标注，F3 的镜像）

理由：CLI 单进程，没有第二个执行者。

**复核**：仍然成立。但**触发条件比 R28 更近了**：
`cmd/l3` 的用法是"跑一半 → 另一个终端接着跑"。**如果用户在两个终端同时跑**，
它们会读同一个 checkpoint、各自推进、后写的顶掉先写的。

**这是"单进程"假设的第一道裂缝。** 记进看板，优先级提到"L4 之前"。

#### L3-10 三个 LLM 角色未在图驱动下验证（R34 标注）

`cmd/l3` 用确定性节点（理由：验收标准"两次产出一致"用真实模型断言不了）。

**复核**：理由成立。但**有一个更便宜的验证方式被漏掉了** ——
`agents/node_test.go` 的 `TestSubAgentNodeWorksUnderTheRealRunner` 用的是 **fake SubAgent**，
而**真实的四个角色（research/outline/designer/renderer）从来没有在图里跑过**。

**可以补**：一个用 `cmd/l2` 的离线 Mock + 真实角色的 L3 测试
（不需要断言"一致"，只需要断言"能跑完"）。→ ④ 改进第二批。

### E 类：观测与测试

#### L3-11 三套 Event 形状，没有统一 Tracer

| 层 | 类型 | 字段 |
|---|---|---|
| L0 | `agent.Event` | `Step / Agent / Kind / ToolName / Content` |
| L2 | `agents.Event`（渲染） | 同上 |
| **L3** | `graph.Event` | `Step / Node / Kind / Detail` |

形状**刻意对齐**（R34 的原话："同一个 Tracer 不加一行就能接住这一层"），
**但没有任何东西真的接住了**——三处各自 `fmt.Printf`。

**这是 P9（观测与业务耦合）的现状**：形状统一了，Tracer 还没有。
→ L4（教学计划把它排在 L4）。

#### L3-12 观测输出**零测试覆盖** —— 而 R34 的 bug 就是这么漏掉的

R34 实跑时发现："已就绪、跳过：research、**outline**" 然后 outline 就跑了。

**为什么单测没抓到**：`Runner` 的 20 个测试函数里，
**没有一条断言过 `Event.Detail` 的内容**。它们断言的 `Event.Kind` 与 `Event.Node`。

**这不是"忘了写"，是"没想到观测也要断言"** —— 因为观测"不在关键路径上"。

> ### 判据
> **可观测量的输出也是产品的一部分。** 它出错时不会让任务失败，
> 但它会**主动误导排查的人** —— 而"误导"比"缺失"更贵。
>
> 而它最容易漏掉的原因很具体：**它不在任何一条断言的射程内。**

**修法**：给 `EventSkipped` 加一条断言（"被强制重做的节点不得出现在跳过清单里"）。
→ ④ 改进第一批（一行测试）。

#### L3-13 缺"全量重放"测试

有一组测试验证了"中断 → 恢复"，但没有一条验证：
**同一次运行跑两遍，所有产物逐字节一致**。

而这是"确定性"的**唯一硬证据** —— L1-6 定过"输出必须稳定"，
`Describe()` 有 `TestDescribeIsStable`，但**产物本身没有**。

**为什么会有影响**：如果产物不稳定，"两次运行结果一致"就无法回归，
而**那是 L4 评测集的前提**（评测要比较两次运行）。

**修法**：`cmd/l3` 加一个 `-verify` 模式（跑两遍、逐字节比）。→ ④ 改进第二批。

## 3. 风险场景（故障注入之外，12 个）

L2 复盘我列了 12 个。本轮同样列 12 个 —— **每个都对应一个"现在的代码会怎样"**。

| # | 场景 | 现在的行为 | 评价 |
|---|---|---|---|
| 1 | 同一 run 换 `Hint` 重启 | **静默接收新指令**，血缘无感知 | 🔴 L3-1 |
| 2 | 中断挂了 30 天再恢复 | **照样恢复**（`ExpiresAt` 恒零） | 🟡 L3-2 |
| 3 | 图跑完，用户想知道花了多少 | **拿不到**（三层都断） | 🔴 L3-3 |
| 4 | 两个终端同时跑同一个 run | 后写的顶掉先写的 | 🟡 L3-9 |
| 5 | `from_future` 错误 | 与 `corrupt` 表现一样（都是退出） | 🟡 L3-4 |
| 6 | 想知道"我上次那个跑到哪了" | **没有命令**（`List` 没人用） | 🟡 L3-5 |
| 7 | 一个节点产出的 payload 是 100MB | 每次 `persist` 全量序列化黑板 → **O(n²)** | 🟡 见下 §4 |
| 8 | checkpoint 文件被别的进程截断 | `corrupt`，明确报错 | ✅ 已覆盖 |
| 9 | `design.pages` 与 `outline.pages` 数量不等 | **不会发生**（`Needs` 保证 design 在 outline 之后；renderer 自己查） | ✅ |
| 10 | 节点的 `Outcome.Next` 指向一条不存在的边 | 建图期 + 运行期**双重拒绝** | ✅ |
| 11 | 黑板里有 500 个 key | `CanSkip` 每次遍历全部 → 慢但正确 | 🟢 |
| 12 | 恢复时 `Pending` 属于另一个 run | `Validate` 拒绝（串台检查） | ✅ |

**第 7 条值得展开**（新发现）：

```go
// runner.go:343
	// ★ 每跑完一个节点就落盘 —— 这才是"进程被杀也不丢"的全部内容。
	if err := r.persist(st); err != nil { … }
```

`persist` 序列化的是**整个黑板**。而黑板是**只追加**的（每一版都留着）。
所以 N 个节点、每个产出 M 字节 → 总写入量是 **O(N²·M)**。

L3 的实际规模（4 个节点、几 KB）完全无所谓。
但如果哪天有一个节点产出大 payload（比如把 3 页 HTML 的全文本也塞进黑板），
**每多一跳，落盘量就线性增长一次**。

**触发条件**：黑板总量超过 ~1MB 时。

**候选修法**（不现在做）：**增量持久化**（只写这一跳新增的产物）——
但那需要 checkpoint 支持"追加"，而"追加"与"原子替换"是两种写入语义
（**正是 F4 那个病**）。所以更稳的方向是：**大产物不进黑板**（存外部，黑板只放 ref）——
而我们已经有 ref 机制了 ✅。

> 记这一条的意义：**它是"黑板只追加"这个决定在下一层（持久化）的账单。**
> 现在不付，但要知道账单在哪。

## 4. 与主流方案对照

### 4.1 三方对照表

| 维度 | LangGraph | Temporal | 企业仓库（Eino） | **我们** |
|---|---|---|---|---|
| 状态是什么 | channel 值快照 | **事件历史**（event sourcing） | 图本地状态（含 `chan`/`ctx`，**不可序列化**） | **黑板快照（纯数据）** |
| 恢复方式 | 从 checkpoint 重放 | **确定性重放全部事件** | compose 的 checkpoint | **从快照续跑（位置由产物推导）** |
| 中断 | `interrupt()` + 恢复值 | Signal / Query | `InterruptInfo`（类型名 + 四处 switch） | `Interrupt` + `Decision`（**确定性 ID**） |
| 幂等 | 调用方负责 | **框架保证**（重放 + 幂等活动） | 无 | **跳过已完成 + 有界重试** |
| 过期 | checkpointer 的保留策略 | retention | **Redis TTL 7d**（五处各写一遍） | `ExpiresAt`（**没有生产者** 🔴） |
| 成本 | 无内建 | 无内建 | **Prometheus 指标**（多种 token + 派生指标） | `StatsReporter`（**L3 丢了** 🔴） |
| 并行 | 支持 | 支持 | **真的并行**（`grqueue` + 有序交付） | 只有 `Layers()` 打印 🟡 |

### 4.2 ⭐ 对照一：成本 —— 我们是"返回值"，它是"指标"

企业仓库的成本统计是 **Prometheus**，而且比我们细：

```go
	metricAgentPromptTokens     = "agent_prompt_tokens_total"
	metricAgentTotalTokens      = "agent_total_tokens_total"
…
	mt.promptTokens += int64(usage.PromptTokens)                    // 累加 ✅ 与 L2-3 同口径
	mt.cachedTokens += int64(usage.PromptTokenDetails.CachedTokens) // ← 我们没有
	mt.reasoningTokens += int64(usage.CompletionTokensDetails.ReasoningTokens) // ← 我们没有
…
	if mt.promptTokens > 0 {
		reqCachedTokenHitRateHist.Observe(float64(mt.cachedTokens) / float64(mt.promptTokens))
	}                                                               // ← 派生指标：缓存命中率
```

**这不是"它做得更多"，而是两种不同的用途**：

| | 返回值（我们 L2） | 指标（企业仓库） |
|---|---|---|
| 回答的问题 | "**这一次**花了多少" | "**这一类**请求平均花多少 / 有没有变坏" |
| 谁用 | 调用方**当场**决策（要不要继续/降级） | 运维 / 成本团队，**跨请求跨时间** |
| 生命周期 | 随调用结束消失 | 永久（Prometheus） |
| 切片能力 | 无 | 按模型 / 请求类型 / 用户 label |

> **两者不冲突，而且都需要。**
> 而 `cachedTokens` / `reasoningTokens` 提醒我：**我们的 `agent.Stats` 太浅了。**
> 对现在的模型（缓存命中通常便宜一个数量级、推理型模型按 reasoning token 计费），
> **不统计这两样，成本算出来是错的。**

→ 记入看板（L4：可观测 + 预算）。

### 4.3 ⭐ 对照二：过期 —— 两家各缺一半

| | 回收（存储层） | 业务语义（数据层） |
|---|---|---|
| 企业仓库 | ✅ Redis TTL 7d（**五个 store 各写一遍**） | ❌ 无 → 过期是**静默的**，`Get` 分不清"写错 key" / "被 GC" / "业务过期" |
| **我们** | ？ | ✅ `ExpiresAt` 字段 + 检查 + 测试 —— **但没有生产者** |

而 R29 我写下的判据是：

> `ExpiresAt` 业务语义：超过它就别恢复了；
> 存储层 TTL：垃圾回收。
> **业务过期写进数据，存储 TTL 只负责回收，且必须远大于它。**

**现在看，这句话是对的，但我只做了一半** —— 写进了数据模型，没写进生产代码。

而且：**我们连"回收"那一半也还没有**（`Delete` 未加，checkpoint 会无限增长）。
→ 合并成看板一条：**"过期的两半，我们各缺一半"”。

**顺带一个观察**：企业仓库那五个 `redisExpiration = 7 * 24 * time.Hour`
**值相同、语义不同、各写一遍**。它们**恰好相等是巧合，不是设计**：

> **同样的常量值在多处重复，会制造一种"看起来统一"的假象。**
> 改其中一处不会影响另四处，但没人知道该改哪些。

这与 L2-3（"同一个字段两处口径"）是同一个形状的弱版本。

### 4.4 对照三：并行 —— 兑现它要付多少

企业仓库**真的并行**（R31 精读）：`grqueue.NewGrQueue(8)` 按 batch 并发跑 LLM。
而它为此付出的协调复杂度是：

| 机制 | 作用 | 代价 |
|---|---|---|
| `DesignTokensReady chan struct{}` | plan 的早渲染 goroutine **等 style 算完** | **8 处 `close()`**，漏一处死锁（R34 精读） |
| `EarlyRendered` / `EarlyFailed` | 早渲染的产出与失败 | 两套记账 + 互斥锁 |
| `DynamicSkipIndices` | 运行时决定跳过哪些页 | 回调 + 共享状态 + 四处改动点 |
| `RegisterValuesMergeFunc` | 并行分支汇入时怎么合并 | 一行**不通用**的"取首条" |

> **这就是"兑现并行"的账单。** 而我们不付这一笔 —— 因为**我们没有需要它的场景**
> （4 个节点、离线、秒级）。
>
> 但 `Layers()` 必须**明说**自己只是候选，否则它是一个**看起来已经兑现的承诺**。

### 5.3 ⚠️ L3-14：改进过程中**新引入**的一个问题（R36）

> **它不是复盘发现的 —— 是"照例跑一遍真的"发现的。**

修完第一批 7 条之后，`go test ./...` **324 个测试全绿**、`go vet` 零告警，
而 `cmd/l3` **退出了 1**：

```
[失败] 运行失败: run l3-demo 记录的 hints 与本次调用不一致
       （记录 [无]，本次 [outline="控制在 3 页"]）
```

**真实原因：`l3-demo.json` 是 v1 时代的记录，它根本没有 `hints` 字段。**
不是"输入变了"，是"记录太老"。

| # | 报出来的 | 真实原因 |
|---|---|---|
| R29 | "缺少 prompt" | 字段**改名**了 |
| R30 | "协议太老"（`Version=0`） | 字段**没写** |
| R34 | "中断的问题"（实为快照读不出来） | **subject** 写死了 |
| **R36** | **"输入变了"** | **记录写在字段存在之前** |

**共同形状（四次都一样）：用一个更具体的判断，去覆盖一个更一般的判断。**

**修法（用已有的机制，不新增）**：

```go
	StateVersion          = 2   // v1 → v2：新增 hints
	StateMinVersion       = 1   // ⚠️ 故意留在 1
	StateVersionWithHints = 2   // "hints 校验"这条规则的起始版本

	if st.Version >= StateVersionWithHints && !maps.Equal(st.Hints, r.hints) { … 拒绝 … }
```

它兑现的正是 R30 补完整的那半句话：**`min ≤ v ≤ current` 也意味着"结构兼容"**，
所以**只有窗口内的记录才适用本版本的结构规则**。

**否决了"迁移"**（读入时把 v1 补成 v2）：v1 记录的前几个节点可能用的是**另一套 hint**，
补上本次的值会让血缘判据认为"全部产物都基于这套 hint" —— **那是一个永久的谎**。

**并且不允许"静默放行"**：新增 `EventNotice`（"我不知道什么" —— 与 `EventSkipped`
的"我跳过了什么"是两类不同的事件）。

> ### 一条适用于所有"加校验"的规律
> **给一份已有数据加"新的校验字段"，等价于一次协议变更。**
> 老数据没有它，而校验会因此得出**错误的结论** —— 所以它必须**带版本门**。
>
> 而这条规律只在**跑真的**时候才会显形：**测试里的数据全是新的。**

| 统一 Tracer | L4（教学计划已排） |
| 增量持久化 | 黑板总量 > 1MB |
| `Delete` / 保留策略 | checkpoint 总体积成为问题 |

## 7. 方法论：本轮学到的三件事

### 7.1 ⭐ **"声明了但没人用"审计** —— 一个可复用的动作

```
列出全部导出承诺 → grep 生产点 / 消费点 → 生产=0 或 消费=0 的一律可疑
```

**它为什么比"读代码"有效**：读代码时你在**验证自己的意图**（"我想的对不对"），
而审计在问一个**不同的问题**（"有人用吗"）。

> 而"意图"是最容易骗到人的东西 —— **写代码的人清楚地记得为什么加它，
> 于是永远不会去问"谁在用"。**

**本轮靠它抓到了 6 个（L3-1 ~ L3-6），占全部问题的 46%。**

### 7.2 **半成品比没有更危险**

L3-2（`ExpiresAt`）与 L3-3（成本）有一个共同点：
**它们看起来是"已经做了的"**。

| | 没有它 | **它是半成品** |
|---|---|---|
| 排查的人 | 知道要去加 | **以为已经有了** |
| 后果 | "缺一个功能" | "**基于一个错误的前提做决定**" |

> 这与 L2-2（`RenderResult.Failed` 声明了但没人读）是同一个病。
> **判断一个能力的标准不是"写了多少"，而是"5 个位置是否都有东西"**：
> 声明 / 实现 / **生产** / **消费** / 测试。

### 7.3 **适配器会静默吞掉它没转发的能力**

L3-3 的根因不是"忘了加统计"，而是：

> L2 用**可选能力 + 类型断言**（`StatsReporter`）来避免接口变胖。
> 这个取舍本身是对的 —— 代价是**每一层适配器都要记得转发**。
> 而 `SubAgentNode` 没有转发，于是能力**静默消失**。

**修法不是"小心一点"，是把"转发"变成可检测的**：
给 `SubAgentNode` 加一条测试 —— **断言它实现了 `StatsReporter`**（当内层实现时）。

> 这与 R23 那条教训是同一个：
> **"每个调用点都要记得做同一件事"的设计，迟早会漏掉一次。**
> 而补法是**让漏掉会被测试抓到**，而不是"下次注意"。
