> ### L4 引入的**新边界**是什么？为什么它比前三阶段都容易做漏？

## 0. 一句话：L4 引入的边界是「**产物与过程**」

按前三个阶段的惯例，先定位**新边界**（这条手法从 L3 起一直在用）：

| 阶段 | 引入的边界 | 它逼着系统重新回答 |
|---|---|---|
| L0 | **模型和我** | "哪些事必须由代码保证？" |
| L1 | **生成和评判** | "谁来判断好坏？" |
| L2 | **多个上下文** | "什么东西必须被外置？" |
| L3 | **进程和进程** | "什么东西必须能跨过去？" |
| **L4** | **产物与过程** | "**除了'产出了什么'，系统还知道什么？**" |

**在此之前，系统只认识产物。** 黑板上的每一个 key 都是产物，
`CanSkip` 看的是产物，`State` 装的是产物 —— 整个 L0~L3 都在做一件事：
**给东西一个类型**（`Artifact` / `schema.Payload`）。

**从 L4 起，系统要认识"它是怎么产出的"** —— 行为（事件）、质量（评分）、消耗（token/时间/钱）。

### 为什么这条边界**最难**

> ### 数据模型的边界是「**业务**」；观测模型的边界是「**我们想知道什么**」。

这一句解释了 L4 与前三个阶段在**方法论**上的根本差别：

| | 数据模型（L0~L3） | 观测模型（L4） |
|---|---|---|
| 什么在逼你设计 | **业务需求**（"research 必须有来源"） | **一个具体的问题**（"这一页声明了 3 张图、画了几张？"） |
| 漏了会怎样 | **报错**（缺字段，解不出来） | **什么都不发生** |
| 有没有编译期约束 | 有（类型 / 校验） | **几乎没有** |

**所以 L4 的风险不是"做错"，是"做漏"** —— 而做漏不会有任何东西提醒你。

> 这与 L3 复盘的核心结论是**同构**的：
> **一个东西只要没有调用点，它就会消失。**
> 而观测与评测集连"调用点"都不需要（它们不是必需的）→ **更容易消失**。

## 1. 五条原理

### 原理一：观测量分三层，而三层的**保留要求相反**

| 层 | 内容 | 体积 | 用途 | 保留策略 |
|---|---|---|---|---|
| **明细**（span / event） | 每一步做了什么、成没成、多久 | 中 | 排查单次运行 | **可开关/可采样** |
| **聚合**（metric） | 计数、直方图（按维度切片） | 小 | 看趋势、告警 | **永远开着**（关了就没有历史） |
| **录播**（prompt + response） | 模型真正看到了什么、回了什么 | **大** | **离线重放、归因** | **不能关**（关了就没法重放） |

**为什么必须分开**：它们的保留要求**互相矛盾** ——
"体积小所以永远开"（聚合）与"体积大所以可关"（录播）**是同一份数据的两个视角**。

> ### 判据
> **同一个事件有多个消费者时，先问他们的"保留要求"是否相同。**
> 不同 → **必须是多个出口**，不能是一个出口 + 一个"要不要存"的标志位。
>
> （企业仓库正是这么做的：`OnTrace` 可被 `DisableOnTrace` 关掉，
>  而 `OnTaskLogTrace` **仍然发**，且**必须保留 prompt** —— 理由写在测试里：*offline replay*。）

### 原理二：观测依赖必须**向外**（业务包不 import 监控库）

观测是**横切关注点**：它出现在每个节点里，却不属于任何节点。

如果直接在业务包里 `import prometheus`：
- 每个包都多一个外部依赖 → **测试要起一个注册表**；
- 换监控后端 = 改所有调用点；
- **业务代码开始知道"这是个要上报的东西"**。

**做法**：定义一个**回调集合**（端口），由**最外层**注入具体实现。
判据与 `llm.Client`、`checkpoint.Store` 是同一条（原则五）。

而有一个**必须做对的细节**：

> **每个 helper 都要判空**，让**中间层也可以传 nil** ——
> 否则"我这一层不关心观测"就得写 `if m != nil && m.OnX != nil` 才能透传，
> 于是**每个透传点都要记得判空**（R23 那条教训的形状）。

### 原理三：预算 —— **检查与记账必须分离**，而分离是有代价的

朴素的预算实现是"开始前扣额度"。**它的语义是错的**：一次失败的运行也算了钱。

正确的语义是「**成功才计入**」：

```
Allow(need)      → 检查（不记账）：还能不能做？
   …做事…
ReportUse(used)  → 记账（成功才调）
```

**而它有一个无法消除的代价**：

```
请求 A：Allow → 通过（假设还有额度）
请求 B：Allow → 通过（**A 还没 ReportUse**）
        ↓
两者都做了事 → 两者都 ReportUse → **超额**
```

> **这是「成功才计入」语义的固有代价**（TOCTOU 窗口）。
> **不要假装它不存在** —— 要在接口文档里写清楚，
> 让调用方知道"这个额度是**软**的，不是硬保证"。
>
> （企业仓库把这句话写在接口注释里了。那是一种**能被审计的妥协**。）

### 原理四：可观测 ≠ 可评测 —— 它们回答的是**不同时间点**的问题

| | 可观测 | 可评测 |
|---|---|---|
| 什么时候用 | **运行时** | **变更时** |
| 数据来自 | 真实流量 | **造出来的用例** |
| 回答 | "线上健康吗" | "**我这次改得好不好**" |
| 失效方式 | 指标口径漂移 | **用例集腐烂（没人维护）** |

**两者缺一不可**：只有可观测 → 只能"上生产才知道"；只有可评测 → 不知道真实分布。

而**评测集是最容易消失的东西**：

- 它**不在业务代码里**（没有调用点、没有编译期约束）；
- 它的"用户"是**开发者自己**，而开发者随时可以绕过它；
- 它**每一轮都花钱**（跑一次 = 一次真实运行）。

> **一个没有调用点的东西会消失** —— 评测集是这条规律的极端形态：
> **它连"声明"都没有。**

### 原理五：硬判据用代码，软判据用模型 —— 而**软判据也是一个产物**

"这段 HTML 好不好看" 只能由模型判；"这一页有没有 3 个要点" 必须由代码判。

**分层的判据不是"哪个更准"，而是"哪个能给出确定答案"**：

| | 硬判据 | 软判据 |
|---|---|---|
| 判据 | 代码 | 模型 |
| 结果 | 确定、可复现 | 概率、有解释 |
| 失效 | 报错 | **给出一个自信的错误评分** |
| 对策 | 校验 | **把它也当成一次运行**：走同一个 Tracer、留 prompt/response |

最后一句是关键：**Judge 的调用必须被录播**，否则"它为什么给 7 分"永远无法归因。
这与原理一（录播层）是同一件事的落地。

## 2. 精读 **R38**：企业仓库的观测、限额、与一个**"缺席"**

### 2.1 `TraceEvent` —— 观测量三层里的**明细 + 录播**在同一个结构里

```go
// TraceEvent 单次 LLM 交互跨度，类似于 KAS 捕获的内容。
type TraceEvent struct {
	SpanID     string `json:"span_id"`      // ┐
	Name       string `json:"name"`         // │ 结构
	Phase      string `json:"phase"`        // │ （谁的 span / 哪个阶段）
	Status     string `json:"status"`       // │
	DurationMs int64  `json:"duration_ms"`  // ┘
	Model      string `json:"model"`        // ┐ 上下文
	PageIndex  int    `json:"page_index"`   // ┘
	SystemPrompt string `json:"system_prompt"` // ┐ 正文
	UserPrompt   string `json:"user_prompt"`   // │ （**大**）
	Response     string `json:"response"`      // ┘
	Error        string `json:"error"`         // 失败
}
```

**它把"明细"和"录播"放进了同一个结构** —— 一个回调就能拿到全部。

| 收益 | 代价 |
|---|---|
| 不用维护两条链路 | **体积巨大**（每次调用都把 prompt 带一遍） |

⭐ **而它的对策不是"拆成两个结构"，是"两个回调"**：

```go
	OnTrace        TraceCallback `json:"-"`   // 上游（在线）—— **可被 DisableOnTrace 关掉**
	OnTaskLogTrace TraceCallback `json:"-"`   // 本地任务日志 —— **仍然要发，且保留 prompt**
```

这正是原理一的实物：**两个消费者，保留要求相反 → 两个出口。**

（R37 精读的那个测试就是在守这条：关掉上游之后，本地那份**必须仍然发一次**，
 且注释写明理由是 **for offline replay**。）

### 2.2 ⭐ `NodeMetrics` —— "无侵入观测"的教科书，以及八个**关于业务的事实**

```go
// NodeMetrics 是 Graph 对外的「无侵入观测」钩子集合。
//
// 设计意图：agent 包不 import prometheus；由 controller 在构造 PipelineInput 时注入具体实现。
//
// 所有回调均可为 nil，NodeMetrics 的 helper 方法内部会判空，业务逻辑无需再包一层 if。
```

**两句话各对应一条原理**：第一句是原理二（依赖向外），第二句是原理二的落地细节（helper 判空）。

而真正值得学的是**它选了哪八个回调**：

| 回调 | 它回答的问题 |
|---|---|
| `OnNodeDone(stage, success, duration)` | 每个阶段成不成、多久 |
| `OnPageRender(pageIndex, pageType, success, duration)` | 每页成不成 —— **按页类型切片** |
| `OnLLMCall(stage, model, success, duration, in, out)` | 每次调用的**成本** |
| `OnLayoutGuard(pageIndex, score, passed, repairAttempt, duration)` | 爆版检测 + **第几次修复** |
| `OnError(stage, err)` | 同一请求可多次触发 |
| `OnRecordLastStatus(stage, err)` | **桥梁回调**（见下） |
| `OnScreenshotDownload(result)` | **外部依赖**的成功率 |
| **`OnImageCountMismatch(pageIndex, expected, actual)`** | ⭐ **对账** |

> ### ⭐⭐ `OnImageCountMismatch` 是这八个里最值钱的
>
> 它不是"成功/失败"这类**通用**指标，而是一个**具体的对账事实**：
> **"这一页声明了 N 张图，实际画了 M 张。"**
>
> **这类指标只有深刻理解业务的人才会想到要报** —— 而它比"失败率"有用得多，
> 因为它捕捉的是**静默的错**：没报错、流程走完了、**但内容不对**。
>
> 这正是我们从 L0 起一直在追的那一类东西（L2-2 `存在 ≠ 完整`、L3-12 观测说反话）。
> **而它的对策在这里第一次变得具体：把对账做成一个指标。**

另外两个细节值得记：

```go
// OnRecordLastStatus 桥梁回调：Logic 层通过它把当前最后阶段+错误传给 Controller 的
// promStage/promErrorType 变量，保证 defer 上报时拿到最新状态。
```

**这是一个被显式标注的妥协** —— "桥梁"这个词说明作者知道它不优雅
（它绕开了函数式上报接口，去写两个可变变量）。
**但它被命名成"桥梁"、被注释解释** —— 于是它是一个**能被审计的妥协**。

> 与 `PipelineInput` 上的 **13 个 `json:"-"`** 是同一个现象：
> **一个类型里"不正常的东西"越多，越要一个个标注出来。**
> 不标注的话，它们会混进正常字段里，而**下一个人分不清哪个是设计、哪个是妥协**。

### 2.3 `otelkit` —— OTel 的**薄**封装（三行函数，但方向对）

```go
func LogError(span trace.Span, err error)                     // SetStatus + RecordError
func SpanSetTag(span trace.Span, key string, value interface{}) // 类型分派
func SpanLogKV(span trace.Span, kvs ...interface{})            // 键值对 → AddEvent("log", attrs…)
```

⭐ `SpanSetTag` 的**类型分派**（string / int / int64 / float64 / bool → 各自的原生属性类型，
default → `fmt.Sprintf("%v")`）值得记：

> **别把结构化信息压成字符串。** —— 压了之后，聚合就只能靠正则了。
>
> 这与我们一路在做的"受控词表 / 不透明字节 vs 结构化"是同一条
> （`Kind` / `ResumeErrorKind` / `Artifact.Payload`）。

而 `otelkit/http2curl.go` 是一颗小宝石：

> **把一次 HTTP 请求转成一行 curl 命令。**
>
> 它解决的是"**这次失败的调用怎么复现**" —— 比"日志里记了 URL 和 body"强一个数量级
> （后者要人工拼回去，而人工拼错了还会误导）。
>
> **可排查性不是"记了多少"，是"能不能一键复现"。**

### 2.4 `Limiter` —— 三条可直接搬的设计

```go
// Limiter 限流器接口（统一 rolling 滑动窗口）。每次请求先 Allow 检查是否受限，
// 生成成功后再 ReportUse 计入窗口。注意 Allow/ReportUse 分离存在固有的
// TOCTOU 窗口（高并发突发时可能多放一次），这是「成功才计入」语义的折中。
type Limiter interface {
	Allow(ctx) *AllowResult
	ReportUse(ctx)
	AllowN(ctx, quantity int) *AllowResult   // 可变增量（配额限流，如按页数累计）
	ReportUseN(ctx, quantity int)
}

type AllowResult struct {
	Count     int64 // 窗口内已用累计
	Remaining int64 // **剩余额度 —— 供调用方日志/展示**
	Limited   bool
}
```

**三条要搬的**：

| # | 设计 | 为什么 |
|---|---|---|
| 1 | **`Allow` / `ReportUse` 分离** | 原理三 —— "成功才计入"；**代价写在注释里** |
| 2 | **`AllowN(quantity)`** | 预算的**可变增量**：token 不是"+1"，是"用了 3700" |
| 3 | **`Remaining` 显式返回** | **剩余额度是要给用户/模型看的**（印证 L2-9 的 `BudgetNotice`） |

**还有两条来自它的工厂函数**：

```go
// NewLimiter: Enable 为 false 时返回 EmptyLimiter（不是 nil）
// LimiterFactory.Get: 未注册时返回 EmptyLimiter（**安全降级，不 nil**）
// LimiterFactory.Register: 重复注册同一 type **视为编程错误，直接 panic**
```

> ### ⭐ 「未注册 ≠ 错误」
> **"这个维度不限额"是一个合法的状态**，不是一个错误。
>
> 返回 nil 的话，**每个调用点都要判空** —— 而"每个调用点都要记得"就是 R23 那条教训。
> 用一个**空对象**（`EmptyLimiter`）把 nil 消掉，调用点就**永远不需要判空**。
>
> 而 `NewLimiterParams == nil` 也返回 `EmptyLimiter` —— 连"配置缺失"都当合法状态。

它与 `composite.go`（多窗口，任一触发即限流）合起来，正好是我们要的"**四维预算**"
（步数 / token / 时间 / 成本 —— 任一超限即停）：**每一维一个 guard，组合成一个**。

### 2.5 ⚠️ 精读最重要的发现是一条**缺席**：它**没有评测集**

```powershell
=== 数据/用例文件（jsonl / golden）===      （空）
=== testdata 目录 ===                      （空）
=== eval 相关目录 ===
  frontends\test_v5_single_page_ppt_bench   ← 唯一一个，是个**前端页面**
```

**48 个测试文件、Prometheus 指标、OTel span、限流器、8 个无侵入观测钩子 —— 而没有一个评测集。**

| 它有的 | 它没有的 |
|---|---|
| **在线可观测**（生产环境聚合 → 看板/告警） | **离线可评测**（改一次 Prompt → 一键看指标升降） |
| 单元测试（48 个，纯函数） | **带真实输入 + 期望输出的用例集** |
| 人工试用（那个 bench 页面） | **能重复跑的回归** |

> ### 这条缺席说明的不是"它做得差"
>
> **它说明"可观测"与"可评测"是两个不同的东西，而生产系统的重心天然偏后者之外。**
>
> | | 可观测 | 可评测 |
> |---|---|---|
> | 谁需要 | **运维 / 值班** | **写代码的人** |
> | 什么时候付代价 | 上线后**持续** | **每次改动前** |
> | 不做的后果 | **立刻**（线上出事） | **缓慢**（"好像变差了，说不清"） |
>
> **"立刻的后果"永远赢过"缓慢的后果"** —— 所以可观测先被做出来。
>
> 而教学计划里 L4 的验收标准恰恰是**它没做到的那一半**：
> > **"改一次 Prompt → 一键看到指标升降。"**
>
> 这句话不是"可观测"的要求，**是"可评测"的要求**。
> 而我们做 L4 的理由，就是把这半边补上。

## 4. 我们的设计（具体到接口）

### 4.1 `internal/observ` —— 统一观测（**L3-11 的欠账**）

L0/L1/L2/L3 现在有**四套**事件形状（`agent.Event` / 渲染事件 / `graph.Event` …），
它们**刻意对齐**（R34 的原话："同一个 Tracer 不加一行就能接住这一层"），
**但没有任何东西真的接住了**。

```go
// Package observ 提供**统一**的运行时观测。
//
// # 它替代什么
//
//	L0/L1/L2/L3 各有一套事件类型，形状刻意对齐而没人接。本包把它们统一成一种。
//
// # 边界（原理二）
//
//	本包**不依赖任何监控库**。它只定义"事件长什么样"与"往哪去"两个端口，
//	具体的后端（文件 / Prometheus / OTel）都是**适配器**，由最外层注入。
package observ

// Event 是一次运行时事件。
//
// ⚠️ 它同时承载**明细**与**录播**（原理一）—— 而两者由不同的出口消费：
//	明细 → 聚合/看板（可采样）   录播 → JSONL（**不可关**）
type Event struct {
	RunID string `json:"run_id"`
	Span  string `json:"span,omitempty"` // 所属 span（无则空）

	// ⚠️ `Layer` / `Kind` 是**词表**（代码定义的有限集合）→ **强类型**；
	//	`Phase` 是**数据**（节点名，由装配决定）→ 自由字符串。
	//	把数据做成词表是错的（加节点就要改枚举）；把词表做成自由字符串是危险的（拼错静默）。
	Layer Layer  `json:"layer"` // agent | graph | tool | llm | eval
	Phase string `json:"phase,omitempty"` // 节点名 / 角色名 —— **数据，不是词表**
	Kind  Kind   `json:"kind"`  // 事件类型（**受控词表** + 目录表，见下）
	Err   string `json:"err,omitempty"`

	// ⚠️ **没有 `Seq` 字段**（实现时删掉的）：
	//	"谁先谁后"是**录播的属性**，不是事件的属性 ——
	//	`Recorder` 的顺序 = 切片下标，`JSONLTracer` 的顺序 = **行号**。
	//	所以序号是**派生值**，"能从别处算出来的就不该单独存"。

	// 正文（**录播层**）—— 体积大，只有本地出口保留。
	SystemPrompt string `json:"system_prompt,omitempty"`
	UserPrompt   string `json:"user_prompt,omitempty"`
	Response     string `json:"response,omitempty"`

	// 数值（**聚合层**）—— 供指标直接消费。
	PromptTokens     int           `json:"prompt_tokens,omitempty"`
	CompletionTokens int           `json:"completion_tokens,omitempty"`
	Duration         time.Duration `json:"duration,omitempty"`

	// Reconcile 是**对账**（原理四 / §2.2）：declared 与 actual 不符时非空。
	//
	// ⚠️ 这一类事件比"成功/失败"值钱得多 —— 它捕捉的是**静默的错**：
	//	流程走完了、没报错，但**内容不对**。企业仓库的
	//	`OnImageCountMismatch(declared, actual)` 就是这一类。
	Reconcile *Reconcile `json:"reconcile,omitempty"`
}

type Reconcile struct {
	What     string `json:"what"`     // "图片数量" / "页数" / "要点条数"
	Declared int    `json:"declared"` // 声明了多少
	Actual   int    `json:"actual"`   // 实际多少
}
```

**出口（端口）**：

```go
// Tracer 是观测的**唯一出口**。
type Tracer interface {
	Trace(Event)
}

// NopTracer 不记录任何东西。
//
// ⚠️ 它必须存在，而且**调用方传 nil 时由构造函数换成它** ——
//	这样"不观测"就永远不需要调用点判空（原理二 + 企业仓库的 EmptyLimiter）。
type NopTracer struct{}
func (NopTracer) Trace(Event) {}

type Recorder struct { ... }

func (r *Recorder) Events() []Event
func (r *Recorder) Count(kind string) int

// JSONLTracer 把**录播层**逐行写盘（事后可重放、可 diff）。
type JSONLTracer struct { ... }

// Fanout 把同一个事件发给多个出口（原理一：多个消费者）。
type Fanout struct { ... }

//

func DisableRemote(remote, local Tracer) Tracer

### 4.2 `internal/budget` —— 预算守卫（**四维**）

```go
// Package budget 提供**四个维度**的预算守卫：步数 / token / 时间 / 成本。
//
// # 语义（原理三）
//
//	Allow(need)      检查，**不记账** —— "还能不能做？"
//	ReportUse(used)  **成功才**记账
//
// # ⚠️ 已知的 TOCTOU 窗口（照搬企业仓库 Limiter 的诚实标注）
//
//	Allow → 通过之后、ReportUse 之前，另一个执行者可能也通过。
//	并发下**可能超一点**。
//
//	这是「**成功才计入**」语义的固有代价 —— 而它的另一面是：
//	「事前扣」会把**失败的运行也算成花了钱**，那是**持续的系统性偏差**。
//
//	**我们接受"并发下可能超一点"，拒绝"每次都多算"。**
package budget

// Need 是"这一步要花多少"（Allow 的入参）。
type Need struct {
	Steps            int
	PromptTokens     int
	CompletionTokens int
	Wall             time.Duration
	CostMilli        int64 // 厘（**整数**，避免浮点误差累积）
}

// Used 是"这一步实际花了多少"（ReportUse 的入参）—— 与 Need 同形，但**含义是过去时**。
type Used = Need

// Limits 是四维上限。
//
// ⚠️ 零值 = **上限 0**（真的不让做），**不是"不限"**。
//
//	理由与 R36 的 `InterruptTTL` 是同一条，但**方向相反** —— 因为两者的
//	"忘记配置"后果不同：
//
//		InterruptTTL 零值 = 未设置 → 用默认    （后果：用默认，**安全**）
//		Limits       零值 = 上限 0 → 什么都做不了（后果：**立刻被发现**）
//
//	而**"不限"是一个需要被显式声明的决定** —— 用 `UnlimitedGuard`（空对象），
//	**不是靠字段的零值**。
//
// # ⚠️ 这一条来自精读 `EmptyLimiter` 的一次观察（R40）
//
//	```go
//	func (l *EmptyLimiter) AllowN(_ *common.Context, _ int) *AllowResult {
//		return &AllowResult{}   // ← 零值
//	}
//	```
//
//	那个零值里有两个字段，而它们**含义相反**：
//
//		Limited: false   → "不限"     ✅ 零值恰是想要的
//		Remaining: 0     → "没额度了" ⚠️ 零值恰是**相反**的意思
//
//	**同一个零值，两个相反的含义** —— 正是 R30 那个病
//	（`SessionStatusDeleted = 0` vs `ListOptions 0 = all`）的又一次现身。
//
//	它在这里没有造成事故（因为判据是 `Limited`），但**它是一颗埋着的雷**：
//	任何按 `Remaining` 判断"还能不能"的调用方都会得到相反的答案。
//	→ 我们的 `Decision` 用 `Exceeded`（哪一维超了）作为判据，
//	  而 `Remaining` **只在 `Exceeded == ""` 时有意义**（并在文档里写明）。
type Limits struct {
	Steps            int64
	PromptTokens     int64
	CompletionTokens int64
	Wall             time.Duration
	CostMilli        int64
}

// Decision 是一次检查的结果。
type Decision struct {
	OK        bool
	Exceeded  string   // 触顶的维度（""=没触顶）—— **必须说清是哪一维**
	Remaining Limits   // 剩余（**要给用户/模型看** —— 印证 L2-9 的 BudgetNotice）
	Notice    string   // 给**模型**看的一句话（可为空）
}

// Guard 是守卫。
type Guard interface {
	Allow(need Need) Decision
	ReportUse(used Used)
	Limits() Limits
	Used() Used
}

// UnlimitedGuard 是"不限"的显式实现（**不是 nil**）。
type UnlimitedGuard struct{}
func (UnlimitedGuard) Allow(Need) Decision { return Decision{OK: true} }
…

// ⚠️ `MultiGuard`（组合多个守卫）—— **本轮不实现**。
//
//	`guarded` 已经同时管**四维 + 时间**了，所以"组合多个维度"是内建的。
//	而 `MultiGuard` 要解决的是**另一个问题**：组合**多个作用域**的预算 ——
//
//		这一轮的总预算   （已在）
//		每个角色的子预算（不在 —— 我们还没有"子预算"这个概念）
//
//	**判据**：我们现在是"一轮一个 Guard"。做 `MultiGuard` = 为一个
//	还不存在的需求（子预算）预留机制 —— 而那正是我们一路在避免的。
//
//	触发条件：**当出现"某个角色要单独限一个额度"的真实需求时**
//	（比如"research 最多花 30% 的预算"）。
//
//	⚠️ 而那时要注意：组合的语义是**"任一超限即停"** —— 与"同一守卫内的多个维度"
//	**完全一致**（无论组合的是维度还是守卫，都是"任一超限即停"）。
//	**但要说清"OR"的主语是"超限"还是"放行"** —— 这是最容易混淆的地方。
type MultiGuard []Guard
```

**与 L3 的关系**：L3 已经有**两层有界**（`maxRunsPerNode` 同节点重做上限 +
`Graph.Next` 必然收敛）。**L4 的预算是第三层，而且是最外层** ——
它管的是"**这一轮总共能花多少**"，与"某一个节点能重做几次"是两个粒度。

> ⚠️ **两层有界的边界要划清**：`maxRunsPerNode` 防"一个节点打转"，
> 预算防"**整体跑不完/花不起**"。重复是不好的 —— 但**不是重复的**：
> 一个节点重做 4 次（在限内）× 20 个节点 = 80 步，**每一层都守住了自己那一半**。

### 4.3 `eval/` —— 评测集（**§2.5 的补课**）

```
eval/
  cases.jsonl          用例集（一行一个用例）
  README.md            说明怎么加用例、怎么读结果
```

```go
// Package eval 提供**离线可评测**：一组用例、一键跑完、给出可比指标。
//
// # 为什么它值得一个包（而不是一个脚本）
//
//	评测集最容易消失（原理四）：它不在业务代码里、没有调用点、每跑一次都花钱。
//	把它做成一个**有类型、有测试、有 README** 的东西，
//	至少让"删掉它"变成一次**显式的决定**，而不是"慢慢没人跑了"。
package eval

// Case 是一个评测用例。
type Case struct {
	ID    string            `json:"id"`
	Topic string            `json:"topic"`
	Hints map[string]string `json:"hints,omitempty"`
	Tags  []string          `json:"tags,omitempty"` // 用于跑子集（"只跑 smoke"）

	// Expect 是**硬判据**（原理五）：能由代码给出确定答案的那些。
	Expect Expectation `json:"expect"`
}

type Expectation struct {
	MustHaveKinds []schema.Kind `json:"must_have_kinds"`
	MinFindings   int           `json:"min_findings"`
	Pages         int           `json:"pages"`
	MaxSteps      int           `json:"max_steps"`
	MaxTokens     int           `json:"max_tokens"`
	MaxWall       time.Duration `json:"max_wall"`
	// MustContain / MustNotContain：页面上必须/不许出现的话。
	// ⚠️ 它们是**最便宜的硬判据** —— 一行字符串断言能挡住一大类回归。
	MustContain    []string `json:"must_contain,omitempty"`
	MustNotContain []string `json:"must_not_contain,omitempty"`
}

// Verdict 是一个用例的判定结果。
type Verdict struct {
	CaseID  string
	Passed  bool
	Failed  []string   // **每一条失败都要说清是哪一条判据**（可执行）
	Metrics Usage      // 这一轮的步数/token/时间/成本
	Judge   *Judgement // 软判据（可为 nil）
}

// Judge 是**软判据**：由模型判断"这份产物好不好"。
//
// ⚠️ 两个硬要求（原理五）：
//	① **它也是一次运行** —— 必须走同一个 Tracer，留 prompt/response
//	   （否则"为什么给 7 分"永远无法归因）；
//	② 它的**输出必须结构化 + 代码校验**（分数范围、理由非空、不许自创维度）——
//	   与 L0~L3 的 `SubmitTool` 是同一条。
type Judge interface {
	Judge(ctx context.Context, c Case, res Result) (Judgement, error)
}

type Judgement struct {
	Scores map[string]int `json:"scores"` // 维度 → 分（**维度是受控词表**）
	Reason string         `json:"reason"`
}
```

```

--------------------------------------------------------------

short-topic     ✅      5     4610    980   0.3s   —
no-findings     ❌      4     3120    640   0.2s   min_findings: 期望 ≥1，实际 0

## 5. 四个故障注入

延续 L2/L3 的工具箱风格（每个对应一个**真实的失败方式**）：

```powershell
$env:L4_LOOP_FOREVER="outline"   # 让某节点无限重做自己 → **必须被预算拦在 maxRunsPerNode 之前/之后**
$env:L4_HUGE_TOKENS="1"          # 伪造一次超大用量 → 触顶 → **降级交付 + 说明，而不是报错**
$env:L4_BAD_CASE="1"             # 往用例集里注入一个必然失败的用例 → 验证**指标会动**
$env:L4_JUDGE_REFUSES="1"        # Judge 返回非法结构 → 走**回灌自愈**（L0 的通道）
```

**其中第 2 条是验收标准的核心**："**预算超限时直接报错丢失可用结果**"
是教学计划里点名的"可能问题" → 所以触顶的行为**必须是"交付部分 + 说明"**，
而不是 `return err`。这与 L2-9 的"触顶但已提交要保留成果"是同一条。

## 6. 明确**不做**（+ 触发条件）

| 不做 | 理由 | 触发条件 |
|---|---|---|
| **接 OTel / Prometheus** | L4 的重点是"**观测模型**"，不是"接哪个后端"。端口定好了，适配器是机械工作 | 真要上生产监控时 |
| **在线采样 / 分级上报** | 我们没有"流量"这个概念（CLI 单次运行） | 变成服务时 |
| **Judge 用真实模型自动跑** | 每一轮都花钱；而**判据的稳定性**要先在离线替身上验证 | 用例集稳定之后（L5） |
| **持久化历史指标**（跨运行的数据库） | 现在只需要"两次运行对比" | 需要看**一段时间的趋势**时 |
| **条件边判据的命中率** | 需要先有"人标注的正确答案" | 有标注数据时（L5） |
| **`cachedTokens` / `reasoningTokens`** | 我们的替身没有"缓存"概念 | 接真实模型跑评测时 |

## 7. 三个设计问题（留给你回答）

**Q1.** 原理三说 `Allow` / `ReportUse` 分离有 TOCTOU 窗口，企业仓库**选择接受**。
那么：**我们该接受吗？**（提示：想想我们的运行形态 —— CLI 单进程、串行节点。
 如果并发是 1，那个窗口还存在吗？如果不存在，"接受它"这个说法还准确吗？）

**Q2.** §2.5 说企业仓库**有可观测、没有评测集**，而原因是
"**立刻的后果赢过缓慢的后果**"。那么反过来：
**如果评测集做错了（比如用例只有 3 个、但都很难），会发生什么？**
