## 1. 为什么 L3 必须做这三件事

不是"因为教学计划里有"，而是 **L2 留下了三个具体的洞**：

| L2 复盘编号 | 洞 | 具体表现 |
|---|---|---|
| **L2-8** | 编排是**中心化串行**，表达不了并行与条件 | "素材不够就再搜一轮"做不到，只能靠 Prompt 求模型 |
| **L2-6** | 没有 HITL | 用户唯一能干预的时刻是"之前"和"之后" |
| **L2-7** | 黑板在内存、磁盘同名覆盖 | **进程一挂，四份产物全丢**；且"黑板说的文件 ≠ 磁盘上的文件" |

再加上 R27（接真实模型）打出来的一个**新**的：

| L2-9 | 编排者**做了一件有确定答案的事，却用了一个概率性的方法** | 它花了 10009 prompt 去"决定"一件早写在 `Needs()` 里的事 |

**这四条指向同一个结论：**

> **L2 的 Supervisor 是一个"用 LLM 实现的状态机"。**
> 它做的事（按依赖顺序调度）**本来就有确定答案**，
> 却交给一个概率模型每轮重新推一遍 —— 于是它**不可测、不可复现、不可恢复**。

L3 就是把它**降级成一个真正的状态机**。

## 2. 原理一：为什么需要"显式图"

### 2.1 我们其实**已经有一张图了**

看 L2 的四个角色：

```
research.Needs()   = []                    → 无前置
outline.Needs()    = [research]            → 前置 research
designer.Needs()   = [outline]             → 前置 outline
renderer.Needs()   = [outline, design]     → 前置 outline + design
```

**这五行就是一张有向无环图。** 拓扑排序的结果恰好就是 L2 实测出来的执行顺序
（R27 的真实运行：`research → outline → design → render`，一次走对）。

而 L2 的 `Supervisor` 在干什么？

```
它拿着这五个角色，每一轮把「工具清单 + 全部历史」发给模型（实测 10009 prompt），
让模型**重新推一遍**"下一步该派谁" —— 而这个答案早就写在 Needs() 里了。
```

> ### 结论
> **L2 的编排者做了一件有确定答案的事，却用了一个概率性的方法。**
>
> 代价是三样，全都实测过：
> · **不可测** —— 路由准确率算不出来（企业仓库 D2 是同一个病）
> · **不可复现** —— 同一主题两次运行，编排序列可能不同
> · **不可恢复** —— 它没有"执行到哪了"这个概念，进程一挂就得从头来

### 2.2 判据：**谁决定下一步**

| 问题 | 谁适合答 | 形态 |
|---|---|---|
| "下一步做 research 还是做 outline？" | **代码**（答案在 `Needs()` 里） | **图的边** |
| "这一步该怎么做？" | **模型**（要读素材、要组织语言） | **Agent 节点** |
| "素材够不够，要不要再搜一轮？" | **代码**（数一数 `Findings` 有几条） | **条件边** |
| "用户说'删掉第 3 页'，是什么意思？" | **人** | **中断** |

一句话：

> ### 图负责「谁下一步」，Agent 负责「这一步怎么做」。
> **图是确定的骨架，Agent 是每根骨头里的肌肉。**

### 2.3 "哪里用图、哪里用 Agent"——L3 的立场

企业仓库是**两套范式并存**（01 索引的隐患 **G**）：
主链路用 Supervisor（自主路由），V5 用 Graph（确定性），A2A 用远端 Agent —— 三套互不相通。

**我们不这么做。** 我们的立场是：

> **Agent 是图里的一种节点类型，不是另一套系统。**

```
┌───────────── 图（确定性骨架：节点 + 边）─────────────┐
│  research ──▶ outline ──▶ [中断] ──▶ design ──▶ render │
│     ↑                                                │
│  每个节点内部是一个 Agent（ReAct 循环，模型自由决策）      │
└──────────────────────────────────────────────────────┘
```

好处很直接：**只有一套东西** —— 一套可观测（Observer）、一套成本统计、一套状态（黑板）。

### 2.4 边从哪来？—— **不需要手写**

这是本轮最漂亮的一个结论：

> **`Needs()` 已经是图的一部分了。L3 只是把它画出来。**

```go
// 概念示意：由 Needs() 自动推导出边
for _, sub := range subs {
	for _, dep := range sub.Needs() {
		edges = append(edges, Edge{From: string(dep), To: string(sub.Kind())})
	}
}
```

于是：

- **加一个角色** → 只写它的 `Needs()`，图自动多几条边；
- **改依赖** → 只改 `Needs()`，图、前置检查、工具描述**三处自动同步**；
- **并行** 也白拿 —— 如果将来加一个只依赖 `outline` 的"配图"角色，
  它会和 `designer` 自动排成**同一层**，不需要谁去说"这两个可以并行"。

这直接兑现了 L2-8（"表达不了并行与条件"）的前半句。

### 2.5 那么 Supervisor 怎么办？

| 选项 | 评价 |
|---|---|
| 完全删掉 | ⛔ 太激进 —— 真需要"事先不知道要做什么"时，图表达不了 |
| 保留它管路由 | ⛔ 那图就白建了 |
| ✅ **关掉它在 L3 链路上的路由职责；把它的角色降为"图的一个可选节点"** | 需要自由探索的场景才用它 |

**并且明确记录代价**：这样做之后，"素材不够就再搜一轮"这类**语义判断**必须由**代码判据**表达
（比如 `len(Findings) < 3` → 回到 research）。这**牺牲了一点灵活性，换来可测与可恢复**。

> 这就是面试题"显式图 vs 隐式对话"的标准答案形状：
> **不是谁更好，而是你愿不愿意用灵活性换可测性 —— 而这取决于你的场景能否事先枚举出判据。**

## 3. 原理二：Checkpoint 存什么、存在哪

### 3.1 一个意外的红利：**L2 的黑板天生可持久化**

回顾 `schema.Artifact`：

```go
type Artifact struct {
	Key, Kind, Version, ProducedBy, Summary string/int
	Shortfall []string
	BasedOn   []Basis
	Payload   json.RawMessage     // ← 关键
}
```

**`Payload` 是 `json.RawMessage`（字节），不是 `any`（接口）。**

这是 L2 设计时的一个刻意选择（为了"只有真正要用它的人才解它"），
但它在 L3 变成了一个**白拿的好处**：

> **黑板可以整个 `json.Marshal` 出去、再 `Unmarshal` 回来，不需要任何类型注册表。**
>
> 对比：如果 `Payload` 是 `any`，序列化就必须记住每个 key 对应哪个具体类型 ——
> 那正是企业仓库 `InterruptInfo` 那个"并集结构 + switch"要解决的问题。

**这是"选对了数据表示"在两年后（阶段后）才兑现的回报。**

### 3.2 状态 = 黑板快照 + 游标

```go
// State 是图的一次完整快照。
type State struct {
	Version   int                       `json:"version"`    // ← 协议版本（见 §4）
	RunID     string                    `json:"run_id"`
	Node      string                    `json:"node"`       // 游标：执行到哪个节点
	Done      []string                  `json:"done"`       // 已完成节点（跳过判据，见 §5）
	Board     map[string][]schema.Artifact `json:"board"`   // 黑板全量快照
	Pending   *Interrupt                `json:"pending,omitempty"`
	UpdatedAt time.Time                 `json:"updated_at"`
}
```

三个要点：

1. **`Board` 是快照，不是引用。** 恢复时整块换回去 —— 因为黑板本来就是 append-only 的不可变结构，
   "换回去"和"原来那份"在语义上完全等价。
2. **`Node` 是游标，`Done` 是已完成集合。** 两者都要：游标回答"接下来跑谁"，
   `Done` 回答"谁可以跳过"（§5 会说明为什么光有游标不够）。
3. **不存 `any`、不存闭包、不存 channel。** 状态必须是**纯数据** ——
   "哪些东西可以被序列化"这条线，划在"能不能跨进程"上。

### 3.3 两种 store 的分界：**谁来解它**

企业仓库有**七个 store**，其中两个与我们直接相关：

| | `CheckPointStore` | `InterruptStore` |
|---|---|---|
| 接口 | `Set(key, []byte)` / `Get(key) ([]byte, bool, error)` | `Set(key, any)` / `Get(key) (*InterruptInfo, bool, error)` |
| 内容 | **不透明字节** | **结构化 + 类型名** |
| 归属 | 图运行时（框架自己解） | 业务（要渲染给用户看、要注入用户答案） |
| 加一种新数据 | 不用改 store | **要改三处 switch**（见 §4） |

> ### 判据：**谁来解它**
> · **框架自己解的** → 存不透明字节，store 不该知道格式；
> · **业务要解的** → 必须能还原成具体类型，于是**必然**要类型名 + 分派。

这条判据比"都是状态所以放一起"精确得多。它同时解释了为什么
`SessionLocker` **只支持 memory/redis**（没有 ks3/mongo）——
因为**锁必须强一致，对象存储做不到**：

> **"能换后端"不是无条件的能力，是由数据的语义（一致性要求）决定的。**

## 4. 原理三：中断发生在进程内，而等待跨越了进程

### 4.1 为什么中断这么难

L2 的 `Critic`（L1）也好、`follow_up` 也好，中断**发生在一次 `Run` 内部**：

```
Run() ──────┤ 中断 ├────── 继续
            ↑
        还在同一个调用栈里
```

但 HITL 要的是：

```
Run() ──┤ 中断 ├──▶ 返回给用户 ──▶ 【进程结束 / 用户明天才回】 ──▶ 恢复
                       ↑                                    ↑
                  同一个进程                          可能**另一个进程 / 另一个 pod**
```

> ### 核心矛盾
> **中断发生在进程内，而"等人"跨越了进程边界。**
> 所以中断状态**必须从进程里搬出来**，而且要能被一个**完全不记得刚才发生了什么的进程**读回来。

这一句就解释了企业仓库为什么有**两套中断序列化机制并存**：

| 机制 | 位置 | 用途 |
|---|---|---|
| Eino 的 `schema.Register[*T]()` + `StatefulInterrupt` | `tools/localtools/follow_up.go` | **框架内部**流转（同一个 runner 内） |
| 企业自己的 `interruptEnvelope{TypeName, Data}` | `store/interruptstore/redis.go` | **跨 HTTP 请求**持久化（另一个 pod 也能读） |

**两套机制序列化的是同一个 `FollowUpInfo`。** 这不是重复劳动，而是
**"进程内"与"跨请求"是两个不同的边界** —— 各自都要一次序列化。

> 我们 L3 只做**一套**（跨请求那套），因为我们没有"框架内建的中断机制"。
> **少一套 = 少一处会漂移的地方。** 这是我们的结构优势，要写清楚。

### 4.2 企业仓库的中断信息为什么是一团"并集"

```go
type InterruptInfo struct {
	FollowUpInfo         *localtools.FollowUpInfo
	ConfirmOutlinesInfo  *localtools.ConfirmOutlinesInfo
	ConfirmStorylineInfo *localtools.ConfirmStorylineInfo
	AIPPTOutlineChatInfo *localtools.AIPPTOutlineChatInfo
}
```

四个可选字段，**恰好一个非 nil**。为什么写成这样？

因为 Go 的 `json.Unmarshal` **无法解到一个接口**（`any`）—— 必须先知道具体类型。
于是"存的时候记下类型名、读的时候 switch 回去"：

```go
// Set：按**具体类型**挑一个字符串
switch value.(type) {
case *localtools.FollowUpInfo:        typeName = "FollowUpInfo"
case *localtools.ConfirmOutlinesInfo: typeName = "ConfirmOutlinesInfo"
...
default: return fmt.Errorf("unsupported type %T", value)
}

// Get：按**字符串** switch 回具体类型
switch env.TypeName {
case interruptTypeFollowUp:         v := &localtools.FollowUpInfo{}; ...
case interruptTypeConfirmOutlines:  v := &localtools.ConfirmOutlinesInfo{}; ...
default: return fmt.Errorf("unknown type %q", env.TypeName)
}
```

### 4.3 由此得到 **F1 的真实形态**（比索引里写的更严重）

01 索引把 F1 记成"类型改名 → 旧 checkpoint 无法恢复"。看完代码，更准确的描述是：

> **加一种新的中断类型，要改四处：**
> ① `InterruptInfo` 加一个字段
> ② `Set` 的 `switch value.(type)` 加一个 case
> ③ `Get` 的 `switch env.TypeName` 加一个 case
> ④ `controller` 里注入用户答案的 `if/else` 再加一个分支
>
> 而且**这四处没有任何编译期约束把它们绑在一起** —— 漏一处，就是运行期的 `unknown type`。

这正是我们反复遇到的同一个病：**"约束没有单一来源"**。

### 4.4 我们的中断协议（F1 / F2 的靶子）

```go
// Interrupt 是一次"等人来定"的中断。
type Interrupt struct {
	Version int    `json:"version"`   // ① 协议版本 —— F1 的靶子
	RunID   string `json:"run_id"`
	Node    string `json:"node"`      // 在哪个节点中断
	Kind    string `json:"kind"`      // ② **业务枚举**，不是 Go 类型名
	Prompt  string `json:"prompt"`    // 给人看的问题
	Options []string `json:"options,omitempty"`
	Payload json.RawMessage `json:"payload,omitempty"` // 业务自己要带的
}

// Decision 是人的回答 —— **三种意图**，不是一个字符串（F2 的靶子）
type Decision struct {
	Intent Intent `json:"intent"` // confirm / revise / abort
	Note   string `json:"note"`   // revise 说明改什么；abort 说明为什么
}

type Intent string
const (
	IntentConfirm Intent = "confirm" // 就这样，继续
	IntentRevise  Intent = "revise"  // 不对，回到某个节点重做
	IntentAbort   Intent = "abort"   // 不做了，带着已完成的部分收尾
)
```

**四处关键改进，每一处都对着企业仓库的一个具体隐患：**

| # | 我们 | 企业仓库 | 解决了什么 |
|---|---|---|---|
| 1 | `Version int` | 无版本号 | 未来协议变更时**能判"这条记录太老，无法恢复"**，而不是 `unknown type` 崩溃 |
| 2 | `Kind` 是**业务枚举**（`"confirm_outline"`） | `typeName` 是 **Go 类型的字符串名**（`"FollowUpInfo"`） | 协议与**代码结构**解耦 —— 重构改名不会让旧记录失效 |
| 3 | **无 `switch`** —— `Payload` 是 `json.RawMessage` | 两处 switch + 并集字段 | **加一种中断类型不用改 store**（因为 store 只管字节，见 §3.3 的判据） |
| 4 | `Intent` 三态 | `UserAnswer string` | 用户能说"删掉第 3 页"，而不是被当成"确认"（S7） |

### 4.5 `IntentRevise` 第一次让 **L2-1 的血缘/新鲜度**有了真实用途

这是本轮最值得记的一条**设计闭环**：

L2 我们做了两样东西，当时只有"演示"级别的用途：

| L2 的产出 | L2 时的用途 |
|---|---|
| `Artifact.BasedOn` + `StaleReasons` | 靠 `L2_REDO` 故障注入才能演示 |
| `Artifact.Shortfall`（部分成功） | 靠 `L2_RENDER_FAIL` 故障注入才能演示 |

**到 L3，它们各自找到了真实的触发点：**

```
用户在大纲处选了「revise：第 3 页换成建议」          ← F2 的场景，L3 的真实输入
        ↓
代码把 outline 重做 → outline@2
        ↓
StaleReasons(design@1)  →  design@1 依据的 outline@1 已更新到 outline@2
StaleReasons(render@1)  →  同理
        ↓
**图据此算出"哪些节点已被污染"，把它们从 Done 里摘掉，重新执行**
```

> **用户改一个字，系统自动知道要重做哪几步** —— 这就是"血缘"存在的全部理由。
> L2 埋的这颗种子，L3 才发芽。

同理，`Shortfall` 在 L3 的用途是 §5 的"能不能跳过"。

## 5. 原理四：幂等与可重放 —— **跳过，还是重跑？**

### 5.1 先看现实：不是所有节点都能重放

| 节点 | 给定同样输入，输出相同吗？ | 能不能重放 |
|---|---|---|
| `research` | ❌ 真实检索每次结果不同（企业仓库的 `web_search` 也一样） | **不能** |
| `outline` | ❌ 模型有随机性 | 不能保证 |
| `designer` | ❌ 同上 | 不能保证 |
| `renderer` | ✅ **不调模型**，纯函数式模板（L2 实测 `TestRendererIsIdempotent`） | **能** |
| **写盘副作用** | ✅ 同名覆盖，且 L2 做了冲突预检 | **能** |

**所以"让每个节点都幂等"是一个做不到的目标。**

### 5.2 正确的问法

> **不是"怎么让节点幂等"，而是"重放一个节点，会不会造成不可逆的破坏"。**

按这个判据分两类：

| 类型 | 例子 | 重放的后果 |
|---|---|---|
| **纯计算 / 读** | research / outline / designer | 只是**多花 token**，状态不会坏 |
| **有副作用** | renderer（写盘） | 覆盖已有文件 —— **可能把已完成的工作覆盖掉** |

于是策略就很清楚了：

> ### 默认「跳过已完成」，只对「有副作用的节点」做重放保护。

### 5.3 但"已完成"是什么？—— **L2 的判据在这里第二次兑现**

恢复时怎么判断一个节点"可以跳过"？如果判据是"它跑过了"，就会踩到 L2 复盘里那条：

```
renderer 跑过了，但 3 页里失败 1 页        ← "存在 ≠ 完整"（L2-2）
design@1 跑过了，但它的依据已经被上游改掉  ← "存在 ≠ 有效"（L2-1）
```

**所以"完成"的判据，恰好就是 L2 已经定好的那三条：**

> ### 一个节点可以跳过 ⟺ 它的产物 **存在 ∧ 完整 ∧ 新鲜**
>
> · 存在 —— `Versions(key) > 0`
> · 完整 —— `Artifact.Shortfall` 为空（L2-2）
> · 新鲜 —— `StaleReasons(a)` 为空（L2-1）
>
> **这三条在 L2 是"能不能交付"的判据，在 L3 是"能不能跳过"的判据。**
> 同一套语义，两种用途 —— 这说明它抓到的是**本质**，不是某个场景的巧合。

**这是一个很强的架构信号**：一个判据能跨阶段复用，说明它描述的是"什么算完成"这件真事。

### 5.4 可重放的第二个前提：副作用要能**抵消**

`renderer` 之所以安全，是因为"写盘"满足：

1. **幂等**：同一份内容写两次，磁盘上的结果一样；
2. **可覆盖**：不追加、不修改别的文件（L2 做了同名冲突预检）。

而"发一封邮件""调用一次付费 API"就不满足 —— **它们没有回滚手段**。

> 判据：**这个副作用能不能被"再做一次"抵消？**
> 能 → 可以重放；不能 → 必须由 `Done` 集合保护，**绝不允许重放**。

## 6. 原理五：状态出了进程，就必然有并发问题

### 6.1 一个 L2 完全没考虑过的问题

L2 时代：黑板在内存里，`Supervisor.Run` 串行跑完 —— **只有一个执行者**，没有并发写。

L3 时代：状态存到磁盘/Redis，**两个请求可能同时操作同一个 run**：

```
请求 A：读 checkpoint@5 ──────────▶ 推进到 @7 ──▶ 写回 @7
请求 B：     读 checkpoint@5 ──────────▶ 推进到 @6 ──▶ 写回 @6
                                    ↑
                        两者都基于 @5，A 的工作凭空消失
```

**一旦状态出进程，"谁有权威改它"就必须有一个答案。**

### 6.2 企业仓库的答案：`SessionLocker`（教科书级）

```go
	locked, unlock, lockErr := h.SessionLocker.TryLock(ctx, session.ID)
	if lockErr != nil { ...500... }
	if !locked {
		result.BuildResultError(c, http.StatusConflict, result.CodeSessionBusy,
			"session is being processed by another request")   // ← 409 Conflict
		return
	}
	defer unlock()
	// ……整个请求处理（模型编排 + 流式输出）都在锁内……
```

**七个细节，每一条都对应一个真实的分布式锁坑：**

| # | 做法 | 不这么做会怎样 |
|---|---|---|
| 1 | `SetNX` + **UUID token** | 盲删/盲续会删掉**别人的**锁 |
| 2 | **短 TTL（5s）+ 后台续期（TTL/3）** | 进程崩了锁永久占用，整个 session 卡死 |
| 3 | 解锁用 **Lua compare-and-delete** | 检查 token 再删 —— 不能盲删 |
| 4 | 续期用 **Lua compare-and-expire** | 同上 |
| 5 | `renewCtx` **独立于请求 ctx**，`ctx.Done()` 另做安全网 | "请求结束"会在 `defer unlock` **之前**把续期取消掉（注释里专门写了这一点） |
| 6 | 续期返回 `0` → **"lock lost during renewal" → 停止续期** | 锁被别人抢走了却不知道 → **两个执行者同时以为自己持有锁** |
| 7 | `sync.Once` 包解锁 | unlock 幂等 |

### 6.3 ⚠️ 但第 6 条**只做了一半** —— 本轮新发现的问题

```go
			if res == 0 {
				ctx.Logger.Warnf("SessionLocker: lock lost during renewal (key=%s), stopping", key)
				return
			}
```

**它发现了锁丢失，但只是打了一条 Warn 日志，然后停止续期 —— 请求本身继续跑，继续写状态。**

于是锁丢失之后：

```
进程 A：锁过期了（GC 停顿 / CPU 饥饿超过 5s）→ 续期返回 0 → 只打了日志 → **继续干活、继续写**
进程 B：抢到锁 → 也读 @5 → 也推进 → 也写
        ↓
**两个执行者同时写同一个 session 的状态** —— 正是这把锁本来要防的事
```

> ### 新问题 **F3**：续期发现锁丢失时**只记录、不中止**
> 证据：`sessionlocker/redis.go:91-93`
> 风险：锁的失效**被降级成了一条日志**，于是它保护不了它该保护的东西。
>
> 这与我们 L1/L2 反复遇到的是**同一个病**：
> **重要事实被降级成日志 = 等于没发生**（L1-3、L2-11 都是它）。

**我们 L3 的对策**（设计层面，实现可视化到：

```go
// TryLock 除了返回 unlock，还返回一个**失效通道**。
// 续期发现锁被抢走时关闭它 —— 调用方必须监听：
//   · 图执行到一半发现收到信号 → **停止推进、放弃写回**（而不是继续写）
TryLock(ctx, runID) (locked bool, lost <-chan struct{}, unlock func(), err error)
```

**"锁丢了要能停下来"比"锁丢了要能发现"重要一个数量级。**

### 6.4 但 L3 要不要**实现**它？

**诚实回答：L3 不实现完整版，只实现接口 + 单进程实现。** 理由：

1. **我们的运行形态是 CLI 单进程** —— 没有第二个执行者，锁没有对手；
2. 引入 Redis 会带进一个**外部依赖**，而 L3 的教学重点是"状态怎么出进程"，不是"怎么协调多进程"；
3. **但概念必须记下来** —— 它是面试题"中断/恢复怎么保证状态一致"的**核心答案**。

> 这条判断力本身值得写进日志：
> **"不需要"有两种 —— 一种是"想过了，我的场景用不上"，另一种是"没想到"。**
> 前者是设计，后者是漏洞。

**触发条件写明**：当出现**第二个执行者**时（多实例部署 / 后台任务与前台请求并存），必须补上。

### 8.2 核心接口

```go
// ─── graph ───

// Node 是图里的一个节点。**它不知道图的存在** —— 只负责"做这一步，然后说下一步怎么选"。
type Node interface {
	Name() string

	// Run 执行一步。返回 nil outcome 表示"按出边规则决定下一步"。
	Run(ctx context.Context, st *State) (*Outcome, error)
}

// Outcome 是节点的执行结果。
type Outcome struct {
	// Next 非空则**强制**跳到这个节点（条件边的一种显式形式）。
	Next string

	// Interrupt 非 nil 表示在这里停下来等人 —— 它会连同 State 一起被持久化。
	Interrupt *Interrupt
}

// Edge 是一条出边。When 为 nil 表示无条件。
type Edge struct {
	From, To string
	When     func(*State) bool
}

type Runner struct {
	nodes  map[string]Node
	edges  map[string][]Edge
	store  checkpoint.Store
}
```

```go
// ─── agents/node.go：原则五的第三次应用 ───
```

```go
// Save 必须原子 —— 否则"写到一半进程被杀"会留下一个**半截的 JSON**，
```

## 10. 三个设计问题（我的答案）

> 用户说「继续」= 按我的方案来。答案写在这里，**实现要照着它做**。

### Q1 答案：**条件边**，但判据可以"不精确"，**绝不能"无界"**

选 (a)，原因是 (b) 的代价我们已经精确测量过 —— **10009 prompt**（R27），换来一个不可测、不可复现的路由。

但 (a) 有个真问题：`len(Findings) < 3` 是一个**硬阈值**，而"素材够不够"本质上是语义判断。阈值定 3 还是 5，都是拍脑袋。

**我的解法：允许判据不精确，但由代码保证它有界。**

```go
// research → research（兜底重搜一次，仅一次）
Edge{From: "research", To: "research", When: func(st *State) bool {
	return tooFewFindings(st) && st.Attempts("research") < maxResearchAttempts
}}
```

> ### 判据可以"不精确"，但不能"无界"。
> **企业仓库的做法正是这个**：`EarlyFailed` 之后**不再重试**（有界），
> 而不是"让模型决定要不要重试"。
>
> 一个不精确但有界的判据，最坏结果是"多花一次 token"；
> 一个精确但无界的判据，最坏结果是"跑不完"。

### Q2 答案：**不一定。而且"新鲜"对根节点意味着"输入没变"** —— 这里有个真问题

`research` 满足"存在 ∧ 完整"时**仍可能不该跳过**：

> **根节点的上游是「用户输入」（主题）。如果用户改了主题，`research@1` 虽然存在且完整，
> 但它依据的是一个已经不存在的输入。**

**解法：给根节点也造一个上游产物。** 开始运行时，代码往黑板写一份虚拟产物：

```
topic@1（由代码写入，不调用模型）
   ↓ BasedOn
research@1 → outline@1 → design@1 → render@1
```

于是：

| 收益 | 说明 |
|---|---|
| **判据统一，没有特例** | 所有节点都是"依据某些产物"，`StaleReasons` 一路通用 |
| **"改了主题"白拿** | 用户换主题 → `topic@2` → `StaleReasons` 自动把 research 及以下全部标脏 —— **不用为"改主题"写任何特殊逻辑** |

> ### 统一比精确更重要 —— 因为**特例是漏洞的温床**。
> 只要有一个节点"不适用新鲜度检查"，就必须在每个用到它的地方都记着
> "哦，这个要特殊处理"。**需要记住的例外，迟早会被忘掉。**

### Q3 答案：**是"想过了"**。四条证据

| # | 证据 | 为什么它能证明 |
|---|---|---|
| 1 | 文档里写了实现的**主体**（TTL/续期/Lua/幂等解锁，七个细节） | **"没想到"的人写不出这七条** |
| 2 | 写明了**触发条件**（"出现第二个执行者时补上"） | "没想到"的人不知道什么时候需要它 |
| 3 | 写明了**为什么不用**（CLI 单进程 + 不引入外部依赖） | 这是**场景判断**，不是"缺能力" |
| 4 | **它出现在"待办"里，而不是"未提及"里** | 见下 |

> ### 判据
> **"没想到"的产物是「沉默」；"想过了"的产物是「一条带触发条件的待办」。**
>
> 换句话说：**能被审计的"不做"，才是决定；不能被审计的"不做"，是疏漏。**
>
> 这也是 R8 精读给的启发 —— 企业仓库 `newA2ATaskStore` 的
> `case config.ContextStoreTypeMemory: return nil, nil` 也是一种"能被审计的不做"。

### ⚠️ 顺带修正一处设计（实现前发现的）

§3.2 我原本设计了三个状态字段：`Node`（游标）+ `Done`（已完成集合）+ `Board`。

**写实现时发现前两个是冗余的：**

> · **"完成"是产物的属性，不是节点的属性** —— 产物在，节点就是完成了；
> · **"接下来跑谁"** 可以从"谁的依赖齐了、但产物还没齐"推导出来。

删掉它们之后：**状态不可能自相矛盾**（不会出现"游标说在 render、但 design 还没做"），
恢复时也**不需要"从游标往后跑"**，只需要问"现在缺什么"。

> **这就是"黑板即状态"的完整含义：位置由产物推导，不由游标记录。**
> （`graph.State` 只保留三样**不可推导**的东西：`Version` / `Topic`（输入）/ `Pending`（人的决定））
