# 多智能体协同开发 · 完整教学计划

> **项目**：`MultiAgentProgram`（从零手写）
> **学习资料**：`beautifulagent-go`（企业级生产项目，只读参考）
> **目标**：吃透多 Agent 架构设计与工具编写，形成面向大厂 Agent 开发岗的可展示作品
> **方式**：以"搭框架、写 Demo"为主线，由 AI 引导逐步实现

---

## 一、学习目标

分为三层，层层递进、逐层验收：

### 1. 认知层（能说清）

- 能讲清 5 种多 Agent 编排范式（Pipeline / Supervisor / Graph / GroupChat / Peer）的**取舍**；
- 能讲清"多 Agent 之间该传自然语言还是结构化产物"以及**为什么**；
- 能讲清 Agent 系统为什么必须有**预算控制**、**上下文管理**、**可恢复性**。

### 2. 工程层（能做出来）

- 独立实现：Agent 循环、工具注册与调用、Supervisor 编排、状态图编排；
- 独立实现：HITL 中断/恢复、状态持久化、预算守卫、评测集与回归；
- 能定位并修复多 Agent 系统的典型故障（丢字段、死循环、上下文丢失）。

### 3. 表达层（能讲清 why）

- 对每个设计决策，能给出**至少 2 个被否决的替代方案**及否决理由；
- 能给出**量化结果**（任务成功率 / token 成本 / 返工率），而不只是"感觉变好了"。

## 二、技术选型与理由

| 维度 | 选择 | 理由 |
|---|---|---|
| 语言 | **Go** | 与学习资料 `beautifulagent-go` 同语言，概念可 1:1 对照 |
| 框架 | **不用框架，手写最小运行时** | Eino / LangGraph 会把编排、上下文、终止藏在内部，不利于理解本质 |
| 依赖 | **尽量只用标准库** | 降低环境成本；除真实模型调用外零第三方依赖 |
| 模型 | **抽象为 `llm.Client` 接口** | 内置 Mock → 离线可跑、可复现；可切换到任意 OpenAI 兼容服务 |
| 存储 | **先文件，再可选 Redis** | 由简到繁，突出"持久化到底解决什么问题" |

> **关键决策**：为什么不用 Eino？
> 因为我们的目标不是"会用一个框架"，而是"理解框架替你做了什么"。
> 学完手写版后，再回头看 Eino 的 `supervisor.go`，你会一眼看出它在解决什么问题。

## 三、教学循环（每一阶段固定四步）

```
① 设计  →  我讲知识点，你回答"为什么这样做 / 不那样做"
② 实现  →  一起写 Demo（可运行是硬要求）
③ 复盘  →  我指出这个 Demo 存在的问题、可能出现的情况
④ 改进  →  对照主流做法 → 再回企业仓库精读印证 → 决定是否改进
             ↓
          进入下一阶段
```

**注意**：每一阶段都必须走完 ③④，否则只是"抄了一遍代码"，拿不到面试分。

## 五、各阶段详解

### P0 · 地基（Foundation）

| 项 | 内容 |
|---|---|
| 🎯 **知识点** | ① 端口-适配器（Ports & Adapters）分层；② 统一 Message 模型（system/user/assistant/tool）；③ Tool 契约 = 名字 + 描述 + 参数 JSON Schema；④ LLM 抽象与"测试替身" |
| 🛠 **实践任务** | 定义 `message` / `tool` / `llm` 三个包；实现 `MockClient` 与 `OpenAIClient`；实现 `boot.NewClient` 做环境切换 |
| 📦 **产出物** | `go run ./cmd/l0` 在**不填任何密钥**的情况下跑通一次模型调用 |
| ✅ **验收标准** | ① 无密钥可运行；② 设 `MULTIAGENT_LLM=openai` 可切真实模型；③ 换模型不改动业务代码 |
| ⚠️ **可能问题** | 接口设计过早耦合实现细节；Mock 行为与真实模型不一致，导致"Mock 通过、真实失败" |
| 🔧 **主流做法** | 依赖倒置 + 契约测试；Mock 与真实实现共用同一套接口测试用例 |
| 🎤 **面试考点** | 为什么要抽象 LLM 层？抽象错了一层会付出什么代价？ |

---

### L0 · 单 Agent + 工具 + ReAct 循环

| 项 | 内容 |
|---|---|
| 🎯 **知识点** | ① ReAct 循环（Thought → Action → Observation）；② 工具调度与参数解析；③ **终止条件**（无 tool_call 即结束 / 最大步数兜底）；④ 工具错误回灌自愈 |
| 🛠 **实践任务** | `agent.Agent.Run` 实现循环；实现 `render_slide_html`（真写入文件）与 `web_search`（Mock 数据）；`cmd/l0` 端到端演示 |
| 📦 **产出物** | 输入一个主题 → 输出 1 页 16:9 HTML 幻灯片（落盘 `out/`） |
| ✅ **验收标准** | ① 能打印完整事件流（assistant → tool_call → tool_result → final）；② 工具参数非法时返回结构化错误且模型能纠正；③ 超过 MaxSteps 时优雅终止 |
| ⚠️ **可能问题** | 见 [六、L0 复盘](#六l0-复盘预设问题) |
| 🔧 **主流做法** | 工具描述即文档；错误结构化；终止条件双保险（自然结束 + 硬上限） |
| 🎤 **面试考点** | ReAct 靠什么终止？工具粒度怎么定？错误为什么不直接抛给用户？ |

---

### L1 · 双 Agent + Critic 评审闭环

| 项 | 内容 |
|---|---|
| 🎯 **知识点** | ① 反思（Reflection）机制；② 评审输出应是**结构化问题清单**而非分数；③ 返工上限与收敛判断；④ Agent 级失败语义 |
| 🛠 **实践任务** | 实现 `critic` Agent（独立 System Prompt）；实现 `layout_check` 工具（返回结构化问题）；在 L0 基础上加"生成→评审→返工"循环 |
| 📦 **产出物** | 一个会"自己发现爆版并返工"的生成器 |
| ✅ **验收标准** | ① 人为注入爆版，Critic 必须发现；② 最多返工 N 次后强制交付；③ 打印每轮问题数量变化 |
| ⚠️ **可能问题** | Critic 与 Generator 互相拉扯无限循环；Critic 过度挑剔导致"改坏";返工次数没有上限 |
| 🔧 **主流做法** | 返工预算 + 收敛判据（问题数不再下降即停）；Critic 用不同模型/不同温度 |
| 🎤 **面试考点** | 为什么需要 Critic？如何避免"评审-返工"死循环？ |

---

### L2 · Supervisor + 多 SubAgent + 结构化协议

| 项 | 内容 |
|---|---|
| 🎯 **知识点** | ① 中心化编排与 transfer 机制；② **结构化 handoff**（Schema 强校验）；③ 共享黑板（Blackboard）；④ 关注点分离：编排者不做数据搬运；⑤ 上下文压缩 |
| 🛠 **实践任务** | 实现 `Supervisor` + `research/outline/designer/renderer` 四个 SubAgent；定义 `schema.Artifact`；实现 `state.Blackboard` |
| 📦 **产出物** | 一句话主题 → 3 页 PPT；可打印每个 Agent 的 handoff payload |
| ✅ **验收标准** | ① handoff 全部过 Schema 校验；② Supervisor 不参与字段搬运；③ 长任务下上下文不爆炸 |
| ⚠️ **可能问题** | Supervisor 变成"JSON 搬运工"；子 Agent 之间无法直接通信导致多跳失真；路由靠 LLM 不可测 |
| 🔧 **主流做法** | 产物存黑板、Agent 间传引用；路由结构化可统计；Graph 固化稳定流程 |
| 🎤 **面试考点** | Supervisor vs GroupChat 怎么选？上下文超长怎么办？ |

---

### L3 · Graph 编排 + HITL + 持久化

| 项 | 内容 |
|---|---|
| 🎯 **知识点** | ① 状态图（节点 + 条件边）；② Checkpoint 与状态快照；③ 中断/恢复（HITL）；④ 幂等与可重放；⑤ 协议版本化 |
| 🛠 **实践任务** | 实现 `graph.Runner`（节点 + 边 + 条件路由）；实现 `checkpoint.Store`（先文件后 Redis）；实现 `interrupt` + `resume`；把 L2 的流程改造成图 |
| 📦 **产出物** | ① 可打印图拓扑；② 生成大纲后中断等用户确认；③ **杀掉进程重启后仍能恢复** |
| ✅ **验收标准** | ① 中断→重启→恢复，产出与不中断一致；② 能解释"哪里用图、哪里用 Agent" |
| ⚠️ **可能问题** | 节点划分过细导致状态管理复杂；中断信息未版本化导致旧 checkpoint 无法恢复；恢复语义单一（只能"确认"不能"修改"） |
| 🔧 **主流做法** | typed state + reducer；中断协议版本化；恢复支持"确认/修改/放弃"三种意图 |
| 🎤 **面试考点** | 显式图 vs 隐式对话的取舍？持久化状态怎么设计？ |

---

### L4 · 可观测 + 评测 + 预算控制

| 项 | 内容 |
|---|---|
| 🎯 **知识点** | ① Trace / Span 与结构化日志；② 可观测 ≠ 可评测；③ Golden set + LLM-as-judge；④ 四维预算（步数/token/时间/成本）；⑤ 打转检测与失败升级链 |
| 🛠 **实践任务** | 实现 `trace.Tracer`（每 Agent / 每工具一个 span）；建 `eval/golden.jsonl`；实现 `budget.Guard`；实现结构化路由日志 |
| 📦 **产出物** | ① 一键回归脚本；② 指标输出：任务成功率 / 平均 token / 返工次数 / 路由准确率；③ 人为触发死循环被预算拦截 |
| ✅ **验收标准** | ① 改一次 Prompt → 一键看到指标升降；② 硬性判据由代码判定，软性才用 LLM |
| ⚠️ **可能问题** | 指标口径不统一无法横向比较；评测集太少导致过拟合；预算超限时直接报错丢失可用结果 |
| 🔧 **主流做法** | 硬/软判据分层；评测集覆盖异常输入；超限时"交付部分结果 + 说明" |
| 🎤 **面试考点** | 你怎么证明 Agent 变好了？怎么防成本爆炸？ |

## 六、L0 复盘（预设问题）

> 这些是我们在写完 L0 后要**逐条验证**的问题。它们既是学习点，也是下一阶段的改进输入。

| # | 问题 | 可能出现的现象 | 主流改进思路 |
|---|---|---|---|
| L0-1 | **没有预算控制** | 模型反复调工具不收敛，token 成本不可控 | 步数/token/时间/成本四维预算 + 打转检测 |
| L0-2 | **上下文只增不减** | 多轮工具调用后消息越来越长，最终超限 | 上下文裁剪 / 摘要 / 产物外置 |
| L0-3 | **工具错误处理粗糙** | 错误信息模型看不懂，反复犯同一个错 | 结构化错误 + 修复提示（hint） |
| L0-4 | **无质量把关** | 生成的内容没人检查，好坏全凭运气 | 引入 Critic（→ L1） |
| L0-5 | **单 Agent 能力边界模糊** | 一个 Prompt 里塞了检索、写作、设计多种职责 | 拆分为多 Agent（→ L2） |
| L0-6 | **无中间产物持久化** | 进程崩溃后全部重来 | 共享黑板 + checkpoint（→ L3） |
| L0-7 | **无观测与评测** | 改了 Prompt 不知道变好还是变坏 | Tracer + golden set（→ L4） |

**⚠️ 特别说明**：L0 的这些"问题"**大多是刻意的**——
先让你亲眼看到问题，再有针对性地引入解法。这叫"问题驱动的架构演进"。
