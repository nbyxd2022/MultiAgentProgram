# 02 · L0 复盘：单 Agent Demo 的问题、风险与改进方向

> 这是"教学循环"的第 ③ 步：**复盘**。
> 对象是刚刚跑通的 L0 Demo（`cmd/l0` + `internal/agent` + `internal/tools`）。
>
> 目的不是否定它，而是让你亲眼看到：**一个"能跑"的 Agent，离"能用"还有多远。**

---

## 0. 先看它做对了什么

复盘容易只盯着缺点，但要先确认设计中的"正确决策"，因为它们是后面所有改进的地基：

| 决策 | 位置 | 为什么正确 |
|---|---|---|
| 模型层抽象为接口 | `internal/llm/llm.go` | 切换模型不改业务代码；离线可测 |
| 工具契约 = 名字+描述+JSON Schema | `internal/tool/tool.go` | 描述即文档，直接决定模型用得对不对 |
| 工具错误**回灌**而非抛出 | `internal/agent/agent.go` `formatToolError` | 模型能自我纠正，而不是整个任务失败 |
| 终止条件**双保险** | 无 tool_call 自然结束 + `MaxSteps` 硬上限 | 防止"理论上可能死循环" |
| 大产物**只回传引用** | `render_slide.go` 返回 `file` 路径而非 HTML 全文 | 上下文成本极低，这是非常关键的取舍 |
| 工具分"有副作用/无副作用" | `render_slide_html` vs `web_search` | 为后续权限分级埋好结构 |

**记住这六条。** 它们是从 L0 到 L4 一直要保留的骨架。

---

## 1. 问题清单

### P1 · 上下文只增不减

- **现状**：`agent.go` 里 `history = append(history, ...)`，从不裁剪。
- **为什么现在没问题**：Demo 只有 3 步。
- **什么时候会炸**：真实模型可能调 10+ 次工具；`web_search` 一次就返回整段 JSON。
- **量化感受**：本次运行 `PromptTokens=920` 且**每一步都在重发全部历史**，
  步数增加时 prompt token 是**平方级增长**。
- **改进方向**：工具结果裁剪/摘要；大产物外置（我们已经在 `render_slide_html` 上做对了，
  但 `web_search` 仍回传全文）；必要时引入摘要压缩。

### P2 · 预算只有 `MaxSteps`，且是"事后"的

- **现状**：只有步数上限；token 只统计、不限制；无时间、无成本限制。
- **可能情况**：某一步模型返回超长内容 → 单步就吃掉大量 token，无人拦截。
- **改进方向**：四维预算（步数 / token / 时间 / 成本）+ **打转检测**
  （记录已访问的 `(工具, 参数)` 组合，重复即判定无效重试）。

### P3 · 用 Prompt 写流程控制

- **现状**：`l0SystemPrompt` 写着"必须先搜索、后渲染，不允许跳过搜索"。
- **问题**：这是**用自然语言写 if-else**。真实模型不保证遵守。
- **可能情况**：
  - 模型直接渲染，跳过搜索（流程约束失效）；
  - 模型搜了 5 次还在搜（"至少一次"理解成"越多越好"）。
- **改进方向**：确定性流程交给**代码或图编排**，而不是交给模型的自觉。
  → 这条直接指向 L2/L3。

### P4 · Mock 掩盖了真实失败

- **现状**：`newL0Mock()` 靠"数 tool 消息条数"决定行为，**永远不会失败**。
- **问题**：我们验证的是"循环写得对"，不是"Prompt 写得好"。
- **可能情况**：接上真实模型后，第一步就可能出现——
  - 不调用任何工具，直接编内容；
  - 调用不存在的工具名；
  - 参数类型错（`bullets` 传成字符串而非数组）；
  - 参数 JSON 被截断（超出输出 token）。
- **改进方向**：Mock 只用于冒烟；**必须增加"真实模型冒烟测试"与"失败注入测试"**。

### P5 · 工具参数没有统一校验层

- **现状**：`Required` 只在 JSON Schema 里声明；运行时靠每个工具自己手工校验。
- **问题**：校验逻辑重复、且容易不一致（工具 A 校验了、工具 B 忘了）。
- **改进方向**：在 Agent 执行工具前加一层**统一参数校验**，
  校验失败先返回结构化错误，避免进入工具内部。

### P6 · 失败只有"回灌"，没有升级链

- **现状**：工具报错 → 回灌 → 模型再试。没有计数、没有降级。
- **可能情况**：模型用**完全相同的参数**重试 3 次，直到 `MaxSteps` 才终止。
- **改进方向**：失败计数 + 升级链
  `回灌自愈 → 换参数重试 → 换工具 → 降级交付 → 终止并说明`。

### P7 · 无质量把关

- **现状**：生成完直接交付。没人检查 bullets 是否重复、是否空洞、是否超 5 条。
- **可能情况**：产出"看起来像 PPT、但没有信息量"的页面，用户无法察觉。
- **改进方向**：引入 Critic Agent（→ L1），输出**结构化问题清单**而非分数。

### P8 · 单 Agent 职责过载

- **现状**：一个 Prompt 同时承担"检索素材 + 组织内容 + 视觉排版"三重职责。
- **问题**：职责越杂，Prompt 越难写好，失败后也**无法定位是哪一环的问题**。
- **改进方向**：按职责拆分 Agent（→ L2），每个 Agent 只做一件事、只有一个验收标准。

### P9 · 观测与业务耦合

- **现状**：`Observer` 直接 `fmt.Printf` 到标准输出。
- **问题**：无法切换为 trace、无法上报指标、无法做离线回放。
- **改进方向**：把事件模型抽出来，实现一个 Tracer 适配器（→ L4）。

### P10 · 无持久化，无幂等保护

- **现状**：产物写入 `out/slide-<title>.html`，同名直接覆盖。
- **可能情况**：重试或重跑覆盖上一版；进程崩溃后中间状态全部丢失。
- **改进方向**：版本化文件名 / 幂等键；关键中间状态持久化（→ L3）。

### P11 · 消息模型丢失了"思考过程"

- **现状**：`message.Message` 没有 `ReasoningContent` 字段。
- **问题**：真实模型的思维链无法被保留、无法被观测、也无法用于调试路由错误。
- **改进方向**：增加 reasoning 字段（企业仓库里对应 `ReasoningContent`）。

### P12 · 工具串行执行

- **现状**：`for _, tc := range resp.ToolCalls` 顺序执行。
- **问题**：当模型一次请求多个**互不依赖**的工具时（如同时搜 3 个关键词），
  串行会让时延线性叠加。
- **改进方向**：识别无依赖的工具调用并行执行（企业仓库用 `grqueue` 并发）。

## 2. 风险场景推演

> 建议在做 L1 之前，**真的接一次真实模型**，观察下面哪些发生了。

| # | 场景 | 触发原因 | 后果 |
|---|---|---|---|
| S1 | 模型跳过搜索直接渲染 | P3（流程靠 Prompt） | 内容空洞、无事实支撑 |
| S2 | `bullets` 传成单个字符串 | P5（无校验层） | 浪费一轮自愈，多花 token |
| S3 | 模型用同样参数反复失败 | P6（无升级链） | 跑满 MaxSteps 才终止，成本翻倍 |
| S4 | 多轮后上下文超限 | P1（只增不减） | 请求被模型服务拒绝 |
| S5 | 生成的要点重复/空洞 | P7（无质检） | 交付质量不可控 |
| S6 | 单步输出超长 | P2（无 token 预算） | 成本失控 |
| S7 | 进程崩溃 | P10（无持久化） | 全部重来 |
| S8 | 一次请求 3 个搜索 | P12（串行） | 时延 3 倍 |

## 3. 主流改进思路对照

| 我们的问题 | 主流做法 | 对应开源/企业实现 |
|---|---|---|
| P1 上下文只增不减 | 工具结果裁剪 + 摘要压缩 + 大产物外置 | 企业仓库 `hotcold`（L1/L2 分层摘要） |
| P2 预算不足 | 四维预算 + 打转检测 | OpenAI Agents SDK guardrails / AutoGen termination |
| P3 流程写在 Prompt | 流程交给图编排，Prompt 只管"怎么做"不管"谁先谁后" | LangGraph / 企业仓库 `v5_html_ppt_agent/graph.go` |
| P4 Mock 掩盖失败 | 契约测试 + 真实模型冒烟 + 失败注入 | 通用工程实践 |
| P5 无参数校验 | 执行前统一校验层 | 企业仓库 Eino `ToolsConfig` 内置校验 |
| P6 无升级链 | retry / fallback / circuit breaker | 企业仓库 `ModelRetryConfig` + fallback 模型 |
| P7 无质检 | Critic Agent + 结构化问题清单 | 企业仓库 `layout_guard_*` |
| P8 职责过载 | 按职责拆 Agent | MetaGPT 角色分工 |
| P9 观测耦合 | 结构化事件 + Tracer | 企业仓库 `otelkit` + Prometheus |
| P10 无持久化 | checkpoint + 幂等键 | 企业仓库 `store/checkpointstore/` |
| P11 丢思考过程 | 消息模型加 reasoning 字段 | 企业仓库 `schema.Message.ReasoningContent` |
| P12 工具串行 | 无依赖工具并行 | 企业仓库 `grqueue` |

## 4. 决策：L0 阶段"现在改"还是"留到后面改"

**不要现在全改。** 学习顺序本身是教学内容：

| 立即改（成本低、收益高） | 留到对应阶段 |
|---|---|
| P5 加统一参数校验层 | P1 上下文管理 → **L2** |
| P6 加失败计数 | P2 预算 → **L4** |
| P11 消息加 reasoning 字段 | P3 流程编排 → **L3** |
| P12 无依赖工具并行 | P7 质检 → **L1** |
| | P8 拆分 Agent → **L2** |
| | P9 Tracer → **L4** |
| | P10 持久化 → **L3** |

**下一步（L1）的核心目标只有一个：把 P7（无质检）解决掉**——
引入 Critic，让系统能"自己发现问题"。
在这个过程中，P12（并行）与 P6（失败计数）会作为顺带收益一起落地。

## 5. 本轮要你回答的问题

进入 L1 之前，请先想清楚这 4 个问题（不用写代码）：

1. Critic 应该输出"一个分数"还是"一份问题清单"？为什么？
2. Critic 和 Generator 用**同一个模型**会有什么隐患？用**不同模型**又有什么代价？
3. 如果 Critic 每轮都能挑出问题，返工什么时候停？停的依据是什么？
4. 我们现在把"必须先搜索"写在 Prompt 里（P3）。如果改用 Critic 来检查"有没有搜索过"，
   这样算解决了吗？还是只是把问题换个地方藏起来？
